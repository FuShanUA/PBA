使用第三方 AI 模型服务会给你的核心优势带来重大风险。如果无法对那些服务（无论是 AI 实验室还是超大规模云服务商，统称为“托管模型提供商”）处理数据的方式进行自主掌控，托管模型提供商可能会提取你的核心优势（即在你使用 AI 模型的过程中暴露和生成的数据中所体现的独特机构知识和专业技能），并以权重或服务的形式将其转售给更广阔的市场。在日益不安全的网络环境中，托管模型提供商存储你的数据也会扩大针对你核心优势的攻击面，并导致你最有价值的资产被卷入许多托管模型提供商正在面临的生存攸关的法律诉讼中。为避免此类情况发生，必须对数据保持自主掌控。

虽然额外的自主掌控可能涉及利用新型云服务商（相比于托管模型提供商，这类提供商可能更愿意接受更具数据保护性的条款）来托管并改进你部署和控制的平台开源模型，但你可能仍倾向于使用托管模型提供商提供的带有围墙花园特性的前沿模型。然而，即便是对于谨慎的法务团队而言，托管模型提供商犹如迷宫般的法律条款中也暗藏着可能危及 AI 主权的陷阱。本文档旨在帮助识别一些常见的陷阱，并提出降低相关风险的最佳实践。文章将引导你了解如何确保保护数据的条款、追踪并仅允许受这些保护覆盖的服务、限制托管模型提供商单方面更改协议条款的能力，以及在出现问题时降低运营中断的风险。

注意：本文档不构成也不包含法律建议，亦不建立任何律师与客户的关系。如需法律建议，请咨询专业律师。

  1. 通过合同保护你的核心优势

1.1 确保强有力的零数据留存（ZDR）

降低这些风险的一个关键方法是获得零数据留存（ZDR）的合同保证。不同的托管模型提供商对 ZDR 的定义各不相同。

强有力的 ZDR 意味着托管模型提供商将不会（1）将你的提示词或响应存储或以其他方式记录到磁盘上（这比在内存中短暂保留更为持久），（2）将你的提示词或响应交由人工审查，（3）使用你的提示词或响应来训练其模型或改进其服务，并且（4）仅在返回请求所需的时间内将提示词和响应保留在内存中。

部分托管模型提供商提供的 ZDR 保护版本被隐藏在合同、技术文档和产品架构中的例外情况所削弱，从而使你的核心优势暴露在他们的掌控之下。本文档第 2 部分将探讨一些最常见的例外情况——请仔细追踪这些例外，并仅允许实际受你保护条款覆盖的服务。

1.2 限制使用你的核心优势

你的核心优势应仅为你带来复利效应，而不应惠及托管模型提供商。部分托管模型提供商将保证不会使用你的数据训练模型。然而，这种保护可能存在遗漏——例如，作为托管模型提供商的超大规模云服务商可能会向你保证，创建你所使用模型的 AI 实验室不会使用你的数据进行训练，但该超大规模云服务商自身可能并未受到同等约束。他们可能会在法律协议或产品文档中隐藏条款，允许他们使用关于你使用模式的元数据，或你的提示词和响应本身，来改进辅助服务和工具。例如，他们可能会使用触发安全分类器的提示词来改进其安全分类器，或者利用你的使用模式来改进其模型测试框架。

最佳实践：

确保条款将托管模型提供商及（如果托管模型提供商是超大规模云服务商）参与数据处理过程的任何 AI 实验室对你数据的使用范围限制在仅为你提供服务——最好是正面声明这一项被允许的用途，而不是试图列出一系列繁杂的限制清单，因为后者容易遗漏风险点。此外，务必确保关于数据使用方式的限制同时适用于你所使用的托管模型提供商的平台以及任何相关的 AI 实验室。

如果无法实现上述要求，底线是绝不允许可将您的数据用于改进您正在使用的产品或服务，包括但不限于模型训练。务必同时约束托管模型提供商及参与处理的任何 AI 实验室。

1.3 确保责任上限足够高，使合同保护落到实处

托管模型提供商可能会针对零信任违规、数据处理义务或其他保护 AI 主权的合同义务，设定极低的名义责任上限，导致其遵守这些义务的动机不足。这种情况在 Beta 服务中尤为常见，但也并非仅限于此。

最佳实践：

除协商确立严格的零信任外，还应确保托管模型提供商在零信任和数据保护违规方面面临足够高的责任敞口，以此激励其切实履行相关义务。

遵循第 3.1 节的缓解策略，防范托管模型提供商单方面修改责任上限。

  1. 仅追踪和许可受合同核心保护覆盖的服务

2.1 Beta 或其他不符零信任条件的服务

许多托管模型提供商不会对 Beta 服务（也称“预览”或“正式发布前”）适用零信任。部分服务、工具和 API 端点也可能默认不符零信任条件。这些例外情况可能以多种方式混入您的法律条款——它们可能出现在超链接的特定服务条款中、Beta 服务的专门章节里，甚至隐藏于条款中声明 Beta 服务不属于零信任义务适用范围的“模型服务”定义内。不符零信任条件和 Beta 状态不仅适用于模型，也可能适用于对模型发起 API 调用的特定配置。例如，模型 A 可能并非 Beta 版本，但如果在调用模型 A 时使用了特定的 Beta 工具、功能或 API，则可能被排除在零信任之外。更为复杂的是，托管模型提供商的默认法律条款几乎从不会明确标示哪些服务、功能和工具属于 Beta——它们通常掩埋在不断更新的在线产品文档，或提供商的控制台/门户内（IT 部门默认极少向法务团队开放这些访问权限，这是有合理原因的）。

最佳实践：

通过合同获取广泛的服务范围（例如，涵盖对托管模型提供商任何 API 的任何使用，包括访问 Beta 服务），确保该范围落入您的数据保护框架内，并保证不存在模型提供商可单方面修改的条款（例如，不附加超链接形式的在线条款）。

如果无法实现上述要求，请与您的 IT 部门协作，建立一份动态更新白名单，涵盖已落入您已获取的数据保护范围内的模型、工具、功能及 API 端点，这通常需要将 Beta 服务排除在外。定期根据对托管模型提供商相关文档的例行检查更新该白名单，并为 IT 部门建立操作流程，以便在允许组织使用新模型、工具和功能前，与法务对接进行审查。

部分托管模型提供商要求在向 Beta 服务发起 API 调用时，必须主动添加“beta”标头才能使调用通过。这可以作为一个有效的技术阻断门——与 IT 团队合作自动拦截包含 beta 标头的调用，作为一项故障保护措施。

2.2 安全分类器触发时数据将被存储

许多托管模型提供商会在安全分类器触发时存储提示词和输出内容，并实施人工审查。这些安全分类器可能且曾经对完全合法的提示词产生误判（误报），这意味着合法提示词也会被存储和审查。

最佳实践：
部分托管模型提供商提供了一种技术选项来禁用此零信任例外，通常被称为禁用滥用监控或安全分类器。如果您无法获得广泛的合同零信任保护来从根本上消除此问题，请确保在操作层面尽可能将您的账户配置为禁用滥用监控（或同等功能）。

2.3 包含图像或文件的提示词引发零信任例外

许多托管模型提供商不对包含图像或文件的提示词适用零信任。另一些提供商可能会声称，使用图像输入或输出（或与图像 API 端点交互）受其（较弱的）零信任概念约束，然而其文档中可能掩藏着披露声明：一旦特定分类器触发安全正命中，您的提示词或响应的所有上下文都将被托管模型提供商保留至磁盘，并可能面临人工审查。即使禁用了滥用监控，对于某些高优先级安全分类器，这种情况依然可能发生。

最佳实践：
寻求定制条款，将零数据留存应用于图像输入与输出，明确要求在任何情况下，提示词或响应均不得存储至磁盘，也不得接受人工审查。

2.4 部分提示词缓存配置可能会超期存储数据

一些托管模型提供商提供涉及扩展或增强提示词缓存的功能（有时这也是使用某些模型或 API 端点的前提条件）。虽然某种形式的提示词缓存有助于降低延迟和成本，有时甚至不可避免，但理想情况下，提示词缓存应具有合理的 TTL（“存活时间”，指明数据保留的时长），并且仅在完成会话所需的时间内将缓存的提示词保留在内存中，此后便清空缓存。这可以与严格的零数据留存保持一致。不可取的提示词缓存配置可能会将您的提示词和响应存储在磁盘上长达不合理的时间。

最佳实践：
若无法通过严格的合同条款落实禁止写入磁盘的零数据留存保护，则应在准入审查流程中增加对可接受提示词缓存配置的核查。

2.5 审慎确定适用的条款

模型的条款与条件可能因您所使用的托管模型提供商平台及具体模型而异。多数情况下，超大规模云服务商不仅会沿用模型创建者的部分条款，还会在此之上附加自身的条款。

最佳实践：
务必对您正在使用的特定托管模型提供商平台的相关条款进行彻底审查。请注意，若您已从模型创建者处争取到有利的定制条款（例如禁用滥用监控），则应确保您所使用的托管模型提供商平台知悉这些定制条款，并落实零数据留存等特殊数据处理要求。例如，若您使用的是 A 实验室创建的模型（且您已与之签订定制条款与保护协议），但通过 B 超大规模云服务商访问该模型，您可能需要促成 A 实验室与 B 超大规模云服务商对接，以便 A 实验室向 B 超大规模云服务商确认应执行特殊的数据处理。

2.6 数据处理条款免责声明

托管模型提供商有时会对特定服务声明不提供数据处理协议或业务伙伴协议，或直接声明所有“数据处理条款”不适用。此类情况通常出现在带超链接的在线条款中。以往多见于测试版功能和网页搜索等特殊功能，尽管理论上可应用于任何服务。

最佳实践：
理想情况下，您应拥有能够凌驾于任何声明免除数据处理保护的在线条款之上的主协议条款。若无法实现，则在将新服务添加至准入清单前须仔细审查。这些数据处理免责声明可能直接适用于该服务，也可能通过服务状态生效（例如服务被标记为“测试版”，从而附加测试版条件），因此务必核查 该服务的特定文档， 模型提供商拥有的任何特定服务条款（通常位于其独立网页上，以长列表形式列出各项服务及其适用的特殊条件），以及 适用于目标服务状态的条款。

2.7 意外的服务启用

部分托管模型提供商可能会自动启用或将服务或模型自动升级至不受零数据留存或本文所述其他 AI 主权保护覆盖的新服务或模型，且不会就此类条款变更向您发出明确通知（尽管变更可能会在单方面更新的技术或合同文档中予以披露）。

最佳实践：
除第 2.1 节和第 3.1 节所述的缓解措施外，还应获得合同保证：对于不满足零数据留存或您其他 AI 主权要求的任何新模型或服务，未经事先通知并获得您的明确书面同意，不得在您的租户环境中启用。

2.8 确保符合相应的认证合规性边界

并非所有托管模型提供商及其所有服务都能满足您组织在特定工作流中可能要求的合规性要求。例如，许多提供商可能拥有 SOC2 认证，但可能并不具备 FedRAMP 认证或 IL2、4、5 级授权。

最佳实践：
若特定工作流需要更严格的技术合规性或认证授权，应在与托管模型提供商的合同条款中明确阐述所需的合规性或认证要求（以及这些要求需适用的具体服务）。与您的工程团队协同，对来自要求更高授权或合规认证环境的数据请求进行安全故障处理，防止其被路由至授权级别较低或未获认证的托管模型提供商端点或服务。

  1. 限制托管模型提供商单方面变更条款的能力

3.1 单方面变更超链接在线条款

托管模型提供商的条款和条件通常会纳入可由其单方面变更的在线条款。这往往是因为托管模型提供商的条款中嵌套了超链接条款，这些条款无需通知即可单方面更新并生效。即便您已成功协商达成主条款，这些条款仍可能引用超链接条款（例如可接受使用政策、特定服务条款、数据处理条款、ZDR 条款等），托管模型提供商同样可以在不发出通知的情况下单方面对其进行更新。托管模型提供商经常会修改这些超链接条款，从而损害 ZDR 及本文件中讨论的其他 AI 主权考量因素。

最佳实践：

争取达成自定义合同条款，避免以引用方式纳入在线条款；如果必须包含链接，应明确规定这些被链接的条款仅在合同生效日当天所写的版本有效。

如果您只能在部分而非全部超链接条款上实现上述目标（即部分超链接条款仍可由托管模型提供商单方面更改），应明确规定严格的条款优先顺序。一旦协商条款与超链接条款之间出现不一致或冲突，单方面更改超链接条款的行为不得损害已协商确定的合同保障（如 ZDR）。

如果您必须同意托管模型提供商可单方面更改的超链接条款，应建立定期检查机制（最好是自动化告警），以监控相关在线条款的任何变更。查看条款和条件的历史版本（例如通过
https://web.archive.org/
）有助于了解具体发生了哪些改动。

3.2 向非法律员工展示的点击即同意条款

模型提供商可能会在其控制台或平台中弹出点击即同意条款，提示用户 ZDR 或其他保护机制将不适用于他们尝试启用的服务。试图启用该服务的工程师可能会在无意中接受这些条款。

最佳实践：
在合同中加入使点击即同意协议失效的条款。如果无法实现这一点，应向控制台或平台用户普及此类风险，并要求他们在接受任何点击即同意协议前先咨询法务部门。

  1. 降低运营中断风险

4.1 触发安全分类器导致的业务中断

条款和条件可能允许托管模型提供商在特定条件下立即暂停或终止服务，包括他们认为您违反了其可接受使用政策（AUP）的情况。这些政策通常包含一系列宽泛的限制条款，且经常被托管模型提供商单方面修改。即使在严格的 ZDR 设置下，托管模型提供商也可能依赖安全分类器（仅存储指示分类器是否触发的元数据，而不存储触发它的提示词）来判断您是否遵守了其 AUP。这些分类器通常过于敏感，可能会对无害的提示词产生误判。这意味着，即使是合规使用其服务，也可能触发暂停或终止，从而危及您的业务连续性。

最佳实践：

在合同中要求，托管模型提供商在启动任何终止或暂停服务之前，必须提供 通知安全分类器触发的情况， 赋予您的安全和 IT 团队一段“调查与整改”期，以评估触发分类器的原因，并与托管模型提供商协作确认该触发是否为误报，或在确属真实违规时商定整改方案， 确保该“调查与整改”期不赋予托管模型提供商获取或审查您 alpha 数据的权利， 提供合理的缓冲期以便暂停或终止服务，确保您有足够的时间迁移至其他模型。

确保您的技术组织已实施适当可观测性基础设施，以便追踪导致安全分类器命中的提示词，协助化解托管模型提供商因标记问题而发起的质询。大多数托管模型提供商都实现了提示词 ID 机制，在发生事件时，可以向您提供违规的 ID，以协助您进行审计。

4.2 阻断合法的模型请求

托管模型提供商的安全分类器可能会阻断合法的请求。即便您已针对某些被禁止的使用场景 secured 了合同豁免权，托管模型提供商的安全分类器仍可能导致您的请求失败，从而强制执行这些使用场景限制，进而中断您的业务。

最佳实践：
在合同中加入明确的许可条款，允许您的特定使用场景；如果可能，还应加入要求托管模型提供商禁用相关安全分类器的条款。不要仅仅在合同中删除阻断性的使用场景限制。

4.3 将流量路由至禁区的全局推理标准

许多托管模型提供商在默认情况下，会按照全局推理标准提供模型服务、工具和功能，将您的流量在其具备算力支持的所有区域的基础设施中进行负载均衡。出于法律或合同要求，其中部分区域可能会被您的业务运营列为禁止项，进而引发事件及相应的业务中断。对于全局推理标准具体涵盖哪些区域，托管模型提供商往往不会在其合同或文档中如实明示；即便有所说明，这些区域清单也常常受制于提供商的单方面变更。

最佳实践：

通过合同条款严格约束托管模型提供商，禁止其将您的流量路由至您所在组织禁止使用的区域。

若无法达成上述要求，部分托管模型提供商可提供针对特定区域的专属推理算力，您可以在采购时通过合同予以明确。需要注意的是，此类区域受限选项通常会产生额外费用。

若上述条件均无法满足，则应在合同中要求托管模型提供商在向其全局推理服务新增区域时必须通知您，并预留充足的提前期，以便您采购区域受限算力或迁移至其他模型服务。

核心结论

要对您的核心资产实现主权控制，前提是精细掌控托管模型提供商处理您数据的具体方式。托管模型提供商所提供的保护措施——哪怕他们美其名曰“ZDR”，哪怕您已经争取到了强有力的 ZDR 条款——对不明就里者而言依然处处是陷阱。务必争取宽泛且具保护性的合同条款，建立新服务的审查机制与允许列表，防止出现脱离保护范围的情况；坚决抵制对协议的单方面更改，同时限制托管模型提供商在自认出错时可采取的行动，以此降低运营中断的风险。对于自身条款究竟能赋予他们对您的核心资产何种处置权，托管模型提供商可谓深思熟虑——您也应予以同等重视。
