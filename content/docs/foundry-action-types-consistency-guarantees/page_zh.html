一致性与隔离

操作通过单个事务将编辑应用于本体论，该事务可以从本体论读取数据、应用用户定义的逻辑，并将编辑写入一个或多个对象和关联。

本页面介绍操作类型在并发执行期间提供的保证，以及如何为特定用例选择合适的隔离级别。

ACID 保证

操作的行为类似于数据库事务，并提供标准的 ACID 属性：

  • 原子性： 操作对本体论的编辑作为单个“全有或全无”的批次应用。这不扩展到操作的其他 副作用 （例如通知或 webhook），也不扩展到支撑函数的副作用（例如其发起的外部调用）。
  • 一致性： 操作的编辑只有在满足本体论的约束时才会提交，例如 值类型约束 and 必填属性.
  • 隔离性： 控制同时执行的操作如何相互影响。 章节 介绍了操作类型提供的隔离级别。
  • 持久性： 操作一旦提交，其编辑将被永久持久化。

操作完成后，之后启动的任何操作或查询都会看到该已完成操作应用的所有编辑。 此保证不适用于同一操作执行期间进行的读取。

这些编辑的可见性取决于操作的写入模式，详见 写入模式.

写入模式

操作提供两种写入模式。 在这两种模式下，操作的编辑都会在操作运行期间收集，并在结束时作为单个原子批次提交到本体论，因此其他操作绝不会观察到部分应用的操作。 两种模式的区别在于操作的 自己的 读取能否看到其到目前为止所做的编辑：

  • 批量写入（默认）： 编辑在操作运行期间收集到批次中，并在结束时作为单个原子操作提交到本体论。操作自身的读取无法看到其批量编辑；每次读取返回的都是本体论中的数据，不包含该操作到目前为止收集的编辑。例如，如果操作更新了某个对象的属性，然后再次读取该对象，读取将返回原始值，而不是更新后的值。
  • 暂存写入： 操作的读取可以看到其自身的编辑。在同一操作执行中，读取操作已编辑的对象会返回编辑后的值，搜索和聚合也会包含这些编辑。暂存写入目前支持 Python, 或日 AIP 逻辑 函数支撑的操作类型。

冲突检查的工作原理

在执行冲突检查的隔离级别下，本体论会在对象级别检测写-写冲突。 如果两个操作并发写入同一对象，其中一个操作将因冲突错误而失败。 即使这些操作写入的是该对象的不同属性，也是如此。

重建支撑对象类型或多对多关联类型的数据集也可能导致冲突。 操作执行之间的冲突仅限于两个操作都写入的对象，但由支撑数据集重建引起的冲突范围更广。 即使重建不会更改操作写入的特定对象，操作在重建运行期间也可能遇到冲突。 这些冲突是暂时的，因此在重建完成后重试操作通常会成功。

检测到冲突时，失败操作的整个编辑将被丢弃。参见 暂时性错误的重试模式 了解冲突如何呈现和重试。

隔离级别

操作类型的 隔离级别 设置了当操作与其他操作并发运行并交互相同数据时适用的保证。 它定义了两件事：操作内每次读取观察到的数据版本，以及哪些并发更改会导致操作失败而不是提交基于已更改数据构建的结果。 更强的级别可排除更多异常，但会在冲突时拒绝更多操作；更弱的级别提交更频繁，但提供的保证更少。

操作类型的隔离级别在 本体论管理器中配置，位于操作类型的 功能 选项卡中。 该级别可在创建后更改，并对后续执行生效。

所有使用批量写入的新操作类型在创建时默认采用 快照隔离 。 使用分阶段写入的操作类型目前仅支持传统模式。 更多信息请参见 当前分阶段写入行为.

遗留版

传统隔离模式在以下位置仍然可用： 功能 选项卡，适用于在引入显式隔离级别之前创建的操作类型。 使用批量写入的新操作类型默认采用快照隔离。

读取： 读取通常来自单一时间点，但这并不保证。同一操作执行期间加载的不同对象可能反映本体论的不同状态，因为在操作运行期间，由于从对象存储检索数据时出现错误，底层数据可能会被刷新。

写入： 传统隔离支持两种写入模式。使用批量写入时，同一操作执行中稍后执行的读取不包括该执行中较早进行的编辑。使用分阶段写入时，稍后的读取包括这些编辑。更多信息请参见 写入的工作原理 和 当前分阶段写入行为.

冲突检查： 如果在对象加载到操作提交之间，另一操作更改了该操作写入的对象，则操作将因冲突错误而失败。但是，由于不保证读取的一致性，基于操作仅 读取 的数据做出的决策可能基于组合了不同时间点数据的视图。

传统隔离模式是为了向后兼容而提供的。

对于新的操作类型，请使用 快照隔离 以获得相同的冲突检查，并额外保证所有读取来自单一时间点。

快照隔离

这是使用批量写入的新操作类型的默认级别。有关使用分阶段写入的操作类型的行为，请参见 当前分阶段写入行为.

数据源可能观察到不同的数据

逻辑规则和函数支持的操作会从一致的时间点读取本体论。当函数调用 源时，该源在操作的时间点视图之外运行。源可以读取本体论或其他系统，而这些读取可能会观察到不同时间点的数据。操作的原子性和冲突检查不涵盖源执行的操作。

读取： 操作直接执行的每次本体论读取都会观察到单一一致的时间点视图，该视图在操作开始时获取。无论其他操作在此操作运行期间提交了什么，读取同一对象或运行同一搜索两次始终返回相同的匹配数据。

写入： 操作使用批量写入，因此在同一操作执行期间稍后执行的读取不会包含该执行中较早进行的编辑。

冲突检查： 如果在对象加载到操作提交之间，另一个操作更改了该操作写入的对象，则该操作将因冲突错误而失败。操作会失败，而不是覆盖并发更改。操作仅 读取 的对象不会在此级别导致冲突失败。有关重试冲突的信息，请参阅 暂时性错误的重试模式.

写偏斜

由于只有 写入 的对象会进行冲突检查，快照隔离 不 检测读写冲突。

两个操作可以各自读取重叠的数据，基于该读取做出决策，写入 不同 对象，并且都成功提交——即使任何一个操作如果看到了另一个操作的写入，都不会提交。

这被称为 写偏斜.

示例： 值班轮换必须始终保持 至少一名 工程师在值班。只有在仍有其他人值班时，工程师才能离开轮换，因此该操作会检查： 当前是否至少有两名工程师在值班？ 工程师 A 和 B 都在值班，并且同时运行操作将自己移出：

  • A 的操作从其快照中读取轮换信息，看到两名工程师在值班，于是继续执行——移除 A 后仍有 B。
  • B 的操作从其自己的快照中读取相同状态，看到两名工程师在值班，并出于相同的原因继续执行。
  • A 写入 A.onCall = false；B 写入 B.onCall = false。这两个操作写入了 不同 对象，因此不存在写-写冲突，两者都成功提交。此时轮换为空，违反了不变量。

快照隔离无法捕获这种情况，因为被违反的不变量存在于操作 读取 （值班工程师集合）的数据上，而不存在于任一操作 写入.

为避免这种异常，请重新设计工作流，将不变量表达为对单个共享对象的写入。

例如，两个操作都可以写入一个 Rotation 对象，该对象具有 onCallCount 属性，从而导致操作冲突。

已提交读

直方图 读已提交 隔离模式即将推出。

读取： 每次读取都会返回读取运行时最新提交的值。没有固定的快照，因此如果另一个操作在两次读取之间提交，则同一操作中在不同时间点进行的两次读取可能会观察到不同的状态。

写入： 操作使用批量写入，因此在同一操作执行期间稍后执行的读取不会包含该执行中较早进行的编辑（参见 写入的工作原理).

冲突检查： 即使另一个操作在执行期间更改了同一对象，操作也允许进行编辑。当两个操作都提交时，对不同属性的更改会被保留。如果两个操作设置了相同的属性，则最后提交的操作决定其值。在同一对象上并发运行大量操作时，仍可能偶尔发生少量冲突。

示例： A Ticket 对象具有 status = "open" 和 priority = "low"。两个操作同时运行：

  • 操作 A 设置 status = "in progress" and priority = "medium".
  • 操作 B 设置 priority = "high".
  • 操作 A 先提交。工单现在为 status = "in progress", priority = "medium".
  • 操作 B 后提交并覆盖了操作 A 对 priority的更改。工单最终为 status = "in progress" and priority = "high"。操作 A 对 status 和操作 B 对 priority 的更改均被保留。

自动预览行为 快照隔离，操作 B 将在冲突检查中失败，因为两个操作写入了同一个对象，而操作 A 的编辑将被保留。

此级别以较弱的正确性保证为代价，产生更高的提交成功率。它适用于操作只写入其已掌握的值（例如作为参数传入的值），且不依赖其读取的内容来决定写入内容的场景。

并发编辑可能被覆盖

当多个操作可以并发设置同一属性时，请谨慎使用 read committed。如果两个操作都提交，则后提交的操作会覆盖该属性先前的值。对其他属性的更改将被保留。

当前分阶段写入行为

使用暂存写入的操作类型目前仅支持旧版隔离模式。

本节介绍暂存写入所提供的保证。

读取： 每次读取都会返回读取执行时刻的最新已提交值，以及该操作自身的暂存编辑。由于没有固定的快照，同一操作在不同时刻进行的两次读取，如果在两次读取之间有其他操作提交，可能会观察到不同的状态。但是，该操作自身的暂存编辑对其后续读取始终可见。

写入： 该操作使用暂存写入，因此在同一操作执行过程中稍后执行的读取会包含该次执行中较早进行的编辑。其他操作在这些编辑于结束时以原子方式提交之前不会看到它们（参见 写入的工作原理).

冲突检查： 如果在对象加载到操作提交之间，另一个操作更改了该操作写入的对象，则该操作将因冲突错误而失败。操作会失败，而不是覆盖并发更改。操作仅 读取 不会导致冲突失败。有关重试冲突的信息，请参见 暂时性错误的重试模式.

此行为将暂存写入的“读己之写”能力与写-写冲突检测相结合，但不保证从本体论（Ontology）读取的数据来自单一时间点。

暂时性错误的重试模式

当操作遇到瞬时错误（包括冲突错误以及从对象存储加载对象的失败）时，平台可以自动重试该操作。每次重试都会使用该操作配置的隔离级别从头开始重新执行该操作，最多尝试 5 次。读取当前值的逻辑会使用新执行可用的数据重新计算其编辑。如果每次尝试都失败，则错误将返回给调用方。

默认情况下，不包含外部系统调用（如 webhook）的操作会被重试，而包含外部系统调用的操作不会被重试——因为重新执行该操作会重复其副作用，例如触发两次 webhook。

您可以在 功能 选项卡中使用 暂时性错误的重试模式 设置来针对每个操作类型调整此行为：

  • 仅重试没有外部调用的操作（默认）： 仅当操作类型没有外部系统调用时，平台才会重试。
  • 所有操作： 平台重试所有操作，包括包含外部调用的操作。当已知操作类型的外部调用可以安全重复（幂等）时使用此选项。
  • 启用： 平台从不自动重试。首次失败时错误即返回给调用方。当调用方希望观察并处理每个冲突时使用此选项。

请注意，在其他方面完全相同的两个操作类型，在此设置不同的情况下，在争用下的行为可能不同——一个似乎总是成功，因为冲突被重试消除，而另一个则向其调用方暴露冲突错误。

自动重试也意味着，经常发生冲突的操作可能需要明显更长的时间才能完成，即使它最终成功。

选择隔离级别

  • 使用快照隔离 ，除非您有特定的理由不这样做。快照隔离是大多数工作流程的最佳隔离级别，包括对单个对象的“读取-修改-写入”逻辑。
  • 对于已创建的操作类型 然后 引入了显式隔离级别后，可将级别设置为快照隔离，以确保执行中的每次读取都来自同一时间点，而不是旧版行为中通常如此但无法保证的情况。但是，由于快照隔离在整个执行过程中使用同一时间点视图，如果操作运行时间较长且尝试编辑频繁更新的数据，则该操作可能会被更频繁地重试。
  • 考虑使用读已提交 唯一 当冲突失败频繁发生、您了解其允许的异常情况，并且操作的写入不依赖于对数据的稳定读取时。请在 读已提交 部分中查看警告，然后再将现有操作类型切换到此模式。
