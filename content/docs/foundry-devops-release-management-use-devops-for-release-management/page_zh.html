使用 DevOps 进行发布管理

本指南概述了使用 DevOps、Marketplace 和空间设置发布管理流程的步骤。假设您已经在开发环境中建立了工作流，以下说明旨在指导您完成设置额外环境并将现有工作流部署到这些新环境的过程。

如下所述，使用 DevOps 和 Marketplace 是实现发布管理流程的一种方式。在 Palantir 平台中还有其他方法可以实现这一点，例如使用 全局分支.

1. 使用空间设置环境

使用 空间 在 Palantir 平台中用于环境。请为您需要的每个环境创建一个空间。例如，您可以创建 Development、 Test和 Production 空间。Palantir 平台中的所有资源和项目都存在于某个空间中，因此您的资源当前所在的空间可以用作您的 Development 空间。如果您希望将当前空间用作您的 Development 空间，您只需再创建 Test 和 Production 空间。

请参阅 有关空间的文档 以了解如何创建和配置空间。

一个空间内可以存在多个工作流，并且资源可以在这些工作流之间共享。

如果您的注册中禁用了创建空间的功能，请联系 Palantir 支持团队来创建新空间。

环境可以在 DevOps 应用程序中进行管理，其配置会跨越整个注册并影响所有存储。您可以通过导航至表格的 设置 选项，然后是 配置环境。

在 环境 设置中，用户可以添加建议的环境（包含给定商店安装内容的空间），或选择其他空间。您还可以重新排列环境列表，以确定它们在此页面上的显示顺序。用户只能在其拥有所有者访问权限的空间中编辑、添加或删除环境，且这些空间只能与一个注册关联。

2. 将资源打包到产品中

使用 DevOps 将开发环境中的资源打包为产品。您可以将工作流打包到一个或多个产品中。典型的划分方式可能如下所示：

  • 数据源产品，包含数据连接资源。
  • 本体论产品，包含对象类型及其支撑数据集，以及通用的操作和函数。
  • 一个或多个用例产品，包含 Workshop 模块，以及特定于工作流的操作和函数。



    请查阅我们关于如何创建产品的指南。

一般来说，最佳做法是将整个项目打包为一个产品，以保持项目与产品之间的 1:1 关系。这样可以简化为资源确定合适产品的过程。

本体论实体不属于任何项目。在决定将对象类型、关联类型、操作类型和函数打包到何处时，请参考以下指导：

  • 对象类型 应打包在支撑 数据集 所在的产品中。

  • 在 关联类型所使用的两个对象类型中，关联类型应打包在最 下游的对象类型所在的产品中。例如，假设有一个用例产品名为 Logistics Use Case ，其中包含一个名为 Truck 的对象类型，它与 Plant 对象类型存在关联，后者位于 Core Ontology 产品中，则该关联类型应打包到 Logistics Use Case 产品中。在这种情况下，我们可以说 Logistics Use Case 产品位于 下游 ，相对于 Core Ontology 产品中，且该 Core Ontology 产品位于 Use Case X 产品的上游。如果两个对象类型位于同一个产品中，则也应将关联类型打包到该产品中。



  • 对于 操作类型，请考虑以下几点：

    • 操作类型通常与某个用例隐式关联。在这些情况下，应将操作类型打包到相关的用例产品中。例如，如果 Reroute Truck 操作类型被应用程序使用，且这些应用程序位于 Logistics Use Case，请将操作类型与用例一起打包。
    • 操作类型可以由函数支撑。在这些情况下，操作类型将依赖于支撑它的函数。请将操作类型与支撑它的函数打包在同一产品中。
    • 一个操作类型可能被多个用例使用，而这些用例分别打包在不同的产品中。在这些情况下，您可以将公共功能（例如操作类型以及可能支撑它们的函数）提取到其独立的产品中，或提取到核心本体论产品中。

  • 函数 应与生成它们的源（例如函数代码仓库或逻辑资源）打包在同一产品中。

关于打包多个项目的指导

工作流通常依赖于跨多个项目的资源，将项目打包为产品时也是如此：产品可以组合在一起，因为打包在一个产品中的资源可以用作下游产品的输入。这意味着您可以跨多个项目对更大的工作流进行发布管理。例如，您可以打包一个数据源产品、一个核心本体论产品以及多个用例产品。用例产品可能包含 Workshop 应用程序或其他依赖于对象类型的资源，而这些对象类型将是核心本体论产品的一部分。在这种情况下，用例产品需要将这些对象类型作为输入，而这些输入将由核心本体论产品满足。

将相关项目打包为产品。这些产品应组合在一起，使一个产品的内容能够满足下游产品的输入。

了解有关关联产品的更多信息。

3. 对您的产品进行发布管理

将您的项目打包为产品后，您现在就可以将这些产品安装到第二个环境中。在包含 Development、 Test和 Production 环境的发布管理流程中，这就是 Test 环境。 了解有关通过 Marketplace 安装产品的更多信息。

对每个后续环境重复此过程。在环境中安装产品后，您可以自动完成升级，只需自定义您的 安装设置。其他自定义设置（如发布渠道和维护窗口）也可以在初始安装期间进行配置。

您可以在 DevOps 应用程序的“环境”选项卡中查看环境。用户可以在其配置的环境中查看产品安装情况。商店中打包的产品显示在左侧栏中，这些产品可以在用户配置的环境中进行安装和升级，例如在 development， test， production 环境中。

用户可以查看其环境中安装的总体概览，以及每个环境的一些摘要信息。从这里，用户可以直接导航到相应的安装，并执行诸如安装、升级、编辑发布渠道和锁定安装等操作。

选择单个环境即可查看该环境的更详细视图。

安装多个产品的指南

如果您一次安装多个产品，请在执行此操作时考虑产品的安装顺序。上游产品需要在其下游依赖项之前安装。安装下游产品时，其输入通常应由同一环境中的资源来满足，例如，使用您 Test 环境中的资源作为 Test 环境安装的输入，其他环境依此类推。

关联产品功能将在打包时向您显示哪些产品可以满足彼此的输入。

在 DevOps 中查看环境

您可以在 DevOps 应用程序的 环境 标签页中查看环境。对于给定的商店，开发环境包含该商店的源产品，用户可以将这些产品安装到自己的其他环境中。用户可以在其配置的环境中查看这些产品安装。商店中打包的产品代表了 development 环境中，然后这些产品会在用户配置的环境中进行安装和升级，例如在 development, test, production 环境中。
