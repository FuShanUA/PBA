Iceberg 客户端身份验证

本节介绍 Iceberg 客户端如何向 Foundry 的 Iceberg 目录进行身份验证。在 Foundry 内使用 Iceberg 时，无需执行这些步骤。

Foundry 的 Iceberg 目录实现了 规范 ↗ （适用于 Iceberg REST 目录）。这意味着，支持 REST 目录的 Iceberg 客户端在与 Foundry 的 Iceberg 目录交互时，可以使用该规范中定义的身份验证机制。

配置 Iceberg 客户端时，可使用以下身份验证选项：

方法描述
OAuth2 client credentials使用客户端 ID 和客户端密钥以服务用户身份进行身份验证。配置完成后，Iceberg 客户端将执行所有必要的令牌交换。
Bearer使用 API 令牌（通常称为 Bearer 令牌）以用户身份进行身份验证。

客户端不应配置云存储（如 S3 或 Azure Data Lake Storage (ADLS)）的凭证。请参阅 访问委派与凭证分发 部分，了解如何通过目录向客户端授予访问权限的详细信息。

使用 API 令牌

API 令牌（也称为 Bearer 令牌）是最快速的身份验证和入门方式。您可以按照 用户生成的令牌 文档中的说明为您的用户生成 API 令牌。

使用 Bearer 令牌配置 Iceberg 客户端时，需要以下属性：

键示例是否必填？描述
urihttps://<hostname>/iceberg是标识 Foundry Iceberg 目录的 URI
tokeneyJwb...是用于 Authorization 标头的 Bearer 令牌值

以下示例使用 Python Iceberg 客户端 (PyIceberg)，并在 ~/.pyiceberg.yaml ↗中配置目录。 目录属性记录在 此处 ↗ ，并且可针对支持 REST 目录的其他 Iceberg 客户端实现进行调整。

catalog:
  foundry:
    uri: https://your.foundry/iceberg
    token: eyJwb...

这些生成的 Bearer 令牌是长期有效的，并且与您的用户绑定。 应谨慎处理这些令牌。 我们建议在生产环境中使用 OAuth2，并将基于令牌的身份验证仅用于开发。

使用 OAuth2

您可以在 Iceberg 客户端中使用 OAuth2，以获得比直接提供 API Bearer 令牌 更高的安全性。您需要创建一个采用客户端凭证授权模式的第三方 OAuth2 应用程序， 相关说明请参阅 此处。

Iceberg 客户端会获得所生成的客户端凭证以及授权服务器的 URL， 该服务器会用客户端凭证换取应用程序令牌。Iceberg 客户端会处理此交换过程 以及后续的令牌刷新。

在为 Iceberg 客户端配置 OAuth2 时，会使用以下属性：

键示例是否必填？描述
urihttps://<hostname>/iceberg是标识 Foundry Iceberg 目录的 URI
oauth2-server-urihttps://<hostname>/iceberg/v1/oauth/tokens是标识授权服务器的 URI
credentialclient_id:client_secret是初始化目录时用于 OAuth2 凭证流程的凭证
scopeapi:iceberg-read api:iceberg-write否以空格分隔的作用域,用于限制权限

使用这些属性,您可以按照以下方式为 OAuth2 配置 PyIceberg 目录客户端:

catalog:
  default:
    uri: https://your.foundry/iceberg
    oauth2-server-uri: https://your.foundry/iceberg/v1/oauth/tokens  # OAuth2 server URL
    credential: 17f...:037...  # client_id:client_secret
    scope: api:iceberg-read api:iceberg-write  # optional, space-separated scope

该 scope 配置是可选的。默认情况下,权限与为第三方应用程序创建的服务用户 所拥有的权限相同。若要将作用域限制为仅允许读取,您可以声明 api:iceberg-read 而不声明 api:iceberg-write。

Foundry 使用 Iceberg 风格的授权服务器,因此所用的端点不同于 该端点 ,即通常用于 OAuth2 客户端的端点。

访问委托与凭证分发

存储访问由 Iceberg 目录使用 Iceberg 规范 ↗中所述的访问委托机制进行委托。Foundry 的目录根据以下支持矩阵提供凭证分发(推荐)或远程签名:

存储位置凭证分发凭证刷新远程签名
ABFS是,通过 SAS 令牌否否
S3是,通过 STS 令牌是是

凭证分发

借助凭证分发,Foundry 的 Iceberg 目录会通过作用域受限的短期分发凭证,向经过身份验证的客户端授予数据访问权限。这种方式可强制实施最小权限原则,并通过最大限度地减少存储凭证的暴露来增强安全性。

当 Iceberg 客户端与 Foundry 的 Iceberg 目录交互时，存储凭证绝不会由用户或应用程序直接提供。相反，Foundry Iceberg 目录会颁发严格限定于特定数据和权限的临时凭证。

凭证分发过程的工作方式如下：

  • 访问请求： Iceberg 客户端使用 Foundry Iceberg REST 目录 API 发起访问一个或多个表的请求；例如，在加载表元数据时。
  • 身份验证： Foundry 的 REST 目录会对客户端进行身份验证，并核实其对所请求的表和操作的权限。
  • 凭证分发： 如果客户端通过了授权，Foundry 的目录将“分发”（即颁发）短效且范围严格限定的存储凭证。每个被分发的凭证仅对特定文件有效，且仅持续有限的时间。
  • 数据访问： 客户端使用这些临时凭证直接访问底层存储（如 S3 或 ABFS）以读取或写入数据。凭证一旦过期，访问权限将被自动撤销。

from pyiceberg.catalog import load_rest
from getpass import getpass

token = getpass("Foundry user token:")

catalog = load_rest(
    "foundry",
    {
        "uri": "https://<your_foundry_url>/iceberg",
        "token": token,
    },
)

table = catalog.load_table("<table_rid>")
print(table.snapshots())
del token

将 <your_foundry_url> 替换为您的 Foundry 主机名，并将 <table_rid> 替换为您的 Iceberg 表的资源标识符。如果此步骤成功，则表明目录可达，并且您的用户拥有正确的权限。

from pyiceberg.catalog import load_rest
from getpass import getpass

foundry_url = "https://<your_foundry_url>"
client_id = "<your_client_id>"

client_secret = getpass("OAuth2 client secret:")

catalog = load_rest(
    name="foundry",
    conf={
        "uri": f"{foundry_url}/iceberg",
        "oauth2-server-uri": f"{foundry_url}/iceberg/v1/oauth/tokens",
        "credential": f"{client_id}:{client_secret}",
        "scope": "api:iceberg-read api:iceberg-write",
    },
)

# List namespaces to verify catalog access
print(catalog.list_namespaces())

# Load a specific table to verify table-level permissions.
# If you are unable to read the table, verify that the service account associated with the third-party application has permissions to access it.
table = catalog.load_table("<table_rid>")
print(table.snapshots())
del client_secret

将 <your_foundry_url>、 <your_client_id>，以及 <table_rid> 替换为特定于您环境的值。
