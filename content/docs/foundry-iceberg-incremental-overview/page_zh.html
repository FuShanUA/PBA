使用 Iceberg 表进行增量处理

增量计算是一种处理输入以生成输出的高效方法。借助增量计算，您只需处理自上次运行以来发生变化的数据，而无需每次都重新处理整个输入。

本页提供了以增量方式使用 Iceberg 表的概念性概述。有关 Python 转换的 API 指南，请参阅 增量 Python 转换 以及随附的 增量代码示例。有关变更日志的具体指导，请参阅 Iceberg 变更日志与 CDC 管道。

本体论对象类型的增量索引

由写时复制 Iceberg 表支撑的对象类型会被 建立索引 ，并且以行级增量方式进行。支撑表中的行编辑和删除会作为对象编辑和删除传播到本体论，因此删除单行只会更新相应的对象，而无需重新索引整个表。

由于 Iceberg 写时复制 通过重写整个数据文件来应用行级更改，因此增量索引构建期间读取的数据量会随被重写文件的大小而变化，而非随更改的行数而变化。与同等数量但集中在少数几个文件中的更改相比，影响分布在多个文件中的行的更改，其建立索引的成本更高。

对于支撑对象的 Iceberg 表，目前不支持读时合并

读时合并将行级更改记录为删除文件，而不是通过重写数据文件来记录；而 Iceberg 变更日志扫描目前无法读取包含删除文件的快照。如果在支撑对象类型的表上发生了以读时合并方式执行的删除或更新操作，增量索引构建将会失败。

请将支撑对象类型的表保持为写时复制模式，这是 Iceberg 的默认设置。Foundry 不会覆盖此设置，因此，表将采用写时复制模式，除非您显式 设置属性 进行其他配置。

读取和写入更改

读取更改

以增量方式读取 Iceberg 表时，Foundry 会根据您请求的读取模式检索给定快照范围内的更改。

在 仅追加 读取模式（默认）下，当快照范围仅包含追加或替换（压缩）操作时，Foundry 可以进行增量解析。如果存在覆盖或删除快照，增量检查将失败，Foundry 要么回退到完整的非增量读取，要么导致作业失败，具体取决于您的 require_incremental 设置。

在 changelog 读取模式下，Foundry 可以跨追加、覆盖、删除和替换操作进行增量解析。此模式支持基于 changelog 的读取，例如 Iceberg 的 changelog 视图 ↗ ，适用于变更数据捕获风格的管道。

写时复制（copy-on-write）与读时合并（merge-on-read）

Iceberg 提供了两种应用行级变更的策略。该选择由表的 生产者 做出，但会约束其 消费者，因此这是一个管道级的决策。

策略作用权衡
写时复制
（Iceberg 默认）		重写每个包含受影响行的数据文件。写入较慢，读取较快
读时合并将现有数据文件保留在原处，并写入额外的 删除文件 ，以将受影响的行标记为已删除。更新和合并操作还会写入一个新数据文件，其中包含更新后的行。消费者会在查询时应用这些删除文件，以重建表的当前状态。写入较快，读取较慢

你的表使用写时复制还是读时合并，这由 write.delete.mode、 write.update.mode以及 write.merge.mode 表属性决定。如果未显式设置这些属性，你的表将继承 Iceberg 的默认设置，即写时复制。这些属性仅在应用行级变更时才会生效。仅进行过追加操作的读时合并表不包含任何删除文件，其行为与写时复制表相同。

读时合并表可受益于使用 Rewrite data files 维护任务进行的定期压缩（compaction），该任务会应用尚未处理的删除文件，并将结果整合到新的数据文件中。因此，读放大只会持续到下一次压缩为止。

读时合并表无法作为变更日志读取

Iceberg 变更日志扫描 ↗ 无法读取包含删除文件的快照。一旦对表应用了读时合并的删除、更新或合并操作，将该表作为变更日志读取便会失败，并出现 Delete files are currently not supported in changelog scans，且该表将无法再支撑 增量索引的本体论对象类型。

对于作为变更日志读取的表，或支撑对象类型的表，请保持使用写时复制模式。
