环境创建

这是一份深入介绍环境初始化流程的高级指南，面向对可能影响初始化性能的技术细节感兴趣的用户。

有关环境相关常见问题的一般性指导，请参阅 环境故障排除指南.

Conda 是一个开源的、与语言无关的包和环境管理器。Mamba 是 Conda 包管理器的开源重新实现。Code Workbook 已改用 Mamba 来解析包依赖关系，并将一组组包安装到独立的环境中。与 Conda 相比，Mamba 在包解析方面具有多项优势，最显著的是速度更快以及错误信息更易读。

本页面介绍了最重要的概念并概述了环境创建流程；欲了解更多信息，请查阅 Conda 官方文档 ↗ 和 Mamba 文档 ↗.

重要术语

  • 包
  • 渠道
  • 环境

包

A 包 是通常包含元数据、库和/或二进制文件的文件集合。Code Workbook 提供对大量可选包（numpy，例如）的访问，以补充核心语言功能。

包是 有版本控制的，并且几乎总是有一组依赖项——即必须同时安装才能使其正常运行的其他包。依赖项可能是包的特定版本、可接受的版本范围，或任意版本。

渠道

A 渠道，有时也称为仓库，是存储包的任何位置。一个渠道可以是本地文件系统中的目录，另一个渠道可以是托管在网络服务器上的目录。

无论类型如何，每个渠道都是一棵按平台架构分隔包的目录树。每个平台子目录都包含一个名为 repodata.json的文件，它是该子目录中所有包的索引。

Conda 在需要获取包时会搜索一组预配置的渠道。有关 Foundry 中渠道管理的更多信息，请参阅 Code Repositories 文档.

环境

Conda 环境 是一个包含特定包集合的目录。每个 Workbook 的环境都是通过将环境配置面板中指定的包传递给 Conda 来创建的。Conda 会构建一组满足配置及所有依赖项的包，并将这些包安装到支撑该 Workbook 的 Spark 模块上。

创建环境

环境创建包含两个主要步骤：解析步骤和安装步骤。

解析步骤

在监听器设置向导的 解析步骤中，指定的包管理器（Conda 或 Mamba）会尝试找到满足所有传递性依赖项的包和版本。传递性依赖项包括环境配置面板中指定的包的依赖项、这些依赖项的依赖项，依此类推。此步骤包含四个阶段：

  1. 下载并处理包索引。Conda 将从每个已配置的渠道下载相关的 repodata.json 文件，并将索引条目转换为内存中的对象。
  2. 缩减索引。Conda 会构建一个包含所有可能用于该环境的包的集合。为此，算法从提供的包规范开始，并递归遍历所有依赖项。所有不需要的包——主要是那些不在依赖关系图中的包——都会被剪除。
  3. 将依赖约束表示为布尔可满足性（SAT）问题。Conda 偏好某些类型的解（例如使用包的最新可用版本），这些偏好会被写入子句构造中。
  4. 运行 SAT 求解器。

安装步骤

如果求解成功， 安装步骤 是下一步。在此步骤中，每个工件都会从相应的通道中检索出来，用于构建环境。此步骤包含三个阶段：

  1. 下载并解压求解后环境中的所有软件包。
  2. 验证软件包内容。根据配置的不同，Conda 会使用校验和，或者验证文件大小是否正确。
  3. 将软件包链接到环境中。

局限性

在某些情况下，上述所有步骤都可能出现缓慢。导致缓慢的原因通常属于以下三类之一：

  • 上游变更
  • 环境规范
  • 软件包大小

上游变更

相当一部分缓慢是由 Foundry 之外的因素造成的。

  • 下载和处理通道索引的耗时随索引文件的总大小而增加；需要考虑的通道越多、这些通道越大，这些步骤所需的时间就越长。
  • 索引缩减也随传递依赖项的数量而增加；传递依赖项的数量取决于软件包选择声明哪些依赖项。

由于这些因素是外部且不透明的，因此对性能退化进行根因分析可能比较困难。某个环境可能突然需要更长的加载时间，原因可能是某个通道最近变大，或者某个软件包在其最新版本中声明了多个新依赖项。

环境规范

更常见的情况是，初始化缓慢与 环境规范 本身直接相关。求解步骤的耗时随环境大小呈超线性增长，因此作为一般经验法则，包含更多软件包的环境初始化所需的时间会不成比例地更长。

有两种方法可以缓解这些情况。

  • 首先，从环境定义中移除不需要的软件包。小型、专用的环境比大型、通用的环境性能要好得多。
  • 其次，尝试在环境配置面板中为某些软件包添加版本约束。为具有大量现有构建的软件包（例如 python ）以及具有复杂依赖关系图的软件包（例如 scipy）固定版本最为有效。这样做可以让 Conda 更激进地缩减索引，这意味着 SAT 求解不需要考虑那么多的软件包版本。

软件包大小

软件包大小 通常比本节中的其他因素问题更小，但在某些情况下仍然相关。

即使只下载和解压单个软件包也可能并非易事。例如， pytorch 软件包的大小约为 460 MB，解压可能需要 35 秒以上。

下载、解压和验证的耗时都随环境中软件包的大小和数量呈线性增长。由于传递依赖项的存在，求解后的环境通常包含比环境定义中明确指定的多得多的软件包，软件包的增加可能导致缓慢。

这种情况下的缓解方法与针对 环境规范的建议类似：尽量保持环境尽可能小。

求解步骤优化：Spec 文件

如果不对环境所请求的软件包集合进行任何更改，则无需重新求解环境，因为那将得到相同的已解析环境。因此，Code Workbook 会避免 解析步骤 环境初始化的求解步骤，其做法是将成功求解的结果存储在一个 spec 文件中。下次需要初始化相同的环境时，Code Workbook 会跳过求解步骤，直接引用该 spec 文件。这样可以获得严格更优的初始化时间，因为 Code Workbook 只需执行安装步骤。作为针对极少数情况下先前成功的环境停止工作的预防措施，Code Workbook 默认会在 24 小时后使 spec 文件失效。此后，在环境下一次成功求解时将生成新的 spec 文件。

初始化优化：Conda Docker

禁用 Conda Docker

在极少数情况下，如果环境所使用的软件包包含 pre-link 或 post-link 脚本 ↗，则使用 Conda Docker 的环境可能在运行时失败。如果包含此类脚本的环境似乎出现失败，您可以在 Code Workbook 环境配置选项卡的左下角手动禁用此优化。禁用 Conda Docker 后，环境仍可受益于其他可用的优化。此配置将针对所使用的配置文件与切换该设置时所在的工作簿分支的组合持久保留。

预热

虽然上述优化可以缩短环境的初始化时间，但您可以通过主动初始化一定数量的模块来完全避免等待环境。这些模块被称为“预热”模块。通过配置预热模块队列，Code Workbook 可确保一组预先初始化的 Spark 模块始终处于就绪状态，随时可供分配。如果您经常需要长时间等待环境初始化，请考虑为相关配置文件实现预热模块队列。有关如何配置预热模块的更多信息，请参阅 预热 Code Workbook 配置文档的相关部分。

上述优化可使 Code Workbook 已存储的环境受益。在请求自定义环境时，Code Workbook 必须执行标准初始化过程，该过程不会受益于任何优化。因此，自定义环境通常具有较慢的初始化时间。要排查自定义配置文件初始化过程缓慢的问题，请参阅 故障排查 文档。
