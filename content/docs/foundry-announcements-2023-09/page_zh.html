代码仓库开发体验改进

发布日期：2023-09-21

Palantir Foundry 的代码仓库应用程序开发体验已通过一系列改进得到优化，具体如下：

  • Task Runner，代码仓库的一项新功能，允许用户运行受支持的命令，例如 install、 formatCode、 tasks，以及 whoneeds。启用 Task Runner 后，从左侧面板的“库”选项卡添加包时，现在会将所请求的包直接安装到您当前的环境中，而不是像之前那样预配 Code Assist 工作区。在此阶段生成的额外日志有助于在需要调试时提供更清晰的信息。此外，复杂筛选器和预览输入配置界面也得到了改进，更易于使用。

使用 Task Runner 添加和安装包

复杂筛选器和预览输入配置界面的改进

  • 更快速的 Python 开发： 平均而言， 云环境中的检查现在快了 20-30 秒，在创建新仓库时，初始检查会受益于新增的 lockfile，以代替立即执行的“已取代”检查。库安装总体上更快，用户现在既可以添加软件包以供稍后安装，也可以安装软件包，而无需在 Conda 和当前运行环境中重新创建工作区。此步骤中不会更新测试环境。
  • Artifacts 速度改进： 当环境没有变化时，Code Assist 可以持久化缓存并加快检查速度。ZSTD 压缩支持已扩展至 Artifacts 和 Mamba，使环境解析和安装比以往更加快捷。
  • 非 Linux 本地开发体验的改进： 已添加 conda-forge 作为所有仓库开箱即用的 artifacts 支撑仓库。此外， noarch Python 库模板让开发者能够更轻松地创建和管理跨平台库。
  • 新增 Python 格式化支持： 可在 black 和 ruff linters 之间进行选择，以确保编码风格的一致性。
  • 自动生成相关配置： 您现在可以在本地运行 vscode gradle 任务。
  • 增强了 macOS 和 Windows 上的本地开发支持： 现已支持通过 gradle 进行本地预览。此外，仓库升级和 Code assist 的前端也变得更加精简。
  • Spark 预览加载器优化： 现在最多可预览 100 万行(此前为 1 万行),并且加载速度提升了 4-5 倍。
  • 在检查日志中导航更加轻松: 直接在检查日志中选择 buildRIDs,即可导航至 Job tracker 中的相应构建。

本体论 SDK(TypeScript 和 Developer Console)[GA],Python SDK [Beta]

发布日期:2023-09-19

本体论 SDK(OSDK)TypeScript 版本和全新的 Developer Console 应用现已在所有堆栈上正式发布(GA)。Python SDK 目前处于 Beta 阶段,预计将于 2023 年 10 月底正式发布(GA)。

本体论软件开发工具包(OSDK)让您能够直接在开发环境中发挥本体论的全部强大功能。您可以使用 Developer Console 生成本体论 SDK,这是一个用于通过 Palantir API 创建和管理第三方应用程序的新门户。有关更多详细信息和说明,请参阅我们的 公开文档。

什么是本体论 SDK 和 Developer Console?

开发者控制台是一款新应用，可让您生成本体论 SDK，以便便捷地访问本体论 API。该 SDK 可以生成为 TypeScript NPM 包，也可以生成为 Python PyPi/Conda 包（测试版）。本体论 SDK 包仅包含开发者在开发者控制台中定义的本体论实体。

开发者可以使用本体论 SDK 轻松读取本体论数据、通过操作向 Foundry 回写数据、执行本体论函数等更多功能。使用 SDK 能够以类型安全的方式与我们的 API 进行交互。

如此一来，开发者便可以有效地将 Foundry 视为后端，依托 Foundry 提供的基础设施和集中式本体论管理，从而能够更加专注于其组织特有的应用程序开发。

一张 GIF 动图，展示了本体论 SDK 在代码编辑器中集成 Foundry 本体论资源。

为什么要使用本体论 SDK？

  • 加速开发： OSDK 支持便捷地访问本体论 API，让您只需几行代码即可读取和回写本体论数据。
  • 强大的类型安全性： 为 OSDK 生成的函数和类型基于您开发时所使用的本体论中选定的子集。所有内容均从您的本体论中提取，因此您可以直接在编辑器中查询和探索数据。
  • 集中式维护： 充分利用本体论在 Foundry 中集中构建和管理这一优势，让您能够专注于构建应用程序，而无需在为应用程序维护和构建数据基础方面投入重复的工作。
  • 跨团队感知： 使用开发者控制台后，应用程序将像原生 Slate 或 Workshop 应用一样显示在 Foundry 的溯源系统中，从而确保任何会影响您应用程序的本体论更改都可以根据其影响进行评估。
  • 设计即安全： OSDK 在生成时会附带一个令牌，其作用域仅限于您希望应用程序访问的本体论实体。

我该如何使用？

本体论 SDK 通过开发者控制台生成，这是 Foundry 的一款新工具，您可以通过它创建和管理为使用 Palantir API 而构建的应用程序。从工作区导航栏中的应用程序门户打开开发者控制台，或使用 CMD + J （MacOS）或 CTRL + J （Windows）进行搜索。

推出敏感数据扫描器 [Beta]

发布日期：2023-09-19

敏感数据扫描器（SDS，前身为 "Foundry Inference"）可帮助组织发现并保护其 Palantir Foundry 数据集中的敏感数据。现已推出 beta 版，治理用户可以使用 SDS 指定要识别的敏感数据模式，以及在发现匹配数据时要执行的自动化操作。此外，用户还可以通过更新后的界面准确跟踪和监控已启动的扫描。

改进的着陆页界面

Sensitive Data Scanner 着陆页现在包含一个进度条，用于汇总显示每次一次性扫描中各数据集的扫描状态。该彩色进度条会根据符合特定条件的数据集数量占队列中待扫描数据集总数的比例进行填充：

  • 蓝色： 当前正在进行或等待扫描的数据集。
  • 橙色： 符合某一条件的数据集。
  • 绿色： 不符合任何条件的数据集。
  • 红色： 扫描失败或被跳过的数据集。
  • 灰色： 已取消的扫描。

此外，通过选择每个扫描项右侧的下拉箭头，您可以轻松查看特定扫描下每个数据集的分类情况。

一次性扫描的详细视图，其中显示了文件的不同分类

估算扫描计算时间

用户还可以查看排队等待 Sensitive Data Scanner 扫描的数据集数量，从而估算扫描可能需要的时间，并鼓励在必要时审视扫描范围。

设置扫描的最后一步会显示将要扫描的数据集数量，并为用户提供创建一次性扫描或定期扫描的选项。

使用 AIP 生成正则表达式匹配条件

您现在可以使用 AIP（在已启用 AIP 的堆栈上）生成正则表达式匹配条件，而无需自己编写正则表达式。要使用此功能，请提供描述所需数据格式的自然语言提示，然后选择 生成 （位于 选择匹配条件 步骤中，即创建一次性扫描时。）

用户使用 AIP 为电子邮件地址生成正则表达式匹配条件

有关更多信息，请查阅 Sensitive Data Scanner 文档。

针对 Python 代码仓库的改进检查现已生效

发布日期：2023-09-19

我们已通过一系列有针对性的改进，提升了 Foundry 堆栈上 Python 仓库的检查性能。需要注意的是，内部堆栈上所有 Python 作业的平均 P95 检查完成时间（即从头到尾运行检查所需的时间）已从 2023 年 3 月的 2 分 15 秒降至 2023 年 6 月的约 1 分 15 秒，降幅达 44.4%。

加快检查速度的改进

我们近期在提升检查效率方面的工作包括以下更新。

针对 Conda 包的 Zstandard (ZST) 压缩

此前，“gzip 压缩”，现已实现 ZST，能够为 conda-pack ↗提供显著更快的压缩和解压缩速度，这对于在您的检查中运行 condaPackRun 和/或 condaPackTest 任务至关重要。

一张显示平均 P95 检查完成时间的图表（从 2023 年 3 月的 2 分 15 秒降至 2023 年 6 月的约 1 分 15 秒）

Jemma 管理的缓存不再被双重压缩

Jemma 是我们的检查运行器，现在不再对文件进行双重压缩，而是使用 ZST 压缩文件，从而降低了资源使用量和 CPU 时间。

避免双重压缩并使用 zst 来压缩缓存目录，使压缩速度显著提升（20MBs → 80MB/s）。下方展示了压缩缓存目录并存储压缩后的文件所需的时间。

更快的 Gradle Conda 任务

通过利用基础 Docker 镜像并在指定位置更新 Gradle 任务，以下常见任务的运行速度将得到提升：

  • condaInfo：将 Conda 安装程序打包到用于运行检查的 Docker 镜像中。
  • setupPythonEnv：将受支持的 Python 版本（主版本和次版本）的 Conda 安装程序打包到用于检查的 Docker 镜像中。
  • vscode：将 Gradle 的 @InputFiles 切换为 @Input ，从而将任务执行时间从 13 秒缩短至 1 秒以内。

针对 Conda 包的自定义 Gradle 缓存

使用自定义 Gradle 缓存可避免导致 Conda 包被双重压缩的低效问题，从而减少计算时间的浪费并提升整体性能。此项改进还得益于制品缓存布局能够根据使用情况刷新条目 TTL 的能力。
