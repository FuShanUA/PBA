构建生产管道

生产工作流需要可靠的管道作为支撑。在构建管道时遵循本文档中 laid out 的原则，将使维护更加容易，让您能够在问题导致 SLA 违约之前发现它们。这里的一些指导也将使分享关于管道中哪些内容重要的知识变得更加容易。这在管道生命周期的所有阶段都很重要，从开发一直到长期维护。

本文档对管道开发人员和管道维护人员都很有用。对于开发人员来说，如果管道将直接投入生产，那么在开始构建管道之前，本文档非常有用。同样，本文档也可以在概念验证管道转换为生产管道时使用。对于管道维护人员来说，以下要素应该是进入维护模式的先决条件。

管道定义与期望

虽然在开始构建生产管道之前，可能并不总是能够对期望有明确的答案，但尽早关注这些期望是很有价值的。强烈建议在确立管道定义和期望时将其记录下来。

这些期望会影响生产管道的设计和设置的多个方面，包括：

  • 管道设计和架构决策。
  • 应如何设置计划（因为这是控制管道构建频率的主要方式）。
  • 需要哪些验证和监控。
  • 当管道处于维护模式时，应如何确定问题的优先级。

您的团队应该解决的重要问题包括：

  • 管道的范围究竟是什么？ 它从哪里开始，到哪里结束？它应该在哪里接入其他管道？
    • 如果您的管道的某些部分与另一个管道或用例重叠，请考虑将重叠部分视为一个独立的管道。
  • 对管道刷新频率的要求是什么？
    • 或者，是否存在一天中数据必须刷新完成的具体时间？
    • 管道是否应在周末运行？
    • 数据何时被视为严重过期？
    • 在刷新频率和支持方面的期望是什么？
    • 请小心 ——虽然这听起来很容易，但这个领域往往是管道维护团队面临最大困难的地方。如果这里没有明确的定义，作为管道维护人员就很难确定工作的优先级或做出正确的修复。
  • 对端到端传播延迟的期望是什么？ 换句话说，从数据进入 Foundry 的那一刻起，到管道输出更新为止，数据流经管道需要多长时间？
  • 对于您从中提取数据的每个外部源，您的联系人是谁？ 外部源可以是 Data Connection 同步，或者是接入您管道的单独的上游 Foundry 管道。
  • 您的数据在正确性方面有哪些功能保证？ 是否存在对您的管道必须成立的关键列或关键验证？
    • 注意： 确定当保证被打破时结果应该是什么是很重要的。失败的验证应该阻止数据到达您的最终用户，还是应该在不阻止管道更新的情况下发出警报？您可能希望选择后者，以便让其他最新的数据流经您的管道？这两种不同情况的实现方式会有所不同。文档是早期开始跟踪保证的好地方。
  • 确定的预期是否兼容？ 随着复杂系统的增长，它们更容易出现故障。通常，您希望在告警触发后留出足够的时间来解决根本问题——无论是意外的管道故障，还是来自上游数据源的数据缺失。
    • 示例 1： 重要的是要结合预期的管道刷新频率来考虑传播延迟。如果预期的刷新频率是每 2 小时一次，而管道需要 1.5 小时才能构建完成，那么可能就难以遵守 SLA。
    • 示例 2： 如果某个工作流需要每小时刷新一次，但上游数据源每天只提供两次数据。这意味着您将无法实现每小时刷新。

生产管道的原则

成功搭建生产管道的关键原则可以概括为： “构建时就要假设日后维护它的不是你本人”.

以下是一些可以帮助您实现这一目标的具体建议：

  • 对代码进行版本控制，并编写有意义的提交信息： 这样可以更轻松地跟踪做了哪些更改、何时提交以及由谁提交。
    • 在生产管道中， Python and 或 如果可能的话是推荐的选择。这两种语言都有大量可用的资源以及强大的开发者社区。虽然 SQL 非常容易上手，但它很快就会变得复杂，因此调试起来可能更加困难。
  • 最重要的是优化可读性： 简单的管道更易于维护。在转换代码中选择标准或现有的解决方案，可以减少日后的维护负担和开发复杂度。如果您 必须 做了一些非常规的操作，请务必对其进行详尽的记录。
  • 尽可能保持管道的线性： 就总体架构而言，更易于维护的管道是那些相当直接且线性的管道，但很难就如何做到这一点给出具体建议。请注意管道的总体结构，并在您的约束条件下尽可能优化可读性和简洁性。一旦您考虑将管道投入生产，花一些时间来理清管道结构通常是值得的。
  • 生产管道通常生命周期很长。 因此，编写管道的人很可能不是长期维护或管理管道的人。请记住，接下来接管管道开发或维护的人需要能够读懂代码并理解管道的设置。
  • 保持简洁的文档：
    • 逻辑文档： 通常建议将与逻辑本身相关的文档保存在代码注释中。
    • 整体管道文档（包括记录管道中反复出现的问题）：也应保存在管道附近、位置直观的地方。一个合适的位置示例是管道所属的 Project 中。管道开发者和维护者应该能够轻松找到它。
    • 请记住：过度记录文档也会使其难以阅读并降低实用性。请保持简洁并记录关键信息。如果您需要记录非常冗长且详细的管道信息，而这些信息不会被经常查阅，可以考虑将其保存在单独的文档中。

开发流程与基础设施设置

开发

管道投入生产后，重要的是确保围绕对管道进行进一步贡献的开发流程已经建立，并有效地传达给管道开发者。这可以确保管道不会发生意外中断。

因此，我们建议阅读：

  • 开发最佳实践: 至少，生产管道应易于阅读、易于维护，并锁定主分支。但为了确保您的开发设置更加稳健，我们建议您阅读本文档中更详细的建议。
  • 分支与管道发布流程: 如果您在管道开发阶段尚未使用分支和管道发布流程，我们建议您在将管道投入生产时采用此流程。本文档将提供一个可供您使用的示例流程。

基础设施（调度）

与此相关的是，尽早设置调度可以让您在开发时无需考虑手动触发管道不同部分的构建。如果您的调度设置混乱，您可能会发现这会阻碍您的开发并降低速度，因为更改不会自动在管道中传播。

在将管道投入生产时，还建议您审查并重构您的调度，因为开发期间使用的调度可能不再合理或可能包含反模式。此步骤应在进入维护模式之前完成。

按照最佳实践设置或审查调度可以通过以下方式实现 调度最佳实践文档.

尽早开始监控

管道开始定期运行后，您应立即开始监控其行为。这可以防止技术债务累积，并让您能够跟踪对管道的预期是否切合实际。考虑到截止日期和团队的能力，立即开始监控可能并不总是可行，但我们鼓励在可能的情况下这样做。
