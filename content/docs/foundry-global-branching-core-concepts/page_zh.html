核心概念

分支

软件开发人员通常使用版本控制系统来协调代码库中的工作。这使得多名工程师能够安全地为同一份代码做出贡献。

在 Palantir 平台中，您可以像软件开发人员思考代码那样来思考数据和变更管理：您需要一种方法，让多人能够对相同的数据进行更改和交互，而不会干扰他人的工作。全局分支汲取了软件开发中的最佳实践，并将其应用于 Palantir 平台，利用了版本控制系统中的一项常见功能，称为 分支。

从宏观层面来看， 分支 允许您分叉现有环境，并在受控分支中处理端到端工作流的各个组件。当您对所做的更改感到满意时，您可以将分支引入的更改合并回 main 分支。

分支工作流

可以在 Foundry 应用程序中或直接在 Global Branching 应用程序中创建全局分支。下图展示了如何使用分支工作流对 Palantir 平台中的资源进行更改。

创建或访问分支

您可以通过 Foundry 应用程序中的分支选择器创建分支，或通过 Global Branching 应用程序创建。

请参阅 分支安全性 文档，了解有关本体论、组织和空间如何与分支创建相关的更多信息。

要访问现有的全局分支，请在任何受支持的应用程序中的分支选择器中选择该分支。您还可以在 Global Branching 应用程序的 分支 选项卡中查找并导航到现有分支。

在受支持的应用程序中处理全局分支时， 分支任务栏 将会显示。

在分支上进行更改

编辑资源

在您的分支中，您可以对 Foundry 资源进行更改，而不会影响 main 分支。但是，在分支上创建或删除 Foundry 资源会影响 main。这不适用于本体论资源：您可以在分支上创建、修改或删除实体，而不会影响 main 分支。

要开始对资源进行更改，某些应用程序要求您预先将资源添加到您的分支；其他应用程序则会在您保存首次更改后自动将其添加。当需要预先添加时，您将在选择分支时收到提示。

来自 main 分支的更新

当您在自己的分支上对资源进行更改时，同一资源可能在 main 分支上被更新。要获取这些更新， 变基 您的分支——也就是说，将 main 的更改合并到您的分支中，并在其上重新应用您之前保存的分支更改。

从您的分支中移除更改

从分支中移除资源会将其状态恢复到该资源在 main 分支上的版本。您可以直接通过 Global Branching 应用程序或分支任务栏从分支中移除资源。

移除资源可能会破坏您的分支状态，因此请务必检查资源的血缘关系，并确保没有其他分支资源依赖于您的更改。

创建并准备提案

当您对分支状态感到满意时，请创建提案以开始审查，并最终将您的更改合并到 main 分支中。要开始操作，请选择 创建提案 （位于 Global Branching 应用程序中）或分支任务栏中的相同选项。创建提案需要分支 Owner 角色或空间 Administrator 权限。请参阅 分支安全性 文档，以了解有关分支角色和权限的更多信息。提案包含一个描述字段，允许您提供审阅更改所需的信息，并支持 Markdown 文本。

在提案页面或分支任务栏中，您可以使用检查来查看资源是否已准备好合并，还可以指派审阅者。

检查

创建提案后，系统会对每个资源运行检查，以确定提案是否可以合并。

检查会显示可能阻止资源合并的任何问题，包括 main 分支与您当前分支之间的冲突，以及所需的审批。所有分支资源的检查都必须通过，才能合并提案。

变基与冲突解决

为了使分支处于可合并状态，其所有资源都需要能够与最新版本的 main 分支合并。当资源与 main 不同步或无法干净地合并时，变基检查将失败。您将被重定向到相应的应用程序，以对您的分支资源进行变基。如果您的分支资源与 main上的资源存在冲突，您必须解决这些冲突才能通过变基检查。

要查看有关不同应用程序如何实现变基的文档，请参阅 集成 页面。

全局分支会在变基过程中自动解决任何非冲突的更改。对于真正的冲突——即同一资源的同一属性在两个 main 与您的分支——无法自动解决；您必须先手动选择一个版本，然后才能继续执行 rebase。

添加审阅者

要合并您的分支，必须满足所有批准策略。非受保护资源仍需由具有编辑级权限的用户批准，当贡献者满足策略时，该批准可能会自动授予。受保护资源需要由 资源保护与批准策略中定义的必需审阅者进行审阅。

对于每个标记为 等待批准的资源，请选择 管理 以分配所需的审查者并查看相关的审批策略。分配审查者后，其将收到通知。

对于代码仓库和 Pipeline Builder 管道，审批策略在资源内部定义。

审查提案

已分配的审查者可以从分支任务栏或 Global Branching 应用程序中选择 审查 来访问资源的审查页面。

拒绝提案中对资源的更改

在评审过程中，任何用户的一次拒绝都会导致该资源的变更被 Rejected。这将 阻止整个提案合并。提出拒绝的用户需要重新评审这些变更并 Approve 它们，之后 提案才能合并。

合并提案

变更获得批准且所有检查均通过后，即可将提案合并到 main 分支，方法是选择 合并提案 ，该选项位于分支任务栏中，也可从 Global Branching 应用程序中访问。有关合并权限的说明，请参阅 分支安全文档.

合并提案时，您可以为受影响的资源（包括分支上未直接更改的资源）触发构建。共有三种构建选项：

  • 构建所有受影响的资源： 所有受分支更改影响的资源都将被构建，从而使上游更改中的数据按需流向下游。
  • 仅构建已修改的资源： 仅构建此分支上直接更改的资源。如果资源依赖于此分支的上游更改，您可能需要手动构建这些资源。
  • 不构建资源： 不会构建任何资源。提案合并后，您需要手动构建资源。

如果发生部分合并失败，提案页面将显示哪些资源已成功合并，哪些资源合并失败并仍保留在分支上。目前您无法回退部分失败的合并。您必须解决显示的所有错误，然后再次尝试合并您的提案。

分支和提案生命周期

分支生命周期

创建分支时，其状态将设置为 活跃。此后，分支可以进入以下状态之一： 非活跃， 已归档，或 已合并。四种可用的分支状态定义如下：

  • 活跃： 正在使用中或正处于合并流程中的分支。当该分支保持活跃状态时，在其上构建或索引的数据将被保留。

  • 非活跃： 在经过可配置的无活动期限后自动被标记为非活跃的分支。在此状态下，本体论资源将被取消索引，并在指定天数后进行数据删除。非活跃分支上的资源构建将立即失败。当分支被标记为非活跃时，您将同时收到电子邮件通知和平台内通知。

    • 将分支标记为非活跃以及触发数据删除的期限定义于 控制面板，具体位于 控制面板 > 空间 > 操作 > 全局分支保留策略。默认情况下，分支非活跃期限设置为 35 天，分支数据删除将在 7 天后触发。
    • 要将非活跃分支恢复为活跃状态，您可以手动移除该分支上的“非活跃”标签。
    • 当您在非活跃分支上打开资源时，会弹出对话框警告您该分支处于非活跃状态。请选择 激活分支 以激活该分支。如果您改为关闭对话框，则可以继续与该资源交互，但不建议这样做。

  • 已归档： 不再使用的分支；归档始终是手动进行的。您将同时收到电子邮件通知和平台内通知。已归档分支的取消索引、构建失败和数据删除的处理方式与非活动分支相同。元数据（例如之前修改过的资源）将被保留，并且已归档的分支可以恢复。已归档的分支不会显示在分支选择器中，但可以在 Global Branching 应用程序中打开和恢复。

    • 当您在已归档的分支上打开资源时，系统会弹出一个对话框，警告您该分支已归档。请选择 恢复分支 以恢复该分支。如果您改为关闭对话框，则可以继续与该资源交互，但不建议这样做。

  • 已合并： 提议已合并的分支。已合并的分支为终止状态：无法恢复，不会出现在分支选择器中，且只能通过 Global Branching 应用程序访问。

使用先前处于非活动状态或已归档的分支

当分支处于非活动状态或已归档时，该分支上的资源可能已发生本体论实体的取消索引，或逻辑和数据的删除。如果该分支随后被激活或恢复，您可能需要执行以下操作来替换已删除或已取消索引的数据：

  • 本体论实体： 要触发本体论实体的重新索引，请进行无操作（no-op）更改（例如对本体论资源的描述进行细微更新），或通过 Ontology Manager 中的横幅重新索引。
  • 代码仓库： 如果作业规范已被删除，请进行无操作（no-op）更改，例如在您仓库中的相关转换内编辑注释，然后提交。随后在代码仓库中运行构建，即可将逻辑重新写入相关数据集并对其进行构建。如果首次构建是从 Data Lineage 等其他应用程序运行的，则不会写入作业规范。
  • 管道构建器： 在管道构建器中进行部署和构建，以将作业规范和数据重新写入您的分支。
  • 构建计划： 已归档或非活动分支上的构建将自动失败。如果某个计划在该分支上构建资源，则可能会因反复构建失败而暂停。您可以从 Build Schedules 应用程序或 Data Lineage 中手动恢复该计划。

已知限制

  • 反复构建失败后，非活动或已归档分支上的计划将自动暂停。如果您重新激活了分支，请视需要手动取消暂停该分支上的计划。
  • 在本地开发过程中，例如直接使用 git 从本地计算机与分支资源进行交互时，系统不会阻止您在非活跃或已归档的分支上进行操作。基于您所做的更改而物化的数据和/或作业规范可能会被删除。

AI FDE

  • AI FDE 不允许修改非活跃或已归档的分支；它会提示您重新激活或恢复该分支以继续。

提案生命周期

提案可处于以下三种状态之一：

  • 开启： 正在进行或已获批的提案。
  • 已合并： 已合并到 main 分支中的提案。
  • 已关闭： 已关闭且未合并的提案。
