对象集服务限制

对象集服务（OSS）是负责从本体论中查询和检索对象的服务。OSS 使用分层执行策略来平衡性能与规模，并根据查询的大小和复杂程度自动选择最优的处理方式。

本页面介绍了 OSS 如何处理不同规模的查询，以及在使用对象集时您需要了解的限制。

查询执行策略

OSS 使用分层执行策略，自动为您的查询选择最优的处理方式：

  1. 下推到存储层： 对于简单查询，OSS 会将操作直接下推到存储层，以利用索引化的数据结构。这是最快的执行路径，所需的计算开销极小。

  2. 内存中执行： 对于包含更复杂操作的查询，OSS 会将数据加载到内存中进行快速处理，直至达到一定容量。这适用于中等规模的查询。

  3. 基于 Spark 的执行： 对于超出内存容量的大规模查询，OSS 会自动回退到基于 Spark 的分布式计算。这能够处理规模大得多的对象集，但代价是额外的延迟和计算资源消耗。

这些执行策略之间的切换是自动的，并基于多个因素：

  • 对象集大小： 较大的集合会触发 Spark 执行
  • 可用的计算资源： OSS 会在性能和资源利用率之间进行平衡

在单个复杂查询中，OSS 可能针对不同的执行阶段使用多种执行策略。了解每种方式的阈值和限制将帮助您设计高效的查询并理解其性能特征。

OSS 在 Object Storage v2 上的执行流程

下图展示了 OSS 如何根据您的查询选择合适的执行策略。根据每个阶段的复杂程度，此决策过程可能在单个查询中执行多次：

关键阈值：

  • 100,000 个对象（默认阈值）： 对于 Search Around 和派生属性，从内存中执行切换到基于 Spark 执行的阈值。
  • 内部分页阈值： 如果任何数据加载步骤需要从 Object Storage v2 获取超过 25 页的数据，OSS 将回退到 Spark。
  • 10,000,000 个对象（默认阈值）： Search Around 操作的最大结果集大小（叶节点限制）。
  • 100,000 个对象（默认阈值）： 使用以下方式将对象加载到内存中的最大数量 .all() or .allAsync() （OSDK 限制； getAllObjects API 可以加载更多）。

对象集大小限制

OSS 根据存储后端和操作类型实施不同的大小限制。这些限制可确保系统稳定性和可预测的性能。

对象存储 v1 (Phonograph) [计划弃用]

计划弃用

对象存储 v1 (Phonograph) 目前处于 计划弃用 阶段，并将于 2026 年 6 月 30 日之后不可用。 迁移您的对象类型和关联类型 到 Object Storage v2。

Object Storage v1 具有以下限制：

  • 将对象加载到内存中： 最多 100,000 个对象 可以使用 .all() or .allAsync() 中的方法加载 小部件允许您使用.
  • Search Around 操作： 在从对象集 A 到对象集 B 执行 Search Around 时，结果集（对象集 B）不能超过 100,000 个对象.

这些限制适用于 Object Storage v1 中的所有操作。对于较大的查询，不会自动回退到基于 Spark 的执行。

对象存储 v2

Object Storage v2 通过其混合执行模型提供了更大的灵活性和可扩展性：

  • 内存中执行： 默认情况下，OSS 会在内存中处理对象集最多为 100,000 个对象.
  • 基于 Spark 的执行： 当 Search Around 操作涉及超过 100,000 个对象时，OSS 会自动切换到基于 Spark 的分布式计算。
  • Search Around 结果限制： Search Around 操作的结果集（从单个数据源加载的“叶”对象集）不能超过 1000 万个对象 （针对每次单独的 Search Around 操作）。此外，查询执行期间所有数据集加载的对象总数不能超过 3000 万个对象.
  • 将对象加载到内存中（OSDK 限制）： 使用 .all() or .allAsync() 方法在 Ontology SDK 中加载对象时，最大数量为 100,000 个对象 以防止内存耗尽和函数超时。您可以使用 getAllObjects API 端点加载更多对象。

在 Functions on Objects 中加载超过 10,000 个对象可能会导致执行超时，具体取决于函数逻辑的复杂程度。请考虑使用分页或筛选来减小对象集的大小。

分页和内存限制

OSS 对分页读取请求施加内存限制。因此，即使还有更多对象，某一页包含的对象数也可能少于请求的页面大小。请勿将短页视为结果集的结束。请继续使用返回的页面令牌请求页面，直到令牌为空。

直方图 loadObjects 端点已弃用。请迁移到带有 StaticObjectSetV2的分页端点。因为 loadObjects 必须返回每个请求的对象，所以它无法返回部分结果。如果加载所请求的对象会超出内存限制，该端点将返回 ObjectSet:ResultSizeLimitExceeded 有时，Webhook 可以正常工作，而来自函数的 API 调用可能会遇到

了解 Search Around 结果集

当您执行 Search Around 操作以遍历对象之间的关联关系时，OSS 使用一种特殊类型的连接操作来高效地查找相关对象。

例如，当您从一组客户对象出发，通过关联关系查找所有相关的订单对象时：

  • 直方图 起始集 是您的客户对象（即您搜索的起始对象）
  • 直方图 结果集 是与这些客户相关联的订单对象（即您搜索的目标对象）

OSS 使用左半连接（left-semi join）实现 Search Around 操作，该操作仅返回结果集中具有匹配关联的对象，而不会复制起始集中的数据。1000 万个对象的限制适用于此结果集，即遍历关联关系后返回的去重对象总数。

在 OSS 限制内工作的最佳实践

为确保最佳性能并避免触及大小限制：

  • 尽早筛选： 在执行连接或将对象加载到内存之前，先应用筛选器以减小对象集的大小。OSS 利用索引数据结构使筛选查询更加高效。

  • 避免无法利用索引的操作： 对派生属性和计算 SQL 列进行的筛选、聚合、排序等操作需要评估所有行，无法使用内部索引。这些操作不会使用快速下推路径，即使对于小型对象集也可能触发内存中或 Spark 执行。例如，如果您想筛选 2026 年 5 月发生的所有订单，请避免使用 (MONTH FROM order_date) = 'May' AND (YEAR FROM order_date) = '2026'。请改用范围筛选器： order_date > '2026-05-01' && order_date < '2026-06-01'.

  • 使用分页： 在 Functions on Objects 中处理大型对象集时，请使用分页模式分批处理对象，而不是一次性加载所有对象。

  • 监控对象集大小： 在执行 Search Around 等高开销操作之前，请使用聚合查询来了解对象集的大小。Search Around 操作的计算开销很高，这就是 OSS 强制实施这些大小限制的原因。

  • 优化数据模型： 如果您经常触及大小限制，请考虑使用传统数据建模原则重构您的本体论。通过将相关数据整合到对象属性中来对本体论进行反规范化，可以减少高开销的 Search Around 操作的需求，并使查询更加高效。您还可以创建更有针对性的对象类型或关联关系，以自然地产生更小的结果集。

  • 考虑计算成本： 基于 Spark 的执行比内存执行使用更多的计算资源。触发 Spark 回退的查询将消耗额外的 计算秒.

OSS 使用大小估算来确定是否执行查询。如果估算大小显著超过限制（超过 2 倍以上），查询可能在达到确切阈值之前失败。这是一种性能优化，旨在避免代价高昂的精确计数操作。
