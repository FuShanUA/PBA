Spark 概念

Spark 简介

什么是 Spark？

Spark 是一种分布式计算系统，在 Foundry 中用于大规模运行数据转换。它最初由 UC Berkeley 的一个研究团队创建，并于 2000 年代后期捐赠给 Apache 基金会。Foundry 允许您使用 Spark 作为底层计算层，对大量数据运行 SQL、Python、Java 和 Mesa 转换（Mesa 是一种专有的基于 Java 的 DSL）。

Spark 是如何工作的？

Spark 依赖于将作业同时分发到多台计算机上来处理数据。与 Hadoop 使用的基于磁盘的两阶段 MapReduce 模型不同，Spark 使用有向无环图（DAG）执行引擎并优先进行内存计算，这使得多个作业能够在用户和项目之间快速并行运行。这些计算机分为驱动器（driver）和执行器（executor）。

  • A 驱动器（driver） 就像是您 Spark 作业的“指挥”。驱动器负责将作业的工作分发给执行器。
  • An 执行器（executor） 就像是您 Spark 作业的“工蜂”。执行器负责执行由驱动器分配给它的那部分作业的计算。这项工作被拆分为若干“分区”，每个执行器会获得一些分区来运行您的代码。执行器完成该任务后，会返回驱动器请求更多的工作，直到作业完成为止。
  • 每个 Spark 作业都有许多与之关联的变量，可以对这些变量进行调整，以创建最适合运行该转换的 Spark 配置文件。
    • 在每个 Spark 作业中，都需要在快速轻松地执行作业与运行该作业所需的成本和资源之间取得平衡。
    • 根据经验法则，更多的执行器和更多的内存应该会缩短运行时间，但同时也会增加成本。
    • 根据作业的特性，驱动器和执行器的某些组合与配置会比其他配置表现更好。这将在以下章节中详细讨论 调优 Spark 配置文件.
    • Spark 配置文件是 Foundry 用来配置上述分布式计算资源（驱动器和执行器）的配置，为其分配适当数量的 CPU 核心和内存。
  • 每个 Spark 作业都关联了五个可配置的变量：
    • Driver 核数： 控制分配给 Spark 驱动器的 CPU 核心数量。
    • Driver 内存： 控制分配给 Spark 驱动器的内存量。
      • 仅控制 JVM 内存。这不包括外部非 Spark 任务（例如调用 Python 库）所需的“堆外”内存
    • 执行器核心数： 控制分配给每个 Spark 执行器的 CPU 核心数量，这进而控制每个执行器中并发运行的任务数量。
    • 执行器内存： 控制分配给每个 Spark 执行器的内存量。
      • 此内存在执行器上运行的所有任务之间共享。
    • 执行器数量： 控制为运行该作业而请求的执行器数量。
  • 所有内置 Spark 配置文件的列表可在 Spark 配置文件参考.

调优 Spark 配置文件

  • 您在运行转换时可能会遇到一些问题，需要调整 Spark 配置文件以创建自定义的非默认配置，从而使您的特定作业能够运行。例如：
    • 您的作业可能需要更多内存。
    • 您的作业运行速度可能低于用例所需的速度。
    • 您可能会遇到导致作业完全失败的错误。
  • 要在 Code Repositories 中使用非默认的 Spark 配置文件，首先需要将该配置文件导入到包含您转换的仓库中。此过程在以下文档中有描述 Spark 配置文件的使用.
    • 导入后，可以按照以下指南将 Spark 配置文件分配给特定的转换 应用转换配置文件 documentation.
  • Pipeline Builder 批量管道中使用的 Spark 配置文件是通过管道的 构建设置.

何时修改默认的 Spark 配置文件

  • 编辑 Spark 配置文件时，经验法则是每次只增加一个变量，且每次只提升一个级别。
    • 例如，首先只调整执行器内存，将其从 EXECUTOR_MEMORY_SMALL to EXECUTOR_MEMORY_MEDIUM，然后再次运行作业，再调整其他内容。这有助于避免因向作业过度分配资源而产生不必要的成本。
  • 虽然后端默认值并不总是对应特定的 Spark 配置文件，但它们通常可以通过标记为以下名称的内置配置文件来近似 SMALL.
    • （针对非 Python 转换的）正确默认值是 EXECUTOR_CORES_SMALL, EXECUTOR_MEMORY_SMALL, DRIVER_CORES_SMALL, DRIVER_MEMORY_SMALL, NUM_EXECUTORS_2.
    • 当 Python 调用在 JVM 之外运行的 Python 库时，可能需要更多的非 JVM 开销内存。
  • 如果您的 Spark 作业遇到任何问题，第一步是优化您的代码。
    • 如果您已经尽可能优化但仍然存在问题，请继续阅读具体的建议。
  • 如果您的作业成功完成，但运行速度低于您的用例所需：
    • 尝试增加执行器数量；增加执行器数量会增加可以并行运行的任务数量，从而提高性能（前提是作业具有足够的并行性），但同时也会因使用更多资源而增加成本。
      • 您可以在 Builds 应用程序页面查看给定构建的图表，帮助您判断增加执行器数量是否有助于提高作业速度。如果任务并发数远未达到执行器数量，增加执行器数量很可能无法缩短运行时间。
    • 如果将执行器数量翻倍未能将运行时间缩短超过 1/3，那么您的代码可能效率低下（例如，从 Catalog 大量读取数据或向 Catalog 大量写入数据）。
      • 例如，如果将生成 6 分钟作业的转换的执行器数量翻倍，作业应在 4 分钟或更短时间内完成。
      • 如果将执行器数量减半使作业变慢不到 50%（例如，从 4 分钟变为 6 分钟），除非运行时间至关重要，否则您应降低到较低的执行器数量以节省成本。
    • 可以对大型配置文件（例如 128 个或更多执行器）施加限制，以确保只有经过批准的用例才能使用大量资源。如果您达到了限制并需要更高的配置，请联系您的 Palantir 代表。
    • 在启动期间，执行器往往以每分钟约 10 个的速度累积到驱动程序。这意味着执行器数量较多但运行时间较短的作业可能应使用较低的执行器数量，以减少系统中的抖动。例如，任何运行时间少于 10 分钟的 64 执行器作业可能应降至 32 个执行器，因为当作业获取完所有计算资源时，它几乎已经完成了。
  • 如果您的作业失败，并且您收到 OOM（内存不足）错误或与代码逻辑无关的“Shuffle 阶段失败”错误：
    • 尝试将执行器内存从 SMALL to MEDIUM。如果您正在处理大量数据，这应该会有所帮助。
      • 如果您认为需要从 MEDIUM to LARGE进行调整，请咨询专家以获取帮助。如果可能，请考虑按照以下说明简化您的转换 故障排除指南.
  • 如果将大量数据收集回驱动程序或执行大型广播连接：
    • 尝试增加驱动程序内存。
  • 如果您看到类似“Spark 模块停止响应”的错误，且输入数据集包含大量文件：
    • 首先尝试增加驱动程序内存。
    • 如果增加驱动程序内存后错误仍然存在，请将驱动程序核心数增加到 2。
  • 如果您的转换需要读取大量文件并遇到 GC（垃圾回收）问题：
    • 尝试将驱动程序核心数增加到 2。

推荐的最佳实践

面向管理员

  • 当某个用例结束时，请删除为该用例创建的所有自定义配置文件。
    • 这样可以减少混乱，避免创建过多导致困惑的自定义配置文件。
  • 设置权限，使资源密集型配置文件仅在管理员明确授予权限后才可访问。
    • 例如， NUM_EXECUTORS_32 and EXECUTOR_MEMORY_LARGE （及以上）应仅在请求并获得批准后才可用。
    • 除以下值之外的所有执行器核心值 EXECUTOR_CORES_SMALL 应受到严格管控（因为这是增加计算能力的一种“隐蔽”方式，在几乎所有情况下，最好引导用户使用 NUM_EXECUTORS 配置文件）。

关于调整 Spark 配置文件

  • 尽可能尝试使用默认配置文件（即不使用任何配置文件）。
    • 这样可以降低成本并减少混乱。
  • 如果无法使用默认配置文件，请尝试使用内置配置文件。
  • 在设置新的配置文件时，请以您的姓名或用例名称命名保存。
    • 这样可以改善组织管理，并确保该配置文件不会在您不知情的情况下被其他用户或项目使用。
    • 否则，您可能会得到一个包含过多配置文件的列表，却不知道哪个配置文件是为哪个用途设置的。
  • 增加内存时，任何超过 8:1 资源比例（由以下组合指示）的配置 EXECUTOR_CORES_SMALL and EXECUTOR_MEMORY_MEDIUM）都应获得管理员的批准。屏蔽 EXECUTOR_CORES_EXTRA_SMALL and EXECUTOR_MEMORY_LARGE。如果用户请求这些配置，通常表明存在优化不足或关键工作流。
  • 配置文件应可分离。每个配置文件应仅影响一个 Spark 变量（或一个 Spark 变量的逻辑组合）。
    • 例如，在创建新配置文件时，仅更改执行器数量，然后在不更改其他变量（如执行器内存或驱动程序内存）的情况下进行测试。
  • 除非在同一 Spark 模块中并发运行许多 Spark 作业的特殊情况，否则不应覆盖驱动程序核心数的默认配置。
  • 默认执行器核心配置很少应被覆盖。
  • 任何运行时间少于 15 分钟的作业都不应使用 64 个执行器。
    • 如此多的执行器会将大部分时间仅用于启动。
  • 每当创建并运行自定义配置文件后，请在事后检查其性能，位置在 Spark详细信息.
    • Spark 详情将跟踪作业的执行速度，并详细显示并发作业的信息。
