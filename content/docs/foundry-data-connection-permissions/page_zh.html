权限参考

Data Connection 中的所有主要概念——代理、源和同步——在 Foundry 中作为 资源进行管理。这样可以灵活地在项目和文件夹中组织这些资源，并允许将安全原语（例如 标记 应用于 Data Connection 资源。

平台所有者应注意不要过度共享 Data Connection 资源。对源和代理具有查看和编辑权限的用户应是受信任的管道开发者。同步生成的数据集可以根据需要导入到下游 Transforms 项目中，从而在不共享代理或源访问权限的情况下授予数据访问权限。

本页面介绍权限在所有 Data Connection 资源中的工作方式，包括：

  • 代理
  • 数据源
  • 同步
  • 插件
  • Webhook
  • 来自代码的外部连接

资源权限

本节所述的权限为默认权限。在某些环境中，默认权限行为可能已通过 自定义角色.

代理

所有者

代理的所有者通常是其创建者，并拥有以下权限：

  • 重新下载代理或为该代理重新生成令牌
  • 继承 Editor 的权限

编辑器

代理的 Editor 可以：

  • 将源部署到该代理。
  • 使用 Agent Manager 配置代理（更改插件和配置，并重启代理）。
  • 与其他用户共享该代理。
  • 继承 Viewer 的权限。
  • 删除该代理。

用户必须是某个项目的 Editor 才能在该项目中创建代理，但必须是该项目的 所有者 才能管理该项目中的代理。这意味着用户可以创建代理，但之后可能无法生成下载链接或对该代理执行其他管理任务。

查看者

代理的 Viewer 可以：

  • 查看代理的配置和状态。

数据源

所有者

默认情况下，源所有者继承 Editor 权限的用户隐藏。

源所有者还可以：

  • 如果用户还具有 Information Security Officer 注册角色。
  • 如果用户同时具有以下权限，则可添加可导出的安全标记 应用标记 和 移除标记 对每个标记的权限。
  • 如果用户具有以下权限，则可添加可导出的组织 扩展访问 针对其自身组织以外的每个组织的权限。用户无需该权限即可添加自己的组织。 扩展访问.
  • 允许将源导入到代码资源中。

添加可导出的标记或组织不需要 Information Security Officer 组织概览

编辑器

源的 Editor 可以：

  • 删除该源。
  • 更改该源分配的代理（还需要对每个要添加的代理具有 Edit 权限）。
  • 更新源配置（还需要对分配给该源的代理具有 Edit 权限）。
  • 重命名该源。
  • 为该源创建、编辑和删除同步。
  • 对数据库源运行 SQL 查询。
  • 与其他用户共享该源。
  • 浏览和预览支持这些操作的源，例如 JDBC 和 Directory 源。
  • 继承 Viewer 的权限。
  • 将源导入到代码资源
如果凭据允许，源 Editor 可以更改源系统

请注意，如果源凭据允许，同步可以更改源系统（例如，从目录或 S3 源中删除文件，或通过任意 SQL 从数据库中删除数据）。只应向那些您也会授予其源用于访问数据的账户的完全访问权限的用户授予对该源（或包含该源的项目）的 Edit 权限。

查看者

  • 源的 Viewer 可以查看源配置，包括分配的代理。

数据源创建权限

对于大多数环境，请使用 网络出口策略 来管控离开 Foundry 的流量。出站策略控制允许的目标地址以及可以使用这些地址的用户，因此用户可以创建数据源和工作流，而无需额外的组织级限制。

基于角色的数据源创建是一个可选的额外控制层，用于限制组织中的哪些用户可以创建数据源。您可以在 控制面板：

  • 默认资源名称： 用户必须具有包含 创建 Data Connection 数据源 工作流的组织角色才能创建数据源。
  • 已禁用 （默认）：用户无需组织级数据源创建工作流即可创建数据源。

此设置适用于整个组织。无论哪种情况，项目权限仍适用于现有数据源。此设置仅管控数据源的创建；它不会取代出站策略管控，也不会更改现有数据源上的权限。

要更改此设置，您必须具有 管理数据源创建授权方法 对相关组织的工作流。 Organization administrator 角色默认包含此工作流。

如果启用基于角色的数据源创建，请先向需要创建数据源的用户或组授予包含 创建 Data Connection 数据源 工作流的角色。您可以使用 组织角色，包括 自定义角色来授予此工作流。

同步

同步权限派生自相关的源和输出数据集。

  • 查看同步 需要对源和数据集具有 View 权限。
  • 编辑同步 需要对源和数据集具有 Edit 权限。
  • 删除同步 需要对源和数据集具有 Edit 权限。
  • 运行同步 需要对数据集具有 Edit 权限。

插件和 JDBC 驱动程序

所有者

  • 继承 Editor 的权限。

编辑器

  • 删除插件/驱动程序（插件/驱动程序必须未分配给任何代理才能成功删除）。
  • 继承 Viewer 的权限。

查看者

  • 查看插件/驱动程序。
  • 下载插件/驱动程序。
  • 将插件添加到代理（还需要对该代理具有 Editor 权限）。

Webhook

Webhook 的权限完全继承自其关联的源。

  • 查看 Webhook 配置 需要对源具有查看权限。
  • 创建 Webhook 需要对源具有编辑权限。
  • 编辑 Webhook 配置 需要对源具有编辑权限。
  • 删除 Webhook 需要对源具有编辑权限。
  • 配置操作以使用 Webhook 需要对源具有编辑权限。
  • 执行 Webhook 需要对源具有编辑权限，但通过操作执行 Webhook 的情况除外。

默认情况下，只有执行 Webhook 的用户才能使用 Data Connection 应用程序中的历史记录标签页查看响应。 webhooks:read-privileged-data 权限可以添加到自定义或默认 角色 中，以允许具有该角色的用户查看其可访问的所有 Webhook 的完整请求和响应历史记录。标准推荐设置是添加一个名为 "Webhook Privileged Data Viewer" 的新角色并授予该权限，并确保需要查看完整 Webhook 历史记录的用户在相关源上具有该角色。

来自代码的外部连接

外部转换、管道和计算模块

当源被导入到代码资源中时，对仓库具有编辑访问权限的用户可以使用为该源配置的连接详细信息编写自定义代码，包括访问机密值。

这意味着将源导入代码的能力以及授予 Editor 对源的访问权限应谨慎管理，只应让受信任的用户访问源和仓库。

  • 在代码资源中导入源（和构建数据的方法是应用一个联合操作。联合操作将两个数据集合并，以包含每个数据集的所有行。在Pipeline Builder中，联合操作会保留所有行，包括重复的行。, 管道 or 计算模块）需要 Editor 对源的权限。
  • 触发导入源的构建需要 Editor ，该选项位于 代码资源 （对源本身无需任何权限）。
  • 从代码资源中移除已导入的源需要 Editor 对源的 or 代码资源。

外部函数

请参阅有关 外部函数权限 的文档，以获取有关在函数仓库中使用 Webhook 权限的详细信息。

Code Repositories 中的自定义 CI 作业

自定义 CI 作业 代码仓库中的自定义 CI 作业可以使用导入到该仓库的源的出口策略和密钥。任何可以编辑该仓库的用户都可以在任意分支上添加使用这些密钥和出口策略的作业。请仅将源导入到您信任其编辑者能够安全使用该源凭据的仓库。

标记传播

如上所述，资源可以应用 组织 和 标记 作为额外的访问控制级别。应用于源的组织和标记将传播到从该源同步生成的数据集。这意味着用户将无法查看从某个源生成的任何数据集中的数据，除非他们具有对该源应用的所有组织和标记的访问权限。

由于源很可能包含不同敏感级别的数据，我们建议您使用适用于该源中可用数据的所有组织和标记来标记该源，然后使用转换通过 stop_propagating 和/或 stop_requiring 功能来清理和取消标记数据。要了解有关取消标记的更多信息，请参阅以下指南： 移除标记 和 移除继承的标记.

在数据同步后对其应用组织和标记不应被视为足够；由于对源的访问实际上就是对数据的访问，因此应使用适用于源中包含的所有内容的组织和标记来标记该源。

最佳实践

提醒一下，Data Connection 的主要资源是代理和源。插件和驱动程序会部署到代理以扩展功能。

代理最佳实践

针对代理有两种推荐的权限设置：每个组织的所有代理放在单个项目中，或者每个代理放在自己的项目中。上图展示了前一种选项；以下指导说明了您可能选择每种选项的原因。

选项 1：将每个组织的所有代理放在单个项目中。

将所有代理放在单个项目中是最简洁的方法，如果由一组用户管理所有代理，则推荐使用此方法。这使您能够在项目级别控制对代理的访问，并在代理下游单独为源和同步设置权限。

仅当所有 Agent Manager 和所有源编辑者都可以访问所有代理时，才选择此选项。请记住，要在代理上部署源，用户必须对该代理拥有 Editor 权限。

选项 2：将每个代理放在其自己的 Project 中。

这种方法可以实现代理权限的完全细粒度控制。它还保证在源管理演进的过程中，结构永远不会偏离“分组”。例如，您可以安全地为源分配/取消分配代理，而无需授予用户对整个代理组的访问权限，并且将来无需为了适应组权限变更而重构 Project。

如果您有多个管理代理的组，并且希望分别控制它们对代理的访问权限，则建议采用这种方法。

Project 编辑者可以在代理上创建源和同步

包含该代理的 Project 的编辑者将能够创建在该代理上运行的新源和同步。请确保不要向不应执行此操作的用户授予该 Project 的 Editor 角色。

源的最佳实践

每个源都应位于其自己的 Project 中的 数据源 层。在源上定义的每个同步都应输出到 数据集 （位于与源相同的 Project 中）。如果源包含敏感数据（如 PII），您可以对源应用 标记 ，该标记将传播到输出数据集。

包含源的 Project 的编辑者将能够为该源创建新同步和编辑现有同步，还可以创建 Webhook 并对其进行配置以在 Foundry 的其他地方使用。

如果源凭据允许，同步可以更改源系统。例如，它们可以从 Directory 或 S3 源中删除文件，或通过任意 SQL 从数据库中删除数据。仅向那些您也会授予其对源所用账户完全访问权限的用户授予对源（或其 Project）的 Edit 访问权限。

插件和 JDBC 驱动程序

对于插件和 JDBC 驱动程序，有两种推荐的权限设置：每个组织的所有资源放在单个 Project 中，或者每个 JDBC/驱动程序放在包含一个或多个需要它的代理的 Project 中。

选项 1：将所有插件和驱动程序放在每个组织的单个 Project 中。

如果由一组用户管理所有代理，则建议采用此方法。这使 Agent Manager 能够访问已上传的所有插件和驱动程序。仅当所有 Agent Manager 之间应对插件和驱动程序拥有同等访问权限时，才应选择这种方法。

实施此方法的推荐流程如下：

  1. 为每个代理创建一个文件夹。
  2. 将当前的插件和驱动程序迁移到相应的代理文件夹。
  3. 选择每个插件和驱动程序的一个副本作为每个资产的权威副本，并将其移动到 Project 根目录。
  4. 将每个代理迁移为使用所需插件和驱动程序的根副本。
  5. 弃用各个代理文件夹。

选项 2：将每种插件和驱动程序类型放在其自己的 Project 中。

这种方法允许将某些“敏感”插件或驱动程序的权限与其他插件或驱动程序分开设置。如果采用这种方法，您必须确保为所需的代理所有者授予对每个项目的足够权限，以便他们可以在代理上使用这些插件和驱动程序。
