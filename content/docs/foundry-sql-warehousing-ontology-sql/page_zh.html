本体论 SQL

Beta

本体论 SQL 目前处于 beta 开发阶段，部分功能可能在您的环境中不可用。功能在持续开发期间可能会发生变化。请联系 Palantir 支持团队以申请使用 Beta 功能。

本体论 SQL 是 Foundry 面向本体论对象的 SQL 查询引擎，专为将熟悉的 SQL 语义引入您的本体论数据而构建。借助本体论 SQL，您可以直接对对象类型、多对多关联和接口运行 SQL 查询。使用本体论 SQL，您可以通过标准 Spark SQL 语法查询本体论对象，并直接针对对象存储执行查询。本体论 SQL 基于 Foundry 的 SQL 基础设施构建，提供统一的 SELECT 语句接口，支持变量、标准 SQL 函数，并与您现有的本体论建模无缝集成。

本体论 SQL 架构

Ontology SQL 为查询本体论对象提供了统一的 SQL 体验，与 Foundry 的其他 SQL 产品共享相同的 SQL 方言和前端体验，同时依托其自身的专用后端运行。

  • 统一的 SQL 方言： Ontology SQL 共享相同的 SQL 解析层和符合 ANSI 标准的 Spark SQL 方言 与 Furnace，确保在 Foundry 的 SQL 生态系统中实现一致的语法和行为。这提供了熟悉的 SQL 体验，而底层的查询规划和优化则专门针对本体论数据进行了定制。
  • 本体论数据提供程序： Ontology SQL 引入了专门用于对象类型和多对多关联表的提供程序。这些提供程序会将对象属性、主键和关联关系等本体论概念转换为与 SQL 兼容的表结构，从而支持使用标准 SQL 语法无缝查询本体论数据。
  • 直接对象存储访问： 查询直接针对 Foundry 的对象存储层执行，该存储层正是对象集所使用的同一底层存储。这种直接访问方式可确保性能和成本特性与其他本体论操作保持一致，且无需中间数据移动。
  • 计算引擎抽象： 规划完成后，对象存储服务（OSS）会确定应由哪个计算引擎执行查询。计算引擎负责运行查询、读取数据并返回结果，同时通过自动资源管理和内置的规模约束来确保可靠的性能。
  • 一致的 API 体验： Ontology SQL 提供与 Furnace 类似的 API 接口，带来一致的开发者体验，并支持随平台的演进实现未来的扩展。
  • 支持的计算引擎： 本体论 SQL 构建于 Foundry 的计算引擎抽象之上，可随着平台的演进支持未来的优化和更新。此外，为了处理更大、更复杂的查询，本体论 SQL 中的某些查询可以在 Spark ↗中执行。

本体论 SQL 入门

访问本体论 SQL

您可以在对象模式下，通过以下工具与本体论 SQL 交互： SQL Studio 或 SQL 控制台。进入对象模式后，您将能够使用标准 SQL 语法查询您的对象类型。如需可用操作的完整参考，请参阅 SQL 方言 文档。

编写您的第一个查询

本体论 SQL 查询使用资源标识符（RID）引用对象类型。基本语法遵循以下模式：

Copied!
1SELECT * FROM `ri.ontology.main.object-type.<object-type-rid>`;

例如，查询某个 Employee 对象类型中所有属性的语句编写如下：

Copied!
1SELECT * FROM `ri.ontology.main.object-type.00000000-0000-0000-0000-000000000000`;

针对多对多关联的查询可以按如下方式编写：

Copied!
1SELECT * FROM `ri.ontology.main.relation.<relation-rid>`;

了解列名称

在查询中引用所有对象属性时，使用的是其 API 名称，而非其显示名称。查询中可用的列直接对应于本体论中定义的属性 API 名称。如需查找 属性 API 名称 ，请访问 Ontology Manager。

例如，如果某个 Employee 对象具有带 API 名称的属性 employeeId， firstName，以及， department，您可以编写如下查询：

Copied!
1SELECT employeeId, firstName, department
2FROM ri.ontology.main.object-type.<employee-rid>;

使用关联类型

一对一和一对多关联

一对一和一对多关联类型无需在 Ontology Manager 中定义即可在 Ontology SQL 中使用。您可以使用 SQL 以任意方式联接对象。无论联接是否使用在 Ontology Manager 中定义的关联，性能都是相同的。

多对多关联

多对多关联需要联接表，并且必须在 Ontology Manager 中定义。要在 SQL 联接中使用它们，必须在 SQL 查询中选择关联类型。

查询多对多关联表时，列名遵循特定的约定以避免歧义。

每个外键列均使用以下模式命名：

<objectTypeApiName>_<relationApiName>

考虑一个介于 Person 和 Car 对象之间的多对多关系。

本体论设置如下：

  • 对象类型： Person （API 名称： person）
    • 主键： personId
    • 关联 API 名称（ Person 侧）： vehicles
  • 对象类型： Car （API 名称： car）
    • 主键： carId
    • 关联 API 名称在 Car 侧： drivers
  • 关联类型 rid： ri.ontology.main.relation.0

以下是一个示例查询，用于查找特定人员驾驶的所有车辆：

Copied!
1SELECT c.*
2FROM `ri.ontology.main.relation.0` AS linkTable
3INNER JOIN `car` AS c
4  ON c.`carId` = linkTable.`person_vehicles`
5WHERE linkTable.`car_drivers` = 'person-123';

以及一个示例查询，用于查找驾驶特定车辆的所有人员：

Copied!
1SELECT p.*
2FROM `ri.ontology.main.relation.0` AS linkTable
3INNER JOIN `person` AS p
4  ON p.`personId` = linkTable.`car_drivers`
5WHERE linkTable.`person_vehicles` = 'car-456';
最佳实践

在处理多对多关联时，请始终使用表别名。如果不使用别名，列名可能变得难以阅读和维护。请比较以下示例：

使用别名（推荐）：

Copied!
1SELECT c.*
2FROM `ri.ontology.main.relation.0` AS linkTable
3INNER JOIN car AS c ON c.carId = linkTable.person_vehicles
4WHERE linkTable.car_drivers = 'person-123';

不使用别名（可读性较差）：
Copied!
1SELECT car.*
2FROM `ri.ontology.main.relation.0`
3INNER JOIN car ON car.carId = `ri.ontology.main.relation.0`.person_vehicles
4WHERE `ri.ontology.main.relation.0`.car_drivers = 'person-123';

使用变量

本体论 SQL 通过 DECLARE 语句支持变量：

Copied!
1DECLARE @minSalary DOUBLE = 75000.0, @department STRING = 'Engineering';
2
3SELECT employeeId, salary
4FROM ri.ontology.main.object-type.<employee-rid>
5WHERE salary > @minSalary AND department = @department;

变量要求

  • 该 DECLARE 语句必须是查询中的第一条语句，且只能使用一次。有关如何声明多个变量，请参考上方的示例。
  • 有关支持的变量类型，请参阅 SQL 方言 文档。
  • 变量名称可以包含字母、数字和下划线。
  • SET 语句不被允许。

保留关键字

某些关键字，例如 user 和 result，均为保留字。最佳实践是使用反引号将列名括起来以避免冲突，如下所示：

Copied!
1SELECT `user`, `result` FROM ri.ontology.main.object-type.<object-rid>;

性能最佳实践

避免在筛选条件中使用函数

当在 WHERE 子句中对列应用函数或转换，或者在使用计算列进行筛选时，查询引擎将无法利用索引。这会严重限制查询性能和计算规模。

避免 以下导致无法使用索引的模式：

Copied!
1-- Filtering on a computed column
2SELECT employeeId, salary, bonus
3FROM employee
4WHERE salary + bonus > 100000;
5
6-- Filtering on a function result
7SELECT employeeId, hireDate
8FROM employee
9WHERE YEAR(hireDate) = 2023;

优先使用 以下模式以允许使用索引：

Copied!
1-- Filter on the original column directly
2SELECT employeeId, salary, bonus
3FROM employee
4WHERE salary > 100000 - bonus;
5
6-- Use date range comparison instead of extracting year
7SELECT employeeId, hireDate
8FROM employee
9WHERE hireDate >= '2023-01-01' AND hireDate < '2024-01-01';

同样的原则也适用于聚合。对查询中被任何部分转换过的列进行过滤（例如， colA + colB AS newColumn）意味着引擎无法使用索引来高效定位匹配的行，从而导致性能下降。

避免选择不必要的大型列

在不需要时，请勿在查询中选择向量（嵌入）等大型列。如果您的分析不需要这些列，它们不仅无法提供任何价值，还会显著增加查询执行时间和内存使用量。

限制和约束

查询结构限制

  • SELECT 仅限查询： 本体论 SQL 仅支持读取操作。不支持数据修改（INSERT、 UPDATE、 DELETE）或架构定义（CREATE、 ALTER、 DROP）操作。
  • 单个 SELECT 语句： 每个查询中仅允许一个 SELECT 语句，但用于变量的 DECLARE 语句除外。
  • 不得混用对象和数据集： 查询必须完全基于本体论对象或完全基于数据集进行操作。不支持在单个查询中混用两者。

数据类型约束

  • Struct 列 必须从查询中排除。包含结构体类型的列将导致查询失败。
  • 向量列 （嵌入）在技术上是受支持的，但由于其体积较大且在 SQL 环境中实用性有限，前端应用程序通常会将它们排除。
  • 所有其他本体论列类型 均受支持，并会自动转换为 SQL 兼容类型。

规模与性能约束

  • 输出限制： 本体论 SQL 服务会将结果截断为最多 10,000 行。即使查询中未提供限制，结果也会被限制为 10,000 行。 OFFSET 受支持，前提是 OFFSET + LIMIT 小于或等于 10,000。例如， OFFSET 1000 LIMIT 1000 可行，但 OFFSET 9000 LIMIT 2000 不可行。如果使用应用程序与本体论 SQL 交互，这些相应的应用程序可能会强制实施更严格的限制。

资源限制

  • 在 OSS Spark 资源饱和期间，作业可能需要排队等待最多 6 秒。
  • 查询执行超时时间为 20 秒。
  • 超出这些时长将导致 NotEnoughSparkResources 错误。

平台限制

  • 仅限对象存储 v2： 本体论 SQL 目前仅在对象存储 v2 上可用。
  • 不支持分支或场景： 查询仅针对主分支执行。对分支和场景的支持计划在未来的版本中推出。
  • 对象集限制：
    • 对象集可用作查询输入，具体取决于前端应用。
    • 对象集不能直接用作查询输出。
