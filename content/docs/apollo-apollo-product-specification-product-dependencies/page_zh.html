可排序版本和版本匹配器的定义见产品版本规范。

版本兼容性

可选的 minimum-version 和 maximum-version 字段充当约束条件，用于指定其依赖项支持哪些版本。当且仅当依赖项版本 v 同时满足下限和上限约束时，该版本才受支持：

  • minimum-version 是一个可排序版本，满足 v >= minimum-version
  • maximum-version 是一个版本匹配器，匹配某个发布版本 upper-bound，且满足 upper-bound >= v

recommended-version（如果指定）必须与给定的最小和最大版本边界兼容，并指示依赖项的推荐版本。

在上面的 postgresql 示例中，以下版本可以满足依赖规范：9.3.6、9.4.0、9.4.2-rc1、9.6.0-rc1 和 9.6.1-22-g1a2b3c4。以下示例不满足版本范围：9.2.0（过低）、10.0.0（过高）、11.1.2-rc2（过高）、9.7.0-1-gabcdef（过高）、9.5.0-custom-branch（不可排序）。

请注意，当 maximum-version 是 Release 版本匹配器时，具有相同 major/minor/patch 组件的快照版本不满足最大版本约束，因为它们的版本更高。例如，如果 maximum-version 为 1.2.3，则 1.2.3 和 1.2.3-rc4 满足最大版本约束，而 1.2.4 和 1.2.3-4-gabcdef 不满足。

可选依赖项

某些 Product Release 可以部署在多种有效配置中。其中某些配置可能需要给定的依赖，而其他配置则可能不需要。optional 字段可用于向 Apollo 指示，某个给定的依赖在某些有效配置中可能不存在。但是，如果该依赖存在于环境中，其版本必须在声明的版本范围内。

Apollo 将确保可选依赖项要么不存在，要么满足上文所述的约束条件。请注意，这意味着可选依赖项不会阻止任何实体的卸载。

被标记为可选依赖项的产品版本必须经过安装，才能在特定环境中被视为非可选依赖项。仅将其声明为受管是不够的。

不应根据可选依赖项的存在得出其他任何结论。具体而言，并非所有遵循可选依赖项的设置在默认情况下都应被视为有效。实际上，其中只有一小部分可能是有效的。

作为示例，考虑一个服务 "nice-service"，它能够将其底层数据存储在 Postgres 或 Cassandra 中，但只能使用其中之一。此类服务应声明对 Postgres 和 Cassandra 的可选依赖，以确保其中任何一个的缺失都不会阻碍 Apollo 对其的管理，并确保实际用于数据存储的服务处于兼容版本。然而，不应假设 "nice-service" 在既没有 Postgres 也没有 Cassandra 的情况下能够正常运行，尽管两者均被列为可选依赖。在使用 Apollo 管理 "nice-service" 时，Environment 编辑器应声明由 Apollo 管理 Postgres 或 Cassandra 之一，以确保该配置满足相应的 Product Release 依赖关系。

"nice-service" 可部署的有效配置集合应由 Product 编辑器单独定义。指定这些内容的位置和格式不在 Product Release 依赖清单扩展文档的讨论范围之内。

安装顺序

在安装带有 Product 依赖的实体时，Apollo 遵循以下规则：

  • 如果产品发布声明了不属于循环必需依赖项的必需依赖项，则在所有必需依赖项成功安装之前，该产品发布将不会被安装。例如，如果产品 A 依赖于产品 B，且 B 与 A 之间没有依赖链，那么 Apollo 将在安装 A 之前先安装 B。
  • Apollo 不保证产品发布的必需依赖项的安装顺序。例如，如果产品 A 依赖于产品 B 和 C，且 B 与 C 之间没有依赖关系，那么 B 或 C 哪个先被安装是不确定的。
  • Apollo 不保证产品发布的可选依赖项会在产品发布本身之前被安装。例如，如果产品 A 对产品 B 存在可选依赖项，那么 Apollo 可能会在安装 B 之前先安装 A。
  • Apollo 不保证循环必需依赖项的安装顺序。例如，如果产品 A 依赖于产品 B，产品 B 依赖于产品 C，产品 C 又依赖于产品 A，那么 Apollo 可能不会在安装 A 之前先安装 B。
