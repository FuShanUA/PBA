在开发环境中自动批准更改

Apollo 用户通常有一组希望放宽批准要求的环境，例如开发环境或预发布环境。Apollo 有意不提供可自动批准环境中所有更改的内置设置。Hub 管理员必须使用 CEL 策略来定义哪些更改、环境和作者有资格获得自动批准。

本页面提供了一些示例，展示 Hub 管理员可以如何配置 CEL 策略，以放宽其开发和预发布环境上的要求。

选择应自动批准哪些环境

使用 autoApproveEnvironments CEL 变量

每个针对环境中更改的 CEL 策略都预先配置了一个初始为空的 autoApproveEnvironments 变量。您可以向该变量添加环境，以允许由此 CEL 策略控制的更改被自动批准。

例如，向 entity-create-policy CEL 策略的变量中添加环境会自动批准新的实体安装。它不会自动批准其他更改，例如配置编辑。请更新控制您希望自动批准的每种其他更改类型的 CEL 策略。

我们建议在向 k8s-namespace-approval-policy 和 network-security-approval-policy 添加自动批准时要格外小心，因为它们控制着高度特权的操作。

定义并使用标签来选择开发环境

使用变量是一种简单的入门方式。但是，每个新环境都需要进行多次变量更改，每个策略各需更改一次。如果您预计会频繁添加新的自动批准环境，可以使用标签来简化该流程。

创建标签，并将 environment 添加到建议的资源类型列表中。例如，您可以将此标签命名为 security/enable-auto-approval。这将是一个布尔标签，因此请将可接受的值设置为 true 和 false。

更新每个针对您希望在这些环境中自动批准的变更类型的 CEL 策略。将以下逻辑添加到策略中，以便在环境具有该标签时自动批准变更：

将自动批准限制为受信任的作者

在上述示例中，我们为已配置环境集中的特定变更类型配置了自动批准，而无论变更请求由谁发起。我们建议添加限制，以确保您仅自动批准由受信任的作者（例如该特定环境的所有者）所做的变更。

我们可以通过检查所引用环境上的 authorRoles 字段，将自动批准限制为在所修改环境中具有 Environment Operator 权限的用户。对于其他用户，将适用标准的批准要求：

您可以根据自己的使用场景自定义此行为，例如，通过检查用户的团队或检查其他所引用资源上的权限。有关 CEL 策略的完整 API 规范，请参阅变更类型 API 参考。
