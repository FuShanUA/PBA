包解析期间检查失败

对于以下检查失败，您可以在代码仓库的“检查”选项卡中查看检查日志。利用这些日志，您可以了解检查失败的原因。

新的 Mamba 错误消息

Palantir 贡献 ↗ 通过为环境初始化错误消息提供更好的格式化，向开源 Mamba 社区做出了贡献。自 2023 年 2 月起，Foundry 服务受益于更能准确反映环境失败所违反的依赖树的错误消息。

依赖树

在以下示例中：

packageA
   ├─ packageB
   └─ packageC
        └─ packageD

这些包 packageB 和 packageC 可以 直接依赖 of packageA. packageD 是……的直接依赖 packageC，但是一个 传递依赖 of packageA。虽然 packageA 对……没有直接约束 packageD, packageA对……的直接要求 packageC 间接地对……施加了约束 packageD。下面是此类概念的一个真实示例：

statsmodels
├─ numpy
├─ scipy
├─ matplotlib
│  │  ├─ libpng
│  │  ├─ setuptools
│  │  ├─ cycler
│  │  ├─ dateutil
│  │  └─ kiwisolver

虽然乍看之下可能不明显， statsmodels 对……施加了约束 libpng，但它通过对……的约束以传递方式实现了这一点 matplotlib.

直接冲突

当在同一个环境中请求同一包的不同版本时，就会发生直接冲突。设想请求一个同时包含 python 3.7 和 python 3.8的简单环境。这是一个 直接冲突 ，将导致环境创建失败。新的错误消息将提供以下信息：

  Could not solve for environment specs
  The following packages are incompatible
  ├─ python 3.7**  is requested and can be installed;
  └─ python 3.8**  is uninstallable because it conflicts with any installable
   versions previously reported.

上面的消息正确地说明了 python 3.7 确实可以安装。但是，如果安装了该版本，任何安装另一个不同版本的尝试都会导致冲突。可以通过从环境中移除任一 python 版本约束来解决此环境问题。

然而，直接冲突相当罕见，与之相反，冲突通常由依赖和传递依赖引起。

直接依赖冲突

NumPy 文档 ↗ 明确指出 numpy >=1.22.0 需要 python >=3.8。因此，尝试创建同时请求 python 3.7.* 和 numpy 1.22.0 的环境将导致 直接依赖冲突。将出现以下错误消息：

Could not solve for environment specs
The following packages are incompatible
├─ numpy 1.22.0**  is installable with the potential options
│  ├─ numpy 1.22.0 would require
│  │  ├─ python >=3.9,<3.10.0a0 , which can be installed;
│  │  └─ python_abi 3.9.* *_cp39, which can be installed;
│  ├─ numpy 1.22.0 would require
│  │  ├─ python >=3.10,<3.11.0a0 , which can be installed;
│  │  └─ python_abi 3.10.* *_cp310, which can be installed;
│  └─ numpy 1.22.0 would require
│     ├─ python >=3.8,<3.9.0a0 , which can be installed;
│     └─ python_abi 3.8.* *_cp38, which can be installed;
└─ python 3.7**  is uninstallable because there are no viable options
   ├─ python [3.7.10|3.7.11|...|3.7.9] conflicts with any installable versions previously reported;
   ├─ python [3.7.0|3.7.1|3.7.2|3.7.3|3.7.6] would require
   │  └─ python_abi * *_cp37m, which conflicts with any installable versions previously reported;
   └─ python [3.7.10|3.7.12|...|3.7.9] would require
      └─ python_abi 3.7.* *_cp37m, which conflicts with any installable versions previously reported.

此错误消息表明 numpy 1.22.0 可以与 Python 3.8、3.9 或 3.10 一起安装，这与请求的 3.7.* 版本冲突。可以通过放宽对 Python 或 NumPy 的约束来解决此环境问题。例如， python 3.8.* 和 numpy 1.22.0，或 python 3.7.* 和 numpy 1.* 都可以成功创建环境。

出于环境故障排除的目的，您可以假设 python 和 python_abi 版本是紧密关联的。您可以通过调整您的 python_abi 版本来调整您的 python 版本，而无需在您的环境中指定 python_abi 。

传递依赖冲突

类似地，包冲突可能由传递性依赖引起。由于传递性依赖的性质，仅请求少量包就可能在环境求解操作中引入数百个约束。请考虑 statsmodels 包中：

statsmodels
├─ numpy
├─ scipy
├─ matplotlib
│  │  ├─ libpng
│  │  ├─ setuptools
│  │  ├─ cycler
│  │  ├─ dateutil
│  │  └─ kiwisolver

请求特定 statsmodels 版本会对允许的 setuptools 版本施加约束，因为该包依赖于 matplotlib。因此，如果环境请求了不兼容的 statsmodels 和 setuptools版本，就可能发生传递性依赖冲突，这是由于 statsmodels 本身对 setuptools.

施加了限制。例如，请看以下请求 huggingface-adapter 0.1.1* 和 transforms 1.645.0:

The following packages are incompatible
  ├─ huggingface-adapter 0.1.1** * is installable and it requires
  │  └─ palantir_models >=0.551.0 *, which requires
  │     └─ pyspark-src >=3.2.1,<3.3.0a0 *, which can be installed;
  └─ transforms 1.645.0 * is uninstallable because it requires
     └─ pyspark-src 3.2.1_palantir.36 *, which conflicts with any installable versions previously reported

的环境。乍一看可能不明显为什么这两个包不兼容。错误消息有助于识别问题来自 huggingface-adapter的传递性依赖与 transforms对 pyspark-src的直接依赖之间的冲突。可以通过放宽对 transforms or huggingface-adapter 任一者的约束来解决此环境问题，以便 Mamba 能够找到一组版本，使 pyspark-src 要求，将会出错。

解读新的错误消息

以下是新的 mamba 错误消息可能提供的所有措辞列表、如何解读它们，以及如何修复它们的一些指导：

  • The following packages are incompatible or The following package could not be installed：这两者通常是详细错误消息的第一句话。这表明整体问题是包 冲突 （由不兼容的版本引起），还是必要包安装本身的问题。
    • 如何修复：直接阅读该语句下方的必要信息。
  • can be installed：这句话通常出现在依赖树的顶部，表示该包本身可以在没有额外约束的情况下安装。然而，假设安装了这个特定版本，由于其他包依赖与该已安装版本冲突，可能会出现一系列冲突。例如， python 3.7** is requested and can be installed 表示可以在环境中安装 Python 3.7。直接列在此语句下方的所有其他冲突都假设环境中已安装 Python 3.7。
  • no viable options：没有任何可安装的版本能够满足所请求环境中其他规范施加的约束。例如，消息 python 3.7** is uninstallable because there are no viable options 表明，如果不是另一个包或约束明确请求不同的 Python 版本， python 3.7.* 的版本本可以被安装。
    • 如何修复：放宽导致允许版本范围超出该包可行选项的包的约束。
  • does not exist, perhaps a (typo or a) missing channel：未找到要安装的包。这很可能意味着包的指定有误，或者所有配置的通道（Settings > Libraries 在 Code Repositories 中，或 环境配置 在 Code Workbook 中）都不包含该包。例如，请求一个包含 python 3.423.* （一个不存在的版本）和 pthon 3.8.* （一个明显的拼写错误）的环境将导致以下错误消息：
 Could not solve for environment specs
  The following packages are incompatible
  ├─ pthon 3.8**  does not exist (perhaps a typo or a missing channel);
  └─ python 3.423** does not exist (perhaps a typo or a missing channel).

  • 如何修复：确保包名不包含任何拼写错误，或确保所有请求的包都可供环境使用。请参阅 发现 Python 库 ，了解如何在 Foundry 中搜索包是否存在的相关建议。

  • is installable and it requires：该包及其指定版本可以安装在环境中，但这会给环境引入一组额外的约束。

  • is uninstallable because it requires：该包及其指定版本无法安装，因为其某些依赖项在环境中产生了冲突。

    • 如何修复：检查消息下方列出的依赖项的问题需求，并放宽它们的约束或该特定包的约束。

  • is installable with the potential options：该软件包有一系列可安装且不冲突的版本。选择其中一个版本可能会导致进一步的约束。

  • conflicts with any installable versions previously reported：通常与上文提到的版本形成对比，这表示某个已被假定的版本 can be installed 已在别处确定，因此该版本将无法满足。

    • 如何修复：确保同一环境不会直接或间接地请求同一软件包的两个不同版本。

  • is missing on the system：这特指缺失的 虚拟软件包 ↗。某些软件包只能在特定的操作系统环境中运行。例如， cudatoolkit ↗ 软件包需要特定版本的 __cuda（一种系统级功能）作为虚拟软件包存在于环境中，以确保该软件包能在现有架构上运行。

  • which cannot be installed (as previously explained)：无法安装该软件包，原因要么是前文已描述的冲突，要么是另一个软件包包含前文已描述的完全相同的约束。

为什么取消版本固定仍无法解决解析失败问题？

即使完全放宽约束，所需软件包或软件包版本仍可能出现以下情况：

  • 不可用。您可以使用以下方式检查可用的软件包和版本： 软件包标签页。如有必要，您可以联系您的 Palantir 代表，请求添加这些软件包。
  • 不兼容。这些软件包定义可能永远无法兼容，即使我们能够访问所有已发布的版本。例如，您依赖的某个 Conda 软件包可能已升级（参见升级 PR）到损坏的新版本。
  • 与您以下环境中的 Python 版本不兼容 meta.yml.

要检查这种情况，您可以比较 Conda 锁定文件 ，将成功检查的锁定文件与失败检查的锁定文件进行对比。要访问 Conda 锁定文件，请选择以下选项： Show hidden files and folders 在设置齿轮中，并导航至 transforms-python/conda-versions.run.linux-64.lock。将在成功和失败运行之间发生变化的库版本固定为 meta.yaml 文件。

请求的包未发生更改却出现失败

出现这种情况的主要原因有两个：

  1. 由于您的转换可能依赖外部软件包（参见 公开管理的 Conda 渠道），遗憾的是，如果上游出现问题，它可能会失败。
  2. 合并升级 PR 后，在运行检查时会触发环境的重新解析，在极少数情况下可能导致软件包解析失败，尤其是在您的环境过度约束的情况下。这是因为升级 PR 可能引入新的依赖项，导致环境需要重新计算。您可以通过测试在应用升级 PR 的提交被还原后检查是否通过，来确认升级 PR 是否是原因所在。然后您可以按照 上文中的章节 重新应用升级 PR。

在您的环境未发生更改时调试运行缓慢问题 meta.yml

In 代码仓库:

  1. 升级您的分支（参见手动分支升级 了解更多信息）。
  2. 如果您仍然遇到速度缓慢的问题，并且您所做的代码更改位于 @transform_df 标签之外，那么这段代码可能减慢了检查速度。请评估这段代码的性能（如适用）。

在您的环境发生更改时作业超时 meta.yml

如果您在长时间运行的作业中遇到内存不足（OOM）错误，这可能是由于软件包版本不兼容导致环境无法求解。要解决此问题，请先升级您的分支，然后执行 上文列出的调试步骤.

避免依赖冲突的最佳实践

在上述错误中，最常见的原因是依赖冲突。为了减少依赖冲突，请遵循以下最佳实践。

避免依赖冲突的最佳实践：Python

为 Python 采用 major.minor 版本控制。

  • In 代码仓库，Python 3.9.*, 3.10.*日 3.11.* 可用。建议您不固定 Python 版本，只需指定包名称 python。但是，如果您的代码需要在特定版本的 Python 上运行，则应在构建和运行部分都固定所选版本。Python 3.8.* 现已弃用；它仍然可以使用，但在 2025 年 1 月之后将不再受支持。Python 3.6.* and 3.7.* 不再受支持。

请确保构建和运行部分中的 Python 依赖项完全相同。Python 依赖项之间的不匹配可能导致不良结果和失败。

诸如 python >=3.9 or python >3.9,<=3.10.11 之类的范围不受 Python 版本支持。如果使用了不受支持的 Python 版本，我们将默认使用 Python 3.6.*，该版本已弃用，因此请确保您在 meta.yaml 中为受支持的 Python 版本指定了有效的固定版本。

  • In 代码仓库（Code Repositories），您可以通过更改 automatic 来切换到您所需的版本控制方式。

Python 版本支持

从 Python 3.9 开始，Foundry 将遵循 Python End Of Life ↗所定义的时间线，这意味着如果某个 Python 版本被宣布为生命周期结束，则平台将不再支持该版本。请查看 Python 版本 页面以了解更多详情。

避免依赖冲突的最佳实践：Python 以外的包

避免显式固定版本，因为这可能导致依赖冲突。即使是 major.minor 版本也可能导致冲突。

在 Code Workbook 中，您可以为 pandas, matplotlib日 numpy 添加最低版本控制，因为 Code Workbook 将默认为 pandas=0, matplotlib=2日 numpy<1.20 在自动设置下。
