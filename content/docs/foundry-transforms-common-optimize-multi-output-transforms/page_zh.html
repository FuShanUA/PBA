优化多输出转换

有两种方法可以通过转换从一组输入数据集派生出一组输出数据集：

  • 创建多个具有相同输入和不同输出的转换。
  • 定义一个接受多个输入并产生多个输出的多输出转换。

也可以采用混合方法，即使用多个多输出转换，每个转换具有相同的输入和不同的输出集。这些选项将在以下部分中进行探讨。

多个单输出转换

单个输出转换具有 X1, X2, ..., Xn 个输入并产生一个输出 Y。要获取多个输出 Y1, Y2, ..., Yn，请编写多个转换，接收这些 X 输入，每个转换写入不同的输出。每个输出都有其自己的转换。

多个单输出转换的优势

以下列表描述了使用多个单输出转换的优势。

  • 每个输出的逻辑包含在不同的转换中，使其更易于维护。
  • 如果每个输出具有不同的输入，我们可以为每个转换分配所需的最小输入集。这可以加快构建速度，并允许您在必要时使用标记分隔输入以限制传播。
  • 您可以独立构建每个输出。
    • 您无需等待所有输出完成即可重新运行单个输出。如果您希望以不同的频率构建转换，这将非常有用。
    • 您可以仅构建单个输出，而无需构建所有输出，因为构建所有输出的成本可能很高。
  • 您可以为每个输出自定义 Spark 配置文件，这在各输出的计算成本不同时非常有用。
  • 您可以写入不同的项目。这是因为您可以将转换移动到不同的代码仓库中。请注意，通过添加一个将数据复制到其他位置的步骤，多输出转换也可以实现这一点。
  • 您可以为转换使用不同的库或框架。例如，某些输出可以使用 Pandas 中的轻量级转换，而其他输出则可以使用 PySpark。
  • 故障仅局限于单个转换，无论其源于数据、代码还是平台。
  • 并行化可在转换之间以及转换内部执行。

多个单输出转换的局限性

相反，采用单输出转换也可能带来以下缺点。

  • 可能存在重复逻辑。
    • 这意味着可维护性可能会更差；您可能需要将重复逻辑提取到共享库中。
    • 这可能意味着每个输出都要执行冗余的 PySpark 操作。根据具体情况，您可能需要保存一个中间数据集，以避免冗余的 Spark 操作。
    • 如果输出数据集彼此依赖性过高，重复逻辑可能需要许多中间数据集。这实际上等同于一个多输出转换。
  • 每个转换都将拥有自己的 Spark 环境，包括驱动程序，并且很可能还包括执行器。
    • 这些计算量会累积，如果所有输出同时运行，可能会出现排队现象。
    • 运行转换的开销成本会应用于所有转换。这包括 Spark 初始化以及运行驱动程序的成本。
    • 尽管可以针对每个转换自定义 Spark 配置文件，但在实践中，逐个微调会带来管理成本，并不总是切实可行。如果不自定义配置文件，那么规模较大的离群数据集可使用的执行器将比多输出转换中的更少，从而导致构建时间延长，并可能出现超时。

总体而言，此选项具有最大的灵活性，但不太适合重复操作，且计算成本可能更高。

多输出转换

多输出转换具有 X1, X2, ... Xn 个输入并生成 Y1, Y2, ... Yn 个输出。 我们对所有输出使用单个转换。

多输出转换的优势

请考虑以下使用多输出转换的优势：

  • 没有重复的转换开销成本。
    • 单一驱动程序和作业。
    • 在大规模场景下，这可能会变得非常显著。
  • 所有输出的逻辑都集中在一个位置。
    • 不再需要中间数据集，将在内存中进行计算。
    • 冗余逻辑不会产生重复成本。

多输出转换的局限性

请考虑以下使用多输出转换的缺点：

  • 如果各个输出的逻辑差异过大，代码可能会变得杂乱无章，更难维护。
  • 每个输出无法独立构建。
    • 您需要等待上一次构建完成所有输出后，才能触发新的构建。您无法在转换中自定义输出的频率。
  • 该转换会被分配一组 Spark 配置文件。需要注意的是，由于单个驱动程序（driver）将处理所有操作并将任务分配给执行器（executor），因此存在一些需要考虑的因素。
    • 这可以通过动态分配（dynamic allocation）配置文件来缓解，但这些配置文件会很快填满资源队列。
    • 不可并行化的任务会给驱动程序带来开销。这包括但不限于：将数据收集到驱动程序、运行用户自定义函数（UDF）以及运行 Python 代码（例如调用 API）。
    • 当数据规模相对于执行器数量较小时，网络输入和输出带来的开销可能会比执行器所执行的计算工作更为显著。
  • 构建失败会影响所有输出。
    • 如果某一个输出的操作耗时超过 24 小时，或包含错误，将会触发所有输出失败。
    • 这可能会使问题调试变得更加困难。
  • 成本使用量会在所有输出数据集之间平均分摊；如果有 10 个输出，则每个数据集会与构建成本的十分之一相关联。这意味着很难确定每个输出的成本关联。
  • 如果输入数据的大小存在波动，构建时长的方差将是所有输入引入的方差之和。这对于增量转换而言可能会变得非常显著，此时使用动态分配配置文件会更为合适。

多输出转换的灵活性较低，但非常适合处理输出中重复的逻辑。

其他注意事项

使用多输出转换时需要考虑的事项：

  • 您可以在 Spark 详情中检查任务并行化是否与执行器数量相匹配。如果构建时间过长或 Spark 配置文件过大，请考虑拆分转换。
  • 每个转换使用的执行器越多，开销成本就越不显著。如果您要将小规模数据集转换为大量输出，那么对于多输出转换而言，网络输入/输出可能比执行器的工作量更为显著。这种情况下，您可以改用多个转换，或在本地并行化的轻量级转换。

使用哪种方法

单输出转换非常灵活，非常适合输出之间的逻辑各不相同的情况。多输出转换的灵活性较低，但在合适的条件下可能更具成本效益。通常，如果满足以下条件，请选择多输出转换：

  • 多输出转换的约束满足您的需求。请查阅 多输出转换的限制 以了解此选项是否适合您的用例。
  • 您对各个输出采用类似的逻辑。
  • 您的操作可以并行执行。

如果满足这些条件，您应选择多输出转换。否则，请根据具体情况逐一决定，同时记住多个单输出转换是备选方案。
