Slate 调试入门

在许多方面，Slate 是开发者可使用的最复杂的 Foundry 工具。Slate 将构建单页 Web 应用的工具整合到一个易于上手的包中，但几乎没有提供内置的约束，而是在实现不同模式方面给予了很大的自由度。这种灵活性是一项强大的功能，允许在 Slate 中构建各种各样的应用、仪表板和工作流工具，但这也意味着很容易实现反模式，从而导致性能低下或混乱、非确定性的应用行为。

要找到此类最复杂的实现问题的根本原因，需要在 Slate 开发最佳实践以及 Web 应用开发一般原则的背景下，对应用逻辑进行逆向工程。

我们将在下面对这些问题进行分解，指出我们发现反模式出现的地方，并建议改进的实践或指导解决方案。我们将从 Web 技术的相关问题开始：

1. 前端 Web 技术

  • Web 浏览器如何工作。
  • 浏览器如何发出网络请求，以及其他服务如何响应这些请求。
  • 浏览器资源如何分配给特定网站的渲染和 JavaScript 执行。
  • HTML 和 CSS 如何协同工作来定义网站的外观。
  • JavaScript 如何被编译和执行。

虽然这些知识并非 Slate 专属，但对这些基础知识的误解是许多关于 Slate 应用（实际上是定制构建的 Web 应用）的性能、布局和样式问题的根源。

W3Schools ↗ 以及许多其他资源都提供了这些主题的基础教程。

2. Postgres 和 SQL

熟悉 SQL 以及 Postgres 数据库如何构建和执行查询也很有帮助，因为大多数应用都是通过查询 Postgres 实例来检索数据的，而数据是从 Foundry 数据集同步到该实例以供应用访问的。

许多关于查询开发、错误和性能的问题并非 Slate 专属，可以通过常见的搜索查询来解答，通常采用以下形式： Postgres + [question].

然而，Slate 在解析和提供 Postgres 生成的错误消息方面并不特别友好，我们建议您查看下文中关于这些问题的常见原因和解决方法的部分，并参考 Postgres 性能与调优 指南以获取更详细的信息。

3. Slate 专属知识

在 Slate 中构建复杂的应用需要一些时间来适应，许多反模式可能源于将其他应用开发概念“强加”到 Slate 上，而不是在 Slate 提供的框架内工作。对于实现给定功能，通常存在隐式的“正确”模式，能够与这些 Slate 核心概念最佳契合。

这些复杂性大部分已在 理解依赖关系中涵盖，其中包括对 Slate 核心组件（依赖图、事件框架、小部件、查询、函数等）的讨论、常见模式（和常见反模式）以及设计和实现的最佳实践。

我们建议开发人员和支持工程师熟悉本文档，因为许多常见问题都可以通过文档中已深入讲解的内容得到解答。在许多情况下，回答问题的最佳方式不是尝试解决具体实例——例如，打开应用并试图逆向推断用户的开发决策——而是理解用户遇到的一般性故障类别，并引导他们参考以下任一内容中的相关讨论：

  • 理解依赖关系
  • 构建复杂布局
  • 启用用户交互
  • 与该问题相关的各种基于网络的资源

对于一些最常见的情况，此常见问题解答文档是获取简要说明和有用参考资料的捷径。

查询失败

与查询相关的问题有多种形式，找出根本原因可以指向多种解决策略。在某些情况下，问题会伴随明确的错误消息出现，但在其他情况下，可能没有错误消息，或者失败条件可能是非确定性的（即有时发生，有时不发生）。以下故障排除步骤介绍了一些常见的根本原因及相关的解决策略。

要进行故障排除，请执行以下步骤：

有时查询会违背同步网络请求的一般使用模式：

  • 试图向浏览器返回过多数据的查询。
    • 根据一般经验法则，查询返回的行数应少于 10,000 行。
      • 有时查询会明确返回“行数过多”的错误，但通常查询会成功，而应用程序的其余部分会非常缓慢。在这些情况下，请查找返回大量行的查询，并尝试减少返回的数据量。
    • 如果您尝试显示包含大量行的表格，或需要以其他方式向用户呈现原始行，请使用 LIMIT and OFFSET 语句来实现分页工作流，可以使用 Table 部件的内置属性，也可以使用自定义工作流。
  • 查询过大以至于仅发出请求就需要很长时间。
    • 查询的往返时间应小于 5 秒。
    • 如果您的查询包含大量数据，请考虑将查询中嵌入的更多逻辑推送到生成数据集的转换层中。

对于这一类一般性问题，请参阅 优化索引和 schema 设计 文档，并考虑应用程序应合理构建结构，使返回到浏览器的数据已是最终形式，而无需在 JavaScript 函数中进行大量处理。

有时问题反而与 Postgres 如何解释和响应请求有关：

  • 由于结构不够优化而运行缓慢的查询。
  • 由于数据集未建立索引或索引不正确而运行缓慢的查询。
  • 语法不正确的查询。

这类问题通常可以通过搜索 Postgres + [error message] or Postgres + [desired query]来解答。对于所有与故障排除或查询性能调查相关的问题，请参阅 Postgres 查询性能与调优 指南。

有时问题反而出在 Slate 如何以及何时根据开发人员的配置执行查询：

  • 查询在页面加载时非确定性地失败。
    • 请参阅 管理查询执行 最佳实践指南中的部分。
  • 查询在 20 秒（Slate 超时期限）时返回无用的错误
    • 通过 Slate 查询发出的请求会超时 在 Slate 端 为 20 秒，无论请求的服务器端发生了什么。要确切诊断这种故障模式，请在查看应用程序时使用 要在标记和发布函数的过程中查看进度，请选择 模式，并在刷新页面时打开 Google Chrome 网络检查器。这将显示每个查询请求的持续时间，如果你看到某个查询在 20s时变红，则可以确定故障原因是 Slate 已将该查询超时。
    • 可以通过提升查询性能来解决此问题： Postgres 查询性能与调优 and 控制查询执行.
    • 有关超时的更多内容，请查看下一节关于 Postgres 查询超时.
  • 在某些情况下失败的查询（因为 Handlebars 渲染未得到充分保护）。
    • 如果你的查询中包含 Handlebars 语句，请确保它们受到 {{#if}} 语句的保护，或通过函数中的逻辑来防范 null 值或其他边缘情况。
  • 在错误的时间执行或未能执行的查询。
    • 请确保你 理解 Slate 中事件发生的原因 ，并且你正在适当地 控制查询执行。对于复杂的应用程序或过度依赖事件的应用程序，关于 Event Madness 的说明很有参考价值。

Postgres 查询超时

当查询超时时，主要有两个影响因素：

  • 数据规模——Postgres 表中有多少行，以及你从查询中返回多少行。
  • 查询优化——查询的"开销"有多大。

作为应用程序开发者，有必要理解这些因素及其对查询的影响。这两者都不是 Slate 或 Foundry 特有的，因此你可以通过搜索 Postgres SQL query performance 来取得进展，并在 Postgres 查询性能与调优 指南。

要进行故障排除，请执行以下步骤：

以下是一些可能有帮助的提示，基于应用程序开发者常见的问题：

  • 数据规模：限制同步到 Postgres 的数据集规模。例如，如果你只需要一年的数据，就不要同步 所有时间 的数据集，然后在查询中进行过滤。

  • 数据规模：减少表中的列数。例如，如果查询中只选择少数几列，请在同步表之前通过转换将其删除，以避免额外开销。

  • 数据规模：尽可能少地返回行。如果你要显示原始行，请使用 OFFSET 和 PAGING 来检索更多行，而不是在任何查询的响应中返回超过几百行。

  • 查询优化：尽可能避免开销高的 SQL 命令。常见的"罪魁祸首"包括 COALESCE、DISTINCT，以及对"不完整"列（例如某些值为 null）的任何 JOIN，或包含前导通配符（%）的 WHERE 子句过滤条件，或复杂的匹配表达式。

  • 查询优化：将工作前移。这包括数据清理（移除空值、格式化日期、映射显示值）和指标计算（月度总计、跨分桶的平均值等），应尽可能推送到转换层。如果你需要允许用户通过过滤器自定义这些内容，你仍然可以跨少数几个维度"预聚合"指标，然后执行一个简单得多的查询，仅对满足这些条件的少数几行进行求和/求平均值等操作。

  • 查询优化：使用 EXPLAIN ANALYZE 来获取查询计划，并理解 Postgres 如何解释你的查询。这将有助于识别耗时所在的瓶颈，从而进一步针对性地进行优化。 这里 ↗ 是一篇关于阅读和理解这些结果的有用入门资料。

  • 查询优化：查看 在 Postgres 中优化查询.

无法在我的 Postgres 查询中引用列

在 Postgres 中，列名被假定为小写。由于 Foundry 允许列名使用灵活的大小写和空格，当表被索引到 Postgres 时，该表会被包装在 " （双引号）字符中，以保留原始大小写。

这意味着如果列名包含大写字符，您在 SQL 查询中引用该列时也需要用双引号将其括起来。

您可以在以下链接了解更多关于此行为的信息： StackOverflow ↗.

Phonograph 查询在提交时截断文本

在一种边缘情况配置中，您可能会观察到引用一个或多个 Text Area widget 的写回查询发送的 Phonograph 请求仅包含部分文本。例如，如果用户输入了长文本，如 This is a test message for writeback 并快速按下 Submit 按钮以触发写回查询，则只有 This is a te 可能被包含在内。

根本原因是 Text Area widget 使用的 0.5 秒防抖延迟，用于防止 Dependency Graph 在每次按键时都重新求值。此延迟意味着，当且仅当以下情况时，查询将在未包含完整文本的情况下提交：

  • 文本区域 widget 是用户最后填写的输入项，并且
  • 在最后一个字符输入到文本区域后不到 0.5 秒内按下了提交按钮。

要进行故障排除，请执行以下步骤：

最简单的解决方案是调整用户体验，使用户无法在输入长文本后 0.5 秒内使用提交选项。例如，在提交查询之前添加确认对话框，或者简单地重新排列表单元素，使文本区域 widget 之后还有另一个需要填写的字段。

其他解决方案是将文本区域 widget 替换为 Text Input widget，后者不包含防抖延迟。也可以使用 Toast widget 作为提交按钮按下与查询执行之间的延迟缓冲，以确保有足够的时间让完整文本被包含在内。

我的函数没有在预期的时间运行

函数与 Events 框架的交互方式不太直观，因为在正常使用中，函数不会被调用，而是由依赖图（Dependency Graph）在其输入过期时执行，其输出会被渲染为 JSON，供下游依赖项使用。

要进行故障排除，请执行以下步骤：

如果函数的行为不符合预期，请确认你了解函数在依赖图（Dependency Graph）和事件框架（Event Framework）中的运作方式，方法是 查看现有的最佳实践文档.

很少需要使用由事件调用 [f_myFunction].run 操作的模式。试图依赖此模式的应用应重构为使用依赖图的正常解析。不要直接触发函数，而是更新上游依赖项，例如通过触发查询或设置被引用变量的值。

没有输入的函数不会在 Recalculate 事件时再次运行。如果 Slate 已经缓存了某组参数的结果，它会直接返回该结果，而不是再次运行函数。要定期运行函数，请提供至少一个随每个间隔变化的输入，例如由定时器更新的变量或时间戳。

应用渲染问题

在某些配置中，如果你尝试将小部件配置为“动态”宽度和高度，你可能会发现页面加载时小部件被渲染在一个小框中。触发 [w_myWidget.resize] 操作会使小部件渲染为预期的大小。

此行为是由 CSS 将各种小部件元素的宽度和高度指定为百分比（通常为 100%）与一个或多个父容器的 Flex 属性之间的冲突引起的。发生这些冲突时，Slate 无法在渲染时确定包裹小部件的元素的正确尺寸，因此会将小部件渲染得过小。

要进行故障排除，请执行以下步骤：

实现响应式小部件尺寸的合适模式是仅使用 Flex 父容器和子小部件上的配置设置。不要通过 CSS 手动设置其他 width or height 属性。要解决此问题，请从根级子小部件开始，逐级向上遍历所有父级小部件，删除任何位置或尺寸相关的 CSS 规则。

您可以使用 margin 和 padding 属性来内嵌或以其他方式对齐子小部件。如果你熟悉 Flexbox CSS 规则，可以使用 Chrome 检查器识别要定位的元素和类，并提供覆盖或额外的 Flexbox 规则，以实现所需的精确行为。

性能

我的应用加载缓慢或在编辑模式下卡顿

与所有 Web 应用一样，Slate 使用最终用户计算机上的浏览器资源来执行 JavaScript 代码，并渲染 HTML 中定义的文档模型 (DOM) 以及 CSS 中指定的样式。其中一部分资源是固定的，这是在 Slate 框架内工作的开销。但是，在性能不佳的情况下，根本原因通常是某种形式的应用过载，即在开发应用过程中定义的配置需要浏览器提供过多的资源来渲染应用、执行 JavaScript，或者仅仅是在内存中存储许多大型查询的结果。

在某些情况下，单个函数或查询可能是原因所在。在这种情况下，您可以使用应用中 依赖项 选项卡中的性能指标来查看各种查询和函数的 Time in Node 。该指标表示在页面加载时解析该特定节点所花费的时间，可以帮助识别可能导致应用瓶颈的候选项。

一般来说，最佳实践是倾向于轻量级、边界清晰、单一用途的应用，并通过“集群”方式将小型应用组合成大型工作流或应用，并在它们之间建立深度链接。

Slate 将应用配置保存为 JSON 文档，其大小限制通常为 2,000,000 字节的 UTF-8 编码字符。尝试保存配置超过大小限制的 Slate 应用将会失败，需要对应用配置进行更改以减小其大小。已打开的 Slate 应用的 JSON 文档可以 通过导出检索.
