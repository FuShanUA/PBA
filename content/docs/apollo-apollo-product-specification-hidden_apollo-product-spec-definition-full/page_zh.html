Apollo 产品完整规范与定义 [Beta]

该 Apollo 产品规范 定义了一种描述 Apollo 产品的属性、需求和期望的方式。 该规范提供了一种简单、简洁的方式来配置产品,从而将通用的应用程序需求从底层基础设施平台(如 Kubernetes)中抽象出来。

该规范包含一组用于定义应用程序固有属性的必需组件，以及一组可启用 Spoke Control Plane 更多功能的可选（选择性加入）扩展。

一个 Apollo 产品定义 是指符合 Apollo 产品规范的服务或应用程序的定义。 Apollo 产品定义旨在与 Apollo 产品的发布版本一同进行版本管理，并且在该 Apollo 产品发布版本中应保持不可变。

Apollo 产品定义被组织到不同的文件中，每个文件都有特定的用途和枚举的规范 特性：

  • [必需] manifest.yml: 声明 Apollo 产品发布版本的固有属性。规范属性的值是不可变的，日后无法更改。每个 Apollo 产品定义都需要此文件。
  • [可选] configuration.yml: 声明规范的运行时组件和能力的默认值与行为。这些值可以在 Apollo 中按安装实例进行覆盖，而 Apollo Hub 负责安全地编排这些变更。此文件中的所有内容以及该文件本身均为可选。

Apollo 产品定义的各个组件会被打包成一个压缩的 tarball，并作为 Apollo 产品发布注册流程的一部分发送给 Apollo。 发布后，Apollo 产品定义将在 Apollo Hub 中表示为一个 Apollo 产品发布。

可以在下方找到 Apollo 产品定义的一个可运行示例。

声明产品特征

根据其预期功能，服务具有不同的 特征 ，这些特征描述了服务的行为或要求。特征表示必需的产品属性（例如所需的内存分配、服务端口、用于基于 TLS 通信的证书），而这些特征的实现则交由 Spoke Control Plane 完成。

Apollo 产品规范定义了少量必需属性，所有 Apollo 产品定义都需要在产品的 manifest.yml中定义这些属性，无论产品类型如何。这些属性使 Apollo 能够了解如何对产品发布进行建模。请参阅 清单规范文档 以了解更多详情。

下面，我们将通过示例介绍如何使用 traits 来满足服务的常见需求，以及开发者如何在 Apollo 产品定义中声明这些内容。

确定服务规模

服务需要计算资源才能运行，因此 Spoke 控制平面会接受 Apollo 产品定义中的多种不同计算维度，其中包括 CPU、内存和节点副本数。

服务通常需要处理来自集群外部的流量（例如，为来自 Web 浏览器的请求提供服务）。 在服务的 configuration.yml中定义端点后，开发人员可以声明这些端点中的哪些应暴露给外部流量。 要使端点能够从外部访问，需要在 Apollo 产品定义 manifest 的 public-proxy-endpoints 和 public-tcp-endpoints 扩展下引用这些端点：

配置管理

Apollo 产品规范旨在让开发者轻松构建可移植的软件，实现无需手动配置步骤的部署以及安全、自主的升级。为此，Apollo 的配置管理侧重于以下几个部分：

  1. 默认配置，定义为 Apollo 产品定义的一部分，旨在声明服务无需手动配置即可正确启动和运行所需的配置。
  2. 如何覆盖和合并特定配置属性，以便在必要时更改默认行为。
  3. 如何将配置映射到服务期望从中读取配置的磁盘文件。
  4. 如何为您的服务自动生成和手动指定 secrets/IAM 凭据。
  5. 如何让您的服务可被其他服务发现，反之亦然。
  6. 一种替换与模板引擎，使开发者能够最大限度地减少重复引用，并在运行时利用服务管理信息。

默认配置

Apollo 产品定义应包含产品的默认配置，使服务无需任何额外的手动配置即可正确部署并启动。默认配置声明在 Apollo Production Configuration 的 configuration.yml 文件中，位于 conf header:

配置覆盖

有时，服务可能需要配置覆盖，以便与默认配置中无法预测的设置配合使用。这些情况可能包括：与外部身份验证提供程序集成、更改垃圾回收间隔以匹配非典型的使用模式，或在负载较重的环境中增加副本数量。Spoke Control Plane 支持定义配置覆盖，以将其合并到 Apollo 产品定义的原始 configuration.yml contents:

  new-field: now-present

Map 合并以递归方式执行，这意味着合并数组字段或类型不同的字段时，将使用覆盖值替换原始值。用于 定义生成的机密 的顶层块不可 被覆盖；这是为了防止因无意间覆盖生成的机密值而导致服务中断或数据丢失。

配置覆盖应当是例外而非常规做法。请参阅 配置替换 以了解 Spoke 控制平面如何最大限度地减少配置覆盖需求。

配置替换

管理配置文件

应用程序和服务从磁盘读取配置时，会使用多种不同的文件格式和应用程序特定的文件名。Product Spec 提供了相应的声明手段，用于指定作为 Apollo 产品定义一部分而声明的配置应如何映射并渲染为不同文件格式的文件。这是在 Apollo 产品定义的 configuration.yml 文件中定义的，位于 managed_files 标题下：

  some-config:
    a: b

    b: c

managed_files:
  some-conf.yml: some-config
  some-other-conf.json:
    type: json
    content: some-other-config

开发人员定义文件名以及应渲染到该文件中的配置子集。默认情况下,所有配置文件都将挂载到主容器的 /opt/palantir/services/<product-name>/var/conf 目录中。

托管文件声明包含以下字段:

  • type [必填]:指示文件所需的格式。支持的值有:
    • json - 内容将被渲染为 JSON ↗
    • yaml, yml - 内容将被渲染为 YAML ↗
  • content [必填]:指示应将 conf 块的哪一部分包含在托管文件中
  • reload-type [可选]:指示服务能否在不重启的情况下重新加载配置文件。可接受的值有:
    • install [默认]:需要重启才能重新加载该文件
    • runtime:无需重启即可重新加载该文件

Control 支持简写形式的托管文件条目,如上例中的 some-conf.yml 所示,其中条目键的文件扩展名(.yml)被用作托管文件的 type,而条目的值被用作托管文件的 content。对于使用此简写形式的条目,重载类型默认为 install。在上例中,以下配置文件将被渲染到主服务容器中:

# some-other-conf.json

管理凭据与机密材料

某些服务依赖凭据或其他机密材料来与其他服务进行身份验证和授权。在某些情况下，这类机密材料可以随机生成。为了减轻这些用例的手动配置负担，Apollo 支持通过以下多种方式自动生成所需的机密材料：

  • 在产品的 configuration.yml中指定要生成的机密信息。这在服务只需要 某种 机密值，用于与集群内的另一个服务建立信任。
  • 公开端点，供管理员为服务手动定义机密值。当某个服务需要使用预先存在的凭据向集群外的服务进行身份验证时，这非常有用。

在运行时生成机密

要指定希望 Spoke Control Plane 代表您的服务生成的机密，可以使用顶层 generated_secrets 字段，该字段位于您产品的 configuration.yml 文件中：

    secret-type: random_string

  myAppRandomByteSecret:

    length: 16
  myAppCustomCharsetSecret:

  myAppRsaKeyPair:

  myAppStigPassword:

  ec_pkcs8:

Spoke Control Plane 会根据所请求的 secret-type 和 length 字段生成机密值，并将生成的值存储在 Kubernetes Secret 对象 ↗中。支持以下机密类型：

  • random_string：将生成指定长度（或默认长度 16）的随机字符串。如果 allow-chars 字段存在，则生成的机密值将仅包含 allow-chars 集合与 base64 ↗ 字符集的交集中出现的字符。同样，如果 disallow-chars 字段存在，则生成的机密值将仅包含所提供的 disallow-chars 集合与 base64 字符集的差集中出现的字符。
  • rsa_pkcs8：将生成指定长度的 RSA PKCS8 密钥对 ↗ 。
  • random_bytes：将生成一个密码学安全的随机二进制值。结果值将以 base-64 编码的形式返回。
  • ec_pkcs8：将生成一个椭圆曲线公钥/私钥对。可接受的长度值为 224、256、384 和 521（这些标准曲线定义于 FIPS 186-3 ↗）。

强烈建议将运行 Spoke Control Plane 的 Kubernetes 集群配置为启用 机密静态加密 ↗。

证书与 CA

Spoke Control Plane 通过主服务容器中的卷挂载，向受管服务提供证书和证书颁发机构（CA）证书。该挂载包含以下文件：

  • ca.cer：所有 PEM 编码证书的串联，这些证书由 Deployment Platform 配置，作为应用程序的 CA 提供。
  • key.pem：PEM 格式的 RSA 私钥。
  • cert.cer：与上述私钥对应的 RSA 公钥 key.pem。
  • truststore.jks：一个 Java 信任库，包含与以下文件中相同的一组 CA ca.cer。此文件是为了方便 Java 应用程序而提供的。
  • keystore.jks：一个 Java 密钥库，其中包含与出现在 key.pem。此文件是为了方便 Java 应用程序而提供的。

参见 引用证书材料 ，了解如何在配置中引用这些证书文件。

      port: 8443
      path: /my-api
      scheme: https
    my-oauth-client:
      role: oauth-client
      client:
        client-id:
        bcryptedOAuthSecret: '{{secret("my-oauth-secret", part: bcrypt_hash)}}'
  consumes:
    neighboring-api:
      role: neighboring-api
      select: uris
      stack: production
      tags: [bar]

Spoke Control Plane 支持通过以下筛选方式来使用由其他服务生成的发现条目：

  • role：如果发现条目的角色与 role 所评估的 consumes 条目中的字段。
  • stack：生成该 discovery 条目的堆栈。默认情况下，discovery 条目仅在服务所在的堆栈中生成。可以将 Discovery 生成到其他堆栈，方法是包含一个 produce-to-additional-stacks 字段，该字段位于顶层 discovery 块下，在这种情况下，它将应用于服务生成的 discovery 中的所有条目。请注意， produce-to-additional-stacks 在单个 discovery 条目中不起作用。
  • tags：服务可以让 discovery 标签显示在其生成的 discovery 条目上，方法是在 conf.tags 键下定义一个字符串列表（例如，上述配置中包含了 foo 标签）。默认情况下，对所消费的 discovery 进行筛选时会接受任何及所有标签；如果在 consumes 条目中包含了标签（如上述 neighboring-api 条目的情况），则只有包含所有指定标签的 discovery 条目才会通过此筛选。

便捷方法：URI 增强

discovery 最常见的用例之一是提供 URI 信息，以支持从一个服务向另一个服务发起网络请求。Spoke Control Plane 通过检测某些需要用 URI 信息"增强"的 discovery 条目，简化了这一用例。任何带有 port 字段若是有效的端口号，便会以这种方式进行增强。此增强的可选输入包括：

  • scheme：URI 的方案；默认为 https
  • path：URI 的路径；默认为 /

Spoke Control Plane 会确保其发现增强与其代表该服务创建的 Kubernetes 服务所确定的 URI 保持一致。例如，如果某个具有上述发现配置块的服务拥有一个 Kubernetes 服务，其名称为 foo 且命名空间为 application-namespace，那么该服务生成的 my-api 发现条目的载荷将被增强，以包含 uri 和 uris 字段：

使用已消费的发现

发现服务与配置 介绍了如何消费其他服务生成的发现，但服务仍需将发现的值注入到其配置中的正确部分。为此，替换语言提供了一个 discovered 方法，用于引用已消费的发现：

  • 在端口 8080 上接受请求，基路径为 /foo。
  • 接受外部流量。
  • 运行 3 个副本。
