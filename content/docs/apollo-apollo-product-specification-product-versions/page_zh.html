产品版本规范

本规范描述了可排序和不可排序的产品版本字符串。只有可排序的版本才能用于 Apollo Product Spec 清单中。

可排序版本字符串

可排序版本字符串属于四种版本类型之一，这些类型由类别（release 或 release candidate）以及是否为快照版本（快照版本末尾包含一个提交哈希）来定义，两者的交叉组合产生以下结果：

Release candidate (rc) snapshot     1.0.0-rc1-1-gaaaaaaa    ^[0-9]+\.[0-9]+\.[0-9]+-rc[0-9]+-[0-9]+-g[a-f0-9]+$

在上面的每个示例中，我们将“基础”版本定义为主版本/次版本/补丁版本组件。在本例中，它们都是相同的，即 1.0.0。版本字符串中的每个数字不得超过 32 位整数的最大值（2,147,483,647）。

排序

对于任意一对可排序的 Product 版本字符串，都可以直接定义一个顺序，用于规定哪个产品版本较新、哪个较旧。该顺序提供的保证使 Apollo 能够：

  • 就产品是向前迁移还是向后迁移做出明智的决策。
  • 通过版本范围来推理产品兼容性；例如，一个产品可以声明它与版本处于 [1.2.3, 2.0.0) 范围内的另一个产品兼容。
  • 对于任意两个可排序的版本 v1 和 v2，定义 v1 是否比 v2 更大（等价于更晚或更新）。

对于这四种变体，以下数值组件用于标识一个版本。从左到右，这些组件依次为：

  • 基础版本的常规表示法（例如，对于 1.2.3，1=主版本，2=次版本，3=补丁版本）
  • 可选的第二个数值组件，用于标识候选发布版本（例如 -rc3）或快照版本（例如 -5-gnm4s9ba）
  • 可选的第三个数值组件，用于标识候选发布快照版本（例如 -rc3-5-gnm4s9ba）。

直观地说，在相同的基础版本下，快照版本大于非快照版本，正常发布版本大于候选发布版本，而正常发布快照版本大于任何类型的候选发布版本。

以下自上而下的流程用于判断 v1 是否大于 v2，写作 v1 > v2；诸如 major(v1) > major(v2) 之类的比较采用整数排序（而非字典序排序）：

  • 如果 major(v1) > major(v2)，则 v1 > v2。
  • 如果 minor(v1) > minor(v2)，则 v1 > v2。
  • 如果 patch(v1) > patch(v2)，则 v1 > v2。
  • 从这里开始，我们假设 v1 和 v2 的基础版本（major/minor/patch）相同。
  • 如果 v1 是普通快照版本而 v2 是普通发布版本，则 v1 > v2。
  • 如果 v1 是普通发布版本而 v2 是 rc 版本，则 v1 > v2。
  • 如果 v1 和 v2 都是普通快照版本且 snapshot(v1) > snapshot(v2)，则 v1 > v2。
  • 如果 v1 和 v2 都是 rc 版本且 rc(v1) > rc(v2)，则 v1 > v2。
  • 从这里开始，我们假设 v1 和 v2 是具有相同 rc() 编号的 rc 版本。
  • 如果 v1 是快照 rc 版本而 v2 是普通 rc 版本，则 v1 > v2。
  • 如果 v1 和 v2 都是快照 rc 版本且 rcSnapshot(v1) > rcSnapshot(v2)，则 v1 > v2。

此外，当且仅当既非 v1 > v2 也非 v2 > v1 时，v1 与 v2 一样大，写作 v1 == v2。如果 v1 > v2 或 v1 == v2，我们写作 v1 >= v2。

示例，每个都大于之前的所有版本：

  • RC：1.0.0-rc1
  • 更大的 RC：1.0.0-rc2
  • RC 快照优先于 RC：1.0.0-rc2-4-gaaaaaaa
  • 更大的 RC 快照：1.0.0-rc2-5-gccccccc
  • 基础版本优先于 RC：2.0.0
  • 快照优先于所有版本：2.0.0-3-gaaaaaaa
  • 更大的快照：2.0.0-4-gbbbbbbb
  • 更大的基础版本：2.1.0-rc1
  • 发布版本优先于 RC：2.1.0

相等性的示例：

  • 1.2.0 == 1.2.0
  • 2.0.0-rc1 == 2.0.0-rc1
  • 2.0.0-rc1-3-gaaaaaaa == 2.0.0-rc1-3-gbbbbbbb
  • 2.0.0-5-gbbbbbbb == 2.0.0-5-gaaaaaaa1

请注意，任何两个 release 和 rc 版本只要在语法上相等，其大小就相同。如第二个示例所示，这一点并不适用于快照版本。

版本匹配器

版本匹配器是对一组发布版本的规范，由以下正则表达式定义：

Copied!
1
`^((x\.x\.x)|([0-9]+\.x\.x)|([0-9]+\.[0-9]+\.x)|([0-9]+\.[0-9]+\.[0-9]+))$`

版本匹配器的序列化形式是与该正则表达式匹配的字符串。例如，1.x.x、2.0.x、x.x.x 和 1.2.3 是有效的版本匹配器，而 x.y.z、x.0.0、0.x.3、x.x.2、1.x 和 ^x\.[0-9]+\.[0-9]+$ 则不是。如果存在（独立的）针对 x 的替换，能够将匹配器转换为该版本，则称该匹配器匹配一个发布版本。例如，1.x.x 匹配 1.0.0 和 1.2.3，但不匹配 2.0.0 或 0.1.1。

不可排序的版本字符串

版本字符串如果匹配以下正则表达式，则遵循不可排序格式：

Copied!
1
^[0-9]+\.[0-9]+\.[0-9]+(-[a-z0-9-]+)?(\.dirty)?$

例如，1.0.0.dirty、0.0.1-custom-description-42 和 2.0.0-1-gaaaaaa.dirty 是有效但不可排序的版本字符串，而 5.0、1.1.2.3-foo、1.1.2.3 和 1.0.0-FOO 在此规范下不是有效的版本字符串，且不受 Apollo 支持。

两个不可排序的版本之间，或可排序版本字符串与不可排序版本字符串之间，均不提供任何排序保证。
