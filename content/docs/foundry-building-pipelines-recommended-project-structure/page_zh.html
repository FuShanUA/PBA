推荐的项目和团队结构

本页面概述了在 Foundry 中构建 数据管道 的推荐方式，即使用 项目 来实现：

  • 整个管道中结构清晰的权限
  • 跨角色的高效协作
  • 清晰且易于维护的管道结构

此外，我们还介绍了 角色和职责 的范围，这些角色和职责需要在生产环境中成功管理管道时得到履行。

本文提供了各个管道阶段的概念性概述及其用途。如需在 Foundry 中设置此结构的分步指南，请参阅 保障数据基础安全 （位于平台安全文档中）。

项目边界

项目 提供了一种在 Foundry 中组织数据和代码的方式。它们是管理围绕特定工作范围进行协作的个人和团队的访问权限的主要单元。此外，项目还提供了捕获和共享元数据的功能，例如项目活动的事件日志、项目文档空间，以及项目资源消耗和计算指标。

在思考什么是一个好项目时，可以类比什么是一个好的微服务：明确的目的、供下游依赖使用的清晰输出数据集/API、由一个足够小的团队拥有，以便他们能够有效协调并为项目管理设定自己的标准。

在决定是创建新项目还是在现有项目中构建时，请考虑：

  • 项目应与代码仓库保持 1:1 的关系。更大的范围可以支持更深入的协作，但也会带来更具挑战性的运维要求，以确保顺畅的版本控制。
  • 项目是您希望对所有相关资源施加文件结构和权限的层级。如果单个概念性“项目”包含需要单独权限的子组件，请考虑在 Foundry 中创建多个项目。

管道阶段

这些阶段定义了构成有序管道的项目的逻辑分离。下面将更详细地描述每个阶段。

  1. 数据连接：同步将来自源系统的原始数据落地到 Datasource project.
  2. 数据源项目: One Datasource project 每个逻辑数据源对应一个项目，定义每个原始数据集的基本清理步骤并应用一致的 schema。
  3. 转换项目：数据集从一个或多个 Datasource projects 中导入，并经过转换以生成规范的、可复用的数据集。
  4. 本体论项目：数据集从一个或多个 Transform projects 中导入，并经过转换以生成表示离散运营对象的规范表。单个本体论项目通常将给定运营领域中相关的对象集合分组在一起，以便于管理。
  5. 工作流项目：工作流项目从本体论项目导入数据以实现特定目标。这通常是运营工作流、数据科学研究、商业智能分析和报告，或应用开发项目。

每个管道阶段都是一个独立的单元，其输出是可供下游项目导入并用于其他用例、管道开发、分析等的数据集。在每个项目中，负责的团队除了实施转换步骤之外，还应 管理其输出的稳定性和完整性 。这包括管理构建计划、配置和监控数据健康检查，以及在相关情况下 编写单元测试 或额外的数据完整性测试。

以下各节将更详细地介绍每种下游项目类型，以跟随数据在管道中的流动。在设计管道的过程中，则应从本体论层反向推导，以确定需要连接的源系统和需要实施的管道转换。

1. 数据连接

在 Foundry 中流经管道的数据通常来自外部源系统。 数据连接 服务提供了一个管理界面，用于注册源系统。对于每个源系统，会配置一个或多个单独的同步，将数据落地到 raw 数据集，位于一个 数据源项目.

为了配置源系统或同步，首先需要由 Agent 管理员 通常需要配置一个数据连接 代理。每个代理应存储在一个仅供 Agent 管理员.

管理新数据源的新连接是一项需要多方协作的工作，需要 数据源所有者Workshop Agent 管理员，而 数据源开发者的协作，不过通常还需要 合规/法务人员 批准将数据从源系统迁移到新环境。

然而，一旦源系统配置完成，数据源开发者就可以独立配置各个同步。这大大减少了团队之间的来回沟通，并确保连接新系统是一项低成本的、一次性的工作。

每个连接的一个关键考虑因素是在 SNAPSHOT之间进行选择，前者会在每次同步时替换当前数据，而 APPEND则会在每次同步时向现有数据累积添加。要更全面地理解这些概念及其对创建高效、高性能管道的影响，请参阅 增量管道 区域的字段中添加命令。

2. 数据源项目

每个源系统都应将数据落地到平台内与之对应的项目中。通常的模式是将每个同步的数据以尽可能“原始”的格式落地。转换为“干净”数据集的转换步骤在该项目中定义 分支回退.

建立这种每个数据源一个项目的模式有许多便利的好处：

  • 鼓励在一致的位置探索新的数据源。
  • 提供一个统一的位置来指定对数据源的访问控制。
  • 最大限度地减少不同团队重复同步相同数据的工作。
  • 代码仓库规模小且专门构建，用于处理源系统数据的类型和格式。
  • 允许在管道层访问数据之前对数据进行匿名化、清理和标准化。

数据源项目目标

在每个数据源项目中，目标是为组织内各种各样的用户、用例和管道准备好可供使用的同步数据。

输出数据集及其 schema 应被视为一个 API——也就是说，目标是使它们在逻辑上组织有序并随时间保持稳定，因为数据源项目的输出数据集是所有下游工作的支柱。输出应与源表或源文件 1:1 对应；数据集中的每一行都应在源系统中有直接对应的行。

为此，原始 → 干净转换的一些典型目标包括：

  • 采用一致的列命名方案。
  • 确保为列应用适当的类型。
  • 处理缺失、格式错误或类型错误的值。
  • 建立主 运行状况检查.
  • 移除 PII（个人身份信息）或其他敏感数据 不适合一般使用的数据。

隐私最佳实践是在这个早期阶段识别敏感字段，因为防止不必要的数据进入共享输出比在使用范围扩大后再纠正访问权限更安全。 敏感数据扫描器 可以支持发现，而 实践中的隐私与公民自由 解释了最小化和混淆如何应用于管道设计。

即使源系统提供了列数据类型信息，有时也需要将值作为 STRING 类型导入。请特别注意 DATE, DATETIME日 TIMESTAMP 类型，它们在源系统中通常以非标准格式表示，而数值类型偶尔也会带来麻烦。如果这些类型在源系统中的格式确实不可靠，则作为 STRING 类型导入可以提供实现更稳健解析的选项，并定义处理格式错误值或丢弃不可用或重复行的逻辑。

除了这些程序化步骤之外，干净的数据集还应得到严格的文档记录。对数据集的定性描述、源系统的来源信息、相应的联系人及管理协议，以及（在相关情况下）描述数据特征的逐列元数据，都将确保未来的开发者正确地使用这些数据。

实现数据源项目

  1. 系统管理员为目标数据源创建一个新项目，并将相应的 数据源开发者 添加到一个新的 用户组 以管理该项目。
    • 只有特定数据源的数据源开发者组的成员才应拥有在该项目中构建数据集的权限。
  2. 直方图 数据源所有者 and Agent 管理员 协作以 部署数据连接代理 在源系统上，并在 UI 中配置数据源连接。
    • 确保配置了适当的权限，以便数据源开发者能够预览源系统中的表和文件。
  3. 直方图 数据源开发者 配置同步 针对项目中的一个或多个原始数据集，考虑正确的同步频率和同步类型，并为每个原始数据集添加适当的数据健康检查。
  4. 直方图 数据源开发者 实现清理转换，以生成可供其他项目使用的“干净”数据集。
  5. 下游开发者通过提交 问题 针对该项目或某个特定的干净数据集，请求来自源系统的新数据集、对干净数据集的增强，或报告数据质量问题。

虽然每个数据源都有其独特之处，但清理和准备源系统的步骤通常有一些共同的步骤，例如将原始字符串值解析为给定类型以及处理错误。当多个数据源具有许多相似的清理转换时，最佳实践是在 或 中定义一个库，以提供一套一致的工具并减少重复代码。

推荐的文件夹结构

  • /raw：用于来自数据连接同步的数据集。
  • /processed （可选）：文件级转换，用于从非表格文件创建表格数据。
  • /clean：用于与 /raw 中的数据集一一对应、但应用了清理步骤的数据集。
  • /analysis：用于为测试或记录清理转换而创建的资源，并展示数据的形态。
  • /scratchpad：在构建或测试清理转换过程中创建的任何临时资源。
  • /documentation: The 调度指标 展示清理管道步骤的图表，以及以 Foundry Notepad.

编写的额外文档（超出顶层项目 README 的部分）。3. 转换项目

转换项目的目标是对共享的、具有语义意义的数据分组进行封装，并生成规范视图以输入到本体论层。

这些项目从一个或多个数据源项目导入干净的数据集，将其与查找数据集进行连接以扩展值，规范化或反规范化关系以创建以对象为中心或以时间为中心的数据集，或者聚合数据以创建标准的共享指标。

推荐的文件夹结构

  • /data
    • /transformed（可选）：这些数据集是转换项目中中间步骤的输出。
    • /output：这些数据集是转换项目的“输出”，也是下游本体论项目中唯一应被依赖的数据集。
  • /analysis：为测试或记录清理转换而创建的资源，并展示数据的形态。
  • /scratchpad：在构建或测试清理转换过程中创建的任何临时资源。
  • /documentation: The 调度指标 展示清理管道步骤的图表，以及以 Notepad 编写的额外文档（超出顶层项目 README 的部分）。

4. 本体论项目

本体论在 Foundry 中强制实施了一个共享的通信层，而精心整理一个干净、有序且稳定的本体论是最高优先级的目标，以确保各种有价值的项目能够同时推进，并丰富共同的运营图景。有关设计和管理本体论的概念与实践的更多信息，请参阅 本体论概念文档.

本体论项目是任何管道的中心点，表示生成符合本体论中定义的单个或相关对象组定义的数据集所需的最终转换。这些项目还（单独）生成同步以支撑对象资源管理器视图的数据集。

由于本体论数据集代表其所表示的操作对象的规范事实，因此它们构成了所有“消费”项目的起点。虽然上游清理和管道步骤的来源和转换逻辑是可见的，但从概念上讲，这些步骤和中间数据集对于仅从本体论项目消费数据的项目开发人员、分析师、数据科学家和操作用户来说可能是一个黑盒。从这个意义上说，本体论层充当操作对象的 API。

实现本体论项目

与数据源项目类似，维护本体论项目的关键因素包括：

  • 完善的文档
  • 有意义的健康检查
  • 定期计划
  • 在以下位置进行整理： 数据目录 以及适当的标记

这些内容将在 维护数据管道 部分以及下文有关记录项目文档的标注中进行更详细的讨论。

此外，随着本体论变得越来越完善，越来越多的团队为本体论层做出贡献，维护数据集“API”的完整性变得更加关键。为此，请考虑实施额外的检查，以确保提议的更改保持输出数据集架构的完整性。这将在即将提供的其他文档中进行更深入的讨论。

推荐的文件夹结构

  • /data
    • /transformed（可选）：这些数据集是本体论项目中中间步骤的输出。
    • /ontology：这些数据集是本体论项目的“输出”，是下游用例或工作流项目中唯一应依赖的数据集。
  • /analysis：为测试或记录清理转换而创建的资源，并展示数据的形态。
  • /scratchpad：在构建或测试清理转换过程中创建的任何临时资源。
  • /documentation：数据血缘图显示用于清理的管道步骤以及以报告形式编写的其他文档（超出顶级项目 README）。

5. 工作流项目

工作流项目，也称为 用例项目，应针对当前上下文灵活设计，但通常围绕单个项目或团队构建，以形成有效的协作单元，并划分职责和访问边界。

通常，工作流项目应引用本体论项目中的数据，以确保操作工作流、商业智能分析和应用程序项目都共享统一的世界观。如果在开发工作流项目的过程中，本体论层中可用的数据源不足以作为来源，则表明应丰富和扩展本体论。避免引用管道中较早（或较晚）的数据，因为这可能会分散特定类型数据的事实来源。

记录项目文档

每个项目在整个开发过程中都应进行详尽的记录。以下是一些常见模式和最佳实践：

  • 在每个项目的根目录中保存一个或多个数据血缘图资源，以捕获最重要的数据集和管道关系。不同的图可以使用不同的配色方案来突出相关特征，例如数据刷新的规律性、相关数据集的分组或数据集特征（如大小）。
  • 为项目添加简短描述——可直接在项目标题下方找到。该描述将用于所有项目的列表视图中。重点在于为可能不熟悉该项目的用户介绍项目的背景。
  • 使用直方图中的 添加文档 按钮（位于顶级项目文件夹的右侧边栏中）以编写 Markdown ↗ 语法。这是解释项目目的、主要输出以及项目使用者所需的任何其他相关信息的最佳位置。
  • 将更多的全局项目文档放在本地创建的 Markdown (.md) 文件中，并上传到 文档 文件夹或 或 中，并从顶层文档链接到这些文件。
  • 为项目的代码仓库添加一个 README.md 文件，并确保每个转换文件都有描述和额外的行内代码注释。

推荐的文件夹结构

Workflow 项目的结构将比其他项目类型更加多样化，应侧重于使主要资源可立即访问且有良好的文档记录。

  • /data
    • /transformed（可选）：这些数据集是工作流项目中中间步骤的输出。
    • /analysis（可选）：这些数据集是分析工作流的输出。
    • /model_output（可选）：这些数据集是模型工作流的输出，随后可以对其进行分析以确定模型拟合度。
    • /user_data（可选）：如果您的工作流允许用户创建自己的数据“切片”，请将其存储在此处的用户专属文件夹中。
  • /analysis：为驱动决策和反馈循环而创建的资源和报告。
  • /models：创建的任何模型都应存储在此处。
    • /templates: Any Code Workbook 模板 为特定项目用途共享的内容应存储在此处。
  • /applications：其他工作流应用程序或子应用程序存储在此处。主应用程序应存储在项目根目录中，以便于访问。
    • /develop：开发中的应用程序、新功能和模板存储在此处。
  • /scratchpad：在构建或测试清理转换过程中创建的任何临时资源。
  • /documentation：数据血缘图显示用于清理的管道步骤以及以报告形式编写的其他文档（超出顶级项目 README）。

管道管理角色

以下角色是在 Foundry 中参与管道的规划、设计、实施和管理的常见角色示例。并非在所有情况下都需要所有角色，尤其是在平台开发的早期阶段，而且个人可能同时担任多个角色。但是，总体上考虑这些角色描述及其相互之间的互动方式，将有助于创建秩序良好、高效的团队。

下图展示了主要角色与其在管道中最常活跃的环节之间的关系。

主要角色

  • 代理管理员： 代理管理员负责创建和配置数据连接 代理 并与相关的 数据源所有者共享。这样可以集中控制代理的安装和配置，以获得更好的安全性和管控。
  • 数据源开发者： 数据源开发者是负责数据湖相关的每个数据源获取流程的工程师。这可以由单个团队完成，也可以按源系统划分。
    • 每个数据源开发者拥有 (1) 一个包含与数据源技术连接的数据连接数据源，以及 (2) 一个用于接收同步数据的 Foundry 项目。
    • 数据源项目的输出是一个经过清洗和准备的数据集，可供一个或多个下游用例项目使用。数据源开发者还定义其拥有的每个数据源的刷新频率，并与 发布经理 or 运营经理 合作安排 管道构建策略.
  • 数据管道开发者： 数据管道开发者是负责构建通用本体论层的数据工程师，该层为所有用例提供数据资产。数据管道开发者负责定义此本体论层，并构建从源结构到本体论结构所需的转换。
  • 发布经理： 发布经理拥有生产管道，并管理发布流程，以确保生产管道符合组织标准并可靠地执行。
    • 对于管道的代码更改，这通常通过向 master 分支提交拉取请求的审批流程以及批准在 master 上运行管道构建来完成。为了持续保证可靠性，发布经理会监控 健康检查 这些检查是与管道和数据源开发者共同为关键数据集定义的。
  • 合规官/法务官： 合规官负责在用例开发之前对其进行审批。此类审批应考虑：(1) 需要使用的数据，(2) 项目的目的，以及 (3) 将有权访问这些数据的用户，并结合其所在司法辖区的数据保护制度以及组织自身的政策进行评估。
  • 用例开发人员： 用例开发人员是负责用例开发的工程师——软件开发人员和/或数据科学家。他们使用来自本体论（Ontology）层的数据，这些数据由合规官批准供其使用。

其他角色

  • 运营经理： 此角色负责监控生产管道的健康运行。他们监控不同数据源的数据刷新、不同管道的构建执行，并协助分诊支持请求。此角色支持 发布经理.
  • 权限所有者/身份管理员： 在大多数情况下，用户到组的分配是在客户的身份管理系统中管理的，相关信息通过 SAML 集成传递到 Foundry。在这种情况下，权限管理员负责该流程。
  • 数据官： 负责将本体论（Ontology）层建模为以用户为中心的世界视图，负责数据质量，并寻找应集成以扩展本体论层的新数据源。数据官还负责监控用例中完成的增强（enrichment），并将其泛化到本体论层以提高可重用性。
  • 项目经理： 项目经理与参与项目的工程师协作，确保技术和业务目标的一致性、遵循平台上开发的最佳实践标准，以及与其他项目团队之间的协调。项目经理还负责项目的文档记录。
  • 数据源所有者： 这是特定源系统的主要联系人。他们需要与 Agent 管理员 在新数据连接的配置过程中密切合作，并在之后对“上游”问题承担一定程度的责任——无论是其服务器或文件系统上运行的代理服务的问题，还是数据本身完整性的问题。
