移除继承的标记和组织

标记 和 组织 根据用户的资格限制对资源的访问。

在派生依赖资源时，如果受限内容被移除或混淆，用户可能希望移除该派生资源上的标记和/或组织。移除继承的标记和组织的过程可以通过使用 stop_propagating 和 stop_requiring 输入转换属性来完成。

  • stop_propagating 用于移除继承的 标记 （例如 PII）。
  • stop_requiring 用于移除继承的 组织 （例如 Palantir）。

术语

  • 组织 是应用于项目的一种访问要求，可确保用户组和资源之间的严格隔离。为了满足访问要求，用户必须是应用于项目的至少一个组织的成员或访客成员。
  • 标记 是应用于资源的一种访问要求，以“全有或全无”的方式限制访问。为了满足访问要求，用户必须是 所有 应用于资源上的标记的成员。
  • 角色 是一组权限，定义了用户可以对给定资源执行的特定工作流（例如查看者、编辑者等）。

重要须知

  • 直方图 stop propagating and stop requiring 关键短语仅适用于组织和标记以及 NOT 角色。
  • 仓库需要至少有一个受保护分支（例如 main）。该分支还必须 强制至少一个必需的审批人.
  • 只能在受保护分支上移除组织和标记。提及未受保护的分支（例如 on_branches=[..., "not-protected-branch"]）将导致构建失败。
  • 移除组织和标记在 Python、Java 和 SQL 中均受支持。
  • 审批移除继承的组织和标记需要特殊的用户权限。用户需要 Remove marking 权限来移除标记，以及 Expand access 权限来移除组织。

  2. 拥有标记的 Remove marking 权限或组织的 Expand access 权限的用户可以批准或拒绝提议的更改。如果添加了多个审查者，任何一个审查者的拒绝都将导致整个拉取请求被拒绝。

  3. 如果获得批准，代码编辑器将合并拉取请求并构建输出数据集。输出数据集构建完成后，将不再带有传播的标记和/或组织。

输入转换属性

要移除继承的标记（例如 PII），请使用 stop_propagating 关键短语。

要移除继承的组织（例如 Palantir），请使用 stop_requiring 关键短语。

这些关键短语中的每一个都必须在 每一个 需要移除标记或组织的输入上指定。对于每次移除，还必须指定移除应应用到的受保护分支。标记 ID、组织 ID 和分支应始终指定为带引号的字符串。

您必须提供至少一个上游组织，因为用户只需满足至少一个组织即可。每个列出的组织都需要审批。 详细工作流 提供了一个说明这一点的示例。

移除权限

要能够查看代码并批准拉取请求，批准者通常必须通过项目和仓库本身上的任何组织和标记，并且拥有一个 角色 包含基本 Stemma View Repository 工作流（默认情况下包含在 Viewer 角色中）。用户还必须对每个组织和标记拥有权限，才能设置批准模式或批准移除这些组织和标记的拉取请求。用户不一定是该组织或标记的成员。

对于标记批准，批准的用户必须拥有 Remove marking 该标记上的角色。

对于组织批准，批准的用户必须拥有 Expand access 该标记上的角色。

批准模式

对于每个仓库以及每个组织和标记，数据治理用户可以定义应使用哪种模式来触发新的批准：

  • 需要重新批准： 这是每个组织和标记的默认模式。对于向已移除该组织和标记的分支发出的任何拉取请求，仓库将始终要求安全批准。此模式可防止逻辑变更，从而确保组织和标记被安全地移除。
  • 不需要重新批准： 当该组织和/或标记首次在某个转换上针对给定输入被移除时，需要批准。后续的逻辑变更不会因安全批准而被阻止。

详细工作流程

在此示例场景中，一位代码编辑者想要使用来自敏感上游项目的两个数据集，移除某些信息，并允许更广泛的受众访问生成的数据集。这两个数据集各自带有两个标记，已作为引用添加到下游项目中。代码编辑者希望四个标记中的三个停止传播，使其不出现在输出数据集上。此外，上游项目仅限于来自 OrgA 或 OrgB 的用户访问，而目的是将下游数据分发给来自 OrgC 的用户。

之前： 。Use LLM 区块支持平台上的任何可用 LLM，这符合 Palantir 的 代码编辑者分支上的数据集继承了全部四个标记，并且仍然仅限于来自 OrgA 或 OrgB 的用户访问。

之后： 。Use LLM 区块支持平台上的任何可用 LLM，这符合 Palantir 的 数据集一旦合并到受保护分支（例如， main），现在仅继承一个标记，并且不再要求用户是以下组织的成员： OrgA or OrgB.

步骤

  1. 代码编辑者在以下位置编写新的转换： feature/clean-data 下游项目仓库的分支。

  1. 由于所有标记更改都是针对以下分支请求的： master 分支，因此在其上工作无需任何批准。 feature/clean-data。换言之，当输出数据集在以下分支上构建时： feature/clean-data 分支，所有上游标记仍将被继承。

  2. 代码编辑者创建一个指向主分支的拉取请求，并向数据治理用户请求批准，这些用户管理受以下标记限制的数据： lemon, apple日 cherry 标记。代码编辑者还向来自 OrgA 的 Expand access 组织管理员请求批准，该管理员可以在需要将 OrgA 数据与其他组织共享时进行批准。

通过移除继承的组织来扩展访问权限的效果是移除所有继承的组织，但仅需要获得对转换中列出的组织具有相应权限的用户的批准。如果您希望要求获得所有组织的批准，则需要在 `stop_requiring` 组件中列出所有 ID。在此示例中，OrgA 对上游项目中的数据负主要责任，因此编辑者选择了 OrgA 进行跨组织批准流程。这样，编辑者只需获得 OrgA 管理员的批准即可移除继承的组织。根据编辑者希望请求哪些组织的批准，编辑者可以选择 `stop_requiring` 以下任一项： (1) OrgA（由 OrgA 管理员批准）， (2) OrgB（由 OrgB 管理员批准），或 (3) 同时 OrgA 和 OrgB（由两个组织的管理员批准）。

最终结果是，输出数据集将不会从输入中继承任何组织，并且仅遵循其所在项目中的组织。

  1. 数据治理用户和组织管理员会收到 Foundry 通知，告知已请求他们的批准。

  2. 假设拉取请求获得批准，代码编辑者将其合并并构建输出数据集，如下面的 晚于 上图所示。

  3. 第二周，另一位代码编辑者对另一个代码文件进行了更改，并打开一个拉取请求以合并到 master。如果没有任何标记需要重新批准，则此拉取请求无需安全审查即可获得批准。如果任何标记确实需要重新批准，则该拉取请求将需要由管理该标记的数据治理用户或组织管理员进行安全审查。
