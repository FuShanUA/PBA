审批

用户可能没有在 Foundry 中进行特定更改的权限，需要为此更改提交请求。该请求会被路由给管理员进行审批。当获得必要的批准后，请求将被调用，即所请求的更改会被应用。

这种在 Foundry 中请求、批准和调用更改的工作流由 审批 应用程序管理。该应用程序可以在 Foundry 中直接访问，或在 控制面板 中用于某些管理工作流。Approvals 整合了合规、治理和同行评审工作流，使其在 Foundry 中易于管理。使用审批的一些示例工作流包括 项目访问请求 和 评审本体论提案.

隐私最佳实践是对需要指定人员问责的敏感或重大变更使用审批步骤。请查阅 实践中的隐私与公民自由 以获取有关使用审批（Approvals）来保持对此类变更的人工监督的指导。

核心概念

请求 由一个或多个 任务组成。所有请求都列在 Approvals 收件箱.

Approvals 收件箱

Approvals 收件箱允许用户搜索相关请求以进行高效处理。在这里，用户可以按类型、创建者或状态等属性筛选请求。

筛选器位于左侧边栏中。要查看等待您评审的请求，请选择 您的收件箱 筛选器。要查看由您创建的请求，请选择 由您创建 筛选器。

即使请求已完成，也会被持久保存，因此您可以将它们作为过去决策的审计日志来参考。

请求

请求包含一组必须 所有 获得批准才能调用任务并应用所请求更改的任务。在 Approvals 应用程序中，收件箱是请求的列表。

请求可以处于以下任一状态：

  • 待批准： 一个未结的请求，其任务需要获得批准才能调用该请求。
  • 已关闭： 一个未调用即被关闭的请求。已关闭的请求无法重新打开。如果请求不再相关，符合条件的用户可以将其关闭。
  • 已拒绝并关闭： 一个被评审者拒绝且未调用即被关闭的请求。该请求无法重新打开。
  • 要求更改： 评审者已要求对其进行更改的请求。该请求保持未结状态，符合条件的用户可以对其进行编辑或提供进一步的说明以满足必要的更改。
  • 需要操作： 所有任务均已批准但在没有用户操作的情况下无法调用的请求。例如，如果请求已获批准，但所需的 检查点 不完整，则在提交检查点之前无法调用该请求。
  • 已完成： 因其所有任务均已获得批准而被调用的请求。

请求操作

请求用户或任何符合条件的评审者都可以编辑或关闭请求。只有符合条件的评审者才能 approve, reject or reject and close 一个请求。

如果一个请求有多个具有不同符合条件的评审者的任务，评审者的操作仅应用于其有资格评审的任务。操作只能在请求级别进行，并相应地应用于任务。

任务

任务是 Foundry 中的单个更改。 所有 与请求关联的任务必须全部获得批准，请求才能被调用并应用所请求的更改。任务的一些示例包括：

  • 群组成员身份： 将用户添加为 组的成员。对该群组具有 Manage permissions and/or Manage membership 权限的管理员可以批准此任务。
  • 项目访问请求： 直接授予用户在项目上的 角色。在项目上具有 Owner 角色的用户可以批准此任务。
  • 标记访问请求： 将用户添加为 标记。具有 Manage permissions 的管理员可以批准此任务。
  • 添加引用请求： 添加一个 对项目的引用。在项目上具有 Editor 或 Owner 角色的用户可以批准此任务。
  • 本体论提案： 对 本体论进行更改。此任务将重定向到 本体论管理器 以了解所提议更改的更多详细信息。在本体论上具有 Owner 角色的管理员可以批准此任务。

任务会经历一系列不同状态的生命周期：

  • 审核中： 任务的要求尚未满足，任务正在等待符合条件的审核人。这是新创建的请求中任务的默认状态。
  • 已批准： 任务的所有要求均已满足，并且已收到所需的批准。
  • 已拒绝： 任务被符合条件的审核人拒绝。当审核人执行 Reject and close 或 Changes requested 操作时会发生这种情况。如果请求尚未关闭，符合条件的审核人可以返回该任务并以批准覆盖最初的拒绝。

在同一个请求中，不同的任务可能有不同的符合条件的审核人，因此同一请求中的不同任务可能处于不同的状态，如下所示。请求要被调用，所有任务都需要获得批准。

必需的检查点

If 检查点 已为某些操作（例如，将用户添加到组）配置，那么相关请求也将需要提供理由说明。

相应的任务将显示检查点是否已完成。通常要求请求用户在提出请求时完成检查点。如果没有完成，符合条件的审核人可以代表请求用户完成检查点。
