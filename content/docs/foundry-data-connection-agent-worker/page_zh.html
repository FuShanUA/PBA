Agent worker 配置参考

旧版

Agent worker 处于 旧版 开发阶段，预计不会再进行额外开发。我们仍提供完整支持。建议在构建新数据源或更新现有工作流时使用 Foundry worker 连接。请参阅 Foundry worker 与 agent worker 的对比 以了解此建议背后的运维原因。

本页面介绍将代理用作 worker 时可用的配置选项，并假定您已经熟悉 数据连接代理 及其 通用配置选项。

要将现有的 agent worker 数据源迁移到 Foundry worker，请参阅 将数据源从 agent worker 切换到 Foundry worker。

设置代理

您必须 设置代理 才能使用 agent worker。配置数据源时，您可以选择 Agent worker 选项，并选择至少一个可用的代理。通过该数据源连接运行的能力将作为作业在代理主机上执行。

能力执行

使用 agent worker 时，能力通过在代理主机上直接运行 Java 代码来执行。这些 Java 进程可能会从您的系统拉取数据并将数据推送到 Foundry（例如 批量同步),或从 Foundry 提取数据并推送到您的系统(如 导出),该方式存在 已知限制。

网络

代理工作器数据源的所有网络配置均在代理主机上完成。Foundry 侧的出站策略不适用:代理主机必须配置防火墙、DNS 和代理设置，才能直接访问源系统。请参阅 配置代理网络访问 以获取完整参考。

内存分配与使用

代理内存是决定使用代理工作器执行的能力性能的关键因素之一。

代理内存的主要可用设置如下:

  • JVM 堆: 在代理设置页面上配置，用于指示代理在启动时应分配的内存量。分配的内存会从操作系统中预留，且不得超过主机上的可用内存。默认 JVM 堆值为 1 GB。
  • 主机内存: 取决于安装代理的机器规格。我们建议至少 16 GB 的内存。

在主机上观察到的实际内存使用量会有所不同，具体取决于代理工作器当前执行的工作负载，以及同一主机上运行的其他进程。

在观察和监控用作 agent worker 的代理的内存使用情况时，有两个主要指标：

  • 操作系统物理内存使用量： 代理主机上的实际总内存使用量，包括代理进程，也包括在同一主机上运行的任何其他进程。该使用量可能超出为代理进程分配的 JVM 堆内存大小，最高可达主机上可用的全部物理内存。
  • 代理内存使用量： 代理的内存使用量，始终小于配置的 JVM 堆内存大小。

有关在代理上监控内存使用情况的信息，请参阅 代理指标和健康监控。

负载均衡

使用 agent worker 时，可以将多个代理分配给单个源连接。代理会被分配作业，以执行特定的 功能 ，这些功能在已分配的源连接上配置。作业在启动时会在其中一个可用的代理上执行。

作业会随机分配给已分配的代理中的一个可用代理。

最大并发同步数 默认为 16，并可在 代理设置中配置。该 最大并发同步数 配额的强制执行范围涵盖所有 功能 以及所有已分配的源，这意味着在任何源上运行任何功能都会消耗一个单位的可用并发同步配额。这包括 流式同步， 变更数据捕获同步， 导出， webhook 以及旧版数据连接 任务。如果已分配的代理当前正在运行的并发同步数量已达到最大值，则新作业将排队等待，直到有足够多的正在运行的功能完成。

一般而言，我们不建议使用多个代理来对超出单个代理成功运行能力的更大工作负载进行负载均衡。使用多个代理的主要预期用途是允许将代理下线进行维护。为了获得最佳性能和可靠性，我们建议多代理设置中的每个代理都应能够处理整套 功能 ，即在已分配的源连接上配置的功能。

直接上传与数据代理上传策略

代理工作进程支持两种选项，用于指定如何将批量同步的数据上传到 Palantir 平台：

数据代理模式

在数据代理模式下，数据通过数据代理服务使用公共 Foundry API 进行上传。这利用了处理 Foundry API 数据集读写调用的同一 API 网关。

配置为使用数据代理模式的代理将在代理配置 YAML 中包含以下内容：

Copied!
1
2
3
4
destinations:
  foundry:
    uploadStrategy:
      type: data-proxy

直接模式 [已淘汰]

直接模式不适用于新代理，也不适用于 2024 年 6 月之后设置的注册。数据代理模式是新代理的默认选项，也是唯一支持的选项。只要安装代理的主机 IP 地址不发生变化，使用直接模式的现有代理将继续正常工作。

在直接模式下，数据直接上传到 Foundry 数据目录中的底层存储桶。虽然这种方式能带来性能提升，但只有在 Palantir Support 进行自定义网络配置时才可行，并且在最新的云基础设施上不可用。

配置为使用直接模式的代理将在代理配置 YAML 中包含以下内容：

Copied!
1
2
3
4
destinations:
  foundry:
    uploadStrategy:
      type: direct

自定义 JDBC 驱动程序

请参阅 JDBC（自定义）连接器文档 以了解如何向代理添加自定义 JDBC 驱动程序。

驱动程序必须由 Palantir Support 签名并直接添加到代理中，才能与代理工作进程配合使用。

请联系 Palantir 支持团队，获取签署自定义 JDBC 驱动程序方面的帮助。

凭据

代理工作进程的一个独特之处在于，内存中的凭据解密是在 Foundry 之外进行的。在 Data Connection 用户界面中输入凭据时，并非由 Foundry 对凭据进行加密，而是在浏览器中使用分配给该数据源的每个代理的公钥对凭据进行加密，然后再发送到 Foundry。加密后的凭据随后存储在 Foundry 中，只能在需要时由相应代理使用其私钥进行解密。

请注意，Foundry 中的所有数据（包括凭据）在静态存储和传输过程中均经过加密。只有在需要访问时，才会在内存中对数据进行解密。

这意味着在使用代理工作进程时，凭据配置将受到以下注意事项和限制的约束：

  • 如果分配给数据源的代理集合发生变化，则必须在 Data Connection 中重新输入凭据。
  • 如果使用新的下载链接重新预配代理，凭据将不会自动转移。必须恢复现有代理的加密密钥，否则必须在 Data Connection 中重新输入所有凭据。

有关在目录和主机之间移动代理的更多信息，请参阅 代理配置参考文档，包括在移动现有代理目录时保留加密凭据的说明。

证书

代理会同时与 Foundry 和您的内部网络进行通信。这意味着代理需要在其信任库中拥有正确的证书，才能建立这些连接。

请查阅有关添加其他证书以连接特定源系统的文档。

如果您要连接的系统需要双向 TLS (mTLS)，则必须手动向代理添加私钥。

已知限制

直接在代理主机上执行功能会带来一些弊端,例如:

  • 代理上可能出现的类路径冲突: 这对于自定义 JDBC 工作流尤其重要，因为自定义 JAR 可能与 Foundry 附带并在代理类路径上运行的依赖项发生冲突。
  • 在代理上运行的作业之间的资源争用： 作业可能会任意占用分配给代理进程的全部内存和磁盘空间，并可能导致其他作业永远无法启动或崩溃。对于使用代理工作器运行的 webhook 而言，这一问题尤其严重。在这种情况下，我们强烈建议为 webhook 执行使用专用代理，以免长时间运行的同步任务阻止短时间运行的 webhook 执行。
  • 缺乏对某些功能的支持： 某些功能，例如 在代码中使用、 虚拟表以及虚拟媒体，均与代理工作器不兼容，因为这些功能需要直接从 Foundry 建立的同步连接，无法作为作业在代理上运行。
