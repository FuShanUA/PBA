设置 agent

您必须 设置 agent 才能使用 agent worker。配置源时，您可以选择 Agent worker 选项并选择至少一个可用的 agent。通过该源连接运行的能力将作为作业在 agent 主机上执行。

能力执行

使用 agent worker 时，能力通过在 agent 主机上直接运行 Java 代码来执行。这些 Java 进程可以从您的系统拉取数据并推送到 Foundry（例如 批量同步），或从 Foundry 拉取数据并推送到您的系统（例如 导出），这存在 已知限制.

网络

agent worker 源的所有网络配置均在 agent 主机上完成。Foundry 侧的出站策略不适用：agent 主机必须配置防火墙、DNS 和代理设置才能直接访问源系统。请参阅 配置 agent 网络访问 获取完整参考。

内存分配与使用

Agent 内存是决定使用 agent worker 执行的能力性能的关键因素之一。

agent 内存的主要可用设置包括：

  • JVM 堆内存： 在 agent 设置页面上配置，指示 agent 在启动时应分配多少内存。分配的内存从操作系统中保留，不得超过主机上的可用内存。默认 JVM 堆内存值为 1 GB。
  • 主机内存： 基于安装 agent 的机器的规格。我们建议至少 16 GB 的内存。

在主机上观察到的实际内存使用量会因 agent worker 当前执行的工作负载（包括同一主机上运行的其他进程）而有所不同。

在观察和监控用作 agent worker 的 agent 的内存使用情况时，有两个主要指标：

  • 操作系统物理内存使用量： agent 主机上的实际总内存使用量，包括 agent 进程以及同一主机上运行的其他任何进程。这可能超出为 agent 进程分配的 JVM 堆内存大小，最高可达全部可用物理内存。
  • Agent 内存使用量： agent 的内存使用量，始终小于配置的 JVM 堆内存大小。

有关监控 agent 内存使用情况的信息，请查看 agent 指标和健康监控。

负载均衡

使用 agent worker 时，可以将多个 agent 分配给单个源连接。agent 会被分配作业以执行特定的 能力 在已分配的源连接上配置。作业在启动时在其中一个可用的 agent 上执行。

作业会随机分配给已分配的 agent 中的一个可用 agent。

最大并发同步数 默认为 16，可在 Agent 设置。该 最大并发同步数 配额在所有 能力 以及所有已分配的源之间统一执行，这意味着在任何源上运行任何功能都会消耗一个单位的可用并发同步配额。这包括 流式同步, 变更数据捕获同步, 导出, 。操作可以对 Foundry 本体论中的数据进行编辑，或通过 和旧版数据连接 任务。如果已分配的 Agent 当前运行的并发同步数已达上限，则新作业将排队，直到足够多的正在运行的功能完成。

通常，我们不建议使用多个 Agent 来对超出单个 Agent 处理能力的较大工作负载进行负载均衡。使用多个 Agent 的主要目的是允许将 Agent 下线进行维护。为了获得最佳性能和可靠性，我们建议多 Agent 设置中的每个 Agent 都应能够处理已分配源连接上配置的全部 能力 。

直接上传与数据代理上传策略

Agent 工作进程支持两种选项，用于指定批量同步的数据应如何上传到 Palantir 平台：

数据代理模式

在数据代理模式下，数据通过数据代理服务使用公共 Foundry API 上传。这利用了与处理 Foundry API 数据集读写调用相同的 API 网关。

配置为使用数据代理模式的 Agent 在其 Agent 配置 YAML 中将包含以下内容：

destinations:
  foundry:
    uploadStrategy:
      type: data-proxy

直接模式 [已弃用]

直接模式不适用于新 Agent 或 2024 年 6 月之后创建的注册。数据代理模式是新 Agent 支持的默认且唯一的选项。只要安装 Agent 的主机 IP 地址不发生变化，使用直接模式的现有 Agent 将继续正常工作。

在直接模式下，数据直接上传到 Foundry 数据目录中的底层存储桶。虽然这能带来性能提升，但只有在 Palantir Support 进行自定义网络配置的情况下才可实现，并且在我们最新的云基础设施上不可用。

配置为使用直接模式的 Agent 在其 Agent 配置 YAML 中将包含以下内容：

自定义 JDBC 驱动程序

有关构建自定义主题的示例，请参阅 JDBC（自定义）连接器文档 以了解如何向 Agent 添加自定义 JDBC 驱动程序的说明。

驱动程序必须由 Palantir Support 签名并直接添加到 Agent 中，才能与 Agent 工作进程配合使用。请联系 Palantir Support 以获取签名自定义 JDBC 驱动程序方面的帮助。

凭据

Agent 工作进程的一个独特之处在于，内存中的凭据解密发生在 Foundry 之外。在数据连接用户界面中输入凭据时，凭据并非由 Foundry 加密，而是在浏览器中使用分配给该源的每个 Agent 的公钥进行加密，然后再发送到 Foundry。加密后的凭据随后存储在 Foundry 中，并且只能在需要时由相应的 Agent 使用其私钥进行解密。

Foundry 中的所有数据（包括凭据）在静态存储和传输过程中均经过加密。数据仅在需要访问时才在内存中解密。

这意味着在使用 Agent 工作进程时，凭据配置需遵循以下注意事项和限制：

  • 如果分配给源的 Agent 集合发生变化，则必须在数据连接中重新输入凭据。
  • 如果使用全新的下载链接重新配置 Agent，凭据将不会自动转移。必须恢复现有 Agent 的加密密钥，否则必须在数据连接中重新输入所有凭据。

有关在目录和主机之间移动 Agent 的更多信息，请参阅 Agent 配置参考文档，其中包括在移动现有 Agent 目录时保留加密凭据的说明。

证书

代理（Agent）同时与 Foundry 和您的内部网络进行通信。这意味着代理需要在其信任库中拥有正确的证书，才能建立这些连接。

请查阅有关添加额外证书以连接到特定源系统的文档。

已知限制

直接在代理主机上执行功能存在一些缺点，例如：

  • 代理上可能存在类路径冲突： 这对于自定义 JDBC 工作流尤为重要，因为自定义 JAR 可能与 Foundry 附带并在代理类路径上运行的依赖项发生冲突。
  • 代理上运行的作业之间可能存在资源争用： 作业可能会任意使用分配给代理进程的全部内存和磁盘空间，并可能导致其他作业永远无法启动或崩溃。这对于使用代理工作器运行的 webhook 尤其成问题。在这种情况下，我们强烈建议为 webhook 执行使用专用代理，以便长时间运行的同步不会阻止短时间运行的 webhook 执行。
  • 缺乏对某些功能的支持： 某些功能，例如 在代码中使用, 虚拟表以及虚拟媒体，与代理工作器不兼容，因为这些功能需要直接来自 Foundry 的同步连接，无法作为作业在代理上运行。
