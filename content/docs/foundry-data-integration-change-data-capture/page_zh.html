变更数据捕获（CDC）

变更数据捕获 ↗ （CDC）是一种企业数据集成模式，通常用于将关系型数据库的实时更新流式传输给其他消费者。

Foundry 支持从产生变更数据捕获流的系统同步、处理和存储数据。平台中的各个组件，包括 数据连接器, 流, 管道，而 Foundry 本体论 都可以使用在底层数据上配置的元数据原生地处理这些变更日志数据，配置位置为 模式 底层数据的元数据。

变更日志元数据

变更日志元数据要求数据具有以下属性：

  • 一个或多个主键列
    • 变更日志数据将包含许多主键列相同的条目，因为变更日志旨在传达具有该主键的记录上发生的每一次单独变更。变更数据捕获对于正在被编辑的数据特别有用，而不是不可变的或仅追加的数据流。
  • 一个或多个排序列
    • 排序列必须是数值型，用于确定具有给定主键集合的记录变更的相对顺序。排序列通常是以长整型表示的时间戳，但情况并非总是如此。即使排序列不是时间戳，最大值也被理解为最新的。
  • 一个删除列
    • 删除列用于确定给定更新是否删除了具有给定主键集合的记录。该列必须是布尔值，如果记录被删除则为 true，否则应为 false。

此变更日志元数据用于指定一种解析策略，将变更日志解析为源系统中数据的当前视图。变更数据捕获的解析策略工作方式如下：

  1. 根据主键列对数据进行分组。
  2. 找到排序列中值最大的条目。
  3. 如果该条目在删除列中的值为 true 则将其删除。

完成这些步骤后，变更日志应被折叠为与生成变更日志的上游源系统中所见相同的视图。变更日志元数据和解析策略被各种 Palantir 组件以不同的方式使用，如下所述。

Data Connection 中的变更数据捕获

Data Connection 中可用的源可能支持将系统数据作为应用了变更日志元数据的流进行同步。源实现同步变更日志数据能力的前提是源系统能够产生具有所需属性（主键列、排序列和删除列）的日志数据。

许多常用的数据库（包括 MySQL、PostgreSQL、Oracle、Db2 和 SQL Server）都可以产生 CDC 变更日志数据。Foundry 中针对这些系统的数据连接器可能支持也可能不支持直接同步这些变更日志。即使连接器目前不支持 CDC 同步，您仍然可以通过 Kafka 或其他流式中间件同步数据，并在数据到达 Foundry 后将其用作变更日志。

在外部数据库上启用变更数据捕获

要从受支持的源类型同步变更日志数据流，您必须为相关表启用正确的设置，在某些情况下，还必须为整个数据库启用正确的设置。

例如，要为 Microsoft SQL Server 启用变更数据捕获，您必须运行命令在数据库上启用 CDC：

USE <database>
GO
EXEC sys.sp_cdc_enable_db
GO

然后，在需要记录变更日志的每个表上运行另一条命令：

EXEC sys.sp_cdc_enable_table
    @source_schema = N'<schema>'
  , @source_name = N'<table_name>'
  , @role_name = NULL
  , @capture_instance = NULL
  , @supports_net_changes = 0
  , @filegroup_name = N'PRIMARY';
GO

以上示例从较高层面说明了启用源系统生成变更日志数据可能需要哪些操作。有关如何为特定系统启用变更数据捕获日志的具体信息，请参阅该系统提供的文档。

保存同步配置，以在指定的输出位置创建新流。

目前，CDC 作业在任何更改后必须手动（重新）启动。所有 CDC 同步作为单个多输出提取作业运行，这意味着每当添加或删除数据流时，来自同一源的现有 CDC 流必须短暂停止。这些流将自动补齐流式同步作业停止期间发生的所有数据变更。

启动输出流后，变更日志数据应开始流动，并显示在输出流式数据集的实时视图中。

为每个源配置自定义 CDC 设置

Foundry 的 CDC 实现利用了开源平台 Debezium ↗ 来读取数据源日志。您可以直接在 Data Connection 界面中为单个源配置 Debezium 连接和引擎属性。首先，导航到您要配置的已创建源。然后选择右上角的 CDC 同步 。选择 CDC 设置 部分以展开配置选项。

Foundry 的默认 CDC 配置旨在提供无摩擦的设置体验，并最大限度地减少对源系统的干扰。但是，我们强烈建议您查看连接器的 特定默认行为 ，尤其是其 快照模式，以确保这些默认设置符合您的数据要求。

每种数据源类型都有推荐的可配置设置。例如，上图显示了 Microsoft SQL Server 连接器的 事务隔离级别 。此外，您还可以使用 高级 Debezium 配置 选项配置任意 Debezium 属性。这种灵活性使您能够根据每个数据源的具体需求自定义设置。

为数据连接器自定义 CDC 设置在多种情况下都很有用，包括以下示例：

  1. 高事务量： 对于经历快速事务突发的数据连接器，默认的 max.batch.size 设置可能导致过多的小批量处理，增加开销并延迟数据传播。通过提高 max.batch.size，您可以将变更合并到更大的批次中，从而提高效率和数据流。
  2. 网络不稳定： 对于容易出现瞬时网络问题或临时错误的数据连接器，增加 error.max.retries 可为连接器提供更多自主恢复的机会，降低数据丢失的风险。
  3. 实时更新： 在近乎实时更新至关重要的高事务环境中，降低 offset.flush.interval.ms 可确保更频繁地刷新偏移量，从而最大限度地缩短恢复窗口并提高变更传播的及时性。

审查 Debezium 文档 ↗ 以了解每种数据连接器类型可以配置哪些属性。

配置任意 Debezium 属性时，您有责任确保兼容性和功能性。不当的配置可能导致意外行为或数据丢失。请谨慎操作，并查阅 Debezium 文档以获取指导。

流中的变更数据捕获

带有变更日志元数据的流将显示数据的两种视图：

  • A 实时视图 显示完整展开的变更日志条目列表。
  • An 归档视图 其中数据根据解析策略进行解析，并折叠为数据的当前最新视图。

架构将在详细信息视图中将变更日志元数据显示为主键解析策略。

流使用提供的排序列解析归档视图，即使数据是乱序接收的。此行为与 Foundry 本体论中的变更日志数据不同，后者根据数据在用于支撑对象类型的流中的到达顺序对数据进行索引。

Pipeline Builder 中的变更数据捕获

Pipeline Builder 为处理和配置变更数据捕获（CDC）流提供了强大的功能。本节介绍两种场景：处理完整的 CDC 流，以及处理需要回填的部分 CDC 流。

处理完整的 CDC 流

在 Pipeline Builder 中处理流式转换时，您可以在保留元数据的同时处理变更日志数据。只要元数据列（主键、排序和删除）在转换过程中保持不变，变更日志元数据就会自动传播到任何输出。

使用回填数据集配置部分 CDC 流

在某些情况下，CDC 流可能不包含所有历史数据，而仅包含从特定时间点开始的变更。要创建完整的数据集，您必须将回填数据集与正在进行的 CDC 流相结合。请使用以下步骤实现此目的：

  1. 准备回填数据集：

    • 使用与 CDC 流相同的 Data Connection 源摄取数据快照。
    • 确保回填数据集包含时间戳列。如果源数据中不存在，请使用 SQL 函数生成一个（CURRENT_TIMESTAMP()，例如）来引用它们。

  2. 在 Pipeline Builder 中合并数据集：

    • 使用 第一个选中的数据集是 转换将回填数据集与正在进行的 CDC 流合并。

  3. 配置 CDC 元数据：

    • 使用直方图中的 Key By 转换面板来准备合并后的数据，以便同步到本体论中。
    • 将主键列设置为与源系统中的主键列一致。
    • 选择时间戳列作为排序列。
    • 如果适用，请指定删除列。

  4. 处理删除和排序：

    • 或 Key By 面板配置为按时间戳列对数据进行排序。
    • 如果源数据不包含显式的删除信息，您可能需要实现推断删除的逻辑（例如，通过比较连续的快照）。

直方图 Key By 转换面板将向流附加必要的 CDC 元数据，包括以下内容：

  • 主键解析策略
  • 排序列
  • 一个删除列

此配置为数据同步到本体论后的正确解析做好准备，确保根据时间戳排序维护每条记录的最新状态。

将 CDC 元数据应用于非 CDC 数据

如果您的输入流缺少变更日志元数据，或者在转换过程中修改了元数据列，您仍然可以使用 Key By 面板将变更日志元数据应用于您的输出。这允许您将任何数据集视为 CDC 流，从而实现强大的数据集成和实时更新功能。

本体论中的变更数据捕获

本体论使用变更日志元数据将数据索引到由流式数据源支撑的对象类型中 对象存储 v2 。流中到达的数据会被解析并索引到最新的当前视图中，该视图在查询本体论时可用（例如，在 Workshop 模块中显示）。

If 保留期 在具有变更日志元数据的数据源上配置了保留期时，在保留窗口时间内未收到更新的任何记录将从本体论中消失。

本体论目前会忽略变更日志元数据中指定的排序列。相反，Object Storage v2 会根据数据到达支撑数据源的顺序对数据进行索引。具体而言，这意味着对于给定的主键，如果一条排序值为 2 的日志条目在 t1 和 data_column=foo到达，随后另一条排序值为 1 的日志条目在 t2 ，使用 data_column=bar到达，则该记录将显示为 data_column=bar ，即使在源系统中最新值为 data_column=foo。因此，如果数据乱序到达，本体论可能会错误地反映源系统中的数据。

由于与 Palantir 配合使用的连接器保证按顺序交付数据，且 Foundry 流保持顺序，因此本体论的这种行为很可能仅影响自定义设置，或在同步前未重新排序而手动回填的较旧流式变更日志。如果您遇到这种情况，我们建议在同步到本体论之前，在 Pipeline Builder 中应用转换来对数据重新排序。

Workshop 中的变更数据捕获

Workshop 支持 自动刷新 ，以便在数据一进入本体论后立即显示频繁更新的数据。自动刷新与 CDC 兼容，可用于确保通过变更数据捕获流入的任何数据在 Workshop 应用程序中及时可用。其用途不限于 CDC 数据：在 Workshop 模块打开期间预期会频繁更新的任何数据都可以使用自动刷新，无论支撑数据源是否具有变更日志元数据。

使用变更数据捕获时的注意事项

在使用 CDC 工作流之前，我们建议您查看以下有关回填、中断和其他已知限制的信息。

回填

所有变更日志同步均仅以“仅向前”的方式处理；不会执行自动回填。

通常，无法对变更日志进行完整回填，因为大多数系统默认不启用 CDC。即使启用了变更日志，大多数系统也包含保留期，超过该期限后变更日志将被永久删除且无法恢复。

如果需要完整回填，我们建议采取以下步骤：

  1. 以“仅向前”的方式设置 CDC 流。
  2. 执行批量同步以提取所需的历史数据。
  3. 将历史批量数据转换为每个主键的“创建”记录流，然后将该流合并到 CDC 流中。

回填可能导致数据乱序，您可能需要手动重新排序或重放流，以便正确准备数据以同步到本体论。

中断

使用 CDC 工作流时，您可能会遇到以下中断情况：

  • 源数据库与 Foundry 代理之间的网络连接中断
  • Foundry 代理主机与 Foundry 之间的网络连接中断
  • Foundry 中断
  • 数据库中断
  • 代理中断

如果数据库中复制日志和变更日志的保留窗口配置为长于预期的最长中断时间，则中断将得到妥善处理。

例如，如果与 Foundry 的连接中断数小时，而 Microsoft SQL Server 上的日志保留窗口设置为一天，数据库将继续记录变更日志条目。Foundry 在恢复在线并重新连接到 Microsoft SQL Server 后，将平稳地完成追赶。由于在变更日志条目队列清空之前不会有新数据流入，因此在变更再次以近实时方式流入 Palantir 之前可能会有一些延迟。

使用来自非变更日志源的变更日志形式数据

数据不需要以变更日志的形式摄取才能使用 CDC 工作流。Palantir 中的任何流式数据都可以使用变更日志元数据进行“键控”，然后在同步到本体论后在工作流中用作 CDC 数据。

这意味着，例如，可以使用流代理进行基于推送的摄取，手动将变更日志形式的记录推送到流中。

类似地，如果变更日志数据在 Kafka 主题中可用，可以使用标准（非 CDC）同步进行摄取。然后，可以使用 Pipeline Builder 对其进行“键控”，并在本体论及后续环节中使用。

移除变更日志元数据

有时，移除变更日志元数据可能很有用。例如，您可能希望移除元数据以分析变更日志所捕获的流程。要移除变更日志元数据，请使用以下方法之一：

  • 对元数据列执行任何转换
  • 手动从流式数据集的 schema 中移除解析策略

启用对 CDC 表的访问

连接到源系统时，您必须在 连接详情中提供用户凭据。这些凭据与在源端设置的权限绑定。对于基本的数据摄取，该用户需要 SELECT 您计划摄取的数据集的权限。但是，CDC 连接可能要求用户同时具有 SELECT 和 EXECUTE 您希望从中摄取的表及其 schema 的权限。

快照模式注意事项

默认情况下，Foundry 会配置 snapshot.mode to schema_only （Oracle、SQL Server）、 no_data （Db2）或 never （PostgreSQL），以避免影响数据库的可用性；这些配置避免了在快照过程中锁定表，从而确保对正在进行的数据库操作造成的中断最小。尽管这些模式避免了表锁定，但如果归档日志在 Debezium 处理之前被清除，它们仍然存在数据丢失风险。例如，Oracle 可能会随时间删除较旧的重做日志；如果 Debezium 尝试读取已删除的日志，则无法在不进行完整快照的情况下恢复丢失的数据。

替代配置

如果您希望防止日志清除或确保基础数据集，请考虑使用更完整的快照配置：

  • recovery

    • 行为： 如果 schema 历史主题丢失或损坏，恢复已在捕获变更的连接器；如果自上次关闭以来未发生 schema 变更，则在重启时重置并重建数据库 schema 历史。
    • 限制： 要求 schema 历史主题具有无限保留期。

  • always

    • 行为： 每次连接器重启时都进行完整快照，确保数据的副本完全最新。
    • 限制： 每次启动时可能导致表锁定和额外开销。
  1. when_needed
    • 行为： 仅当 Debezium 无法检测到有效偏移量时才进行快照；例如，偏移量不存在或已过期。
    • 限制： 触发快照时仍可能锁定表。
