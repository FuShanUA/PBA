为 Foundry 编写 OAuth2 客户端

本文档面向希望编写 OAuth2 客户端以连接到 Foundry 的 Foundry 用户或管理员。本页面提供了对 OAuth 2.0 授权框架 ↗ 的描述，以及有关 Foundry 的 OAuth2 实现的详细信息。此外， Foundry 第三方应用程序与 API 协议 规定了第三方应用程序在 Foundry 平台上的使用，第三方应用程序的创建者和管理员应理解该协议。

OAuth2 概述

OAuth2 授权框架使第三方应用程序能够获得对服务的受控访问。OAuth2 通过提供一个层来改进传统的客户端-服务器授权模型，使客户端（如第三方应用程序）能够通过使用专门颁发的访问令牌和刷新令牌来请求访问，而不是使用用户的凭据或静态持有者令牌。OAuth2 通过使用授权许可（grant）来管理这种访问，授权许可 是获取访问令牌的方法。

支持 OAuth2 集成

以下各节介绍如何在第三方应用程序中支持 OAuth2。在本文档中， 客户端 指第三方应用程序， 授权服务器 指 Foundry 的授权服务器，而 用户 指第三方应用程序的最终用户。

要在 Foundry 中使用 OAuth2，您必须按照 注册第三方应用程序 中的说明注册您的应用程序，并从下一小节中选择一种授权方式。

授权码模式

授权码许可允许客户端代表现有的 Foundry 用户执行操作。应用程序必须请求其需要访问的一组 Foundry 权限，然后 Foundry 用户必须明确授予客户端访问其账户中这些权限的权限。Foundry 允许将客户端限制为一组有限的资源，或限制为用户可以访问的所有资源。

授权码许可的工作方式如下：

  1. 客户端创建一个 code_verifier and code_challenge。这对于 是推荐 但非必需的，适用于 机密客户端 ↗，例如可以安全存储客户端密钥的基于服务器的应用程序。对于 必填 for 公共客户端 ↗，例如无法安全存储客户端密钥的原生应用程序，则是必需的。
    • 直方图 code_verifier 是一个加密随机字符串，包含 A-Z、a-z、0-9、 - (hyphen), . (period), _ （下划线）和 ~ （波浪号），长度为 43 到 128 个字符。
    • 直方图 code_challenge 是通过对 code_verifier 执行 SHA256 计算并转换为不带填充的 Base64-URL 编码值而派生的。
  2. 客户端应用程序应打开浏览器，并将用户发送到 授权端点 URL，并添加以下参数作为查询参数：
    • response_type：应设置为 code.
    • client_id：应设置为第三方应用程序在 Foundry 中注册时生成的 ID。
    • redirect_uri：这告诉授权服务器在用户批准请求后将用户重定向到哪里。如果未指定，将默认使用 Foundry 中第三方应用程序设置中的第一个重定向 URI 值。
    • scope：这定义了所请求的权限。公共 API 的作用域位于 《API 文档》中。添加 offline_access 作用域以获取刷新令牌。如果需要多个作用域，请使用空格作为分隔符将作用域连接起来。
    • state：这是应用程序生成的随机字符串，将原样传回应用程序。应用程序应检查返回的值是否与原始字符串匹配，以防止 CSRF 攻击。
    • code_challenge：如果客户端创建了 code_challenge，则应填充此参数。授权服务器将在内部将 code_challenge 参数与其生成的授权码相关联。
    • code_challenge_method：应设置为 S256.
  3. 当用户访问该 URL 时，授权服务器会向用户显示类似于以下的提示，然后用户可以选择批准应用程序的请求。

  1. 如果请求成功，授权服务器随后会将用户重定向到指定的重定向 URI，并附加以下参数作为查询参数：
    • code：这是授权服务器生成的授权码。
    • state：这是客户端在授权请求中传递的相同参数。客户端应检查其是否与原始 state 请求中发送的参数匹配。
  2. 然后，客户端应通过调用 令牌端点来将授权码换取访问令牌。应使用 application/x-www-form-urlencoded 格式在请求体中发送以下参数：
    • grant_type：应设置为 authorization_code.
    • code：从授权服务器收到的代码。
    • redirect_uri：用户代理将被重定向到的绝对 URI。
    • client_id：应设置为第三方应用程序在 Foundry 中注册时生成的 ID。
    • code_verifier：如果客户端生成了 code_verifier，则应在此请求中发送。授权服务器将验证该 code_verifier 是否与 code_challenge 之前请求中发送的相匹配。
  3. 授权服务器随后会返回一个访问令牌，客户端可使用该令牌访问所请求的资源（例如 REST API）。响应包含以下参数：
    • access_token：客户端可用于访问所请求资源的令牌。
    • token_type：所颁发令牌的类型。
    • expires_in：访问令牌的有效期（以秒为单位）。
    • refresh_token：仅当请求的范围包含 offline_access时才会返回。如果客户端希望在用户不在场授权请求的情况下刷新访问令牌，则应使用此项。更多信息请参见 刷新访问令牌.

客户端凭证授予

客户端凭证授予专为非交互式服务用户类型的工作流而设计，客户端执行的操作不与普通 Foundry 用户关联。客户端不代表普通 Foundry 用户行事。

相反，此授予类型会自动创建一个与客户端关联的 Foundry 服务用户，随后可为其授予访问 Foundry 资源的权限。通过此授予获取的令牌可用于代表所创建的服务用户访问资源。服务用户账户的用户名与应用的客户端 ID 相同。

默认情况下，服务账户无权访问任何资源。Foundry 管理员必须为该服务用户账户分配所需的角色和权限，客户端才能在 Foundry 中执行操作。

客户端凭证授予的工作方式如下：

  1. 客户端调用 令牌端点来将授权码换取访问令牌。应使用 application/x-www-form-urlencoded 格式在请求体中发送以下参数：
    • grant_type：应设置为 client_credentials.
    • client_id：应设置为第三方应用程序在 Foundry 中注册时生成的 ID。
    • client_secret：应设置为在 Foundry 中注册第三方应用程序时生成的客户端密钥。
  2. 授权服务器随后会返回以下内容：
    • access_token：客户端可用于访问所请求资源的令牌。
    • token_type：所颁发令牌的类型。
    • expires_in：访问令牌的有效期（以秒为单位）。
  3. 然后，客户端可以使用访问令牌来访问所请求的资源。

刷新访问令牌

访问令牌会在一段时间后过期，需要重新获取。任何在用户不在场时需要访问 Foundry API 的客户端都需要刷新令牌。

可以按照以下步骤完成：

  1. 客户端应按照 授权码授予 中概述的步骤操作，并指定 offline_access 作为所请求 scope parameter.
  2. 的一部分。客户端应保存返回的 refresh_token 在最终步骤中返回的 授权码授予.
  3. 如果访问令牌过期，客户端可以通过调用 令牌端点 端点并使用以下参数来刷新令牌：
    • grant_type：应设置为 refresh_token.
    • refresh_token：之前为给定用户获取的访问令牌。
    • client_id：应设置为第三方应用程序在 Foundry 中注册时生成的 ID。
    • client_secret：应设置为在 Foundry 中注册第三方应用程序时生成的客户端密钥。
  4. 授权服务器随后将返回以下内容：
    • access_token 客户端可用于访问所请求资源的令牌。
    • token_type：所颁发令牌的类型。
    • expires_in：访问令牌的有效期（以秒为单位）。
    • refresh_token：可用于刷新访问令牌的刷新令牌。Foundry 会在每次使用先前颁发的刷新令牌时轮换刷新令牌。请确保同时保存 access_token 和 refresh_token.

刷新令牌轮换

刷新令牌可用于获取新的访问令牌。Foundry 通过在每次使用先前颁发的刷新令牌时轮换刷新令牌，来降低与刷新令牌相关的风险。 重用检测保护机制确保：如果刷新令牌在首次使用一分钟后被重用，则基于该授权创建的所有访问令牌都将失效，并且需要重新进行授权流程。 允许一分钟的重复使用间隔，以应对可能出现的瞬时错误（如网络故障）。此外，超过 30 天未活动的刷新令牌将自动失效。这些保障措施通过确保不存在长期有效的刷新令牌，降低了令牌可能被泄露所带来的风险。

OAuth2 API 参考

以下端点可用于获取 OAuth2 令牌。

授权端点

GET /multipass/api/oauth2/authorize

授权端点，由客户端用于获取授权码。

查询参数

参数名称类型描述
response_type字符串此项必须设置为 code.
client_id字符串客户端的唯一标识符。
redirect_uri字符串用户代理将被重定向到的绝对 URI。它必须与在控制面板中指定的重定向 URI 之一匹配。您可以再次访问此 URI，方法是导航到 管理应用程序 screen.
scope字符串要请求的权限范围。公共 API 的范围位于 《API 文档》 中，并且应以空格分隔的字符串形式列出。
state字符串（可选）传递给服务器的任意字符串，服务器会将其原样传回客户端。这有助于防止跨站请求伪造。
code_challenge字符串（可选）由客户端生成的代码质询；与 带代码交换证明密钥（PKCE）的授权码许可
code_challenge_method字符串（可选）一起使用。此项应设置为 S256 if code_challenge 时使用。

重定向查询参数

如果请求成功，用户的浏览器将被重定向到第三方应用程序设置中指定的重定向 URI 或请求中传递的重定向 URI。重定向请求 URI 中将包含以下查询参数：

参数名称类型描述
code字符串生成的授权码。此代码将在 10 分钟后过期。
state字符串（可选）如果 state 参数出现在授权请求中，则此处将包含该确切值。

令牌端点

POST /multipass/api/oauth2/token

令牌端点由客户端用于通过出示其授权许可或刷新令牌来获取访问令牌。

标头参数

参数名称描述
Content-Type必须为 application/x-www-form-urlencoded.

请求正文参数

参数名称类型描述
grant_type字符串值必须为 authorization_code, refresh_token，或 client_credentials
code字符串（可选）从授权端点收到的授权码。当许可类型为 authorization_code
refresh_token字符串（可选）时，此项为必需。 grant_type is refresh_token。该值应为 refresh_token 即在获取授权码的原始请求中所获得的值。
redirect_uri字符串（可选/必需）用户代理将被重定向到的绝对 URI。此项为 必填 如果在授权请求中指定了重定向 URI。
scope字符串（可选）要请求的权限范围。公共 API 的范围位于 《API 文档》 中，并且应以空格分隔的字符串形式列出。
client_id字符串客户端的唯一标识符。
client_secret字符串（可选）应用程序注册时颁发的应用程序客户端密钥。当 grant_type is client_credentials.
code_verifier字符串（可选）用于 PKCE 请求的代码验证器，由应用程序在授权请求之前生成。

响应正文

响应 JSON 包含以下字段。

字段名称type描述
access_token字符串用于访问资源的凭据。
token_type字符串颁发的令牌类型。
expires_in字符串访问令牌的有效期（以秒为单位）。
refresh_token字符串（可选）用于获取新访问令牌的凭据。Foundry 会轮换 refresh_token 每次调用 refresh_token 许可时都会轮换。请务必同时保存 access_token 和 refresh_token.
