调试失败的流

在编写流式管道时，您可能会遇到流式处理失败的情况。本页面提供了调试失败流的建议工作流程，并介绍了 Foundry 中可用的工具，帮助您了解流失败的原因。

失败的类型

失败可以按失败类型进行分类，每种失败类型可能指向不同的根本原因。以下是一些最常见的失败类型及其可能发生的原因。

  • 立即失败： 流在启动后 5 分钟内失败。
  • 瞬时失败： 流运行一段时间后失败一次，随后成功重启并继续运行。
  • 持续失败： 流运行一段时间后，出现一系列立即失败，每次失败都在流重启后的 5-10 分钟内发生。

立即失败

快速失败的流通常存在用户编写的逻辑问题。例如，失败可能来自无效的类型转换、解析异常或其他阻止流式集群成功启动的问题。

如果之前成功的流现在失败了，请检查逻辑和上游流的任何更改，以找出潜在问题。

要确定这些问题的根本原因，请按照以下 检查流式集群日志 工作流程中的步骤操作。

瞬时失败

之前成功运行但在重启后再次运行的流出现失败，通常指向由网络中断引起的基础设施问题。中断通常由运行您 Foundry 实例的云服务提供商引起（例如 AWS、Azure 或 GCP 中断）。为您的流应用调度计划将使 Foundry 能够自动重新运行您的流，并从上次中断的地方继续处理。

持续失败

之前成功运行但现在在没有任何逻辑更改的情况下反复失败的流通常最难识别。但是，它们通常由以下两个因素之一引起：流的新输入数据阻止了流的进展（例如无效类型、损坏的数据等），或者存在持续的基础设施问题（AWS 中断等）。

要检查错误是否由管道中的逻辑引起，请按照以下 检查流式集群日志 工作流程中的步骤操作。

常见调试工作流程

下面，我们概述了一些可用于解决常见流式问题的工作流程。这些检查不需要按特定顺序进行。

检查流式集群日志

按照以下步骤操作： 检索流日志 并在日志中搜索任何异常、错误或“throwable”。这些日志通常会通过“ERROR”、“throwable”或“Exception”等关键字提供潜在潜在问题的描述。

检查管道逻辑

管道逻辑的更改通常会因用户编写的代码中的错误而导致中断。通常，上一步中获取的日志中的异常会指向导致问题的特定代码。如果是这样，您可以尝试回滚任何更改，看看是否能解决问题。

检查输入数据

有时，如果流式管道遇到意外数据，管道中的逻辑可能会抛出异常。这种行为的一个示例是：管道将两列相除，当除数为 0 or null时返回某个值。检查输入流末尾的记录，以查看数据是否以可能导致流式管道问题的方式发生了更改。如果发现数据已更改，请考虑添加过滤器或逻辑来清理数据或将其删除。

检查流详情

Foundry 会在流失败时检测常见异常，并将其显示在流详情页面中。请检查详情，看看那里是否出现任何错误。

有时，您可以在流日志中找到比详情页面更多的错误信息。我们建议同时检查这两个位置，以获取有关流失败的信息。

检索流日志

您在流处理过程中可能会遇到失败，需要访问构建的日志来确定原因。构建日志通常是确定不同类型流失败原因的最佳位置。

要检索流式处理作业的日志，请先导航到流详情页面 数据集预览.

接下来，找到您要查看的作业，然后点击 下载日志 .

选择您希望下载的日志是以最早的日志行在前还是最新的日志行在前。

流错误

作业反复失败并出现不可恢复的错误

Caused by: com.palantir.logsafe.exceptions.SafeIllegalStateException: Start transaction rid is not part of the current view.

此错误通常是由于输入数据集的新快照在流式处理中运行而导致的。

流式处理会在收到记录后立即将其发送到下游，这使得记录不可逆。创建新快照时，流式处理作业会忽略之前的事务，仅使用新事务。要丢弃旧记录以使用新快照，请运行手动重放。

此问题可通过执行管道的新部署来解决，该部署会通过选择 窗口中，选择管道交付中的数据处理起始时间： 中的 部署管道 向导来重放流。
