流

类似于 数据集，流（stream）是数据从进入 Foundry 到被下游系统处理这一过程中的数据表示。流是对一组行的封装，这些行由持久化的“热缓冲区”和由文件系统支持的“冷存储”共同存储。使用 Foundry 流的好处在于，它们提供与 Foundry 数据集相同的原语（分支、版本控制、权限管理、模式管理等），同时还提供数据的低延迟视图。

流本质上是表格式的，因此本质上是结构化的。它们以开源格式存储，例如 对字段名称进行清理，使其符合，以及关于列本身的元数据。这些元数据作为模式（schema）与流一起存储。

流存储

热缓冲区

当记录流入 Foundry 流时，它们会被存储在热缓冲区中，所有支持读取流的下游应用都可以以低延迟访问该热缓冲区。这个热缓冲区对于实现低延迟转换和可用性至关重要。它为数据摄取提供至少一次（at-least-once）语义，并为平台中的数据处理提供可选的恰好一次（exactly-once）语义。

冷缓冲区

Foundry 流中的所有数据每隔几分钟就会从热缓冲区传输到冷存储。我们将此过程称为“归档”，它使数据可以作为标准的 Foundry 数据集使用。这意味着任何 Foundry 应用都可以对流数据进行操作，即使它不实时处理来自热缓冲区的数据。 数据集视图 Foundry 流的数据集视图的行为与平台中的标准 Foundry 数据集完全相同。

流处理

从流中读取数据

启用了低延迟的 Foundry 产品能够读取数据的混合视图。通过同时从热存储层和冷存储层读取数据，产品可以提供完整的数据视图。该视图使产品既能访问仍处于热存储中的低延迟记录，也能访问已传输到冷存储的较旧数据。这样，Foundry 流既可以享受热存储的低延迟，又能享受冷存储的较低存储成本。

事务

与标准的 Foundry 数据集不同，流本身不具有固有的事务边界。相反，每一行都被视为独立的事务，并且状态是按行跟踪的。这允许以细粒度级别读取流，因此 Foundry 可以支持基于推送的转换，而无需批处理或轮询。

流类型

您可以根据每个流的吞吐量需求为其配置流类型。这些流类型设置适用于流如何将数据写入上述 热缓冲区 存储。只有在流指标表明流在写入热缓冲区存储时遇到瓶颈的情况下，您才需要修改流类型设置。延迟和吞吐量是相互权衡的，因此只有在检查流指标后才设置高吞吐量/压缩流类型。 我们支持以下流配置：

  1. 高吞吐量： 这最适合每秒发送大量数据的流。启用此流类型可能会以较高的吞吐量为代价引入一些非零的延迟。因此，在启用之前，您应该检查流指标。如果平均批次大小等于最大批次大小，或者作业因 Kafka 生产者批次过期而失败，您可能需要启用高吞吐量设置。
  2. 已压缩： 启用此配置后，在向热存储缓冲区生成数据时会对消息批次进行压缩。压缩有助于减小所发送数据的大小，从而降低网络和存储的使用量，但代价是压缩和解压缩会占用一些额外的 CPU 资源。我们仅建议在流中包含大量重复字符串且出现网络带宽不足症状（如非零延迟、吞吐量低于预期或记录丢失）时启用此流类型。

您可以在创建新流时设置流类型，位置在 对象 页面。您也可以在现有流的流设置中更新流类型。为此，请在 Foundry 中导航到您的流式数据集并选择 详情 在工具栏中。然后，前往 流设置。您可以在此处更改流类型并启用/禁用压缩。

分区

为了保持高吞吐量，Foundry 会将输入流拆分为多个分区以进行并行处理。创建流时，您可以通过吞吐量滑块控制我们创建的分区数量。尽管数据是分区的，但对流的所有读取和写入操作都像只有一个分区一样进行。此行为为 Foundry 流的使用者和生产者提供了设计透明性。

给定流的每个额外分区都会提高该流可处理的最大吞吐量。一个实用的经验法则是，每个分区可将吞吐量提高约 5mb/s。

  • BYTE

流式作业

所有流式作业在内部都表示为 作业图，它提供流式管道的可视化表示。在数据处理过程中，数据会根据有向边流经作业图，直到到达数据汇。

检查点

Foundry 流式处理通过将活动状态和当前处理位置存储在检查点中，在处理数据时提供容错能力。

检查点由数据源定期生成，并与来自源的数据一起流经作业图。 一旦检查点到达作业图末尾的所有数据汇，源在该检查点之前发出的所有行也必定已到达数据汇。

检查点允许流式作业从最新检查点的位置重新启动，而不是重新处理已读取的数据。检查点存储作业图中每个运算符的状态，以及流中最后处理的数据点。在您的流式作业的 作业详情 页面上，您可以实时查看流的最近几个检查点的状态、大小和持续时间。

流式处理一致性保证

Foundry 中的流式处理具有两种一致性保证： AT_LEAST_ONCE 和 EXACTLY_ONCE.

AT_LEAST_ONCE 语义

AT_LEAST_ONCE 语义保证消息至少会被下游传递一次，但在检查点失败或重试的情况下，消息可能会被传递多次。这意味着可能出现重复消息，使用方应用程序的设计应能够处理或容忍重复消息。

的优势 AT_LEAST_ONCE 语义

  • 确保不会丢失任何消息，提供高级别的消息持久性。
  • 与 EXACTLY_ONCE 语义相比，通常具有更低的延迟，因为消息的传递无需阻塞等待记录的簿记操作。

的缺点 AT_LEAST_ONCE 语义

  • 要求下游使用方应用程序能够处理重复消息。

EXACTLY_ONCE 语义

EXACTLY_ONCE 语义保证每条消息将被精确传递和处理一次，确保不会出现重复或缺失的消息。这是最强级别的消息传递保证，可以大大简化使用方应用程序的设计。

的优势 EXACTLY_ONCE 语义

  • 确保不会丢失任何消息，提供高级别的消息持久性。
  • 无需使用方应用程序处理重复消息或实现幂等处理。
  • 确保处理结果的一致性，因为每条消息都只被处理一次。

的缺点 EXACTLY_ONCE 语义

  • 通常比 AT_LEAST_ONCE 语义引入更高的延迟，因为需要额外的协调和跟踪来确保消息不会被重复。Foundry 流式处理通过检查点机制解决了这个问题。

延迟权衡

在 AT_LEAST_ONCE 和 EXACTLY_ONCE 语义之间进行选择时，通常需要在延迟和处理复杂性之间进行权衡。 AT_LEAST_ONCE 语义通常提供较低的延迟，因为它们不需要复杂的协调或跟踪机制，但它们将处理重复数据和保持一致性的更多责任交给了消费应用程序。当 EXACTLY_ONCE 启用时，记录只有在每个检查点完成后才会在下游可见（默认为两秒）。值得注意的是，记录仍以流式速度进行处理，只是在“最终确定”后才在下游显示。

另一方面， EXACTLY_ONCE 语义提供更强的保证，并通过确保每条消息仅被处理一次来简化消费应用程序的设计。然而，由于所需的额外开销，这种保证是以更高的延迟为代价的。

Foundry 中的流式数据源目前仅支持 AT_LEAST_ONCE 语义用于提取和导出。流式管道 do 同时支持 AT_LEAST_ONCE 和 EXACTLY_ONCE 语义，这可以在 构建设置 管道构建器（Pipeline Builder）的部分中进行配置。
