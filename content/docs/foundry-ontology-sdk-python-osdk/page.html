Python OSDK

This page provides generic documentation for the Python OSDK, based on an Example Restaurant object type. You can generate documentation specific to your Ontology in Developer Console.

The examples on this page target Python OSDK 2.x. If you are upgrading from 1.x, see the Python OSDK migration guide for the syntax changes, including the required .object_type accessor. Version-specific documentation is also available in-platform in the Developer Console at /workspace/developer-console/.

Prerequisites

Every example on this page assumes a client variable that is already connected to your Ontology, and a generated object class such as ExampleRestaurant. How you create the client depends on where your code runs.

Access object RID

By default, the object RID is not included as an accessible attribute on loaded objects. To access an object's RID programmatically, pass include_rid=True to your loading method:

Copied!
1
2
3
# Load a single object with RID access
result = client.ontology.objects.ExampleRestaurant.get("primaryKey", include_rid=True)
object_rid = result.rid

The include_rid=True parameter can be used with other loading methods as well:

    print(restaurant.rid)

# Page with RID access

Load pages of example restaurants

Load a list of objects of a requested page size, after a given page token if present. page_size sets the size of one page, not a limit on the total number of objects.

A single page is often the right choice when the data is only needed as a sample or for display, since a user interface can only show a limited number of objects at once. Load the page that fits the view and fetch more as the user scrolls, rather than loading every object up front.

This endpoint uses the underlying object syncing technology of the object type. If the Example Restaurant object type is backed by Object Storage v2, there is no request limit. If it is backed by Object Storage v1 (Phonograph), there is a limit of 10,000 results: requesting more than 10,000 Example Restaurant objects returns an ObjectsExceededLimit error.

Parameters:

  • pageSize integer (optional): The size of the page to request, up to a maximum of 10,000. If not provided, the request loads up to 10,000 Example Restaurant objects. Subsequent pages use the pageSize of the initial page.
  • pageToken string (optional): If provided, requests a page with a size less than or equal to the pageSize of the first requested page.
  • properties list (optional): The properties to load, as ExampleRestaurant.object_type.<property> references. If omitted, the API uses its default property selection.

page() does not request its own snapshot, but a snapshot configured for the function run still applies. When no snapshot applies, changes between pages may cause duplicates or omissions.

Load all example restaurants

iterate() returns an iterator that fetches successive pages from a consistent snapshot until every matching object has been returned. Iterating over an object set directly, as in for restaurant in client.ontology.objects.ExampleRestaurant, behaves the same way.

To fetch a fixed number of objects as a list, use take(n) instead. take(n) returns at most n objects and silently drops the rest, so use it only when a partial result is correct, such as a sample or a list for display.

Before loading every object, consider whether you need to:

  • Compute a count, sum, or other summary: Use aggregations instead, which run in the backend without loading objects.
  • Show a sample or a list in a user interface: Use take(n) or load a single page instead.
  • Read only some properties: Pass properties to load only those properties.
  • Hold every object in memory at once: Process each object inside the loop as it arrives instead of wrapping the iterator in list(...), unless your code needs all objects at the same time.

Fetch options

Python OSDK loading methods accept parameters that control which properties and object metadata are returned. The table below lists the synchronous methods; the corresponding asynchronous methods accept the same parameters.

ParameterSupported methodsDescription
propertiesget(), page(), iterate(), take()Return only the listed generated property references.
apply_modifiersget(), page(), iterate(), take()Request a different returned representation for specific properties, such as a value selected by a configured reducer.
include_ridget(), page(), iterate(), take()Populate the returned object's rid attribute. The default value is False.
load_property_securitiesget(), page(), iterate(), take()Load property-level security metadata for the returned object. The default value is False.
load_ontology_defined_derived_propertiesget(), page(), iterate(), take()When properties is omitted, set to True to also return ontology-defined derived properties. Has no effect when properties is provided.
page_sizepage()Set the maximum number of objects in each page.
page_tokenpage()Resume paging from a previous page iterator's next_page_token.
num_itemstake()Set the maximum number of objects to return.

Select properties

Pass generated property references to the properties parameter to restrict which properties are returned. When properties is omitted or empty, the OSDK returns the object type's native properties, except vector properties. Ontology-defined derived properties are not returned by default and must be selected explicitly. The following example returns only restaurant_id and restaurant_name:

Copied!
1
2
3
4
5

result = client.ontology.objects.ExampleRestaurant.page(
    page_size=30,
    properties=[
        ExampleRestaurant.object_type.restaurant_id,
        ExampleRestaurant.object_type.restaurant_name,
    ],
)

Selecting an array property returns its complete, unreduced value, even when a property reducer is configured in Ontology Manager. The same behavior applies to native and ontology-defined derived properties.

Properties are loaded when the request runs, whether or not your code reads them afterward. On object types with large text, array, or other wide properties, loading unneeded properties can be much slower and use more network bandwidth than loading only the ones you read. Pass properties with the properties your code reads to load only those properties. The API also returns the primary-key property, even when it is not selected.

Select ontology-defined derived properties

To read an ontology-defined derived property, include it in properties together with every other property your code reads. For example, assume Example Restaurant has an ontology-defined derived property menu_item_count that counts linked Menu Item objects:

    100,
    properties=[
        ExampleRestaurant.object_type.restaurant_name,
        ExampleRestaurant.object_type.menu_item_count,
    ],
)

Ontology-defined derived properties are computed at query time by traversing links or aggregating across linked objects. Selecting them explicitly means that a derived property added to the object type later does not add latency or compute cost to your existing requests.

If you cannot list the properties you need yet, set load_ontology_defined_derived_properties=True on a request that omits properties. The response then includes ontology-defined derived properties along with native properties:

Copied!
1
2
3
4
result = client.ontology.objects.ExampleRestaurant.take(
    100,
    load_ontology_defined_derived_properties=True,
)

load_ontology_defined_derived_properties=True adds the cost of computing every ontology-defined derived property to each request. It has no effect when properties is provided, because only the selected properties are returned.

Objects that a function receives as parameters are loaded by the platform rather than by your request. Review properties loaded for object parameters.

Apply property modifiers

Beta

Property modifiers in the Python OSDK are in the beta phase of development. Functionality may change during active development.

Each generated object type with supported property configurations includes an ApplyModifiers class. Pass an instance of that class to apply_modifiers. The generated class restricts each property to the modifiers supported by its Ontology configuration:

  • "applyReducers": For an array property with a configured reducer, return the selected array element instead of the full array.
  • "extractMainValue": For a struct property with a configured main value, return only the main value field or fields.
  • "applyReducersAndExtractMainValue": For a struct array configured with both features, select one struct with the reducer, then return its main value field or fields.

If you also pass properties, include every property named in apply_modifiers. Otherwise, the OSDK raises a ValueError.

For example, assume an Equipment object type has a nullable maintenance_history property of type Date array, with a reducer configured to select the most recent date. Selecting the property without apply_modifiers returns the complete array:

In this example, equipment.modified_properties.maintenance_history contains one date selected by the reducer rather than the full array. Applying a modifier does not change the stored or derived property data. Omit the modifier and read the ordinary property attribute when you need the complete value.

Load ordered results

Load an ordered list of Example Restaurant objects by specifying a sort direction for specific properties. When calling via APIs, you specify sorting criteria in the fields array. When calling via SDKs, you can chain multiple order_by calls together. The sort order for strings is case-sensitive, meaning that numbers come before uppercase letters, which come before lowercase letters. For example, Cat comes before bat.

Parameters:

  • field string: The property you want to sort by. With the SDK, reference it as ExampleRestaurant.object_type.<property>.
  • direction asc | desc: The direction you want to sort in, either ascending or descending. With the SDK, use the asc() and desc() methods on the property accessor.

Example query:

Copied!
1
2
3
4
5
6
7

from ontology_sdk.ontology.objects import ExampleRestaurant

ordered_restaurants = (
    client.ontology.objects.ExampleRestaurant
    .where(~ExampleRestaurant.object_type.restaurant_name.is_null())
    .order_by(ExampleRestaurant.object_type.restaurant_name.asc())
    .iterate(properties=[ExampleRestaurant.object_type.restaurant_name])
)

In this example, ~ negates the filter that follows it, so ~ExampleRestaurant.object_type.restaurant_name.is_null() matches only the objects that have a restaurant name value. For the other Boolean operators available on filters, see Not filter, And filter, and Or filter.

Paging consistency and snapshots

When you load objects across more than one page, the data can change between requests. The following table describes whether each loading method requests its own snapshot. A snapshot configured for the function run still applies, regardless of the loading method:

MethodRequests its own snapshotBehavior when data changes between pages
iterate(), or iterating over an object set directlyYesEvery page reflects the same point in time, so each object is returned exactly once. If the snapshot cannot be maintained, the request fails. These guarantees do not apply to object types with streaming input datasources.
page() and take()NoWhen no snapshot applies, changes between pages may cause duplicates or omissions.

This table describes the synchronous methods. The asynchronous methods, which are in beta, may behave differently; for example, async_take() reads from a snapshot in some SDK versions.

A traversal can fail with PagingInconsistencyDetected if the service detects an inconsistency between pages. A long-running traversal can also fail if its snapshot expires. Consistent snapshots are not guaranteed for streaming datasources. iterate() cannot be configured to skip the snapshot.

If a full traversal of a frequently updated object type fails with a snapshot error, choose the approach whose trade-offs your workflow can tolerate:

  • Aggregate instead: If you need a count, sum, or other summary, use aggregations, which do not page through objects.
  • Traverse faster: Use properties to load fewer properties, and narrow the object set with a filter, so the traversal finishes before the snapshot expires.
  • Filter to a stable subset: For append-only data, use a fixed time cutoff to exclude recent objects, provided that late arrivals or backfills cannot add objects before the cutoff during the traversal.
  • Page without requesting a snapshot: Iterate over the pages returned by page() instead of calling iterate(). page() does not request its own snapshot, but a snapshot configured for the function run still applies. When no snapshot applies, changes between pages may cause duplicates or omissions.

The following example fetches successive pages without requesting its own snapshot and skips objects whose primary keys have already been processed:

from ontology_sdk.ontology.objects import ExampleRestaurant

seen = set()
for page in client.ontology.objects.ExampleRestaurant.page(
    page_size=1000,
    properties=[ExampleRestaurant.object_type.restaurant_name],
):
    for restaurant in page:
        primary_key = restaurant.get_primary_key()
        if primary_key not in seen:
            seen.add(primary_key)
            # Process restaurant

When no snapshot applies, changes between pages may cause objects to be missed. Deduplication does not recover those objects.

Snapshots in functions and actions

When the OSDK is used inside a Python function, the function's own consistent snapshot configuration also applies. When the OSDK client carries a snapshot for the function run, it applies regardless of the loading method.

  • Snapshot isolation actions: Function-backed actions configured with snapshot isolation use the action's snapshot for the function run. These actions require snapshots to remain enabled.
  • Read committed actions: With read committed isolation, the action does not supply a snapshot for the run, but iterate() still requests one for its own traversal.
  • Expired snapshots: Snapshots have a limited lifetime. If a long-running function fails because its snapshot expired, reassess whether the workflow requires a consistent view across reads. If it does not, you can disable snapshots in the function configuration. If it does, keep snapshots enabled and ensure the reads complete before the snapshot expires. Disabling snapshots does not prevent paging inconsistency errors from iterate(), which requests its own snapshot regardless of the function configuration.

Links

Link traversal takes one of two forms, depending on whether you start from a single object instance or from an object set. The examples below assume Example Restaurant has a many-to-one city link and a one-to-many reviews link. Substitute the link API names from your own Ontology.

On an object instance, each link is a method named after the link API name in snake case. A one-to-one or many-to-one link returns the linked object, or None. A one-to-many or many-to-many link returns an object set, so every object set method is available on it.

Example query:

Copied!
1
2
3

restaurant = client.ontology.objects.ExampleRestaurant.get("primaryKey")

# A many-to-one link returns the linked object, or None.
city = restaurant.city()

# A one-to-many link returns an object set.
for review in restaurant.reviews().iterate():
    ...

On an object set, each link generates a search_around_<link_name>() method that returns an object set of the linked type, so traversals can be chained and combined with filters and aggregations.

Example query:

Copied!
1
reviews = client.ontology.objects.ExampleRestaurant.search_around_reviews()

If the link is only known at runtime, search_around() takes the link API name as a string and dispatches to the corresponding typed method. Prefer the typed search_around_<link_name>() methods where the link is known; search_around() raises a RuntimeError if the name is not a valid link for the object type.

Example query:

Copied!
1
linked = client.ontology.objects.ExampleRestaurant.search_around("reviews")

Filtering

The types of filtering you can perform depend on the types of the properties on a given object type. You can also combine these filters with Boolean expressions to construct more complex filters.

This endpoint uses the underlying object syncing technology of the object type. If the Example Restaurant object type is backed by Object Storage v2, there is no request limit. If it is backed by Object Storage v1 (Phonograph), there is a limit of 10,000 results: requesting more than 10,000 Example Restaurant objects returns an ObjectsExceededLimit error.

Parameters:

  • where SearchQuery (optional): Filter on a particular property. The possible operations depend on the type of the property.
  • orderBy OrderByQuery (optional): Order the results based on a particular property. If using the SDK, you can chain the .where call with an .order_by call to achieve the same result.
  • pageSize integer (optional): The size of the page to request, up to a maximum of 10,000. If not provided, the request loads up to 10,000 Example Restaurant objects. Subsequent pages use the pageSize of the initial page. If using the SDK, chain the .where call with the .page method and pass the page_size keyword argument.
  • pageToken string (optional): If provided, requests a page with a size less than or equal to the pageSize of the first requested page. If using the SDK, chain the .where call with the .page method and pass the page_token keyword argument.

Example query:

Types of search filters (SearchQuery)

The following filters are available, depending on the type of the property you filter on:

  • Contains any terms
  • Contains all terms
  • Contains all terms in order
  • Range comparison
  • Equal to
  • Null check
  • Not filter
  • And filter
  • Or filter

Contains any terms

Only applies to String properties. Returns Example Restaurant objects where restaurantName contains any of the whitespace-separated words (case-insensitive) in any order in the provided value.

Parameters:

  • field string: Name of the property to use (for example, restaurantName).
  • value string: Whitespace-separated set of words to match on. For example, foo bar matches bar baz but not baz qux.
  • fuzzy boolean: Allows approximate matching in search queries.

Group by linked object properties

For a many-to-one relationship, use with_properties to materialize the linked object's derived property. Then, group by the materialized property.

The following example sums the number of reviews for Example Restaurants, grouped by a property on a linked object. Replace linked_object and linked_property with the link and property names from your own Ontology:

Derived properties are a beta feature. To use with_properties and the derived accessor, run your code inside the AllowBetaFeatures context described in Beta features.

Copied!
1

19
from ontology_sdk.ontology.objects import ExampleRestaurant

restaurants = client.ontology.objects.ExampleRestaurant

result = (
    restaurants.with_properties(
        linked_property=
            ExampleRestaurant.object_type.derived.linked_object().linked_property.get()
    )
    .where(
        ~ExampleRestaurant.object_type.derived.property("linked_property").is_null()
    )
    .group_by(
        ExampleRestaurant.object_type.derived.property("linked_property").exact()
    )
    .aggregate({"sum": ExampleRestaurant.object_type.number_of_reviews.sum()})
    .compute()
    .to_dict()
)

Key steps:

  1. Use with_properties to add a property by pulling it from a linked object via the derived accessor.
  2. Filter out rows where the property is null.
  3. Use the property as the grouping key in group_by, then aggregate.
