Build a to-do application

In this tutorial, we will build a release checklist application with Pilot. It will allow you to organize a list of tasks and track their completion.

Pilot will help you build the release checklist, inspect its proposed Ontology, and test the generated application. The tutorial creates a new object type and actions, so use a project and Ontology where you can create resources.

The generated to-do application lets you add tasks, mark them complete or incomplete, filter the list, and delete tasks. Follow the application walkthrough first, or go to reuse an existing task model or build the checklist as a widget if you would like to jump to specific sections.

Generated layouts and names can vary. Compare the controls and results with the screenshots as you proceed. Orange outlines identify the controls or status indicators used in the adjacent steps.

Before creating the application, allow Pilot to propose the new entities:

  1. Select Modify Ontology permissions, beneath Ontology.
  2. Enable Allow Pilot to create new object types and Allow Pilot to create new action types.

Inspect the proposed data model

In the workspace, select Ontology above the application preview. This example needs:

  • A Release Checklist Task object type with ID, Title, and Completed properties
  • An action to add a task
  • An action to set a task's completion status
  • An action to delete a task

Check that the entities are marked Proposed by Pilot. They still need implementation in Foundry before the application can use them with production data.

Select the task object type to open its data preview. Confirm that the three requested sample tasks are present. If Pilot reused existing entities or generated a different model, describe the discrepancy in the chat and inspect the result again before deployment.

Test with seed data

Select Preview and confirm that Notional data is selected. The screenshot shows where to find the data-source control, task input, and filters.

Test the generated controls:

  1. Enter Verify the published checklist and select Add task. Confirm that the task appears and the remaining count increases by one.
  2. Mark the task complete. Confirm that its checkbox is selected and the remaining count decreases by one.
  3. Select Completed. Confirm that the completed task appears.
  4. Select Active. Confirm that the completed task is absent.
  5. Return to All and reload the preview. Confirm that the task and its completed state remain.
  6. Mark the task incomplete. Confirm that the remaining count increases.
  7. Delete this test task. Confirm that it disappears and the original sample tasks remain.

If a control fails, describe the actual behavior and expected result to Pilot, then repeat the check after the fix. These checks validate local preview behavior; production permissions and the proposed Ontology definitions still need validation.

Implement the Ontology on a branch

Select Deploy in the upper-right corner of Pilot. This opens the deployment checklist on the left of the preview. The example below shows a configured application; your checklist will reflect your progress.

Under Implement Ontology entities, new definitions can appear as Not found on Main. Create a deployment branch for them:

  1. Select Create branch. Pilot may open the Create deployment branch dialog when you first enter Deploy.
  2. Enter a branch name such as Release checklist tutorial.
  3. Check the Location and Application entities. This example proposes one object type and three action types.
  4. When the form is ready, select Create branch.

Wait for implementation and object indexing. While indexing is in progress, actions can fail and data can be missing. If branch creation is unavailable, inspect the explanation; Global Branching must be enabled.

After implementation, check the selected Branch on the left and Production data on branch above the preview.

The branch preview uses records on the selected Foundry branch. The local seed tasks are separate, so the new task object type can initially have no records.

To validate the application, add a release task such as Validate the deployment branch, repeat the completion, filter, reload, and delete checks, and remove the test task when finished. Then select View branch to open Global Branching.

Review and merge the Ontology proposal

In Global Branching:

  1. Confirm that the branch contains the task object type and three actions.
  2. Select Create proposal in the upper-right corner.
  3. Enter a Proposal name and Proposal description, then select Create.

Wait for the task object type to finish indexing, then review the proposal before merging:

  1. Open Changes and confirm that the proposal creates the intended task object type and actions without modifying unrelated definitions.
  2. Return to Overview to inspect the resource checks and required approvals. The example below shows four resources with passed checks and automatic approvals; your policies can differ.
  3. Select Merge proposal, review the confirmation, and confirm Merge proposal. Wait for the proposal to show Merged.

Return to Pilot and select Switch to Main. Confirm that Implement Ontology entities reports All entities up to date on Main.

Review the generated actions' submission criteria before sharing the application. The default criteria allow only the user who created the action with Pilot to submit it. Configure the intended access in Ontology Manager.

Configure the application and run checks

In the deployment checklist, open Configure application and subdomain and select Configure application.

  1. Enter a Developer Console application name, such as Release checklist tutorial.
  2. Select the Organization. The Subdomain field appears after this selection.
  3. Enter an available subdomain. Wait for the availability check, then select Create application.

Confirm that the application card appears and reports Application scope up to date. If it displays Domain pending approval, contact your enrollment administrator to approve the request before hosting the website. See Approve the subdomain request.

Next, open Pass all CI checks.

  1. Select Generate deployment files to enable checks when prompted, or Update files if the deployment files are outdated.
  2. Wait for SUCCEEDED on the commit you intend to release.
  3. If a check fails, open its build output, ask Pilot to fix the reported problem, and wait for checks on the updated commit to pass.

Release and verify the hosted application

After successful checks, select Tag and release at the bottom of the deployment checklist:

  1. Review the selected branch or commit and the latest released tag.
  2. Choose Patch, Minor, Major, or Custom.
  3. Check Releasing at the bottom of the dialog, then confirm Tag and release. The example selects patch version 0.0.2; your version numbers can differ.

Wait for the release build to succeed. Creating a tag does not approve the domain or confirm that the website is available.

Complete domain approval and follow the application release steps. Open the hosted application after deployment succeeds and repeat the seven task checks against a synthetic test task. Verify the data source and your permissions before executing actions against real records.

Reuse an existing task model

To build against existing definitions, open the Pilot welcome screen:

  1. Set Type to OSDK application and choose your theme, save location, and Ontology.
  2. Select Add context > Add object types, search for your task object type, and open its details. Choose Select, then Confirm selection.
  3. Select Add context > Add action types. Filter by the affected task object type, select its add, completion, and delete actions, then choose Confirm selection.
  4. In Modify Ontology permissions, keep creation and modification prohibited.
  5. Describe the checklist interactions and explicitly ask Pilot to use only the selected existing definitions.

Before selecting Create application, check the four attachment tags beneath the prompt and the message Pilot cannot make changes to the Ontology.

After generation, inspect Ontology. This example should show Existing 4 and Proposed 0, with Do not allow modifications on the object type and all three actions.

Repeat the seed-data checks. Then select Production data, wait for the preview to reload, and test the deployed actions using a synthetic task. Verify completion, filters, and persistence after reloading, then delete the test task. The production list is separate from the seed records.

Select Deploy. If the existing definitions are unchanged, confirm All entities up to date on Main. If Create deployment branch opens even though those definitions are up to date, select Cancel.

Continue with application configuration, CI, and release as described above.

Embed and test the released widget

Create a Workshop module in your project. See Getting started with Workshop if this is your first module.

In the Workshop editor, select Add widget. In the widget picker, choose Foundry & custom apps, then Custom widget.

Configure the widget in the right-hand panel:

  1. Under Widget setup, choose Select, find your published widget set, and confirm the selection.
  2. Choose the checklist under Widget.
  3. Select its published Version. This example uses 0.0.3.

Next, check the layout:

  1. Open Display and set Row height to Flex for this example. The generated widget fills its container; Auto (max) gave it zero height.
  2. Arrange the surrounding sections. This example uses one section with Column width set to Flex.
  3. Confirm that the checklist and its controls are visible. See Auto sizing if your widget uses a different layout.

Select Save and publish, then View. If widget Dev mode is active, select Pause before testing the release, or Stop to end development mode. Selecting a published version alone does not disable your personal development override.

Repeat the seven task checks in the published Workshop module, including a full-page reload. Delete the synthetic task when finished. This example defines no parameters or events; if you add them, configure and test their Workshop bindings separately.

Configure a heading in Workshop

The new-entity widget generated for this example includes a string parameter named Heading. Your generated widget may expose different parameters; inspect its configuration first.

In the Workshop module, select the released widget:

  1. Under Widget setup > Parameters > Heading, choose Select string variable.
  2. Choose New string variable > Static, then open the created variable.
  3. Set Default value to Workshop release tasks and name the variable Checklist heading.
  4. Confirm that the widget displays the configured heading.

Set the widget and section dimensions as described above. Select Save and publish, then View, and pause Dev mode if it is active.

Repeat all seven task checks. Confirm that both the heading and task completion persist after a full-page reload, then delete the synthetic task. This widget defines no events; event bindings require separate configuration and testing.
