管理商店权限

Marketplace 商店可以是 Foundry 部署本地的，也可以是远程的。本地 Marketplace 商店可以位于 Project 或文件夹中，并将继承其所在 Project 或文件夹的权限。远程商店在一个 Foundry 部署上创建，然后在其他部署上提供。远程商店的权限 在 Control Panel 中配置.

查看权限

要在 DevOps 或 Marketplace 中查看本地 Marketplace 商店，您需要拥有 marketplace:read-local-marketplace 操作，该操作通常随 Viewer 组织概览 Viewer 远程商店的权限在 Control Panel 中配置。

安装产品权限

要从本地或远程商店安装产品，您必须能够查看该商店并拥有 marketplace:install-from-local-marketplace 操作，该操作通常随 Viewer 组织概览

对于作为此安装输入而选择的每个资源，您必须拥有 marketplace:use-resource-as-input 操作，该操作通常也随 Viewer 组织概览

此外，您可以安装的位置（通常是 Space 和本体论）需要 marketplace:install-in 操作，该操作通常随 Editor 组织概览

每次安装时，Marketplace 要么在所选的 Space 中创建一个新 Project，要么安装到现有 Project 中。为此，您需要 marketplace:install-in 对 Space、所选 Project 或文件夹的操作。此权限通常随 Editor 组织概览

您还必须对商店上存在的至少一个组织标记拥有访问权限。但是，访问包含该商店的 Project 本身就已经要求对其中一个组织标记拥有访问权限。

创建商店权限

要创建本地商店，您必须拥有 marketplace:create-local-marketplace 在 Project 或文件夹中的操作，该操作通常随 Editor 组织概览

目前，远程商店只能由 Palantir 创建。

编辑产品权限

要在本地商店中创建或编辑产品，您必须拥有 marketplace:create-block, marketplace:edit-block-set日 marketplace:upload-attachment 操作，这些操作通常会授予 Editor 组织概览

远程商店在 DevOps 中不可编辑。

数据集打包权限

打包包含底层数据的资源——最常见的是 数据集 作为输出添加——会读取该资源的文件，以便在安装时重新创建其内容。读取这些文件需要 foundry-data-proxy:get-files (和）操作，此外还需要 编辑权限 来构建产品。如果没有此操作，将数据集作为输出打包时会失败并出现 foundry-data-proxy:get-files 权限错误，即使草稿的其余部分可能打包成功。只有 包含静态数据 打包选项会读取数据集的文件。如果您不需要产品中数据集的行，请选择 仅包含数据集定义 or 包含转换或管道 ；这两个选项都不需要 和 操作。第二个选项以数据集的关联生产者命名，因此它可能改为读取 包含同步, 包含受限视图，或类似内容，具体取决于数据集的构建方式。

默认情况下， foundry-data-proxy:get-files 操作会授予 Viewer, Editor日 Owner 角色，因此打包数据集不需要额外的权限。此操作仅在配置为 限制下载.

限制下载的部署通常会自定义其 角色集 以移除下载操作，包括 foundry-data-proxy:get-files，从默认角色中移除，并通过专用角色来授予——例如， Exporter 角色。在此类部署上， Owner 角色本身不包含下载操作，因此如果所有者未被授予启用下载的角色，则无法将数据集作为输出打包。授予该角色（或以其他方式授予 foundry-data-proxy:get-files 对数据集的权限）即可解决该错误。

这种分离是有意为之的。将导出原始数据的能力与资源所有权解耦，符合最小权限原则，并支持集中化的 下载控制。因此， Owner 角色不一定包含对限制下载的注册（enrollment）的导出或下载权限。

导出产品权限

要从本地商店导出产品，用户必须具有 marketplace:export-block-set 操作权限，该权限通常授予 Owner 角色。目前，用户无法从远程商店导出产品。

导入产品权限

要向本地商店导入产品，用户必须具有 marketplace:import-blockset-with-provenance 操作权限，该权限通常授予 Owner 角色。目前，用户无法向远程商店导入产品。

编辑商店标签权限

要编辑本地商店上的标签，用户必须具有 marketplace:edit-local-marketplace 操作权限，该权限通常授予 Editor 角色。目前，用户无法编辑远程商店上的标签。

应用于产品创建的组织标记

Marketplace 产品中打包的所有资源都带有一个或多个组织标记，这些标记通常继承自资源所在的项目。 同样，Marketplace 商店也带有其所在项目的组织标记。

您可能无权查看资源所属的所有组织。

如果产品资源与 Marketplace 商店的组织标记不同，您必须获得 Expand access 这些组织标记的权限。 例如，假设某个 Workshop 应用程序属于 组织 A，而该商店同时属于 组织 A 和 组织 B。 Expand access 权限， 组织 A 是成功将此 Workshop 应用程序打包到 Marketplace 商店中所必需的，因为您正在将内容从 组织 A to 组织 B.

如果产品资源具有 Marketplace 商店所不具备的组织标记，您必须获得 Remove 这些组织标记的权限。 例如，假设某个 Workshop 应用程序同时属于 组织 A 和 组织 B，而该商店属于 唯一 to 组织 A。该 Remove 权限， 组织 B 是成功将此 Workshop 应用程序打包到 Marketplace 商店中所必需的，因为您正在移除（或 取消标记） 组织 B.

应用于产品安装的组织标记

通常，Marketplace 商店必须包含您要安装到的空间（Space）的所有相关组织标记。这意味着本地 Marketplace 商店必须位于一个包含您要安装到的空间的所有相关组织标记的项目中。

例如，如果某个 Marketplace 商店仅具有 组织 A 的 标记，而您想将该商店的产品安装到同时包含 组织 A 和 组织 B的空间中，您必须获得 Expand access 权限，用于 组织 A 权限，因为在安装时您正在将内容从 组织 A to 组织 B.

在安装过程中，您也可以选择仅将 组织 A 的 标记应用于您的产品安装；这样可以避免扩展访问权限的需要。

或者，您可以将组织 B 的标记添加到商店中，这将允许更多用户从该商店安装产品。例如，如果某个 Marketplace 商店同时具有组织 A 和组织 B 的标记，而您想将该商店的产品安装到仅包含组织 A 的空间中，则无需额外权限。但是，仅有权访问组织 B 的用户也将能够从此商店安装产品。

要求批准新产品版本

可以将 Marketplace 商店配置为在发布新产品版本之前需要批准。启用后，审批人必须审查并批准每个草稿，然后才能最终确定新版本。

审批用户必须与草稿作者不同，并且必须具有 marketplace:finalize-block-set 对商店的操作权限。此操作默认授予商店所有者和编辑者。要自定义允许的审批人列表，请使用自定义角色集。

产品创建和安装权限

多组织场景

在 Foundry 中，您必须是资源的 Owner 才能将资源从一个项目移动到另一个项目，但如果移动会扩大移动后可以访问该资源的组织集合，您还需要对所涉及的标记拥有额外的权限。

例如，假设某个资源位于 项目 A中，该项目属于 组织 A，而您想将该资源移动到 项目 B，该项目同时属于 组织 A 和 组织 B。您必须对该 Expand access 标记拥有 组织 A 标记的权限。 Expand access 是一项提升权限，允许您将资源（属于 组织 A ，在我们的示例中）的访问范围扩展到其他组织（例如 组织 B).

如果资源带有指示 PII 或其他敏感数据的标记，您必须拥有 Remove Marking 权限才能移除该特定标记。

如果 项目 A 中的资源被打包为存储在 项目 B中的产品，然后安装到 项目 C中，您必须同时对 Expand 组织标记和 Remove 可能存在的任何额外标记拥有足够的权限，因为这些标记会在产品移动过程中被移除。

关于权限结构的指导

为避免在产品创建、安装及后续过程中出现阻碍，我们建议采取以下做法：

  • 资源最初应位于一个属于单一组织的项目中，该组织专用于打包资源，且不带任何额外标记。
    • 将资源打包为产品的用户必须对该单一组织拥有上述列出的足够权限，该权限可以授予更广泛的用户群体。
  • 任何预期从商店安装产品的组织都应能够访问 Marketplace 商店项目所在的空间。您可以为此目的创建一个专用空间，并纳入应有权访问该商店的各个组织。
    • 安装产品的用户不需要对组织标记拥有额外权限即可执行安装。

这种权限结构使任何阻碍都发生在打包阶段，让您能够在安装过程开始之前进行必要的更改。
