数据集

A 数据集 是数据从进入 Foundry 到被映射到 本体论 中的最基本的数据表示形式。从根本上说，数据集是围绕一组 文件 的封装，这些文件存储在 支撑文件系统 中。使用 Foundry 数据集的好处在于，它们为权限管理、模式（schema）管理、版本控制以及随时间推移的更新提供了集成支持。我们将在本文档的其余部分中探讨这些功能背后的概念。

在 Foundry 的数据集成层中，数据集可以存储和表示所有类型的数据，无论是结构化、非结构化还是半结构化数据：

  • 结构化 （表格）数据由包含开源格式（例如 Parquet ↗）表格数据的文件以及有关数据集中列的元数据组成。这些元数据作为 模式.
  • Unstructured 数据由没有关联模式的文件组成；示例包括非表格文件（如客户支持电子邮件），以及媒体文件（如图像、视频或 PDF 文档）。Foundry 提供两种存储非结构化数据的方式：作为无模式数据集或作为 媒体集，后者是一种针对媒体工作流优化的独立资源类型。如果您要在 Foundry 中 手动上传非结构化数据 ，可以选择 作为媒体集上传 or 上传到无模式的数据集.
  • 半结构化 数据是非表格形式的，但仍可包含提供一定程度组织性的标签或元数据；示例包括 XML 或 JSON 等文件格式。半结构化数据没有专用的上传选项；您可以将这些文件上传到无模式的数据集，然后在下游数据转换中 推断表格模式 ，以提升性能和使用便利性。

事务

数据集的设计初衷是随时间推移而变化。当您在 Foundry 中打开一个数据集并看到行和列时，您实际上看到的是最新的 数据集视图.

作为最终用户，您通常会使用 构建来修改数据集，它们允许您根据指定的逻辑更新数据集的内容。然而，在幕后，数据集是随着时间推移通过 事务来更新的，事务表示对数据集内文件的修改。事务有一个简单的生命周期：

  • 当事务 启动后，它处于 OPEN 状态。在此状态下，可以在数据集的支撑文件系统中打开和写入文件。
  • 事务可以被 提交，这会使其进入 COMMITTED 状态，并且所有已写入的文件现在都会出现在最新的数据集视图中。
  • 事务可以被 中止，这会使其进入 ABORTED 状态。事务期间写入的任何文件都将被忽略。

如果您是一名软件工程师，您可能熟悉 Git。数据集事务是 Foundry 支持数据版本控制的基础，有时也被称为“数据界的 Git”。事务类似于 Git 中的 提交（commit） ：对数据集内容的一次原子性更改。

事务类型

在事务中修改数据集文件的方式取决于事务类型。共有四种可能的事务类型： SNAPSHOT, APPEND, UPDATE日 DELETE.

SNAPSHOT

A SNAPSHOT 事务会用一组全新的文件替换数据集的当前视图。

SNAPSHOT 事务是最简单的事务类型，并且是 批处理管道.

APPEND

An APPEND 事务会向当前数据集视图添加新文件。

An APPEND 事务无法修改当前数据集视图中的现有文件。如果打开一个 APPEND 事务并覆盖了现有文件，那么尝试提交该事务将会失败。

APPEND 事务是以下功能的基础： 增量管道。通过仅将新数据同步到 Foundry，并仅在整个管道中处理这些新数据，可以对大型数据集的变更进行高性能的端到端处理。但是，构建和维护增量管道会带来额外的复杂性。 了解更多关于增量管道的信息。

UPDATE

An UPDATE 事务（例如 APPEND）会向数据集视图添加新文件，但也可能覆盖现有文件的内容。

An UPDATE 覆盖现有文件内容的事务将破坏以下对象的仅追加（append-only）要求： 增量管道。如果数据集收到此类 UPDATE 事务，下游管道将无法增量处理数据，而必须回退到 SNAPSHOT （批处理）处理。

An UPDATE 仅添加新文件而不覆盖任何现有文件的事务不会影响增量性。除非别无选择，否则不要在 UPDATE 事务中覆盖现有文件。更多详细信息，请参阅 增量转换和仅追加输入.

配置 基于文件的同步 以从外部系统摄取数据时，您选择的事务类型决定了数据在管道中的流动方式。三种常见的摄取模式为：

  • 批量镜像（SNAPSHOT): 每次同步运行都会摄取所有文件并提交一个 SNAPSHOT 事务。这是最简单的模式，适用于完整文件集足够小、可以在每次运行时重新加载的情况。
  • 增量镜像（APPEND): 每次同步运行仅摄取新文件并提交一个 APPEND 事务。此模式支持端到端增量管道，是在文件仅被添加而不被修改时推荐使用的方法。
  • 增量镜像（UPDATE): 每次同步运行会摄取新增和修改的文件并提交一个 UPDATE 事务。仅在外部系统会修改现有文件时才使用此模式，因为它会阻止下游的增量处理。

有关这些模式的详细配置指导（包括筛选器设置和相互冲突的选项），请参阅 基于文件的同步.

DELETE

A DELETE 事务会移除当前数据集视图中的文件。

提交一个 DELETE 事务并不会从底层支撑文件系统中删除文件——它只是从数据集视图中移除该文件的引用。

在实践中， DELETE 事务主要用于实现数据保留工作流。通过根据保留策略（通常基于文件的存在时间）删除数据集上的文件，可以将数据从 Foundry 中移除，这既有助于降低存储成本，也有助于满足数据治理要求。

事务类型示例

假设数据集某个分支的事务历史如下（从最早的开始）：

  1. SNAPSHOT 包含文件 A and B
  2. APPEND 添加文件 C
  3. UPDATE 修改文件 A 使其内容不同， A'
  4. DELETE 移除文件 B

此时，当前数据集视图将包含 A' 和 C。如果我们添加第五个 SNAPSHOT 事务，其中包含文件 D，则当前数据集视图将仅包含 D （因为 SNAPSHOT 事务会开启新视图），而前四个事务将位于旧视图中。

保留

由于 DELETE 事务实际上并不会从 支撑文件系统中移除旧数据，您可以使用 保留策略 来移除不再需要的事务中的数据。

数据集视图

数据集视图表示数据集在某个时间点某个分支上的有效文件内容。历史视图类似于数据集的历史版本。要计算视图中包含哪些文件：

  1. 从一个空的文件集合开始。
  2. 给定时间点的视图始于该时间点之前最新的 SNAPSHOT 事务。如果不存在 SNAPSHOT 事务，则改为采用该数据集最早的事务。
  3. 对于视图中的第一个事务以及随后的每个事务，执行以下操作：
    • 折线图 SNAPSHOT （仅可能是第一个事务）或 APPEND 事务，将该事务的所有文件添加到集合中。
    • 对于 UPDATE 事务，将该事务的所有文件添加到集合中并替换现有文件。
    • 折线图 DELETE 事务，从集合中移除该事务中的所有文件。

最终得到的文件集合即构成一个数据集视图。

由于新视图仅在 SNAPSHOT 事务处开始，数据集历史中的视图数量等于其包含的 SNAPSHOT 事务的数量。如果数据集仅包含 SNAPSHOT 事务，这意味着视图数量等于事务数量。对于增量数据集， APPEND, UPDATE日 DELETE 事务会扩展当前视图而不是开始一个新视图，因此视图数量仍然等于 SNAPSHOT 事务的数量。

一个视图可能包含来自多个分支的事务。例如，给定一个以 SNAPSHOT 开头的增量数据集，以及 APPEND 分支上的某些 master 事务，如果该分支上的后续事务也是 APPEND （或者严格来说是 不 SNAPSHOT）事务，那么这些事务将构成该分支上数据集视图的开头。

模式（Schema）

模式是 数据集视图 上的元数据，用于定义视图中的文件应如何解释。这包括如何解析视图中的文件，以及文件中的列或字段的命名和类型。Foundry 中最常见的模式是 表格模式——它们描述数据集中的列，包括列的名称和 字段类型.

无法保证数据集中的文件实际符合指定的模式。例如，可以将 Parquet 模式应用于包含 CSV 文件的数据集。在这种情况下，尝试读取数据集内容的客户端应用程序会遇到错误，原因是某些文件不符合该模式。

由于模式存储在 数据集视图上，模式可以随时间变化。这很有用，因为数据集的内容可能会在结构上随时间变化。例如，新事务可能会为表格数据集引入新列或更改字段的类型。

在 Foundry 中，你可以在 数据集预览 应用程序中查看任何数据集的模式，方法是导航到 详情 选项卡并选择 模式.

支持的字段类型

以下是数据集可用的字段类型列表：

  • BOOLEAN
  • BYTE
  • SHORT
  • INTEGER
  • LONG
  • FLOAT
  • DOUBLE
  • DECIMAL
  • STRING
  • MAP
  • ARRAY
  • STRUCT
  • BINARY
  • DATE
  • TIMESTAMP

某些字段类型需要额外的参数：

  • DECIMAL requires precision and scale。如果你不确定这些参数应设置什么值，一个不错的默认值是 precision: 38 and scale: 18. 38 是可能的最高精度值。
  • MAP requires mapKeyType and mapValueType，它们都是字段类型。
  • ARRAY requires arraySubType，一种字段类型。
  • STRUCT requires subSchemas，字段类型的列表。

有关上述这些字段类型的更多信息（包括描述和示例），请参阅 Spark 数据类型文档 ↗.

模式选项

在监听器设置向导的 模式 已应用标签 详情 选项卡中，你可以在模式元数据底部的 options 块中为 CSV 文件添加可选的解析配置。请参阅 CSV 解析 文档以了解更多信息。

文件格式

模式包含有关数据集中文件底层存储格式的信息。三种最广泛使用的格式是：

  • Parquet
  • Avro
  • 文本

文本文件格式可用于表示多种文件类型，包括各种 CSV 格式或 JSON 文件。有关如何解析文本的额外信息存储在一个名为以下字段的 schema 字段中 customMetadata.

实际上，对于 JSON 或 XML 等非表格格式，我们建议将文件存储在非结构化（无 schema）数据集中，并在下游数据转换中应用 schema，具体说明见 schema 推断文档.

支撑文件系统

数据集中跟踪的文件并非存储在 Foundry 本身。相反，系统会维护文件在 Foundry 中的 逻辑路径 与其 物理路径 之间的映射，物理路径位于支撑文件系统中。Foundry 的支撑文件系统由以下内容中的基目录指定： Hadoop FileSystem ↗。这可以是自托管的 HDFS 集群，但更常见的做法是使用云存储提供商（如 Amazon S3）进行配置。所有数据集文件都存储在支撑文件系统基目录之下的文件夹层级结构中。
