计划与约束

计划

计划是 Apollo 将指令从 Hub 传递给托管环境中的 代理 的方式。每个计划都是一个工作单元，例如配置变更或发布升级，只有当所有相关 约束 都得到满足时，才会下发给代理执行。

Apollo 支持以下计划类型：

  • 安装新实体。
  • 修改托管实体的 配置覆盖 。
  • 修改现有 Apollo 托管实体的版本和配置覆盖。请参阅 关于编排引擎如何决定下发哪个计划的一般准则 ，以进一步了解 Apollo 为何始终将相关配置覆盖与发布升级同步应用。
  • 卸载实体。
  • 创建、编辑和删除 机密。

计划和约束会显示在环境或实体的 活动 标签页中。您还可以查看代理针对特定环境或实体执行的计划历史，其中每个计划都有开始时间、结束时间和状态。

Apollo 采用的基于计划的范式与其他“控制循环”系统不同。Apollo 不会在无人察觉的情况下直接在后台执行操作，而是生成一个计划；一旦所有约束条件都得到满足，该计划就会被发送给代理执行。这种基于计划的范式为用户提供了更高的透明度和可见性，使其能够了解环境中正在进行的、即将进行的以及以往所做的变更。

计划生命周期

编排引擎

每个 Hub 环境中的编排引擎：

  1. 持续评估每个 Spoke 的所有可能计划。
  2. 评估与每个可能计划相关的所有约束条件。
  3. 将约束条件已得到满足的计划下发给该 Spoke 的代理执行。

关于编排引擎如何决定下发哪个计划的一般性准则

  • 用于将已撤回版本下线或执行 break-glass 命令的计划优先于其他类型的计划。
  • Apollo 旨在将实体的状态提升到最新可能的状态。例如，Apollo 会发布一个计划，将实体升级到通过所有相关约束的最新版本，并将实体的配置更改为与该版本匹配的最新配置覆盖。这样可以实现升级与相应配置的同步进行。有关特定版本配置覆盖的更多信息，请参阅相关文档： 管理实体。

当因没有需要执行的工作而无法发布计划时，Apollo 会将其推理显示在实体的 活动 标签页中。这有助于您了解为什么没有执行任何工作，以及在必要时可以采取哪些操作来解除工作阻塞。

代理

每个 Spoke 环境中的代理：

  1. 持续轮询编排引擎以获取新计划，并回报环境及其实体的状态。
  2. 针对每个已发布的计划，在 Spoke 中执行所需的更改
  3. 将计划成功或失败的结果报告回编排引擎。

查看计划的状态

您可以在 计划 实体或环境主页的选项卡。选择一个计划，即可查看其详细信息、元数据、计划中每个任务的状态以及计划规范。

对于失败的计划，您可以查看 Agent 的原始计划输出，其中说明了失败原因，以便您解决问题。

计划失败、抑制和回滚

当计划失败时，Apollo 会自动创建实体级别的 抑制窗口，这将阻止对该实体进行后续工作。Apollo 将继续为环境中的其他实体发布新计划。如果某个环境中处于自动抑制窗口下的实体数量超过 配置的阈值，Apollo 将自动创建环境级别的抑制窗口，因为这可能表明存在系统范围内的问题。环境级别的抑制将阻止对环境中的所有实体进行后续工作。一旦处于抑制窗口下的实体数量恢复到阈值以下，Apollo 将自动移除环境级别的抑制。

在一个计划失败并应用了自动抑制窗口后，尽管存在自动抑制窗口，Apollo 仍将允许“回滚”计划恢复旧的世界状态。但如果抑制窗口是由人工创建的，则此规则不适用——Apollo 将始终遵循这些抑制窗口。

什么会导致 Apollo 使某个实体的计划失效并为其考虑新计划

Apollo 将为某个 实体 请求新的计划，当发生以下任一情况时：

  • 观察到相关实体的依赖者或依赖项的 报告状态 发生了变化。
  • 观察到该实体的 实体设置 发生了变化。例如，该实体正在跟踪的发布通道已被更改。
  • 观察到该实体的 配置覆盖 或 密钥 发生了变化。
  • 有产品发布被添加到实体所配置的发布通道中。
  • 实体所配置的发布通道中的一项产品发布被撤回。
  • 当现有计划因约束条件被阻塞超过四小时阈值时。

由于环境报告状态的变化而导致的计划失效，基于环境中实体的依赖关系图。修改一个实体时，会为该实体本身及其在依赖关系图中的相邻项（即其依赖项和依赖它的项）创建新的计划请求。Apollo 会为一个实体的依赖项和依赖它的项请求计划，因为一个实体的版本变更可能会改变其依赖项和依赖它的项能够升级到的版本，这是由于 产品依赖约束。

请考虑以下某个环境中实体的示例依赖关系图：

服务 A 依赖于服务 B，而服务 B 又依赖于服务 C。目前，假设这些服务声明的依赖项仅限于此。

对服务 C 实体的修改将为服务 C 和服务 B 请求新的计划，因为服务 B 声明了对服务 C 的依赖。

对服务 B 实体的修改将为服务 C（作为依赖项）、服务 B 实体本身以及服务 A（作为依赖它的实体）请求一个新的计划。

对服务 A 实体的修改将为服务 B（作为依赖项）以及服务 A 本身请求一个新的计划。

约束

约束是计划在由代理执行之前必须满足的条件。Apollo 会评估约束，以确保代理仅在安全且可接受的情况下才执行计划。

Apollo 的约束求解引擎将原本需要人工在执行升级前完成的验证工作自动化；例如，在 GitOps 模型中，这类验证会在代码审查时进行。

约束会显示在实体的 活动 标签页中，帮助您了解计划为何被阻止启动，例如在升级未进行时。约束还提供了足够的信息，让您可以采取操作来解除计划的阻止状态，使其能够由代理执行。在 break-the-glass 紧急场景中，如需绕过约束，可随时发出 命令。

下面列出了一些约束示例。

维护窗口约束

环境编辑者 可以定义时间窗口，指定在哪些时间段内允许 Apollo 对其环境中的实体进行更改，即安装、升级或更改配置。这些称为 环境和实体维护窗口。产品编辑者可以为其产品定义维护窗口，以确定 Apollo 何时可以 将发布提升到发布渠道。这些称为 产品维护窗口。维护窗口约束会阻止计划在所定义的时间窗口之外进行更改。

在评估是否可以执行某个计划时，Apollo 会计算 已解析的维护窗口 ，具体取决于实体以及正在执行的操作类型（停机或不停机）。如果当前时间不在已解析的维护窗口内，Apollo 将阻止执行该计划，直到下一个维护窗口。您可以等待下一个维护窗口，或者 编辑日程 （前提是您是环境编辑者）。您还可以申请批准一项临时的 维护窗口覆盖 ，以允许计划在正常维护窗口之外执行。

Apollo 如何为实体计算 已解析的维护窗口

  • 如果 产品维护窗口覆盖 未设置（这是默认行为）：
    • 如果操作无需停机，则使用产品维护窗口。
    • 如果操作需要停机，则使用产品维护窗口与实体停机窗口的交集。
  • 如果 产品维护窗口覆盖 已设置，或者未为该产品定义产品维护窗口：
    • 如果操作无需停机，则使用实体的不停机窗口
    • 如果操作需要停机，则使用实体的停机窗口。

默认情况下，Apollo 将忽略 无停机维护窗口 在将已撤回的版本下线时。对于需要停机的下线操作，情况并非如此，这类操作会遵守维护窗口。要覆盖此行为，请将 require-maintenance-windows-for-no-downtime-recalled-release-roll-offs 字段设置为 true （在环境设置中）。

产品依赖约束可确保 Apollo 仅在满足以下条件时才执行计划：

  1. 拟定的计划不会违反这些依赖项中的任何一项。
  2. 所有依赖实体均满足其与目标产品版本之间的版本约束。

定义产品依赖项后，您便可以安全地在多个环境中部署软件，而无需手动验证每次升级，也无需与其他团队协调发布。

要覆盖某个实体的产品依赖约束，您可以在 实体高级设置中添加要忽略的依赖项。当被忽略的依赖项所提供的某些功能并非必需、因此也不会部署时，此选项非常有用。只有在您了解被忽略的依赖项将对产品产生的确切影响时，才应使用此选项。

抑制窗口约束

抑制窗口会阻止 Apollo 在配置的时间内发布计划,并且会取代维护窗口。可以为单个实体或整个环境设置抑制窗口。可以通过三种方式创建抑制窗口:

  • 由用户手动创建。环境编辑者可以为整个环境或特定实体设置抑制窗口,而环境操作员或实体操作员只能在其拥有相应角色的实体上设置抑制窗口。
  • 当某个实体的计划失败时自动创建。当 Apollo 尝试回滚失败的计划时,将忽略这些抑制窗口。
  • 在 版本晋升期间自动创建。这是为了避免新版本不断取代以前的版本、导致晋升无法达到目标浸泡时间的情况。这些抑制窗口在撤下 已召回的版本时将被忽略。

在执行手动变更之前,应始终对实体应用手动抑制窗口。否则,Apollo 可能会发布与这些变更冲突的计划,并可能导致意外行为。

创建抑制窗口时,如果选择了 取消活动计划 选项,则会取消该抑制窗口范围内的活动计划。Apollo 还提供了专用的 取消活动计划 针对环境、实体或单个计划的操作。由于 Apollo 可以立即重新下发已取消的计划，此操作会提示您创建一个短暂的抑制窗口。请详细了解如何 配置抑制窗口 和 取消处于活动状态的计划。

制品缺失约束

要执行安装或升级计划， Apollo 代理 必须能够从分配给该环境的制品注册表中拉取发布制品。如果缺少任何制品，Apollo 会阻止该计划。

每个产品发布都会在 清单中声明其所需的制品。在计算计划时，Apollo 会：

  1. 根据产品发布的清单确定其需要哪些制品。
  2. 从分配给该环境的 制品注册表 中为每个制品选择合适的注册表。
  3. 探测每个注册表以检查制品是否存在。对于预计无需 Hub 访问 的注册表，Apollo 会跳过此检查。

如果缺少任何制品，Apollo 会阻止该计划，直到制品可用为止。要解除对该计划的阻止，请将缺失的制品发布到制品注册表。

约束视图将制品分为三类：

  • 不可用：Apollo 在所选注册表中未能找到的制品。其中包括注册表请求失败的制品。
  • 可用：存在且可拉取的制品。
  • 未检查：Apollo 无法验证的制品，原因是没有注册表与该制品的 URI 匹配，或 Apollo Hub 无法访问该注册表。这些制品不会阻塞计划。

如果 Apollo 报告某个制品不可用，但该制品存在于注册表中，请验证 Apollo Hub 是否能够连接到 Artifact Registry。如果 Apollo Hub 无法访问该注册表，请将 Hub access 设置（位于 Artifact Registry 上）更改为 Hub access not expected ，以便 Apollo 跳过针对该注册表的制品可用性检查。
