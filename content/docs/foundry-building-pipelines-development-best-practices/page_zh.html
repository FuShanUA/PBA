开发最佳实践

本指南旨在为正在开发转换的管道开发者提供指导。 通用 建议对项目经理或平台管理员也可能有所帮助，因为这些建议侧重于整洁管道的更高层次原则。

通用最佳实践

管道开发即软件开发

通用软件开发中的许多最佳实践同样适用于定义构成数据管道的转换。以下是一些体现这种方法的常见实践：

  • 降低认知负担： 尽可能减少不必要的思考。如果需要使用复杂或不直观的函数或 API 调用，请确保有清晰的文档。
  • 善待未来的自己： 管道是您数据企业的基石。在规划和实施时要着眼长远、志存高远。
  • 不要重复自己（DRY）： 重复的代码或概念需要更多的维护工作，并会导致隐蔽的错误。相反，应在各个层面频繁重构，包括构建和发布您自己的库或包以供跨仓库使用，从而确保最小程度的重复。
  • 避免技术债务： 长期思维的必然结果是：面对项目特定需求的截止日期时，技术债务很容易累积，但终将带来麻烦。
  • 约定很重要： 设定一个先例并坚持下去；这可以降低认知负担，并有助于提高 Code Repositories 之间的可读性。例如，列和数据集名称通常按以下方式编写： snake_case - 遵循这一约定意味着其他想要引用您出色数据集的人都知道它是 awesome_dataset，而不是 AwesomeDataset or Awesome_Dataset.
  • 少即是多： 由许多较小单元组成的系统比由少数大型单元组成的系统更易于维护和推理；因此应倾向于：
    • 范围紧密的 Foundry 项目
    • 链接在一起的较小转换
    • 简短的函数——以及转换中的辅助函数

反模式

  • 覆盖 vs. 删除： 与其他文件系统不同，Foundry 资源和数据集连接到其他工件，而不仅仅是文件本身。因此，如果您正在迭代管道或数据，只有当您从根本上希望删除该类型的数据时才应执行删除。例如，如果您向数据集写入了包含错误数据的事务，请不要删除该数据集；而是写入一个新 SNAPSHOT 事务来覆盖前一个事务。尝试删除数据集可能比在同一位置创建新数据集带来更多挑战。
  • 不要引入循环依赖： 如果您希望将转换的数据集输出用作其他转换的输入，应确保代码中没有引入任何循环依赖。Foundry 的构建编排层会尝试阻止您在当前分支上配置任何循环，并且如果检测到循环，您的 Code Repository 分支将无法通过检查

Foundry 会在正在开发的分支上检查循环依赖，但在编写代码时不会跨所有分支运行检查，例如存在仅存在于 master 分支上的本体论回写数据集的情况。当尝试将功能分支与包含循环依赖的分支合并时，如果在其他分支上检测到循环依赖，Foundry 仍将无法通过检查。

项目文件夹结构

请参阅 推荐的项目结构 以了解通过多个项目组织整个数据流的总体模型。

最佳实践

  • 在项目级别管理权限： 如果您预计需要在项目内进一步划分权限，请考虑是否应将项目进一步分解为更小的部分。 了解有关应用和管理权限的概念与实践的更多信息。
  • 保持项目范围紧密： 避免“功能蔓延”，以及在项目中添加关联性不强的资源或特定于用例的逻辑
  • 使用有意义的文件夹名称： 请记住，您设计的 Project 不仅供团队日常迭代和开发使用，也供团队外部人员使用。请考虑至少应有一个 /Documentation 文件夹和一个 /Output 文件夹。不同的用例或工作流 Project 需要更具体的名称，但请始终记住，您的 Project 结构和命名方案是访问者的路标。

反模式

  • 在您的主文件夹中工作： 您的个人文件夹不适合用于开发——其访问控制非常严格，且难以共享。请考虑在您的 Project 中创建一个 /scratch 文件夹用于实验或临时性工作，而不是在您的主文件夹中构建。

命名

最佳实践

  • 遵循惯例： 为列、数据集、仓库、文件和其他资源命名时，请遵循您所在组织的通用模式或您的 Foundry 实例的惯例。
  • 选择描述性名称： 花些时间想出两三个词的名称，让读者能够了解所命名资源的用途或内容。考虑将名称中具有区分度的部分放在前面；当名称较长在下拉菜单中被截断时，这会有所帮助，并且便于在浏览代码库或文件列表时立即区分不同的引用。避免使用缩写。

反模式

  • 含义不清的名称： 选择仅递增数字的名称（即 dataset1, dataset2等）或单个字母的名称，会使您的代码更难阅读和重构，也会让新开发人员更难接手您的工作。
  • 仅通过路径区分的名称： 在某些情况下这是可以接受的，例如当您有 /raw/my_important_dataset 用户偏好 /clean/my_important_dataset时，但在许多情况下，这种命名模式可能会在仅突出显示数据集名称本身的视图中造成混淆。请记住，数据溯源会被跟踪且易于查看，因此您无需将这种“状态”嵌入到数据集的名称中。

数据类型

最佳实践

显式转换列类型： 如果您在 数据源 Project中工作，请在 raw → clean 转换中显式转换列类型，即使数据连接的 schema 推断已选择了正确的值。这有助于在源系统的列类型发生变化，或在同步期间某个无效值导致错误推断时，捕获破坏性变更。

嵌入图模板时,可以使用 Workshop 变量对其进行参数化。这样您就可以创建根据用户输入或工作流中的其他数据动态更新的可视化效果。

对“仅时间”数据类型使用 Timestamps： Spark 没有适用于字段值如“10:59:00”的仅时间数据类型。为了利用 Spark timestamp 类型自带的时间函数，请将值转换为秒，然后加上 -2208988800 再将其转换为 timestamp，以将其置于第 0 年。或者，将其保留为字符串，让用户根据需要自行解析。

反模式

  • 将所有数值字段转换为数值数据类型： 考虑一个飞机 ID 列，例如 545, 972, 314。将这些转换为整数列可能很诱人（毕竟，它们看起来像整数，甚至在源系统中可能就是整数）。然而，这存在显著的缺点：

    • 如果前导零是有意义的，例如 123 和 0123 都是应加以区分的合法 ID，这将导致错误。
    • 这些 ID 在 UI 中的格式可能不理想（例如 545.0, 1,234，右对齐）。
    • 如果 ID 过长，可能会遇到 MAX_INT 问题。
    • 数值函数永远不会应用于这些值（例如，您绝不会将两个飞机 ID 相加）。 经验法则是：只有对数值字段执行算术运算是合理的情况下，才将其转换为数值数据类型，否则应将其转换为字符串。

  • 在不同时区中存储时间戳： — Spark 时间戳与时区无关。它们在内部以 UTC（又称 Zulu、GMT）存储；时区的显示应由前端完成。

    • 如果您出于显示目的需要特定时区，请使用 PySpark 的 from_unixtime() 函数 ↗ 以将字符串存储在相应的时区中。
    • 如果给定数据源中的时间戳位于 UTC 以外的时区，请使用 PySpark 的 to_utc_timestamp() 函数 ↗ 将其规范化为 UTC。

代码注释

反模式

  • 在提交中注释掉代码： 在进行更改时，很容易想要注释掉旧代码并将其留作参考，或者以备日后需要回退。您可以在迭代过程中使用注释，但不要提交包含被注释掉语句的代码。这样做会积累冗余内容并降低可读性。旧代码很容易在之前的提交中找到。

  • 包含作者信息和日期的注释： 这些信息会在提交/git 仓库中自动跟踪。手动注释它们容易导致内容未及时更新，并产生冗余。

  • 过度冗长的注释： 注释应分享 决策背后的理由 而不是解释逻辑本身。努力编写“自文档化”的代码；如果一组语句难以理解，那就是需要重构和简化的明确信号。

仓库实践

最佳实践

  • 保护 master 分支： 如果您与团队一起开发，或者只是在开发一个长期的个人项目，请保护 master 分支并实践 GitFlow ↗ 或您偏好的开发工作流。关键概念只是确保进入 master 的代码经过审查和测试。

  • 编写提交信息： 提交信息是仓库中所有活动的日志。请花时间为您的更改编写有用的描述：

    • 代码审查者可以查看您的提交，以了解您的工作流程以及做了哪些更改。
    • 如果您想回退某个更改，如果能够一眼找到您要查找的提交，就会容易得多。
    • 构建按钮会自动生成带有时间戳的提交信息；请避免使用它。先点击提交，编写提交信息，然后再点击构建。

  • 清理您的分支： 在长期存在的仓库中，分支可能会不断累积。如果某个分支的开发已被放弃，尤其是当某个分支已合并到另一个分支时，请通过 删除该分支来保持整洁。这有助于清晰了解哪些分支正在积极开发。

  • 升级您的仓库： 当收到提示时，请按照步骤升级您仓库中的语言包。此过程将向包含升级内容的活跃分支发起一个拉取请求。您可以随时在升级分支上运行管道构建，以确保版本升级不会影响您的代码。不过，及时跟进这些升级通常可以确保您不会遇到在其他地方已出现并在升级版本中修复的边缘情况。

  • 实践代码审查： 在与队友协作开发转换时，请在拉取请求过程中实施一些代码审查实践。Palantir 的 Code Review Best Practices ↗ 博客文章涵盖了许多概念，这些概念同样适用于审查数据转换代码。

嵌入图模板时,可以使用 Workshop 变量对其进行参数化。这样您就可以创建根据用户输入或工作流中的其他数据动态更新的可视化效果。

在仓库之间共享代码： Foundry 中的仓库基于项目级别运行，这有多种原因，但通常存在可以在管道之间重用的逻辑，这有以下几个优点：

  • 遵循 DRY 原则的通用代码重用。

  • 避免数据基础的不同区域之间出现分叉/不一致的逻辑。

  • 有些管道理想情况下会使用基础管道，但它们有更严格的 SLA 或性能要求。在这种情况下，解决方案通常是共享逻辑而不共享转换/数据集，这样关键管道就可以依赖预过滤的数据集、更少的转换、不同的构建计划等。

  • Code Repositories 是实现这一目标的绝佳方式。例如，在使用 Python 转换时，库可以将自身发布到 Conda 频道，并允许其他仓库使用它们。请参阅相关文档： 共享 Python 库.

  • 共享仓库的另一个优势是 语义化版本控制。共享仓库可以用版本号（例如 1.0.0、1.0.1、2.0.0）标记其提交，而使用方库可以选择如何获取新版本。例如，某个仓库可以选择获取最新版本（上面的 2.0.0），也可以只获取特定版本（比如 1.0.1），并推迟获取新版本，直到手动决定更新。当管道非常关键且管道所有者希望有机会选择加入/批准对共享仓库的更改时，后一种做法尤其有价值。

  • 发布： 同样地，如果团队希望为管道制定明确的发布计划，一种选择（可避免使用 staging 实例或长期存在的 develop 分支）是将逻辑提取到共享仓库的函数中，并使用语义化版本让使用方仓库保持在主要版本上，例如 1.0.0、2.0.0，甚至是 .0.0。这样，开发人员可以继续迭代逻辑并标记中间版本，而不会使其在 master 上生效。此外，在使用方仓库的分支上，只要开发人员不在发布日期之前将其合并到 master，就始终可以获取中间版本。

单元测试

单元测试是提高和维护代码质量的一种流行方式。在 单元测试 ↗中，软件的小型离散组件（“单元”）以单独、独立和自动化的方式进行测试。

  • Python 单元测试： 您可以启用 pytest 单元测试，作为 Python 转换仓库 CI 检查的一部分，具体请按照 Python 单元测试说明.

  • Java 单元测试： 配置 Java 转换单元测试的步骤可以在 Java 单元测试文档中找到.

最佳实践

单元测试应该：

  • 一次只测试一段逻辑；
  • 保持轻量（请参阅特定语言的说明，了解如何减少内存使用的技巧）；
  • 不依赖额外输入即可运行；以及
  • 不相互依赖或相互调用。

运行状况检查

最佳实践

检查您的数据健康状况： 通常，一旦管道的一部分完成，很容易设置好计划后就不再关注。然而，即使您的逻辑是正确的，传入的数据也可能以影响构建的方式发生变化，导致性能变慢、数据规模增加，甚至构建彻底失败。对数据集大小和构建时间配置基本检查，即使您不配置警报，也能随时间提供这些关键指标的视图，以便您观察例如数据集大小的增长率或数据集的平均构建时间。阅读有关具体 健康检查 可用性以及如何配置它们的更多信息。

嵌入图模板时,可以使用 Workshop 变量对其进行参数化。这样您就可以创建根据用户输入或工作流中的其他数据动态更新的可视化效果。

扩展健康检查： 在大多数情况下，默认的健康检查配置应该已经足够。但如果您需要更大的灵活性，可以考虑添加一个或多个派生 health check 数据集到您的管道中。该数据集的转换可以执行任意逻辑来判断其输入数据集（即您正在验证的数据集）的有效性，然后输出格式化的数据，以便简单的健康检查（例如 Allowed Value）能够报告该数据集是否有效。

为该数据集设置一个调度计划，使其在输入数据集发生更新时进行构建，这样您就拥有了一套额外的全面健康检查。
