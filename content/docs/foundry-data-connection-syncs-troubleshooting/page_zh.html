PKIX 和 SSL 异常

有关证书和 TLS 的故障排除，包括 PKIX 和 SSLHandshakeException 错误，请参阅 证书和 TLS.

如果您的同步失败并出现错误 Response 421 received. Server closed connection，这表明您可能正在使用不受支持的 SSL 协议/端口组合进行连接。例如，通过端口 991 的隐式 FTPS，这是一个过时且不受支持的标准。在这种情况下，首选方法是通过端口 21 使用显式 SSL。

出口代理问题

FTP 同步

如果您的同步是 FTP/S 同步，请确保您没有使用出口代理负载均衡器。FTP 是一种有状态协议，因此如果连续的请求不是来自同一 IP，使用负载均衡器可能会导致同步失败。

由于负载均衡的特性，故障将是不确定性的；即使负载均衡代理已就位，同步和预览有时也可能会成功。

此外，HTTP 代理不支持 FTP 和 FTPS 的主动模式传输。主动模式要求 FTP 服务器回连到客户端，而这无法通过 HTTP 代理实现。在 FTP/FTPS 连接中使用 HTTP 代理时，仅支持被动模式传输。请确保在通过 HTTP 代理连接时，您的 FTP 源配置为使用被动模式。

增量 JDBC 同步问题

要查看针对您的源系统运行的确切查询，请参阅 _data-ingestion.log.

如果您的同步是增量同步，请确保您已提供一个单调递增的列（例如时间戳或 id）以及该列的初始值。

选择增量列后，您需要确保已将 ? 运算符添加到 SQL 同步配置页面中的查询（ ? 会被替换为“增量”值，并且只能使用一个 ? ）。例如， SELECT * FROM table WHERE id > ?.

缺失行和行未更新

如果您认为同步的数据集中缺少某些行，或者之前同步的行未被正确更新，请检查以下内容：

  • 如果向现有数据集添加了新行，并且新行在增量列中存储的值小于当前游标，则这些新行将不会被同步。
    • 例如，如果您使用 ID 作为单调递增列，并且上次同步中最后同步的 ID 值为 10，然后您添加了一行 ID 5，那么该值为 ID 5 的行将不会被同步。
  • 如果由于上述原因某些行未被同步，您仍可以通过以下方式同步这些行：
    • 执行快照同步而非增量同步，或
    • 调整查询以针对缺失的行，并将其作为一次性任务运行。

重复行

如果您认为现有行正在被重新同步，请检查以下内容：

  • 如果源数据库中的现有行被更新，并且这些行的增量列发生更改，使其大于当前游标，则这些行将被重新同步，从而导致重复。例如，如果您用作增量列的列是一个时间戳，表示行的插入时间或最后更新时间，而您在数据集同步之间更新了某一行，则该更新后的行将被重新同步。
    • 如果由于上述原因存在重复行，您可以通过以下方式将其删除：
      • 执行快照同步而非增量同步，或
      • 使用下游转换来删除重复行。
  • 如果您选择的增量列的数据类型是时间戳且使用亚毫秒精度，则重复行将被重新同步。这是因为目前增量 JDBC 同步仅将时间戳值序列化到毫秒精度，并且增量值随后总是向下舍入到最接近的毫秒。因此，具有微秒和/或纳秒精度的行将始终被重新同步，因为与当前（向下舍入的）增量值的比较结果始终为“正”。
  • 如果由于上述原因存在重复行，您需要将增量列转换为 LONG 或 STRING （采用 ISO-8601 格式）。

增量同步时抛出 NullPointerException

如果增量同步时抛出 NullPointerException，这可能表明 SQL 查询正在从数据库中检索会导致增量列包含空值的行。

  • 空值被同步，则同步将在 Data Connection 尝试更新同步的增量状态时失败，因为当前状态将与同步的空值进行比较并抛出错误。 SELECT * FROM table WHERE (col > ? OR timestamp > 1) AND col IS NOT NULL.

同步挂起

以下是同步挂起的一些常见原因及其相应的解决方法：

所有同步：在获取阶段挂起

  • 要检查数据源是否可用，请尝试连接该数据源并与之交互（不使用您的代理或其他 Foundry 产品）。如果您能够成功连接且查询按预期运行，请联系您的 Palantir 代表以获取进一步帮助。
  • 如果您发现无法连接到数据源，或者发送到数据源的查询响应缓慢，则该数据源可能正在承受高于正常水平的流量或已宕机。为了减轻繁忙数据源的影响，我们建议采取以下措施：
    • 将您的同步拆分为多个较小的同步。
    • 使用增量同步（如适用）。
    • 在您知道数据源不繁忙的时间段安排同步。

JDBC 同步：在获取阶段挂起

如果您的同步完成获取阶段所需的时间超出预期，可能是因为代理正在进行大量的网络和数据库调用。要调整同步期间进行的网络和数据库调用次数，您可以更改 Fetch Size 参数：

  • 直方图 Fetch Size 参数位于数据源配置的“高级选项”部分，用于定义给定查询每次数据库往返期间获取的行数。因此：
    • 减小 Fetch Size 参数将导致每次调用数据库时返回较少的行，并且需要更多的调用。但是，这意味着代理将使用更少的内存，因为在给定时间内代理堆中存储的行数会更少。
    • 增大 Fetch Size 参数将导致每次调用数据库时返回更多的行，并且需要更少的调用。但是，这意味着代理将使用更多的内存，因为在给定时间内代理堆中存储的行数会更多。
    • 我们建议从 Fetch Size: 500 开始，并据此进行调整。

JDBC 同步：在上传阶段挂起

如果您的同步上传文件耗时很长或在上传阶段失败，则可能是网络链路过载。在这种情况下，我们建议调整 Max file size 参数：

  • 直方图 Max file size 参数位于数据源配置的“高级选项”部分，用于定义上传到 Foundry 的输出文件的最大大小（以字节或行数为单位）。因此：
    • 减小 Max file size 参数可能会增加网络压力，因为较小的文件会更频繁地上传；如果文件上传失败，重新上传的成本较低。
    • 增大 Max file size 参数将需要更少的总带宽，但此类上传更有可能失败。
    • 我们推荐 Max file size: 120mb。

FTP / SFTP / Directory / 同步：在获取阶段挂起

基于文件的同步在获取阶段挂起的最常见原因是代理正在遍历一个大型文件系统。

遍历文件系统的同步将对文件系统进行两次完整遍历（除非另行配置）。这是为了确保同步不会上传当前正在写入或以任何方式被更改的文件。

  • 为了避免较长的遍历时间，请确保您已在数据源配置页面中指定要遍历的子文件夹。
    • 注意：任何正则表达式过滤器都将在文件相对于数据源根目录的路径上运行。
  • 如果未指定子文件夹，同步将遍历数据源根目录。

大型基于文件的同步容易受到瞬时故障的影响

基于文件的同步是事务性的。如果同步在任何时刻失败，事务将被中止，该次运行中的所有文件都不会提交到数据集。例如，如果同步配置为上传一百万个文件，而在上传除最后一个文件之外的所有文件后发生网络错误，则整个事务将被中止。所有已上传的文件都不会被提交，数据集视图也不会被修改。

由于这种事务性行为，在单次运行中处理大量文件的同步更容易受到瞬时网络问题或源系统问题的影响。要减少同步失败的影响：

  • 用途 增量式 APPEND 同步 而非 SNAPSHOT syncs.
  • 应用文件数量限制过滤器，使每次运行处理较小的文件批次。

这样，失败时只需重新同步当前批次，而不是所有文件。

更多详情，请参阅 同步失败行为 和 优化基于文件的同步.

如果您的同步失败并出现 REQUEST_ENTITY_TOO_LARGE 错误

下载、处理和上传大文件容易出错且速度缓慢。 REQUEST_ENTITY_TOO_LARGE 如果单个文件超过为代理上传目标配置的最大大小，则会发生服务异常。对于 data-proxy 上传策略，默认设置为 100GB。

如果您的同步失败并出现 BadPaddingException 错误

BadPaddingException 出现异常是因为存储在代理中的源凭据加密密钥与预期不符。这通常发生在手动升级代理管理器时，但旧的 /var/data 目录未被复制到新的安装位置。

解决此问题的最简单方法是使用受影响的代理为每个源重新输入凭据。

同步了意外的数据

如果 JDBC 同步中的时间戳列在 Foundry 中显示为 Long 列

当从 JDBC 源同步包含时间戳列的行时，这些时间戳列将在 Foundry 中被转换为 long 列。此行为的存在是出于向后兼容性的原因。

要修复这些列的数据类型，我们建议使用 Python 转换 环境来执行此清理操作。以下是将该列 "mytimestamp" 转换回时间戳格式的示例代码片段：
