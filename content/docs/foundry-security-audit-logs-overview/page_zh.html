审计日志

审计日志全面记录了在 Foundry 中执行的每一项操作，使安全团队能够检测威胁、调查事件、确保合规，并在整个平台中维持问责机制。审计日志可以被视为用户在平台中所有操作的精炼记录。这通常是详细程度与精确度之间的折中：过于详细的日志可能包含更多信息，但更难以分析推理。

审计日志捕获的内容

Foundry 中的审计日志包含足够的信息，可以回答任何安全调查或合规审查中的关键问题：

  • 谁 执行了操作（用户身份、会话或服务账户）。
  • 什么 操作是什么（按类型和意图分类）。
  • 当 操作何时发生（用于时间分析的精确时间戳）。
  • 在 操作发生在何处（涉及哪些资源和系统）。

有时，审计日志会包含有关用户的上下文信息，包括个人身份信息（PII），例如姓名和电子邮件地址，以及其他潜在的敏感使用数据。因此，审计日志内容应被视为敏感信息，仅供具备必要安全资质的人员查看。

隐私最佳实践是维护审计日志，因为可问责的工作流需要可追溯的记录，包括谁执行了操作、执行了什么操作以及何时发生。审计数据本身可能是敏感的，因此请应用基于目的的、最小权限的访问控制并进行审查 实践中的隐私与公民自由 在设计监控工作流时。

审计日志（及相关详细信息）通常应在客户拥有的、专门用于安全监控的独立系统（即“安全信息与事件管理”，或 SIEM 解决方案）中消费和分析（如果可用）。如果尚未配置此类系统，Foundry 本身也足够灵活，可以直接在平台中执行一些轻量级的 SIEM 原生工作流。

审计交付

Foundry 提供灵活的审计日志交付机制，以满足多样化的安全基础设施和 SIEM 需求。您选择的交付方式取决于贵组织现有的安全工具和分析工作流。

比较交付方式

Audit.3 日志（推荐用于所有新实施）：

Audit.3 架构日志 为安全运营提供了显著优势：

  • 低延迟： 在事件发生后约 15 分钟内即可获取，支持及时的威胁检测。
  • 直接 API 访问： 通过公共 API 直接摄取到外部 SIEM，无需以 Foundry 作为中介。
  • 结构化类别： 强制执行的标准化类别为自动化分析提供了可预测的结构。
  • 面向未来： 新的 Foundry 功能会自动使用现有类别，因此监控查询无需更新。

Audit.3 日志可通过 API 摄取到 SIEM，或在必要时通过 审计导出到 Foundry 数据集 。

Audit.2 日志（旧版，仅用于历史分析）：

历史 audit.2 架构日志 会在约 24 小时内被编译、压缩并移动到日志归档存储中，存储位置取决于环境（例如 S3 存储桶）。这些日志：

  • 在分析之前必须导出到 Foundry 数据集。
  • 不支持通过 API 直接摄取到外部 SIEM。
  • 类别使用为可选，且结构不一致。
  • 仅应用于分析以下版本之前的历史时期： audit.3 migration.

从归档存储中，Foundry 可以通过以下方式向客户交付 audit.2 日志：通过审计导出至 Foundry 审计导出至 Foundry.

直接将审计日志摄取到 SIEM

外部 SIEM 可以直接从存储中摄取 audit.3 日志，使用 Palantir 的 list-log-files 和 get-log-file-content 审计 API 端点。您无需创建审计日志导出数据集即可使用这些端点。对于拥有专门安全运营中心和成熟 SIEM 平台的组织，推荐使用此方法，因为它提供以下优势：

  • 最低延迟： 日志在 15 分钟内即可在您的 SIEM 中可用，便于快速威胁检测和响应。
  • 原生集成： 日志直接流入您现有的安全工具和告警工作流。
  • 无需中间环节： 无需先将日志路由到 Foundry，简化了架构，并且如果审计日志不导出到 Foundry 本身进行分析，还可节省存储/计算方面的潜在成本。
  • 标准协议： 使用与大多数主流 SIEM 平台集成的常见 API 模式。

SIEM 摄取是 audit.3 日志相对于历史 audit.2 日志的一项优势，历史日志没有允许外部 SIEM 直接摄取的公开 API（audit.2 日志必须先导出到 Foundry 数据集，然后再从该数据集导出到 SIEM）。

SIEM 摄取的分页和轮询

直方图 list-log-files 端点 使用基于令牌的分页。 nextPageToken 字段 始终 存在于响应中，即使 data 字段为空或被省略，这意味着没有新的日志文件可用。

要持续轮询新的审计日志，请按照以下步骤操作：

  1. 使用一个 startDate 和可选的 endDate.
  2. 发起初始请求。存储响应中的 nextPageToken 。
  3. 在后续请求中，提供之前存储的 nextPageToken 以从上次中断处继续。将返回自上次请求以来生成的新日志文件。
  4. 当 data 字段为空时，表示暂无新日志，但 nextPageToken 仍然有效，应保存以用于下一个轮询周期。

此设计允许 SIEM 集成以任意频率进行轮询，而不会遗漏日志或收到重复数据。如果省略 endDate 参数，端点将始终返回最新可用的日志，适合开放式持续轮询。

导出设置

要设置审计日志导出到 Foundry 数据集，请按照以下步骤操作：

  1. 导航至 控制面板.
  2. 在顶部工具栏中，确认已从下拉菜单中选择相关的 配置 。
  3. 在左侧边栏中，选择 搜索，然后搜索并选择 审计日志.
  4. 选择 创建导出数据集.
  5. 选择日志类型：选择 audit.3 以使用当前审计日志的新架构，或选择 audit.2 如果您需要分析升级到 audit.3 架构之前的历史审计日志。请查看 重要限制 从以下版本迁移时 audit.2 to audit.3.
  6. 选择一个 导出位置和名称 用于存放此审计日志数据集在 Foundry 中的位置。
  7. 用途 标记 来限制您的高度敏感审计日志数据集，并指定一组具有知悉权限的合格平台管理员，他们可以查看可能敏感的使用详情（如 PII 和搜索查询）。默认情况下，审计日志数据集将使用上面所选组织进行标记。请查看我们的 组织标记 文档以了解更多信息。
  8. （可选）启用 开始日期筛选 以将此数据集限制为在给定日期或之后发生的事件。
  9. （可选）启用特定于数据集的 保留策略 以限制日志在此特定导出数据集中保留的天数（最多 730 天）。保留策略基于日志添加到导出数据集时的事务时间戳，而不是日志条目本身的时间戳。删除 相关事务 在被标记为删除后最多可能需要七天时间。以下两个示例说明了这在实践中的运作方式：
    • 示例一：
      • 开始日期：2025-01-01
      • 保留策略：90 天
      • 在此情况下，导出数据集最初将包含自 2025 年 1 月 1 日以来的日志。在数据集创建 90 天后，保留策略将生效；仅保留最近 90 天内添加的日志，而不是数据集中最初包含的自 2025 年 1 月初以来的所有日志。实际上，这意味着 90 天后，随着较旧日志的删除，数据集的大小会显著减小。
    • 示例二：
      • 开始日期：30 天前
      • 保留策略：90 天
      • 在此场景中，导出数据集将从过去 30 天的日志开始。随着新日志的添加，数据集将不断增长，直到保存最近 90 天数据的滚动窗口。根据保留策略，添加时间超过 90 天的事务中的日志将被删除。
  10. 确认 您了解创建数据集的安全影响以及您应用于审计日志导出数据集的配置设置，然后选择 创建导出.

审计架构

Palantir 产品生成的所有日志均为 结构化 日志。这意味着它们遵循特定的 schema，下游系统可以依赖该 schema 进行自动分析和告警。

Palantir 审计日志目前以历史 audit.2 模式 以及新的改进版 schema 交付， audit.3. Audit.2 新事件的日志很快将不再支持以该 schema 导出，只有历史日志可以以该 schema 使用；所有新事件将仅支持以 audit.3 schema 导出。

在这两种 audit.2 和 audit.3 schema 中，审计日志会因生成日志的产品而异。这是因为每个产品所关注的领域不同，因此需要描述的关注点也不同。这种差异在 audit.2中更为明显，下文将对此进行说明。

产品特定的信息主要记录在 requestFields 和 resultFields 为 audit.3 日志（或 request_params 和 result_params 为 audit.2 日志）中。这些字段的内容会根据记录日志的产品和被记录的事件而变化。

审计日志类别

Palantir 日志使用一个称为 审计日志类别 的概念，使日志在几乎不需要产品特定知识的情况下更易于理解。安全分析师无需跟踪数百个特定于服务的事件名称，而是可以通过类别专注于高级操作，例如数据加载、权限更改或身份验证尝试，而无需关心生成日志的是哪个产品或功能。这种抽象使分析师能够构建适用于所有 Foundry 服务的监控查询，而无需了解实现细节。例如，过滤 dataExport 可以捕获所有数据导出事件，无论使用什么产品导出数据。

借助审计日志类别，审计日志被描述为可审计事件的集合。审计日志类别基于一组核心概念，并划分为描述对这些概念所执行操作的类别，例如以下内容：

类别描述示例用例
authenticationCheck通过程序化或手动身份验证事件（例如令牌验证）检查身份验证状态。检测暗示撞库攻击的令牌验证模式。
dataCreate表示向平台中添加了先前不存在的新数据条目。此事件可能会在单独的服务中反映为 dataPromote （如果它记录在落地服务中）。跟踪数据创建模式并执行治理策略。
dataDelete与数据删除相关，与删除的粒度无关。在关键或受保护资源被删除时发出警报。
dataExport从平台导出数据。用于诸如从平台下载数据到 Palantir 外部系统、CSV 文件等场景。如果数据被导出到另一个 Palantir 系统，请使用 dataPromote category.在大量导出、敏感数据导出或工作时间之外的导出时发出警报。
dataImport导入到平台。与 dataPromote, dataImport 不同，它仅指从平台外部摄取的数据。这意味着一个服务中的 dataImport 可能会在单独的服务中显示为 dataPromote 。监控恶意文件上传或策略违规。
dataLoad指加载要返回给用户的数据。对于纯后端加载，请使用 internal.建立正常的访问模式基线，并检测异常的批量数据访问。
tokenGeneration导致生成新令牌的操作。检测异常的令牌创建，这可能表明正在为批量数据访问做准备。
userLogin用户的登录事件。监控失败的登录尝试、异常的登录时间或地理位置异常。
userLogout用户的登出事件。跟踪会话持续时间并识别异常长的会话。

审计日志类别也经历了版本变更，从 audit.2 日志中较宽松的形式变为 audit.3 日志中更严格、更丰富的形式。在 audit.3中，每条日志必须至少指定一个类别，并且每个类别都明确定义了将出现哪些请求和结果字段，从而使自动化分析更加可靠。

请参阅我们已记录的 审计日志类别 以获取包含字段规范的可用类别详细列表。此外，请查阅 监控安全审计日志 文档以获取有关使用类别的更多指导。

审计日志归因

审计日志会写入每个环境的单一日志归档中。当审计日志通过交付管道处理时，用户 ID 字段（uid 和 otherUids 菜单中选择 模式 见下文）会被提取，并将用户映射到其相应的组织。

为给定组织编排的审计导出仅限于归因于该组织的审计日志。仅由服务（非人类）用户执行的操作通常不会归因于任何组织，因为这些用户不是组织成员。使用 客户端凭据授予 且仅由注册组织使用的第三方应用程序服务用户的特殊情况，确实会生成归因于该组织的审计日志。

Audit.3 日志

任何新的日志导出或分析都应使用 audit.3 日志，而不是 audit.2 日志。

Audit.3 日志基于新的日志架构构建，与 audit.2 日志相比具有多项优势。新架构及关联交付管道为审计日志使用者带来的主要优势如下：

  • 更快的交付： 延迟从可能超过 24 小时缩短至 15 分钟或更短，从而实现近实时的威胁检测。
  • 结构化类别： 强制执行的、有文档记录的类别为分析提供了可预测的结构。这有助于减少在推断日志内容时对单个产品的理解需求，尤其是当分析需求涵盖整个工作流时（例如， dataExport).
  • 增强的顶层字段： 诸如 product 之类的新字段允许按产品名称进行更轻松的过滤，而无需复杂的事件名称映射过滤器即可将分析聚焦于单个产品的使用情况。
  • 直接 API 访问： 现在提供公共 API，可将审计日志摄取到外部 SIEM 中，而无需 Foundry 作为中介。
  • 丰富的上下文： 在交付过程中提取的有关用户、资源和关系的额外上下文化信息可供使用，以便于下游分析。

架构保证

Audit.3 日志的生成遵循以下保证：

  1. 明确的类别定义： 每个审计类别都明确定义了其适用的值/项目；例如， dataLoad 描述了具体的 资源 被加载。
  2. 类别的并集： 每个日志严格作为审计类别的并集生成。这意味着日志不会包含自由格式的数据，从而确保结构可预测。
  3. 提升的关键信息： 审计日志中的某些重要信息会被提升到 audit.3 schema 的顶层。例如，所有命名的资源都出现在顶层，同时也出现在请求和结果字段中。

这些保证意味着，对于任何特定的日志，都可以判断出（1）创建它的可审计事件是什么，以及（2）它具体包含哪些字段。这些保证与产品无关，使安全分析师能够构建适用于所有 Foundry 服务的监控查询。

Audit.2 日志

只有对记录新 audit.3 日志之前的历史时期的分析才应使用 audit.2 日志。请参阅 重要限制 从以下版本迁移时 audit.2 to audit.3，因为将新事件作为日志归档到 audit.2 schema 中的做法即将被弃用。 Audit.2 日志对请求或结果参数的结构 不提供跨产品保证 。因此，对审计日志的推理通常必须逐个产品进行。

从 audit.2 迁移到 audit.3

当前使用 audit.2 日志进行安全监控或合规性管理的组织必须将其分析迁移到 audit.3 schema。本节为转换您的审计日志工作流提供指导，以便利用 audit.3.

audit.2 与 audit.3 之间的差异

直方图 audit.3 schema 相较于 audit.2代表了根本性的架构变更，而不仅仅是版本更新。影响迁移的关键差异将在以下各节中介绍。

字段名称和结构变更

  • request_params and result_params in audit.2 现在命名为 requestFields and resultFields in audit.3.
  • 的内容通常与其 requestFields and resultFields 对应项完全不同（ audit.2 在request_params and result_params).
  • 中找到的信息现在可能在 request_params in audit.2 中，反之亦然。 resultFields in audit.3在查找
  • 中的特定信息时，请务必同时检查两者 requestFields and resultFields 。 audit.3.
  • 直方图 type 顶层字段标识了生成该日志的 schema： "audit.2" or "audit.3".

事件名称变更

  • 事件名称（在 name 字段中）在不同 schema 之间可能不同，当解析特别依赖于事件名称时，这可能导致不匹配。
  • audit.3 中的事件名称更加标准化，通常遵循（产品名称）_（端点名称）的结构，全部大写并使用蛇形命名法。例如： DATA_PROXY_SERVICE_GENERATED_GET_DATASET_AS_CSV2.
  • 虽然并非所有 audit.2 to audit.3 事件名称都存在直接的 1:1 映射，但大多数 audit.2 日志事件名称可以直接映射到 audit.3.
  • 推荐做法： 用途 审计类别 而不是具体的事件名称来进行后续查询，因为类别在两种模式之间提供了一致的抽象（尽管 audit.2 可以选择性地使用类别）。

新能力

  • In audit.3，有一个顶层 categories 字段，其值为强制性的标准化值。
  • 诸如 product, service, entities日 users 可在 audit.3 中使用，以便于筛选。
  • 直方图 users 字段可在 audit.3 中使用，其中包含与日志条目关联的所有用户的用户 ID。其他用户配置字段（userName, firstName, lastName, groups, realm）已在模式中定义，但目前尚未填充数据；如有需要，请在下游进行补充。

重要限制

  • 无历史回填： Audit.3 仅捕获其启用之后发生的事件。历史事件将仅保留在 audit.2 日志模式中。

由于 2025 年 11 月 24 日至 25 日期间为正式发布做准备而进行的基础设施更新，部分注册可能经历了约三小时的 audit.3 日志可用性缺口。我们建议在此期间使用 audit.2 日志作为备用方案以满足分析需求，并在 2025 年 12 月 4 日之后完全迁移至 audit.3 进行分析。

  • 并行记录期： 在过渡期内，两种模式都会发出日志，以便在完全切换之前进行验证。

迁移路径

如果您已有基于 audit.2 日志构建的分析，您的迁移方式取决于您目前在哪里执行分析。请按照下文中与您的分析方式相符的章节中的步骤操作。

如果您使用外部 SIEM

我们强烈建议迁移到直接 API 摄取，而不是继续使用 Foundry 导出数据集。此方式具有以下优势：

  • 显著更低的延迟： 约 15 分钟或更短，而 audit.2.
  • 更简单的架构： 消除了 Foundry 作为中间环节，减少了额外的延迟或故障点。
  • 原生 SIEM 集成： 完整日志直接流入您现有的安全工具。

迁移步骤：

  1. 配置您的 SIEM 以从 list-log-files and get-log-file-content 审计 API 端点进行摄取。
  2. 更新解析规则以处理新的 audit.3 模式结构（参见下方的 章节).
  3. 尽可能更新检测规则，使用类别而不是事件名称。
  4. 在验证期内与您现有的 audit.2 摄取并行运行。
  5. 彻底测试告警和检测工作流。
  6. 验证完成后，弃用您的 audit.2 Foundry 导出和 SIEM 摄取。

如果您在 Foundry 中分析日志

  1. 创建一个新的 audit.3 导出数据集，在控制面板中按照 导出设置说明操作.
  2. 在过渡期内保持您现有的 audit.2 导出数据集持续运行。
  3. 创建一个新的全局分支（Global Branch）来执行迁移，将多个 PR 打包在一起（如有必要，可能涉及多个代码仓库）。
  4. 使用数据血缘（Data Lineage）应用查看您对 audit.2 数据在 Foundry 中的下游消费情况，以了解哪些分析已弃用、哪些需要迁移。
  5. 按照下方的重构步骤更新您的分析。

不要按每个事件名称逐一迁移分析，而是重构您的分析以使用标准化的 审计类别 而不是各个产品的事件名称：

  • 跨产品： 在所有 Foundry 服务中保持一致地工作。

在过渡期间进行验证

在并行记录日志期间：

  • 同时对两个数据源 audit.2 and audit.3 运行分析。
  • 比较输出结果，确保 audit.3 分析捕获了预期的事件。
  • 验证基于类别的筛选器是否提供与事件名称筛选器相同或更好的覆盖范围。
  • 对于 SIEM 用户：验证警报是否在 audit.3 data.

完成切换

一旦您验证了您的 audit.3 分析提供了相同或更好的覆盖范围：

  • 将所有下游消费者切换为使用 audit.3 API 或数据集。
  • 禁用您的 audit.2 导出数据集（如果使用 Foundry 导出），通过 审计日志 在 Control Panel 中的应用程序。请参阅 导出数据集禁用 获取指导。
  • 移除 audit.2 摄取（如果使用外部 SIEM）。
  • 历史 audit.2 日志在您停止生成新的 audit.2 日志后仍可访问。回溯过去的分析或调查需要分别查询 audit.2 （历史）和 audit.3 （当前）日志。请参阅 重要限制 的文档以获取更多信息。

常见迁移挑战

来自 audit.2 的某些事件名称可能在 audit.3中没有直接对应的名称。这种情况通常发生在：

  • 该事件信号较弱，因此未特意迁移到 audit.3.

  • 使用直方图中的 审计类别 文档，以了解每个类别保证包含哪些字段。
  • 尽可能优先使用顶层字段（entities, users, categories等），而不是解析请求/结果字段。
  • 构建防御性解析逻辑，以妥善处理缺失或意外的字段。

挑战：切换日期前后的连续性

您需要分析跨越历史 audit.2 和当前 audit.3 数据的时间段。请参阅 重要限制 的文档以获取更多信息。

解决方案

  • 对于 SIEM 分析：在过渡期间保持并行摄取，然后依靠 SIEM 的历史数据保留来处理 audit.2 logs.
  • 对于 Foundry 分析：创建一个统一视图，合并 audit.2 and audit.3 datasets.
  • 使用直方图中的 type 字段，以便在需要时应用特定于 schema 的解析逻辑（例如，在 audit.3中使用类别进行筛选，以及在 audit.2).
  • 由于 schema 差异，并非所有指标都能实现完美的连续性。
