计划的构建从未运行

构建已计划在指定时间运行，但未尝试运行。

要进行故障排除，请执行以下步骤：

  1. 是否有另一个同步正在针对此数据集和分支运行？请验证没有其他作业在同一时间运行，因为无法在同一数据集和分支上同时运行两个同步。

  2. 计划是否已暂停？请在此数据集的计划概览页面上验证该计划未暂停。您可以通过同步的 在 Scheduler 中编辑 视图或数据集预览的 管理调度 选项。

  3. 此同步的代理是否已禁用？请导航到此同步源关联的代理，并验证该代理未被禁用。

运行数据摄取导致数据集中出现重复行，当运行 SNAPSHOT 事务

同步已运行，但导致了重复行。

  1. 创建新同步时，请选择运行 APPEND 类型的同步，而不是 Snapshot.
  2. 在声明增量设置时，如果 last_upd_in_appl_ts 是唯一且始终递增的列，请将其设置为该列，然后选择一个小于此列中所有其他值的值。
  3. 此后，无需其他操作，因为 Data Connection 将跟踪已同步的最新值，并且仅引入较新的其他行。较新意味着大于之前的值，较新的时间戳大于较旧的时间戳。

数据库与数据集之间的列类型不一致

同步后，我的类型与数据集上显示的类型不同。

要进行故障排除，请执行以下步骤：

  1. 如果该列是 TIMESTAMP，请验证结果类型是否为 LONG 在 Foundry 中。如果是 LONG，您需要使用您选择的数据准备工具（Code Repositories、Preparation 或其他应用程序）解析该类型为 TIMESTAMP。这是数据库创建者提供的许多驱动程序的副作用，其中类型会还原为其最安全的表示形式。
  2. 如果该列是 DECIMAL 并且与原始数据库的精度不同，我们建议在数据库本身的查询中将数字转换为特定的精度和小数位数，或将该列转换为 VARCHAR 在查询中，然后在 Foundry 中重新转换。

TIME 类型列在数据库和数据集之间丢失亚秒精度

我的数据库包含 TIME 类型列，具有亚秒精度和非零亚秒分量的值，但数据集中的值仅反映到秒级分量的区别。

对于大多数基于 JDBC 的源（包括 PostgreSQL 和 Microsoft SQL Server）， TIME 数据库中的值在 Foundry 输出数据集中反映为 INTEGER 表示自午夜以来的毫秒数，向下舍入到最接近的整秒。因此，数据库中的值例如 05:00:00.000, 05:00:00.200日 05:00:00.800 都将变为 18000000 在输出数据集中。

要保留亚秒级的区别，请考虑在同步配置的 SQL 语句中将值转换为字符串，如下面的 Postgres 示例所示：

SELECT record_id, CAST(column_with_time_type AS text) FROM table_name

运行中查询的状态

查询开始运行后，如何检查其状态？

要进行故障排除，请执行以下步骤：

  1. 打开 作业跟踪器 应用程序并选择正在运行的同步。
  2. 同步的最细粒度状态显示在此处。
  3. 如果可能，请在源数据库中验证查询行为。

同步因架构不匹配而失败

如果文件或 JDBC 表的 schema 在增量 APPEND 事务之间发生变化，您的数据集将开始失败并报 schema 不匹配的错误。Data Connection 会为 JDBC 抽取推断 schema，但对于基于文件的抽取，仅传播现有 schema。在这种情况下，如果 schema 相同，您需要重新应用 schema 推断。如果 schema 确实在 APPEND 事务之间发生了变化，则需要为新 schema 创建新的数据集。

要进行故障排除，请执行以下步骤：

基于文件的

  1. 如果文件是 XLSX 或 CSV 表格数据，则可以在已同步的数据集上重新推断 schema 而不会出现问题。如果此 schema 与之前的匹配，数据集将顺利添加追加的行。

  2. 如果在推断 schema 后仍然出现 schema 错误（在数据集预览或其他应用程序中），则此新文件需要改为同步到新的数据集，因为它表示表的根本不同的视图。

  3. 如果数据集已经追加了新 schema 的数据，我们建议联系 Palantir Support 回退此事务。此外，需要通过转到同步概览页面并暂停与此同步关联的任何计划，来暂停文件到当前数据集的同步。

  4. 具有新 schema 的后续文件应同步到与原始数据集不同的数据集，因此我们建议将原始同步中的信息复制到新的同步中，但将目标数据集替换为另一个数据集（在数据集名称中注明新版本）。

  5. 此外，最好删除原始同步，以避免将来发生任何 schema 不匹配错误，从而损坏 Foundry 中的现有数据。

JDBC

  1. 如果您预计 schema 在某个时候会发生变化并以新形式持续到未来，最好将原始表存入一个名称中指示 schema 版本的数据集。（例如 account_transactions_v1.0).
  2. 如果 schema 在同步执行之前在原始表中发生变化：
    • 暂停同步的计划（如果存在）
  3. 如果 schema 在同步执行之后在原始表中发生变化：
    • 暂停同步的计划（如果存在）
    • 联系 Palantir Support 回退此很可能已损坏目标数据集的事务
  4. 在同步暂停后，当您准备好迁移到新 schema 时，必须首先将新 schema 存入新的数据集：
    • 将同步克隆为新的同步，并将目标数据集替换为新的数据集（例如 account_transactions_v1.1）。然后可以将此新数据集与原始数据集合并，以包含完整的数据集。
    • 如果您的用例需要，您可以在验证新同步中的行为正确后删除原始同步。这确保不会在旧数据集中存入损坏的数据，但代价是降低了先前加载配置的透明度。

重新添加已删除的同步作业规范时出现权限错误

删除同步的作业规范后，尝试重新添加它会导致权限错误。

要解决此问题：

创建一个输出到相同数据集的新同步。这将建立具有正确权限的新作业规范，同时保留目标数据集中的现有数据。

Bootvisor 状态为 Unknown

我的 Bootvisor 卡在 Unknown 状态，无法停止/启动。

在继续之前，请联系 Palantir Support 检查您的设置。按照以下步骤操作将暂时阻止同步在此代理上运行。请确保为数据源配置多个代理，或在维护窗口期间执行这些步骤，以防止停机。

  1. 暂停代理上的同步。
  2. 等待所有当前正在运行的同步完成。
  3. 停止代理（此步骤可能会失败，具体取决于代理的当前状态）。
  4. 通过 SSH 登录到代理机器。
  5. kill 所有与 Data Connection 相关的 JVM 进程。
  6. 使用以下命令启动 Bootvisor ./service/bin/init.sh start.
  7. 在 Data Connection 中启动代理，并验证代理未处于 paused 状态。
