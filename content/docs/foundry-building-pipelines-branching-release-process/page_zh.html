分支与发布流程

本文档旨在概述通过 Code Repositories 中的 Projects 管理的数据管道的分支管理最佳实践和发布流程。

总体目标是在新数据功能/数据质量修复的快速迭代与稳定且符合流程规范的变更管理流程之间取得平衡。

发布范围

在深入了解发布管理流程的内部细节之前，我们需要更好地定义我们发布的“产品”究竟是什么？就我们的目的而言，我们将把 product 设置为 作为概念单元发布的一组资产.

我们在此处对产品的定义可以涵盖在多个仓库中管理的代码以及其他 Foundry 资源。

以 推荐的项目结构 作为我们在 Foundry 中构建管道的参考，我们可以看到管道由多个不同类型的项目定义——数据源、转换、本体论和工作流。然而，在大多数情况下，我们不会将每个项目单独作为一个产品来管理，而是将每个项目的一部分资源定义为以下产品类型之一：

  • 本体论产品：该产品是由数据源、管道和本体论项目创建的输出数据集的集合。
  • 用例产品：每个用例项目代表一个独立的用例。每个用例都被定义为一个产品。

产品分支管理

以下部分介绍了我们为管理每个产品的发布而要部署的分支策略。 了解有关分支的更多信息，以及分支在 Code Repositories 和数据集之间如何运作。

分支命名

强烈建议在产品内的所有仓库中使用相同的分支名称。这将确保下游分支从正确的上游分支读取数据。

我们建议遵循的通用分支策略基于一种名为 GitFlow ↗ 的常见实践，并做了一些修改。主要变化是建议跳过 release 分支。由于 Foundry 中构件的部署方式，我们可以将变更从 dev 合并到 master 测试完成后直接合并。

常用分支

master - 这是生产分支。因此，它是一个受保护的分支，只有发布经理角色才能批准将 PR 合并到该分支。假定 master 分支使用生产数据作为数据源。

dev - dev （又称开发）分支是一个暂存分支，派生自 master 分支。当您想使用测试数据测试完整功能时，它最为相关。 dev 分支的数据源可以来自 master （这会通过 代码仓库自动完成）或来自 UAT 数据源。

feature-[X] - 功能分支是开发和测试特定功能的地方。该分支派生自 dev 分支。这是一个短生命周期的分支，意味着一旦该分支被合并到 master 后即可删除。由于该分支派生自 dev 只要后备分支没有被重新配置，并且输入数据集在功能分支上不存在，它将使用与 dev 分支相同的数据源。

其他特殊分支

major-release-[X] - 特殊分支，用于集成由于源系统架构变更（以特定频率发生）而需要的所有变更。

hot-fix-[X] - 特殊分支，用于修复在生产环境中发现的问题，而代码库已迁移到新版本。由于我们假定 dev 和 master 是同步的（除非有正在积极测试的功能），我们不太可能需要这样的分支。

分支管理工作流

如上所述，一些分支是永久性的，而另一些分支是短期的。以下部分描述了分支之间推荐的工作流程。

  • At t0, master 和 dev 分支被创建。

  • At t1, feature x 分支创建自 dev

  • At t2, feature y 分支创建自 dev

  • At t3, feature x 被合并到 dev

  • At t4, dev 被合并到 master，以及 feature x 分支被删除

  • At t5, dev 被合并到 feature y 以获取最新状态 dev

  • At t6，功能 y 被合并到 dev 以及稍后从 dev to master 如前所述

除了开发和发布到 dev 和 master 的功能之外，还有一个用于重大版本发布的长期分支，例如 major-release-[X] 正在开发中。

建议持续将 dev 合并到 major-release-[X] ，以保持最新功能同步。我们建议尽量保持本体论架构稳定，并通过数据源和转换项目中的转换来隐藏后端架构变更。

代码库升级

代码库升级 是定期提示更新代码仓库中配置文件的机制。这些更新会应用修复或提升语言包依赖的版本，最佳实践是及时应用这些推荐的升级。

如果您错过了提示中的“升级”按钮，该按钮也可以在右上角“...”选项菜单下的任何分支中找到：

升级过程应与功能开发周期同等对待。这意味着：

  1. master 应通过 dev.

  2. 进行升级。当提示升级 dev时，将自动创建一个功能分支。在 CI 检查完成后，您可以在该分支上运行构建来测试配置变更。确认升级后转换仍能正常执行后，将配置变更合并到 dev。一旦 dev 升级完成，应使用 PR 将这些变更推送到 master。

  3. 要升级所有打开的功能分支，请将 dev 合并回每个分支，以包含这些配置升级。

维护窗口

从想法到生产的快速迭代循环在开发实践中很常见，对于依赖最终用户反馈来确定下一轮迭代的项目成功至关重要。为了支持这样的流程，我们建议建立预定义的维护窗口。

例如，一旦所有功能 PR 合并完成，所有数据集都会在 dev 分支上构建，以便在周三和周五验证结果。在这些日子里，只有针对验证期间发现的问题的修复才会被合并到 dev，直到 dev 最终被合并到 master ，即在周四和周一，即“发布日”

建议与所有相关方就此节奏达成一致，以确保他们在这些日子里投入足够的时间来推进新功能。

功能测试和最终用户验证

功能开发完成后，测试和验证功能结果的正确性以及对任何依赖资源的影响至关重要。在代码仓库中，我们将输出数据集视为应测试的功能结果。

根据我们上面定义的分支结构，当我们构建输出数据集时，它将使用同一功能分支上输入数据集中的数据，或者通过回退逻辑从源分支读取数据，在简化版本中是 master，在另一个版本中是 dev。

开发人员级别的测试可以使用数据集 健康检查、依赖的测试数据集，或使用诸如 Contour.

测试方法

强烈不建议通过预览或 SQL 助手进行此类测试。预览助手在执行代码时仅使用数据样本，可能无法揭示所有情况——尤其是在涉及一个或多个连接操作的代码中。SQL 助手测试的是代码的正确性，而不是构建的输出，在某些情况下两者可能不同。

功能开发完成后，新功能代码需要经过评审才能合并到 dev 分支，并且功能成果需要由最终用户验证其正确性和完整性。

我们建议将 Pull Request 评审用于前者，将 Foundry Issues 用于后者，两者结合使用，如下图所示。

  1. 开发人员从其功能分支创建一个 pull request 到 dev 分支，并添加实现说明。

  2. 开发负责人评审 PR，与开发人员协作完成所需的修改，最后将 PR 合并到 dev.

在 pull request 评审期间，请务必检查任何受影响数据集的 schema 变更。Schema 应被视为您的数据 API，因此对列名或列类型的任何更改对于任何消费者而言都算是“破坏性”变更。在可能的情况下，尽量通过创建新列而不是删除或修改旧列来减少破坏性变更，同时宣布旧列的弃用，并为数据消费者（通过 Data Connection 识别）提供更新到新列的说明。在下一次主要版本发布时，上一次主要版本中弃用的列可以被删除。

要在 pull request 中评审 schema 变更，请使用 受影响的数据集 标签页。

  1. 开发负责人在 dev 分支上运行构建，以创建功能输出数据集。
  2. 开发人员在输出数据集上创建一个 Foundry Issue，记录任何测试和验证请求，并将该 issue 分配给相关的最终用户进行验证。
  3. 最终用户收到该 issue，其中包含完整上下文以及相关数据集和待测试分支的视图。他们与开发人员就所需的修改进行协作，直到 issue 得到解决并标记为可合并。然后该 issue 会被分配给发布经理。
  4. 发布经理关闭该 issue 并合并 dev into master.
  5. 发布经理删除该功能分支。

上述工作流使各方之间能够进行相对快速的协作循环，同时不会丢失上下文。已关闭的 issue 会保留在平台上，可以作为变更管理流程的审计记录。
