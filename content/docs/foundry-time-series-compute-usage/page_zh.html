时间序列查询计算用量

Foundry 将时间序列数据以高度优化的格式缓存到磁盘上，用于时间序列查询。查询这些数据需要使用计算秒数（compute-seconds）。

时间序列查询通过以下方式使用计算资源：

  1. 每个查询都有固定的每查询计算秒数消耗率。
  2. 每个查询还会根据其读取的时间序列点数产生额外的计算秒数计量。

对更大的时间序列索引进行查询将读取更多的点。以下部分介绍了其计算方式的说明。

计算资源的计量方式

当您为 Foundry 用量付费时，每个查询会消耗固定的最低数量的计算秒数。默认数量为 4 计算秒数。这是为查询提供服务所需的基础计算用量。如果您与 Palantir 签订了企业合同，请在进行计算用量计算之前联系您的 Palantir 代表。

时间序列数据的存储在 Foundry 存储下计量。存储时间序列数据不使用任何计算资源；只有对时间序列进行索引和主动查询数据时才会使用计算资源。

时间序列查询计算资源仅在查询存储在 Foundry 中的时间序列数据时使用。时间序列查询通过两种方式使用计算资源：

  1. 每个查询使用最低数量的计算秒数。在基于用量的 Foundry 实例上，每个查询使用 4 计算秒数。
  2. 查询会根据其自身所考虑的点数超出固定的最低成本进行扩展。查询期间扫描的点数取决于所查询序列的大小和所执行逻辑的复杂程度，后者可能会对点进行大量的比较/操作。

以下公式根据查询推导计算秒数：

compute-seconds = 4 + points_scanned / 25000

调查时间序列查询用量

直方图 资源管理 应用程序允许您深入查看数据集用量信息，应作为调查 Foundry 平台中用量问题的起点。

用户可以使用多种工具在 Foundry 中查询时间序列数据。时间序列查询用量始终归属于每个工具所产生或修改的资源。

  • 在 Quiver 中，时间序列查询将归属于发起查询所使用的单个 Quiver 分析或仪表板。
  • 在 Workshop 中，查询将归属于发起查询的 Workshop 应用。当 Workshop 应用嵌入了查询时间序列的 Quiver 组件时，用量仍归属于上层的 Workshop 应用程序。
  • 对于使用 FoundryTS 库查询时间序列的转换，这些查询的计算用量将归属于编写该转换的仓库。

了解用量的驱动因素

在按用量合同为 Foundry 付费时，时间序列查询的计算用量有三个主要驱动因素：

  1. 查询数量

    • 每个查询的最低用量为 4 计算秒数。这意味着用户执行的查询越多、运行查询的 Quiver 仪表板越多、以及运行 FoundryTS 查询的定时构建越多，使用的计算秒数就越多。

  2. 所查询序列的大小

    • 减少读取的点数通常会降低计算用量和延迟。例如，对一个包含 10,000,000 个点的序列执行聚合查询，将比对一个包含 100,000 个点的序列执行相同查询使用更多计算资源。但实际用量取决于具体查询。减少读取点数最常用的技术是在每个序列上添加时间范围筛选器。

  3. 查询的复杂程度

    • 与底层序列执行更复杂交互的查询将在该序列之上运行更多操作。在运行这些操作时，随着扫描的点数增多，查询用量也会增加。

    有关更多信息和使用示例，请参阅以下章节 查询复杂度.

使用时间序列管理用量

管理查询总数对于管理时间序列查询的总计算用量非常重要。在 Foundry 中使用时间序列时，请考虑以下实践：

  • 在构建基于时间序列的分析或仪表板时，请考虑每次更新时必须运行的查询总数。还应考虑拆分更新路径，以免在参数更改时所有查询都进行更新。
  • 在运行 FoundryTS 构建时，请确保合理设置调度计划，使构建不会比必要的更频繁地运行。
  • 当对时间序列应用时间范围时，Foundry 的时间序列后端只会读取该时间范围内的数据点。因此，Foundry 中的时间序列查询可以根据其查询的范围进行优化。限制查询的时间范围 数据集。 需要计算资源；选择合适的时间范围可以显著减少扫描的数据点总数，从而减少查询所使用的计算资源。
  • 为任务选择正确的粒度；并非所有工作流都需要最大粒度的数据。在某些情况下，这意味着针对特定工作流进行预聚合。在其他使用场景中，这意味着将不同粒度存储在不同的序列中。虽然维护多个最新序列可能会增加索引计算量，但存储多个序列本身不需要计算资源。因此，持有多个不同粒度的序列可能比始终查询最细粒度的序列更经济。

计算用量

要预测时间序列查询的成本，请务必始终了解所查询序列的大小。

考虑以下示例，其中对一个包含 100,000 个数据点的序列执行三个查询，每个查询都会扫描该序列中的所有数据点：

series_size: 100,000 points
minimum_query_usage: 4-compute seconds
points_per_compute_second: 25,000 points
total_queries: 3

 
compute-seconds = num_queries * minimum_query_usage + total_points / points_per_compute_second
compute-seconds = 3 queries * 4 compute-seconds + 100,000 points * 3 queries / 25,000 points-per-second
compute-seconds = 3 * 4 + 300,000 / 25,000
compute-seconds = 24 compute-seconds

查询复杂度示例

时间序列查询的复杂度随着对所查询时间序列应用的嵌套操作增多而增加。

举个例子，考虑以下 FoundryTS 代码，它将两个时间序列相加，并以 Pandas 数据帧的形式返回新序列在 1 年时间范围内的所有数据点：

series_1 = N.TimeseriesNode('series_1')
series_2 = N.TimeseriesNode('series_2')
result = F.dsl(program='a+b', return_type=float)([series_1, series_2]).time_range(start='2022-01-01', end='2023-01-01')
result.to_pandas()

此代码将向 Codex 发出具有以下形状的查询：

{
  id: dsl-fomula
  children: [
    { id: timeseries },
    { id: timeseries }
  ]
}

评估 to_pandas 调用将产生扫描 result 时间序列在所请求的 1 年时间范围内的数据点，以及计算结果所需的两个组成序列中的数据点（在本例中，每个序列各为 1 年范围）的成本。

现在，考虑以下应用了更多嵌套操作的 FoundryTS 代码。首先，我们定义一个由另外两个序列相加得到的序列。然后，我们将该序列与其 7 天滚动平均值进行比较，并以 Pandas 数据帧的形式加载结果中一年的数据点：

series_1 = N.TimeseriesNode('series_1')
series_2 = N.TimeseriesNode('series_1')
intermediate_1 = F.dsl(program='a+b', return_type=float)([series_1, series_2])
intermediate_2 = intermediate_1.rolling_aggregate('mean', '7d')
result = F.dsl(program='a-b', return_type=float)([intermediate_1, intermediate_2]).time_range(start='2022-01-01', end='2023-01-01')
result.to_pandas()

此代码将向 Codex 发出具有以下形状的查询：

{
  id: dsl-fomula
  children: [
    {
      id: dsl-fomula
      children: [
        { id: timeseries },
        { id: timeseries }
      ]
    },
    {
      id: rolling-aggregate
      children: [
        {
          id: dsl-fomula
          children: [
            { id: timeseries },
            { id: timeseries }
          ]
        }
      ]
    }
  ]
}

此查询树中的每个节点都会产生扫描 1 年范围数据点以生成最终结果的成本。
