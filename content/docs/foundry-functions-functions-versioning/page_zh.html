函数版本控制

本文档介绍函数所使用的版本控制系统。函数发布的版本由其发布者选定，并且在创建之后不可变。采用适当的版本对于为您的函数的使用者提供稳定可靠的体验至关重要。

向后兼容的更改与破坏性更改

函数的版本控制系统会区分向后兼容的更改和破坏性更改。 向后兼容的更改 是指不会对您的函数的现有使用者造成干扰的更改。不向后兼容的更改可称为 向后不兼容 或 破坏性 更改。

以下是一些向后兼容更改的示例：

  • 在函数签名中添加可选输入。
  • 在不改变函数预期行为的前提下优化函数性能。
  • 在不改变函数预期行为的前提下修复函数中的错误。

以下是一些破坏性更改的示例：

  • 在函数签名中添加必需输入。
  • 将函数签名的输出类型从整数更改为字符串。
  • 删除函数。

在考虑对现有版本的更改是否向后兼容时，请自问该更改是否会对现有版本的使用者造成干扰，或需要使用者予以特别关注。

请记住，您最终负责决定函数的预期使用模式。

语义化版本控制系统

函数按照 语义化版本控制 ↗ 系统进行版本管理。

在语义化版本控制中，版本采用以下形式 X.Y.Z ，其中 X、 Y和 Z——分别称为主版本号、次版本号和修订号——均为非负整数（例如， 1.2.3）。版本还可以在修订号后紧跟连字符，以附加由字母数字字符组成的预发布标识符（例如， 1.2.3-rc1）。

本页简要概述了语义化版本控制。我们建议您阅读 完整规范 ↗ ，因为遵循该规范是发布可在其他应用程序中可靠使用的函数的重要一环。

选择发布版本

发布函数的新版本时，请考虑语义化版本控制规范中的以下要点：

  • 主版本 0 （0.y.z）用于初始开发。在初始开发阶段，函数可能随时发生变化，使用者不应将您的函数视为稳定版本。
  • 当您进行向后不兼容的更改时，应递增主版本号。
  • 当您以向后兼容的方式添加功能时，应递增次版本号。
  • 当您进行向后兼容的错误修复时，应递增补丁版本号。
  • 预发布版本表示该版本不稳定，可能无法满足其关联的正式版本所标示的预期兼容性要求。

向后兼容性检查

在发布新版本之前，系统会对您的函数执行向后兼容性检查。具体而言，如果出现以下任何破坏性更改，您将收到警告：

  • 删除函数。这包括在您的 Python 或 TypeScript 函数代码仓库中删除函数。
  • 删除函数签名中的输入（即使是可选输入）。
  • 重新排列函数签名中输入的顺序。
  • 向函数签名中添加必需输入。
  • 不良的输入类型更改（例如从整数更改为字符串）。请注意，扩展数值输入类型（例如从整数扩展为浮点数）将产生警告。
  • 不良的输出类型更改（例如从字符串更改为可选字符串）。

如果这些检查因任何原因而失败，建议您发布主版本。但是，如果您仍处于初始开发阶段（即您仍处于主版本 0）。

Palantir 的内置检查并不能涵盖所有类型的破坏性变更。例如，您内部实现引起的破坏性变更可能无法被检测到。仅凭这些检查的成功结果就发布次要版本或补丁版本并不安全。

注意事项：自定义类型

函数数据类型的内部表示目前缺乏有关自定义类型字段可选性的充分信息。因此，您可能会注意到，对于自定义类型的输入和输出，向后兼容性检查会在您删除或添加任何字段时发出警告，包括可选字段，例如 quantity?: Integer （Typescript 中）或 quantity: Integer = 0 （Python 中）。

我们目前正在进行更改，以便今后在删除输出自定义类型上的可选字段或添加输入自定义类型上的可选字段时，您不会再收到警告。

删除输入自定义类型上的可选字段时，您仍会收到警告。通常认为，忽略调用方提供的任何字段是一种不良做法，因为调用方很可能期望所提供的字段能够决定您的函数的行为。

限制稳定版本标签

稳定的语义化版本发布（非预发布版本）可立即被下游生产应用程序使用，前提是这些应用程序已配置为通过版本范围引用该函数（例如， >=1.2.3 <2.0.0）。因此，在将代码更改发布为新的稳定版本之前，务必对其进行审查和测试。

您可以对函数稳定版本的发布实施限制，方法是 启用一个开关 ，该开关位于受保护分支的仓库设置中。

常见问题

在 0.y.z 初始开发阶段选择发布版本

常见做法是，将任何破坏性变更放在次版本中发布，而将任何向后兼容的更改放在补丁版本中发布。这是许多开发领域（例如 Node/NPM 生态系统）中使用者做出的假设，正如他们广泛使用 插入符范围 ↗。

意外地将向后不兼容的更改作为补丁版本或次版本发布

一旦您意识到自己发布了破坏性变更，就应纠正该问题，并在新的次版本中恢复向后兼容性。

请考虑以下示例。

  1. 您有一个名为 myFunction 、版本为 1.0.0 的函数，它接受单个字符串输入。
  2. 您向 myFunction 添加了一个新的必需输入，并在次要版本发布中意外发布了此更改 1.1.0。

要解决此问题，您可以撤销对签名的破坏性更改（也就是说，移除您在 1.1.0中新添加的必需输入），并在版本 1.2.0中发布此更改。

在发布失败或尚未发布时检查向后兼容性

对于 TypeScript 或 Python 函数，您的函数可能会失败，或者需要几分钟才能发布。在这两种情况下，内置的向后兼容性检查都将无法运行。如果您想在发布新版本之前查看这些检查的结果，您有以下选项：

  • 如果上一次发布失败，您应该使用“自定义标签”选项与最后一个成功的标签进行比较。
  • 如果上一次发布尚未发布完毕，您应该等待其完成。
