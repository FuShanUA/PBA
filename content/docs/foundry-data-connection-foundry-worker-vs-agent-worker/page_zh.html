Foundry worker 与 agent worker 的对比

旧版

Agent worker 的开发目前处于 旧版 阶段。Foundry worker 是运行所有数据连接源的推荐方式。本页将说明其中的原因，并解答有关从 agent worker 迁移的常见问题。

背景

Agent worker 曾是数据连接源在 Foundry 中运行的最初方式：各项功能在客户管理的 agent 在客户网络内托管。 Foundry 工作进程 是当前所有数据源的推荐选项：各项功能在 Foundry 的容器化、可扩展的作业执行环境中运行。代理现在仅充当网络代理，并遵循 代理出口策略；它们不再执行功能。

请参阅 架构图 以了解每种连接类型如何组合在一起，以及 核心概念 以查看定义。

Foundry worker 的优势

可扩展性与隔离性

Foundry worker 在专属容器中运行每项功能，容器大小根据作业而定。作业不再争夺代理的共享 JVM 堆，长时间运行的同步任务也不会再阻止短作业并行执行。计算资源可按每个作业独立扩展，而不受单个代理主机容量的限制。

稳定性与发布节奏

Foundry worker 在 Foundry 的托管计算环境中运行，并随平台其余部分持续更新。Agent worker 在客户管理的主机上运行，只能在代理的 维护时段，通常每周一次。因此，缺陷修复和改进需要更长时间才能到达代理。代理工作进程还会受到主机级问题（资源耗尽、操作系统或 JVM 问题、计划停机）的影响；请参阅 代理故障排查 以了解常见故障模式。Foundry 工作进程通过将客户管理的运行时从执行路径中移除，避免了这些问题。

访问所有功能和最新开发内容

虚拟表、 虚拟媒体、 在代码中使用源 来自 外部转换, 外部函数 和 计算模块，以及近年来新增的若干功能不在 agent worker 上运行。新功能和持续的功能开发仅面向 Foundry worker。

更低的运维负担

Foundry worker 消除了调整 agent JVM 堆、规划 agent 主机容量以及在操作系统层面监控 agent 进程的需要。当 agent 仍在使用时，它们仅通过 agent 代理 充当网络代理——与在 agent 上运行计算相比，运维开销要小得多。

更简洁的凭证生命周期

Foundry 集中管理数据源凭证，而不是将其绑定到特定 agent。将 agent 重新分配给数据源时，不再需要重新输入机密信息。重新预配 agent 主机也不会使凭证失效。

常见问题

Foundry worker 与 agent worker 一样安全吗？

是的。在这两种模式下，Foundry 存储的源凭据在静态和传输过程中均经过加密。唯一的实质性区别在于源凭据加密密钥的存放位置：是存放在代理主机的磁盘上（agent worker 模式），还是在 Foundry 内部进行安全管理（Foundry worker 模式）。使用 agent proxy，与源系统之间的网络连接仍仅限出站方向，且由您网络内部的代理发起。这与 agent worker 模式一致。

Foundry worker 的性能是否与 agent worker 相当？

是的。容器化作业不会争用单个代理的堆内存，并且可以按作业进行扩展。

这会改变我的网络连接模式吗？

不会。使用 agent proxy，代理仍会向 Foundry 发起出站 WebSocket 连接，且流向您源系统的所有流量仍源自您网络内部的代理——不会为您的网络引入新的入站路径，与 agent worker 的模式相同。变化的是 能力执行的位置，而不是 Foundry 连接到您系统的方式。

我现有的 agent worker 数据源会怎么样？

现有的 agent worker 数据源将继续正常工作。Agent worker 是旧版功能，但仍受到全面支持。当您准备好时，可使用 引导式向导完成迁移。请注意，此迁移在 30 天内可撤销。

那么 agent proxy 呢？

Agent proxy 与 agent worker 并不相同。 Agent proxy 是 Foundry worker 的一种网络连接模式，而不是一种 worker 类型。如果在关于新数据源的讨论中出现“agent”一词，所指的几乎总是 agent proxy。参见 架构 以查看架构图。

将数据源从 agent worker 切换到 Foundry worker

大多数基于 agent 的数据源都应迁移到 Foundry worker，可以是 直接连接 用于可从 Foundry 访问的系统，或 agent-proxy 连接 用于托管在独立网络上的数据源。

如果您在从 agent worker 迁移到 Foundry worker 的过程中遇到任何问题，可以在 30 天内恢复之前的连接设置。

前提条件

在开始迁移之前，请确保满足以下条件：

  • 您至少有一个已分配给该数据源且状态正常的代理，该代理可以提供数据源机密、证书以及 JDBC 驱动程序（如适用）。
  • 您拥有创建出口策略所需的权限。要创建新的出口策略，您必须有权访问名为 Manage network egress configuration 的工作流（位于 控制面板中），该访问权限将授予 Information Security Officer 角色。

迁移步骤

要执行向 Foundry worker 的迁移，请按照以下步骤操作：

  1. 导航至 连接设置 > 连接详情 并选择 计算:代理工作进程。这将打开一个对话框，您可以在其中选择 迁移到 Foundry 工作进程。
  1. 查看迁移概述。该分步引导对话框将说明所涉及的步骤，并确认该过程是可逆的。选择 继续 以继续。
  1. 选择一个代表性代理。请选择当前已分配给该源的健康代理。所选代理用于将机密和证书复制到 Foundry，并根据该代理的当前设置建议所需的出站配置。您必须确认，所选代理上的机密将保存到 Foundry。
  1. 将证书复制到源。使用 Foundry worker 时，必须将证书直接应用于源，而非应用于代理。请从代表性代理中选择需要传输到您的数据源的证书。如果在代理上未找到任何证书，则可以跳过此步骤。
  1. （可选）如果源类型需要，请配置 JDBC 驱动程序。从代表性代理中选择一个驱动程序，供 Foundry worker 使用。
  1. 添加出站策略。配置 直接连接 或 代理连接 出站策略,用于定义 Foundry 工作进程应如何访问您的源系统。

  1. 查看确认步骤。在完成迁移之前,请确认以下事项:

    • 所有正在运行的作业(同步、导出、任务)将作为迁移的一部分被终止。已调度的作业将在下次计划运行时在 Foundry 中运行,但未调度的作业必须手动重新启动。
    • 如有必要,您有 30 天的时间可以恢复到之前的配置。

    选择 迁移 以完成该过程。

手动切换

如果您不想使用引导式迁移向导，可以选择 手动切换到 Foundry 工作进程 （位于迁移对话框中）。请注意，手动切换时必须重新输入凭据，因为系统不会执行从代理自动传输密钥的操作。

恢复到代理工作进程

迁移后的 30 天内，您可以将数据源恢复到之前的代理工作进程配置：

  1. 导航到 连接设置 > 连接详情 （位于已迁移的数据源上）。
  2. 在 Compute 下拉菜单中，选择 Agent worker > Revert。
  3. 在 Revert source to Agent worker 对话框中，确认以下事项：
    • 所有连接设置（包括凭证）都将恢复到迁移前的状态。此后所做的任何更改都将丢失。
    • 未调度的作业（同步、导出、任务）将需要手动重启。已调度的作业将在下次计划运行时使用迁移前的连接设置。迁移后成功启动的作业将继续使用迁移后的设置运行，直至完成。
  4. 选择 回退迁移 以确认。

如果您更愿意手动重新配置代理工作节点上的源，而不是恢复迁移前的设置，请选择 切换为通过代理工作节点手动连接 （位于对话框中）。

故障排除

本部分介绍了迁移过程中可能出现的情况，以及建议的解决步骤。请注意，迁移在 30 天内是可逆的。

Could not resolve type id as a subtype of 'com.palantir.magritte.api.Source'

建议的解决方案：

  • 当找不到源所需的依赖项时，会出现这种情况。请确保已配置特定源所需的所有证书、代理和驱动程序，然后重试迁移。

UnknownHostException

建议的解决方案：

  • 请确保已为该源分配正确的出口策略。
  • 确认 Foundry 能够访问引发异常的端点。

Driver class not found

建议的解决方案：

  • 确认正确的驱动程序已上传到 JDBC 源。

PKIX path building failed

建议的解决方案：

  • 确保已将正确的证书添加到源。
