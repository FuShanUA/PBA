在证书过期后恢复代理连接

如果连接 Foundry 所需的证书在替换证书安装之前过期或被轮换，Agent Manager 可能会失去与 Foundry 的连接。这包括用于信任 Foundry 的证书以及用于检查 TLS 流量的代理的证书。通过 管理代理证书 单独添加替换证书无法修复已断开连接的 Agent Manager：它需要一个正常工作的连接来获取更新。

检查主机上的 Agent Manager 日志中是否存在证书验证错误，例如 SSLHandshakeException, PKIX path building failed，或 CertificateExpiredException。从 Palantir Support 获取 Foundry 的当前证书颁发机构 (CA) 证书，或从网络管理员处获取代理的证书。如果 Foundry 或代理仍在提供过期的服务器证书，其管理员必须先续订证书，然后才能恢复代理连接。

在 Data Connection 中使用以下方法将所需的证书添加到受影响的代理 管理代理证书，然后选择以下恢复方法之一。对每个受影响的代理重复此过程。

更新主机上的信任库

  1. 以运行 Agent Manager 的用户身份连接到主机。导航到其安装目录，如果配置了自动重启则将其禁用，停止 Agent Manager，并备份其信任库：

使用当前证书重新安装

如果无法更新本地信任库，请使用包含当前证书的新软件包重新安装现有代理：

  1. 在 Data Connection 中添加证书后，选择 重新安装代理 在现有代理的概览页面上，获取新的下载 URL。下载新的软件包；旧软件包仍将包含之前的证书。
  2. 请按照 重新安装代理，包括停止旧安装并保留其源加密密钥。保留 var/data/source-encryption-key and var/data/source-encryption-key.private 来自旧安装，以便现有的源凭据仍然可用。
  3. 确认 Agent Manager 和代理均在 Data Connection 中重新连接。

代理配置的常见问题

代理和代理管理器显示 "offline" 状态，但在代理主机上返回 "running"

  • 第一步是检查从安装代理的主机是否可以访问 Foundry。为此，请运行 curl -s https://<your domain name>/magritte-coordinator/api/ping > /dev/null && echo pass || echo fail 在安装代理的主机上。
    • 如果一切正常，您应该会看到 pass 作为输出。在这种情况下，您应该：
      • 确定是否需要代理服务器才能访问 Foundry，如果需要，请检查代理是否已配置为使用该代理服务器（有关如何配置代理以使用代理服务器的说明，请参阅 代理服务器配置 页面）。您可以通过运行以下命令来验证是否正在使用代理服务器 echo $http_proxy 在基于 Unix 的机器的命令行上。
      • 如果您认为不需要代理服务器，或者已经配置了代理服务器，请联系您的 Palantir 代表。
    • 如果无法从主机访问 Foundry，您可能会看到如下错误： curl: (6) Could not resolve host: ...。在这种情况下，很可能是某些东西阻止了连接（例如防火墙或代理服务器），您应该联系您的 Palantir 代表。

代理管理器显示 "offline" 状态

  • 检查以下内容 <agent-manager-install-location>/var/log/startup.log file.

    • 如果您看到以下错误： Caused by: java.net.BindException: {} Address already in use，则表示已有进程正在使用代理管理器尝试绑定的端口。

      • 要解决此问题，您应首先确定代理管理器尝试绑定的端口。可以通过检查以下内容来完成 <agent-manager-directory>/var/conf/install.yml 文件并查找 port 参数（例如 port: 1234 - 此处 1234 即为端口号）。请注意，如果未定义端口参数，代理管理器将使用默认端口 7032。
      • 一旦您知道了代理管理器尝试绑定的端口，就应该识别已在该端口上运行的进程。可以通过运行以下命令来实现： ps aux | grep $(lsof -i:<PORT> |awk 'NR>1 {print $2}' |sort -n |uniq) where <PORT> 是代理管理器尝试绑定的端口。
        • 如果上述命令返回的响应包含： com.palantir.magritte.bootvisor.BootvisorApplication 则表示另一个代理管理器已在运行。
        • 在这种情况下，您应该确定这是否是有意为之；如果是，您需要按照以下步骤更改配置中的端口，以避免两个代理管理器发生冲突。否则，您需要确定要在此主机上使用哪个特定的代理管理器安装，停止其他正在运行的实例，并仅启动您今后打算使用的那个。

    • 要修复 BindException 错误，您需要为代理管理器找到一个当前未被使用的新端口。

      • 端口号应介于 1025 和 65536 之间（端口号 0 到 1024 保留给特权服务，并被指定为知名端口）。
      • 您可以通过执行以下命令来检查某个端口上是否已有进程在运行： lsof -i :<PORT> where <PORT> 是所选的端口号。

    • 找到可用端口后，您需要添加（或更新） port 参数，该参数位于以下路径的配置中： <agent-manager-directory>/var/conf/install.yml

    • 下面是一个示例 Agent Manager 配置片段，其中端口设置为 7032:

      Copied!
      1
2
3
...
port: 7032
auto-start-agent: true

    • 保存上述配置后，运行以下命令重启 Agent Manager： <agent-manager-root>/service/bin/init.sh stop && <agent-manager-root>/service/bin/init.sh start.

引导程序显示 "never reported" 状态

  • 检查以下内容 <agent-manager-directory>/var/data/processes/<latest-bootstrapper-directory>/var/log/startup.log 文件。

    • 如果您看到以下错误： Caused by: java.net.BindException: {} Address already in use，则表示 Bootstrapper 尝试绑定的端口上已有进程在运行。

      • 要解决此问题，您首先需要确定 Bootstrapper 尝试绑定到哪个端口。这可以通过在 Data Connection 应用中导航到代理概览页面来完成。在该页面中，您需要选择“高级”配置按钮，然后点击“Bootstrapper”选项卡。Bootstrapper 将尝试绑定的端口定义在 port 参数中（例如， port: 1234 ——此处 1234 即为端口号）。请注意，Bootstrapper 的默认端口为 7002。
      • 知道 Bootstrapper 尝试绑定的端口后，您应确定已在该端口上运行的进程。可以通过运行以下命令来实现： ps aux | grep $(lsof -i:$PORT |awk 'NR>1 {print $2}' |sort -n |uniq) where $PORT 是 Bootstrapper 尝试绑定的端口。
        • 如果上述命令返回的响应中包含 com.palantir.magritte.bootstrapper.MagritteBootstrapperApplication 则表示另一个 Bootstrapper 已在运行。
        • 在这种情况下，您应确定这是否是有意为之；如果是，您需要按照以下步骤更改配置中的端口，以避免两个 Bootstrapper 冲突。否则，您需要确定要在此主机上使用哪个特定的 Bootstrapper 安装，停止其他正在运行的实例，并仅启动您今后打算使用的那个。

    • 要修复 BindException 错误，您需要为 Bootstrapper 找一个当前未被使用的新端口。

      • 端口号应介于 1025 和 65536 之间（端口号 0 到 1024 保留给特权服务，并被指定为知名端口）。
      • 您可以通过执行以下命令来检查某个端口上是否已有进程在运行： lsof -i :<PORT> where <PORT> 是所选的端口号。

    • 找到可用端口后，您需要设置 port 参数，该参数位于 Bootstrapper 的配置中。这可以通过在 Data Connection 应用中导航到代理概览页面来完成。在该页面中选择高级配置按钮，然后导航到“Bootstrapper”选项卡。

    • 下面是一个示例 Bootstrapper 配置片段，其中端口设置为 7002:

      Copied!

  adminConnectors:
    ...
    port: 7002 #This is the port value

    • 更新配置后，您需要保存更改并重启代理，以使更改生效。

代理显示 "online" 但不响应重启

多数情况下，这是由另一个正在运行的代理“幽灵”实例导致的，您需要找到并将其关闭。

要查找并终止旧进程，请按照以下步骤操作：

  1. 通过运行以下命令停止 Agent Manager： <agent-manager-install-location>/service/bin/init.sh stop.
  2. 删除 <agent-manager-install-location>/var/data/processes/index.json file.
  3. 运行 for folder in $(ls -d <agent-manager-root>/var/data/processes/*/); do $folder/service/bin/init.sh stop; done 以关闭旧进程。
  4. 返回 Data Connection 并检查代理是否不再报告（需要 2-3 分钟）。
  5. 启动 Agent Manager（<agent-manager-install-location>/service/bin/init.sh start).

在安装代理的主机上手动启动代理（而不是通过 Data Connection 启动）可能会导致产生“幽灵”进程。

代理状态显示 "Unhealthy"

代理进程显示为“不健康”时，通常是因为它已崩溃，或被操作系统或其他软件（如防病毒软件）关闭。

操作系统关闭该进程的原因有多种，但最常见的原因是操作系统没有足够的内存来运行它，这被称为 OOM（内存耗尽）终止。

要检查是否有任何 agent 或 Explorer 子进程被操作系统因 OOM（内存不足）而终止，你可以运行以下命令： grep "exited with return code 137" -r <agent-manager-directory> --include=*.log。这将在 Agent Manager 目录中的所有日志文件里搜索包含 'exited with return code 137' 的条目（返回码 137 表示进程因 OOM 被终止）。

以下是上述命令生成的示例输出，显示 agent 子进程正在因 OOM 被终止： ./var/data/processes/bootstrapper~<>/var/log/magritte-bootstrapper.log:ERROR [timestamp] com.palantir.magritte.bootstrapper.ProcessMonitor: magritte-agent exited with return code 137。如果你看到类似这样的输出，你应该按照以下步骤调整堆大小。

你还可以通过运行以下命令来检查操作系统日志中的 OOM 终止条目： dmesg -T | egrep -i 'killed process'。此命令将在内核环形缓冲区中搜索 'killed process' 日志条目，这表示进程因 OOM 被终止。

被 OOM 终止的进程的实际日志条目如下所示：

  • [timestamp] Out of memory: Killed process 9423 (java) total-vm:2928192kB, anon-rss:108604kB, file-rss:0kB, shmem-rss:0kB, UID:0 pgtables:1232kB oom_score_adj:0
  • 上面的日志行显示被终止的进程的 PID 为 9423（注意：你的日志信息可能因 Linux 发行版和系统配置而异）。
  • 在这种情况下，你应该尝试验证被终止的进程是否与你的 agent 相关。最简单的方法是对齐时间戳，即如果某个条目的时间戳与你的 agent 变得不健康的时间相吻合，则两者很可能是相关的。注意，任何不包含 (java) 的条目都可以忽略，因为它们与你的 agent 无关。
调整堆大小

在更改任何堆分配之前，你应该首先：

  • 计算主机有多少可用内存。
  • 要查看主机有多少可用内存，你可以运行 free -h。在一个 6 GB 的系统上，输出可能如下所示：
Copied!
1

                total        used        free      shared  buff/cache   available
Mem:          5.8Gi       961Mi       2.8Gi       9.0Mi       2.1Gi       4.6Gi
Swap:         1.0Gi          0B       1.0Gi

在 free 命令生成的输出中， available 列显示了可以用于启动新应用程序的内存量。要确定可以分配给 agent 多少内存，我们建议你停止 agent 并运行 free -h ，同时使系统处于正常到高负载状态。available 值将告诉你可以为所有 agent 进程（合计）分配的最大内存量。如果可能，我们建议你预留大约 2 - 4GB 的缓冲区，以应对系统上其他进程需要更多内存的情况，以及 agent 进程的堆外内存使用。并非所有版本的 free 都会显示 available 列，因此你可能需要查阅你系统上版本的文档以找到等效的信息。

确定分配给以下每个子进程的内存量：Agent Manager、Bootstrapper、agent 和 Explorer。

要了解分配给 agent 和 Explorer 子进程的内存量，你应该导航到 Data Connection 中的 agent 配置页面，选择高级配置按钮，然后选择 "Bootstrapper" 标签页。在那里你会看到每个子进程都有自己的配置块；在每个配置块中，你应该会看到一个 jvmHeapSize 参数，它定义了分配给相关进程的内存量。

默认情况下，Bootstrapper 子进程被分配 512mb 的内存。可以通过首先导航到 <agent-manager-directory>/var/data/processes/ 目录来确认这一点；然后你需要运行 ls -lrt 来找到最近创建的 bootstrapper~<uuid> 目录。进入最近创建的 bootstrapper~<uuid> 目录后，你可以检查 ./var/conf/launcher-custom.yml 文件的内容。其中， Xmx 值就是分配给 Bootstrapper 的内存量。

默认情况下，Agent Manager 子进程也被分配 512mb 的内存。可以通过检查文件 <agent-manager-directory>/var/conf/launcher-custom.yml的内容来确认这一点。其中， Xmx 值就是分配给 Agent Manager 的内存量。

安装在 Windows 机器上的代理不使用 launcher-custom.yml 文件，因此默认情况下，Java 会为 Agent Manager 和 Bootstrapper 进程各分配系统可用总内存的 25%。要解决此问题，您需要手动设置 Agent Manager 和 Bootstrapper 的堆大小，可按照以下步骤操作：

  1. 确保您已终止所有代理进程，即：（Agent Manager、Bootstrapper、agent 和 Explorer）。
  2. 设置 JAVA_HOME： setx -m JAVA_HOME "{BOOTVISOR_INSTALL_DIR}\jdk\{JDK_VERSION}-win_x64\"
  3. 设置 Agent Manager 堆大小： setx -m MAGRITTE_BOOTVISOR_WIN_OPTS "-Xmx512M -Xms512M"
  4. 设置 Bootstrapper 堆大小： setx -m MAGRITTE_BOOTSTRAPPER_OPTS "-Xmx512M -Xms512M"
  5. 关闭命令提示符并打开一个新的命令提示符窗口。这是使上述设置生效所必需的。
  6. 启动 Agent Manager： .\service\bin\magritte-bootvisor-win

确定主机有多少可用内存以及分配给上述各子进程多少内存后，您应决定：减少分配给上述进程的内存量，或增加主机的可用内存量。

能否安全地减少代理进程使用的内存量，取决于您的代理设置（例如，最大并发同步数和文件上传并行度）、正在同步的数据类型以及代理的典型负载。减少堆大小会降低操作系统终止进程的可能性，但会增加 Java 进程耗尽堆空间的可能性。您可能需要测试不同的值以找到合适的配置。如果您在调整此值时需要帮助，请联系您的 Palantir 代表。

要减少分配给一个（或多个）子进程的内存量，请执行以下操作：

  1. 决定应为上述各子进程分配多少内存。
    • 注意：我们不建议将堆大小降低到低于下面列出的默认值。
  2. 接下来，在 Data Connection 中导航到该代理，选择高级配置按钮，然后选择 Bootstrapper tab.
  3. 在此，您可以为每个单独的子进程设置 jvmHeapSize 参数。
  4. 下面是一个示例 Bootstrapper 配置片段 使用 代理 的 jvmHeapSize 设置为 3gb： 
    Copied!
    1
2
3
agent:
    ....
    jvmHeapSize: 3g #This is jvm heap size value
  5. 更新配置后，您需要保存更改并重启代理，以使更改生效。

默认堆分配

默认情况下，一个代理需要约 3gb 的内存，分配如下：

  • agent 子进程 1gb
  • Explorer 子进程 1gb
  • Bootstrapper 子进程 512mb
  • agent Manager 子进程 512mb

Java 进程还会使用一定量的堆外内存；因此，我们建议您确保至少留有 ≥ 4gb 的空闲内存供其使用。

无法下载代理安装包

代理下载失败主要有两个原因：网络连接和链接过期。

如果您可以连接到 Foundry，但在下载时收到无效的 tar.gz 文件或错误消息，则您的链接可能已过期或失效。

  • 过期链接： 下载链接在十分钟后过期。
  • 失效链接： 下载链接受一次性下载密钥保护。将代理下载链接粘贴到 Microsoft Teams 等应用程序中可能会使链接失效，因为这些应用程序会尝试扫描链接以查看是否可以预览；此扫描会使一次性下载密钥失效。如果您的链接无效，请尝试在 UI 中重新生成链接，并手动输入两个密钥词，而不是复制整个链接。

如果您在下载代理安装包时遇到 disconnected unexpectedly 错误，请尝试强制 curl 使用 HTTP 1.0，方法是在下载命令中添加 --http1.0 标志。这可以解决在某些网络环境中可能出现的协议协商问题。

无法管理代理

用户必须是 Project 的编辑者才能在该 Project 中创建代理，但必须是该 Project 的所有者才能管理该 Project 中的代理。这意味着用户可以创建代理，但随后可能无法生成下载链接或对该代理执行其他管理任务。有关代理权限的更多信息，请查阅我们 权限参考 文档。

由于 PERMISSION_DENIED 错误而无法创建代理

如果您收到 PERMISSION_DENIED 错误（在尝试创建代理时），请验证以下内容：

  • 组织级角色： 您必须拥有 Organization administrator, Data flows administrator，或分配了 创建数据连接代理 工作流的自定义角色。组织角色在 组织权限 页面（位于 Control Panel 中）进行管理。
  • Project 级角色： 您必须是 Editor or Owner 您想在其中保存新创建代理的 Project 的相应权限。

如果您仅在现有 Project 上拥有 Editor 权限，但缺少所需的组织级角色，请尝试在其他您拥有相应权限的 Project 中创建代理，或向管理员申请必要的角色。

有关代理权限的更多详细信息，请查阅我们 权限参考 文档。

使用不安全的 TLSv1.0 和 TLSv1.1 协议连接到数据源

Palantir 不支持 TLSv.1.0 和 TLSv1.1，因为它们是过时且不安全的协议。Data Connection 代理所使用的 OpenJDK 的 Amazon Corretto 构建版本在 jdk.tls.disabledAlgorithms 安全属性（位于 java.security 文件。

尝试连接到仅支持 TLSv1.0 和 TLSv1.1 的数据源系统时将失败，并出现各种错误，包括 Error: The server selected protocol version TLS10 is not accepted by client preferences.

我们强烈不建议使用已弃用的 TLS 版本。Palantir 对使用这些版本所带来的安全风险不承担责任。

如果确实存在临时支持 TLSv1.0 和 TLSv1.1 的关键需求，请执行以下步骤：

  1. 在代理概览页面中，导航至 代理设置 并选择 高级 菜单中选择 管理配置 部分。然后，选择 Bootstrapper tab.
  2. 将 tlsProtocols 条目添加到两个 agent and explorer 配置块中，后跟您要启用的协议。请务必同时包含 TLSv1.2，以免使用该协议的数据源中断。例如：

配置代理日志

要调整代理在其主机上的日志存储设置，请按照以下步骤操作：

  1. 在 Data Connection 中，导航到 代理 页面。选择您要配置的代理的名称。
  2. 在配置面板中，选择 高级.
  3. 日志的配置选项可在 日志记录 块下找到。在此处，您可以配置何时开始丢弃日志的限制、是否以及如何归档日志，以及其他设置。
    • 该配置应考虑分配给代理主机的资源、您对日志级别粒度的偏好，以及您对日志保留的偏好。有关更多信息和指导，请查阅 Dropwizard 配置参考 ↗.
  4. 在 Foundry 中重启代理，方法是选择 重启代理 （位于屏幕右上角）。

您的新配置现在应该已生效。

我的代理已停机（不可用）多长时间了？

代理不可用可能有多种原因；例如，代理可能正在重启，或者运行代理的底层硬件可能处于离线状态或正在重启。

有两种方法可以确定代理首次变为不可用的时间：

  • 在 Data Connection UI 中选择您的代理后，您可以在 Metrics tab.
  • 在监听器设置向导的 概述 部分（位于 Data Connection UI 中）查看代理的状态，以及代理状态上次报告的日期和时间。

当安装代理的主机崩溃时，缓存文件会发生什么？

这些文件将保留在磁盘上，直到 Bootvisor 清理旧的进程文件夹（30 天或 10 个旧文件夹会触发清理）。这些文件已加密，而解密它们的密钥仅存在于已终止进程的内存中。
