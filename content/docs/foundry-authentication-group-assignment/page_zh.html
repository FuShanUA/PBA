分组分配

作为设置身份验证提供程序的一部分，管理员可以定义基于规则的组。基于规则的组成员资格是根据登录时评估的规则自动分配的。可以为每个身份验证提供程序配置这些规则。要设置基于规则的组，请导航至 Control Panel > Authentication > Authentication provider > Manage group assignment 以使用分组分配编辑器。

定义基于规则的组

规则

分组分配规则包含一个或多个 AND 条件，这些条件根据用户属性或提供程序组进行评估。对于每条规则，符合所有条件的用户将被分配到指定基于规则的组的成员资格。管理员可以通过对同一组应用单独的分配规则来指定 OR 条件。

条件使用正则表达式（regex）模式进行匹配。提供三种匹配选项：

  • 包含模式匹配：该模式匹配用户的至少一个提供程序组或用户数组类型属性中的某个值。
  • 不包含模式匹配：该模式不匹配用户的任何提供程序组，或不匹配用户数组类型属性中的任何值。
  • 等于模式匹配：该模式匹配用户的字符串类型属性。

组

Foundry 在整个平台中使用三种类型的 用户组 ：

  1. 基于规则的组：用于管理员定义的、在登录时应用的规则。
  2. 内部组：在 Foundry 中手动分配，可以包含用户以及其他外部组、基于规则的组或内部组。
  3. 外部组：也称为提供程序组，这些组在外部定义，通常由身份提供程序定义。这些组在用户登录时被导入。

在这三种组类型中，只有基于规则的组成员资格可以在 Foundry 中使用此处讨论的自动化规则来定义。

基于规则的组有助于保证组成员资格的清晰性和一致性，因此我们建议尽可能使用基于规则的组而非内部组。内部组适用于临时访问、临时群组创建，或外部身份提供程序无法满足的特定入职或撤销需求的情况。由于这些情况下的访问需要人工参与，基于规则的组所使用的属性和组条件可能不足以确定访问权限。

验证和测试

  • 导航至 Control Panel > Authentication > Authentication provider > Manage group assignment > Test rules 以针对现有用户验证规则。这将显示用户匹配哪些规则以及他们在下次登录时将被分配到哪些组。只有已使用此提供程序登录过的用户才能在 测试规则 panel.
  • 规则在用户登录时应用，无论他们是现有用户还是新用户。规则 不会追溯运行 在保存时。
  • 正则表达式的正确性是定义基于规则的组时常见的故障点。不匹配的模式往往会悄无声息地失败，同时导致意外的用户分配。常见原因包括：
    • 部分模式：模式必须完整匹配提供程序组名称或属性值，而不是部分匹配。模式 admin 不匹配该组 admin-users。使用 admin.* instead.
    • 未转义的特殊字符：未转义的 . 匹配任意字符，因此模式 team.a 也匹配 team-a。请转义需要按字面匹配的特殊字符，例如 team\.a.
    • 意外的大小写：匹配区分大小写。在模式开头添加 (?i) 以使其不区分大小写，这样 (?i)admin.* 同时匹配 Admin-Users and admin-users.
    • 反向条件：使用不包含模式匹配的条件在其模式不匹配用户的任何提供程序组或属性值时即满足，因此拼写错误会导致该条件无法排除任何人，并将该组分配给满足规则其他条件的每个用户。

从组 AUM 迁移到基于规则的组

某些 Foundry 身份验证设置使用一种名为 group asynchronous user manager (AUM) 的旧版工具来进行自动用户分配。Group AUM 没有用户界面，它由 Palantir 代表根据客户管理员的指示进行配置。

启用了 group AUM 的客户注册无法使用基于规则的组。未来，group AUM 规则将自动迁移到基于规则的组规则。
