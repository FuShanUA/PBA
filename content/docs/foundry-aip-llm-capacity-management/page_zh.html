LLM 容量管理

LLM 容量是行业层面的有限资源，所有提供商（Azure、OpenAI、AWS Bedrock、Google Cloud Vertex 等）均限制每个账户可用的最大容量。因此，Palantir AIP 遵循 LLM 提供商引入的市场级约束。整个行业的标准计量单位是每分钟令牌数（TPM）和每分钟请求数（RPM）。

注册容量与速率限制

Palantir 为每个注册设定了一定的最大容量，称为“注册级别速率限制”。该容量使用 TPM 和 RPM 按模型进行度量，涵盖您的注册中启用的所有提供商的所有模型，包括 GPT、Claude、Gemini、Llama、Mixtral 等。通过这种方式，每个模型都拥有单独、独立的容量，不受其他模型使用情况的影响。

AIP 中的 LLM 容量在三个层面进行管理：注册级别限制设定总体上限， 项目速率限制 控制每个项目可使用的容量，而 用户速率限制 则管控未归属于项目的流量的单个用户消耗。

默认情况下，所有客户均处于中等层级，该层级的容量足以构建原型并扩展到若干用例，即使面对数百名用户和大型数据集（例如数百万份文档）也绰绰有余。

此外，如果需要额外的容量，AIP 提供将注册容量从中等层级升级为大型或 XL 层级的选项。如果您频繁达到注册速率限制，导致无法扩展 AIP 的使用，或者预计将增加管道数量或用户总数，请联系 Palantir 支持团队。

注册限制现在显示在 AIP 速率限制 标签页（位于 Resource Management 应用程序）中，同时还显示注册层级。

AIP 通过注册层级（尤其是 XL 层级）提供足够的容量来构建大规模工作流。这些层级已为数百家大规模使用 LLM 的 Palantir 客户提供了充足的容量，并且我们会继续提高这些限制。

有关各模型和各层级注册速率限制的完整明细，请参阅 LLM 注册速率限制。

AIP 使用情况和限制

注册管理员可以导航到 AIP 使用情况和限制 页面（位于 Resource Management 应用程序中），以执行以下操作：

  • 查看使用情况： 查看您注册中所有项目和资源在所有 Palantir 提供的模型上的 LLM token 和请求使用情况。

  • 管理速率限制： 管理您注册的项目和用户速率限制。

    • 项目速率限制： 按模型配置给定项目中所有资源在任意给定分钟内合计可使用的 TPM 和 RPM 的最大百分比。
    • 用户速率限制： 按模型配置任何单个用户在任意给定分钟内可使用的最大 TPM 和 RPM。

根据 AIP 使用情况采取行动

如果您在注册或项目级别达到速率限制,可以考虑采取以下任一措施:

  • 调整项目限制,为可能占满您注册容量的特定资源或项目设置使用上限。
  • 跟踪交互式使用情况,确保其没有因管道而受到速率限制。如果确实如此,您可以在项目级别限制这些管道,或者将资源移至限制更高的单独项目。
  • 将构建安排在一天中的不同时间段,并将大型构建安排在周末——尽可能避免同时运行多个大型构建,并尽可能将常规构建安排在不同时间或以不同频率运行,以避免冲突。
  • 将您的工作流切换到您的注册当前尚未使用、因此可用容量充足的其他模型。
  • 请求升级到更大的层级。

管理速率限制

LLM 请求按以下两种方式之一进行归因，且这两种方式互斥——每个请求仅受其中一种限制类型的约束：

  • 按项目归因的请求 受注册限制和相关项目限制的约束。这涵盖请求源自已配置项目资源的工作流（例如 Pipeline Builder 管道、AIP Logic、Automate、Chatbot Studio 和 Workshop 应用）。按用户限制不适用于这些请求。
  • 按用户归因的请求 受注册限制和调用用户的按用户限制的约束。这涵盖请求直接源自用户会话（而非项目资源）的工作流（例如 AI FDE、AIP Assist、AIP Analyst、Pipeline Builder Explain 和 Generate 等原生助手功能，以及 Continue (VS Code) 和 Claude Code 等连接到 Foundry 所提供模型的 IDE 集成）。

管理项目速率限制

在 管理速率限制 标签页（位于 AIP 用量和限制 页面（位于资源管理中），管理员可以灵活地在 AIP 中出现宏大用例时，最大化面向生产用例的 LLM 使用量，并限制或禁止实验性项目占满整个注册容量。注册管理员可以按模型配置给定项目内所有资源在任意给定分钟内合计可使用的 TPM 和 RPM 的最大百分比。

默认情况下，所有项目都会获得一个特定的运行限额。管理员可以创建额外的项目限额，定义每个限额包含哪些项目，以及可以使用注册容量的百分比。

模型覆盖设置

在每个项目限额内，您可以配置特定于模型的覆盖设置，以进一步控制模型层面的容量分配。模型覆盖设置允许您为各个模型设置不同的百分比限额，从而覆盖基础项目限额。这些覆盖设置仅适用于包含在该特定项目限额中的项目（对于默认限额，则适用于未分配到任何其他手动创建的项目限额的所有项目）。

模型覆盖支持更细粒度的容量管理，并允许您创建模型“允许列表”；您可以将基础项目限制设置为 0%，然后仅为已批准的模型添加具有特定百分比的模型覆盖。您还可以通过将特定模型的覆盖限制百分比设置为 0% 来明确禁止使用这些模型。

例如，以下步骤说明了如何限制项目限制中的项目仅使用 Claude Sonnet 4 和 GPT-4.1：

  1. 将基础项目限制设置为 0%。
  2. 为 Claude Sonnet 4 添加 30% 的模型覆盖。
  3. 为 GPT-4.1 添加 25% 的模型覆盖。

包含在此项目限制中的所有项目的用户，将只能在其分配的容量限制内访问指定的模型。

用户速率限制

单用户速率限制用于管控单个用户在归属于该用户的请求中可用的容量。它们可确保任何单个用户都无法通过交互式工作流耗尽该注册中某个模型的全部容量。

用户速率限制在 管理速率限制 选项卡上进行管理，该选项卡位于资源管理的 AIP 使用与限制 页面下。注册管理员可以查看默认的单用户限制、创建用户组覆盖以及配置单模型覆盖。

默认单用户限制

每个模型的默认每用户限额显示在 选项卡中(位于 列中(位于 注册速率限制表)。这些默认值由 Palantir 设置,适用于所有用户,除非管理员在 用户速率限制 选项卡中进行了覆盖。 每个模型的默认每用户限额显示在 用户速率限制 选项卡中(位于 每用户限额 列中(位于 注册速率限制表)。这些默认值由 Palantir 设置,适用于所有用户,除非管理员在 用户速率限制 选项卡中进行了覆盖。

我们建议使用 Palantir 的默认用户速率限制。我们定义这些限制,旨在平衡以下两个方面:(a) 防止注册限额被单个用户占满;以及 (b) 让用户能够高效使用 Foundry 中的最新 AIP 工具,从而最大限度地提高工作效率。如果管理员选择为所有模型设置新的自定义限制,则应随着新模型的发布重新审视该限制,以确保不会无意间限制其用户。

每用户覆盖设置

注册管理员可以覆盖每用户默认值，为特定用户（作为特定用户组的一部分）授予不同的每用户限制。这对于高级用户、交互式应用程序背后的服务账户，或者其用户归属工作流需要持续高吞吐量的团队非常有用，而无需提高注册的整体容量层级。它也可作为一种工具，用于保护生产工作流中使用的某个模型的容量，避免被用户意外占满。

每用户覆盖可以通过以下两种方式之一来表示：

  • 注册限制的百分比： 介于 1 到 100 之间的值，表示注册级别速率限制的百分比。例如，如果某个注册对某个模型拥有 400 万 TPM，而管理员配置了 25% 的覆盖，则受该覆盖影响的任何用户将获得 100 万 TPM 的有效限制。
  • 绝对 TPM 和 RPM 值： 明确的每分钟令牌数和每分钟请求数值。当基于百分比的方法不符合所需限制时，这为管理员提供了精确的控制。

配置覆盖后，它将取代已发布的每用户默认值；它不会与默认值混合，也不会受默认值下限的约束。

将某个模型的每用户限制设置为低于 50,000 TPM 或 10 RPM，可能会导致受影响用户的某些 AIP 功能无法正常使用。当配置的限制低于这些建议的最低值时，覆盖表单会显示警告。

覆盖级别

每用户覆盖可以在三个级别进行配置，并按具体程度依次应用：

  1. 默认每用户覆盖： 一个适用于该注册中所有用户、且跨所有模型生效的统一百分比。它将成为新的基线，取代 Palantir 发布的各模型默认值。
  2. 按模型覆盖： 在默认值的基础上，针对一个或多个特定模型设置的不同百分比或绝对限制。按模型覆盖允许管理员针对单个模型提高或降低每用户限制，而无需更改整个目录范围内的限制。
  3. 用户组覆盖： 针对一个或多个 Foundry 用户组的覆盖。用户组覆盖定义自身的默认百分比，并可选择定义自身的按模型覆盖（百分比或绝对限制）。当用户属于某个覆盖所针对的用户组时，将使用该组的配置，而不是整个注册范围内的每用户默认值。

如果未在任何级别配置覆盖，则将使用该模型发布的每用户默认值。

用户组覆盖的解析方式

用户组覆盖适用于一组具名的 Foundry 用户组。每个覆盖都包含一个名称、可选的描述、可选的默认百分比，以及一组可选的各模型限制。当用户属于某个覆盖中列出的任一用户组时，该用户即与该覆盖匹配。

如果用户属于多个覆盖所涵盖的用户组，则在这些覆盖中产生的最高限制将对该用户和模型生效。这使得覆盖具有累加性和可预测性：通过一个用户组授予用户的更高限制，不会因其属于另一个配置较低的用户组而被静默撤销。例如，假设某个注册的默认用户限制为 40%。用户 A 属于两个不同的用户限制覆盖下的两个用户组，其中一个将用户限制定义为 10%，另一个定义为注册容量的 35%。用户 A 的用户限制将为 35%，即各覆盖中最高的限制。

当移除某个用户组覆盖时，受影响用户组的成员将回退到整个注册范围的每用户配置。如果该注册自身没有每用户配置，则回退到已发布的每用户默认值。

AIP 预留容量

预留容量是资源管理中的一项 AIP LLM 容量管理工具。预留容量可保证占用模型可用的每分钟令牌数(TPM)和每分钟请求数(RPM)中的一定份额。请将其用于不得因项目速率限制、注册限制或共享同一池的其他资源竞争而被限流的关键生产工作流。

核心功能

  • 预留容量在模型级别进行配置,即从该模型可用的总容量中预留特定数量的 TPM 和 RPM。
  • 可以为项目分配总预留容量的百分比,使您能够优先保障最关键的资源,并根据组织要求自定义 LLM 分配。
  • 当预留容量耗尽时,已分配该容量的项目将自动回退到受现有项目限制和注册限制约束的共享容量。

可用性和成本

预留容量适用于所有模型。您最多可预留模型总容量的 50%。如果总容量随后减少,您的预留量将予以保留,最多可达新总容量的 95%。

根据过去一年 AIP 的性能表现，预留容量已足以实现 99.9% 的正常运行时间。我们无法保证 100% 的容量可用性，但根据过去一年的使用模式，超过 99% 的 LLM 请求失败是由 enrollment 和项目速率限制导致的。这些问题可以通过预留容量工具加以解决。

预留容量作为一项服务不会产生额外费用；额外费用将取决于额外的 token 用量，这与 AIP 中所有其他 LLM 使用情况相同。对于未来的新用例或特定模型，此政策可能会有所变化。如果此政策发生变化，我们不会对使用预留容量的现有工作流追溯收费；这些工作流将继续仅根据额外的 token 用量产生费用。

具有 resource management administrator 权限的用户可以为模型预留容量，并将其分配给特定项目。

使用示例

请参考以下示例，以进一步了解预留容量的使用：

  • 对于给定模型，您的 enrollment 拥有 100 万 TPM 的容量。对于包含生产应用程序的项目，该应用程序的默认限额为 enrollment 容量的 70%，即 70 万 TPM。
  • 要提高此生产应用程序的容量，您可以通过提高项目速率限制，将包含该应用程序的项目的容量提升至注册容量的 100%，即 100 万 TPM。
  • 虽然该应用程序的限额现已达到注册限额的 100%，但它仍在与其他资源争夺此共享容量。您可以在 查看使用量 标签页（位于 AIP 使用量与限制 部分中，该部分属于资源管理应用程序）中识别竞争资源。之后，您可以错开竞争资源的时间安排，或将资源迁移到不同的模型。
  • 为确保此生产应用程序即使在您优化时间安排和模型使用后仍能获得所需容量，您可以使用预留容量。假设您从可用的 100 万 TPM 中预留 25 万 TPM，剩余 75 万 TPM 作为共享容量。
  • 您可以将该预留容量分配给关键资源，例如您的生产应用程序。该应用程序会首先使用其预留的 25 万 TPM。该容量耗尽后，应用程序将使用 75 万 TPM 的共享容量，并与其他资源竞争。注册的总容量仍为 100 万 TPM：其中 25 万 TPM 专供此应用程序使用，其余 75 万 TPM 由所有资源共享。

AIP 注册中 LLM 成本的可见性

使用 分析 页面来查看您启用了 AIP 的注册中的 LLM 使用成本。

在 分析 页面中，选择 按来源筛选： All LLMs 和 按来源分组。这将生成一个按模型细分的每日 LLM 成本图表。

优先处理交互式查询

通常，AIP 会优先处理交互式请求，而非包含批量请求的管道。交互式查询定义为用户与 LLM 进行的任何实时交互，例如 Workshop、Chatbot Studio、AIP Logic LLM 面板中的预览，以及 Pipeline Builder LLM 节点中的预览。批量查询定义为在用户不期望立即获得响应的情况下发送的大量请求，例如转换管道、Pipeline Builder、Automate（用于 Logic）。

此原则目前保证，注册和项目级别始终会有 20% 的容量预留给交互式查询。这意味着，对于某个模型的 100,000 TPM 容量，在任何给定分钟内，管道最多只能使用 80,000 TPM,而至少有 20,000 TPM(最多可达 100,000 TPM)可用于交互式查询。

常见问题

项目级和用户级速率限制预期如何使用的示例是什么?

请考虑以下示例：

  • 某注册在生产环境中只有一个 AIP 用例，因此包含该用例的项目被移至
  • 除了这个生产用例之外，还有一个处于测试阶段的用例需要考虑。该测试阶段的用例应能够运行测试，而不会占用全部生产用量。可以将此用例添加到容量上限为 30% 的
  • 除了前面提到的用例之外，我们还添加了第二个生产用例。不过，与使用 GPT-5 的第一个用例不同，这个用例使用的是 Claude Sonnet 4.6。我们可以放心地将这个新用例与第一个生产用例一同添加到“生产”限额中。
  • 同一注册希望让一组用户能够试用 LLM。注册管理员将两个项目添加到容量上限为 20% 的“实验”限额中。
  • 从技术上讲，测试项目和这两个实验项目合计最多可消耗 70% 的容量，但历史数据显示，实际使用量通常低于这一水平。
  • 最后，该注册希望防止其生产用例被单个用户占用。管理员将 GPT-5 和 Claude Sonnet 4.6 的默认用户速率限制覆盖值设置为注册容量的 10%，同时提高了 Claude Opus 4.6 和 GPT-5.4 的容量。此外，他们还将用户主文件夹的容量设置为 0%（以避免在私有文件夹中进行构建，并鼓励协作），并在控制面板的 AIP 设置中为这些指定用户授予 LLM 构建者权限。

为什么在限制类别中，百分比是针对每个项目强制执行，而不是在项目和用户之间共享？

  • 多个项目和资源能够共享相同的 100% 容量，原因在于：根据一年多以来数百个客户的历史 LLM 使用模式，大多数项目和资源并不会调用 LLM。因此，多个资源可以共享相同的 100% 容量。
  • 如果限制类别中的所有项目共享相同的使用百分比，则会对使用量实施硬性限制。然而，根据现有的使用情况，这种做法在 99.9% 的情况下并无必要。多个资源在同一分钟内同时使用最大容量的情况极为罕见，即使发生这种情况，请求也会重试直至成功。

为什么会存在 AIP 使用限制？

  • 首先，不同提供商在 TPM、RPM 以及区域可用性方面的服务存在显著差异。虽然 AIP 确实利用了所有提供商的容量，但 Palantir 无法绕过各云服务提供商施加的限制。

  • 除此之外，与大多数提供商的常规服务相比，Palantir 向客户提供的 LLM 容量需要满足更高的合规要求。Palantir 保证零数据保留（ZDR），并可控制数据路由至特定区域（地域限制）。

  • 大多数提供商（即 Azure OpenAI、AWS Bedrock、GCP Vertex 以及 Palantir 托管的模型）均支持地域限制，但对地域受限的请求，其 LLM 容量保证也较小。其他提供商（如 OpenAI 直连、Anthropic 直连和 xAI）在较少的区域提供其模型。

    • 客户在 Control Panel 中的 AIP Settings下启用的模型提供商越多，其获得的容量就越高。
    • 对于使用量较高的客户，我们提供升级到更大层级以获取更多容量的选项。
    • 没有地域限制的 AIP 客户可以使用更大的容量池。
    • 某些模型在某些区域仍未广泛可用。有时 Palantir 会获得这些模型的早期访问权限，但这并非总能实现。
    • 某些功能仍不可用，例如 batch API。Batch API 支持在 24 小时内处理数十亿个 token，但需要在该时间段内存储数据，这无法满足 Palantir 的合规要求。

  • 如上所述，我们的中型到 XL 级别足以支持大规模生产工作流。请联系 Palantir 支持团队以更改您的级别。

解决容量问题的最大障碍是什么？

  • 地域限制是导致容量问题的最主要原因。如果您的注册受到地域限制，并且您能够从法律角度移除地域限制，则应与您的 Palantir 团队合作进行此项操作。
  • 新模型在早期阶段通常容量有限。
  • 对于运行数百万个条目的大型管道，容量问题要难解决得多。
