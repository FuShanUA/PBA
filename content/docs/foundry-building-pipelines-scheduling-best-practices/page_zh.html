调度最佳实践

为了确保生产管道的调度易于管理，我们制定了一套调度指南。使用此页面管理您负责的调度。

  • 每个数据集应仅由一个调度构建。
    • 您可以在数据血缘图中查看每个数据集上的调度数量，方法是选择 调度数量 在节点颜色下拉菜单中。
  • 您必须拥有一个 强制构建 调度，用于每个原始 Data Connection 同步。
    • 其他调度上不应有强制构建。强制构建只应与 Data Connection 同步一起使用。
  • 尽量避免 全量构建 并使用 连接构建 instead.
  • 您的调度应只构建您拥有的数据集；您的调度不应构建您不拥有的数据集。
  • 已删除（回收站中）的数据集不应由您的调度构建。使用 升级助手 来调查和修正包含已删除资源的调度。
  • 为您的调度添加重试（我们建议重试三次，间隔为一到三分钟）。
  • 避免在管道的每个步骤上有多个调度；而应将数据集合并到逻辑调度中。

最佳实践

每个管道一个调度

在大多数情况下，每个管道应只有一个调度。实际上，管道中的每个数据集应只关联一个计划构建。让一个数据集由两个不同的调度构建可能导致排队，并使两个调度都变慢。保持调度集合简单整洁，可以明确每个调度的职责，并在某个数据集上构建失败时更容易调试。这也有助于管道维护；当您想要配置管道时，只需在一个地方进行检查或修改。

对于按多个顺序步骤运行的管道，可以例外；下面描述了其中一些示例：

  1. 如果管道有多个终端节点，您可以考虑为每个节点设置单独的调度。在下面显示的示例管道中，最自然的方法是设置三个调度：定义在 Apex 1, Apex 2 and Apex 3上。但是，在 Shared 上创建调度并将此数据集视为其他管道的输入也可能是有益的。
  2. 如果您的管道使用了验证表，您可能需要为它们设置单独的调度。
  3. 请参阅 稳定性建议 以了解有关如何有效处理此类复杂管道的更多信息。

项目范围的调度

在可能的情况下，所有调度都应设置为项目范围，这样调度能否成功运行就不依赖于单个用户（调度所有者）的权限。否则，调度所有者的权限可能会发生变化，从而阻止调度数据集的构建。这一点尤为重要，因为在编辑调度后，调度的所有权可能会发生变化，因为最后修改调度的用户会成为调度的所有者。

在某些情况下，无法将调度设置为项目范围：

  • 权限被切断的转换
  • Contour 作业
  • Fusion 同步

用户范围的调度：每个调度一个所有者

对于无法设置为项目范围的调度，最好由单个用户拥有给定管道上的所有调度。该用户通常是“服务用户”（不与单个人员绑定的特殊用户账户）。或者，唯一所有者可以是负责项目中所有调度修改的团队负责人。

由单一用户拥有管道上的调度可以降低复杂性，并保护调度免受用户权限或团队构成变化的不利影响。

除了有助于保持权限一致性外，单一所有者还便于在 Builds 应用中跟踪相关构建，您可以在其中按“启动者”筛选所有构建。

如上所述，最后修改调度的用户将成为该调度的所有者。如果多个用户配置文件在管理同一个调度，且团队内的访问权限不统一，那么在未考虑所有权变更的情况下，您可能会遇到难以追溯的权限错误。

使用重试

在配置调度时使用重试。重试是作业的一部分；如果作业因可重试的异常而失败，构建编排层将重新启动同一作业的新尝试，而不会使构建失败。

我们建议将调度配置为至少三次重试，且重试之间至少间隔一分钟。这使平台能够自动拦截将要失败的作业，并在同一构建中重新触发它们。额外的一分钟间隔为平台提供了从导致作业首次失败的瞬时问题中恢复的机会。

在某些情况下，您可能不希望在作业上启用重试。例如，具有非常严格的服务级别协议（SLA）的管道，您希望在出现故障时立即收到警报；或者具有非幂等副作用的转换。但是，即使您未在调度配置中启用重试，作业仍可能作为 裁决.

避免多数据集强制构建

调度可以启用“强制构建”选项，无论数据集是否过期，调度中的所有数据集都将被构建。此选项对 Data Connection 同步非常有用，因为这些数据集在平台中始终是最新的，因此除非使用强制构建，否则它们永远不会作为计划构建的一部分被构建。但是，我们不建议在包含派生数据集的多数据集调度中启用强制构建选项，因为这会在资源使用方面产生高昂成本。相反，请拆分您的调度，将必须强制构建的数据集放在单独的调度中。

调度中应包含什么和排除什么

明确指定调度中包含的内容。显式忽略位于管道之外的数据集。构建解析可能很复杂，但明确指定包含的内容比隐式方式提供了更高的透明度。

  • 在下面的示例管道截图中， Owned By Someone 应从定义于 Apex 2上的调度中排除。同样适用于 Cleaned 1 and Cleaned 2 ——在任一对象上触发作业都会因缺少权限而立即导致构建失败。

此外，调度不应依赖或尝试构建以下数据集：

  • 当前位于回收站中的： 要修复包含已回收资源的现有调度，请使用 升级助手 来调查您拥有的调度，以便将相关资源从回收站恢复或从调度中排除。
  • 由 Contour 生成的： 要使调度被视为“可用于生产环境”，我们需要能够审查管道的更改，并在出现问题时回退到之前的版本。Contour 不支持此类工作流，因此我们不建议用户在生产管道中使用它们。
  • 由 Code Workbook 和 Code Workspaces 生成： 与 Contour 输出数据集相比，这并非严格规则，但我们不建议在生产管道中使用 Code Workbook 和 Code Workspaces。Code Workbook 和 Code Workspaces 非常适合迭代开发解决方案，但在变更管理和回滚方面不如 Code Repositories 稳健。 了解 Code Workbook、Code Workspaces 和 Code Repositories 之间的区别。

管道的所有输出都应在您的计划中被标记为“目标”。计划可以有一个或多个目标，即安装该计划的数据集。计划还可以有一个或多个输出，即由该计划构建且不在构建过程中的其他地方使用的最终数据集。在大多数情况下，目标数据集和输出数据集是相同的，但在某些情况下（尤其是多输出构建），构建的目标数据集和输出数据集可能不同。作为一般规则，管道的所有输出都应定义为目标。

快速失败

勾选以下选项，将构建配置为在某个作业失败时立即失败： 失败时中止构建 复选框，位于 高级选项中。快速失败将使您更早获得信号。

为计划命名

所有计划都应具有描述性名称。随着管道复杂度的增加和用户数量的增长，计划名称会非常有帮助。

描述性的计划名称可以为与计划交互的人员提供有关计划意图的信息；例如，未来负责修复与您的计划相关的问题的人员。

如果您有多个数据摄取流，或者预计其他用户会从您的管道中分叉出任何路径，或者预计维护责任会随时间变化，那么为计划命名尤为重要。
