函数中的 Webhook

本页面上的源导入说明和代码示例特定于 TypeScript v1 函数。如需更 强大的功能（包括对 Ontology SDK 和可配置资源请求的支持），我们建议 迁移到 TypeScript v2。

本指南将引导你设置一个可以使用 Webhook向外部系统发出请求的函数。

如果要在 TypeScript v2 或 Python 函数中使用 Webhook，请改为 将其发布为 Webhook 函数。将已发布的函数导入你的函数仓库，并 使用 Ontology SDK 调用它。Webhook 函数还可以由 Workshop、 函数支撑的操作以及其他函数调用。

先决条件

本指南假设你已创建数据连接源和 Webhook。如需更多信息，请参阅 有关如何创建数据连接源和 Webhook 的文档。

支持由出站应用程序支撑的 Webhook。如需更多信息，请参阅出站应用程序配置页面中的 支持的工作流 部分。

将源导入函数仓库

在按照本指南操作之前，请确保你已创建函数仓库，并了解如何编写和发布函数，如 我们的教程中所述。

您必须先启用数据源，使其能够被导入到代码仓库中。为此，请前往 启用代码导入 菜单，为您的 REST API 数据源启用允许将该数据源导入代码仓库的选项。由于无法在所有使用函数的工作流中执行导出时的标记验证，因此您还必须在 启用导出 菜单中为每个数据源启用不带标记验证的导出。

接下来，要在函数中使用 webhook，必须先将该 webhook 的支撑 REST API 数据源导入到仓库中。选择 资源导入 左侧面板 以查看已导入到仓库中的数据源。然后选择 添加 > 数据源 以显示搜索对话框，您可以在其中选择要导入的数据源。只有具有 API 名称的数据源才能通过此对话框导入。

将数据源导入函数仓库以供 webhook 使用的方式，与将数据源导入 Python 转换仓库和计算模块的方式有所不同。仅将特定数据源用于 webhook 用途的函数仓库将 不会 显示在数据源概览中列出的仓库列表中。任何具有 Viewer 对源具有访问权限的用户将能够导入这些 webhook 并在外部函数中使用。

示例：从函数中进行多次调用

在下面的示例中，我们将介绍如何使用单个函数对字典 API 进行多次调用。

如果您的函数不进行任何本体论编辑，您将创建 @Query() 函数。如果您想进行本体论编辑，则需要改用 @OntologyEditFunction 装饰器。有关从函数进行本体论编辑的更多信息，请参阅我们的 文档。

使用标准的 TypeScript async/await 模式 ↗，可以在函数中同时发起多个 webhook 调用。请使用 isOk 辅助函数检查调用是否成功，该函数导出自 @foundry/functions-api。

以下函数接受一个 TypeScript 字符串数组形式的单词列表，并为每个单词进行一次调用：

import { OntologyEditFunction, isOk } from "@foundry/functions-api";
import { MyDictionarySource } from "@foundry/external-systems/sources";

export class MyFunctions {

    @OntologyEditFunction()
    public async defineWords(words: string[]): Promise<void> {

        const results = await Promise.all(words.map(word => MyDictionarySource.webhooks.GetDefinition.call({
            wordToDefine: word
        })));

        results.forEach((result, i) => {
            if (isOk(result)) {
                const output = result.value.output;
                output.dictionary_definitions.forEach(definitions_for_word => {
                    definitions_for_word.meanings.forEach(meaning => {
                        meaning.definitions.forEach(def_for_part_of_speech => {
                            console.log(`Found a ${meaning.partOfSpeech} definition for "${words[i]}": ${def_for_part_of_speech.definition}`);
                        })
                    })
                });
            }
        });
    }
}

import { OntologyEditFunction, isOk } from "@foundry/functions-api";
import { MyDictionarySource } from "@foundry/external-systems/sources";

export class MyFunctions {

    @OntologyEditFunction()
    public async defineWords(words: string[]): Promise<void> {

        const results = await Promise.all(words.map(word => MyDictionarySource.webhooks.GetDefinition.call({
            wordToDefine: word
        })));

        results.forEach((result, i) => {
            if (isOk(result)) {
                // Extract the response
            } else {
                const errorName = result.error.name;

                if (errorName === "WebhookExecutionFailedToStart") {
                    console.log("We were unable to initiate a request to the dictionary API.");
                } else if (errorName === "ParsingResponseFailed") {
                    console.log("The external request succeeded, but the response couldn't be parsed.");
                } else {
                    console.log("Something went wrong.");
                }
            }
        });
    }
}

在处理错误时，编写的代码应监听特定的名称并作出相应的处理。函数目前会返回以下错误：

错误描述
WebhookExecutionFailedToStartwebhook 启动失败。如果返回此错误，则可以放心地假定未向外部系统发出任何请求。
WebhookExecutionTimedOutwebhook 已开始执行，但在配置的 webhook 时间限制内未收到来自外部系统的响应。
RemoteRestApiReturnedError外部系统返回了错误。仅针对在 REST API 源上配置的 webhook 返回。
RemoteApiReturnedError外部系统返回了错误。仅针对在非 REST API 源上配置的 webhook 返回。
ParsingResponseFailedwebhook 执行成功，但未能成功解析来自外部系统的响应。例如，当来自外部系统的响应未包含预期字段时，就可能出现这种情况。由于 webhook 调用的结果不一定会被使用，因此是否将其标记为面向最终用户的失败由应用程序构建者决定。
ServerErrorWebhook 服务或连接器内部发生了问题。
UnknownError发生了无法直接归因于任何 Foundry 服务的错误。

此错误类型列表可能会发生变化；用户应将代码设计为包含默认分支，以防函数执行器返回带有新名称的错误。

限制

目前，对于可以在本体论编辑函数内发起的请求数量没有限制，但现有的 函数资源限制 仍然适用。 Webhook 限制 也同样会被强制执行。

函数目前支持具有以下输入和输出类型的 Webhook：

  • 附件
  • 布尔值
  • 整数
  • 长整数
  • 双精度浮点数
  • 字符串
  • 可选值
  • 日期
  • 时间戳
  • 列表
  • 枚举（允许的字符串类型值列表）
  • 包含和不包含预期字段的记录

当从 @Query 函数调用 Webhook 时，该 Webhook 必须仅执行 Read API 调用,它们不会修改外部系统。查询函数会被频繁重试,或在页面加载时被静默执行,因此无法提供与使用 @OntologyEditFunction。配置 webhook 时,您可以使用以下选项来指定是否可以安全地从查询函数中执行该 webhook: Read API 或 Write API。

不支持的 webhook 功能

  • 使用 OR 类型作为输入或输出参数的 webhook 目前不受支持。不会为这些 webhook 生成代码。

处理函数和 webhook 中的版本变更

函数和 webhook 都有版本,调用方可以调用任意版本的函数或 webhook。发布函数时,当时可用的最新 webhook 版本将被固定到该函数。

当函数仓库在 代码仓库 应用程序中打开时,用于自动补全的已生成代码绑定将始终使用最新版本的 webhook。此 webhook 版本显示在左侧的 资源导入 侧面板中。

在发布依赖其功能的函数之前,请确保您的 webhook 稳定。

请记住，在对 webhook 或函数进行更改时，需要重新发布函数并将用户升级到新版本。此前发布并固定的函数版本仍可供使用。

权限

下表总结了编写、发布和使用外部函数所需的权限。

操作用户所需权限
将 webhook 导入函数仓库函数编辑者webhooks:editor （对 webhook），该权限授予 编辑者 默认角色。
发布调用 webhook 的函数函数编辑者webhooks:execute 权限（对源），该权限仅授予 所有者 和 编辑者 默认角色。
将操作配置为使用 @OntologyEditFunction() 来调用 webhooks操作编辑者webhooks:grant-action-validated-execution 权限（对 webhook）以及 Viewer 权限（对函数）
执行 @Query() webhook（在 Workshop 中）最终用户webhooks:execute 权限（对源），该权限仅授予 Owner 和 Editor 默认角色。
执行 @OntologyEditFunction() （在操作中）最终用户用户必须满足 提交条件 （针对该操作）。在这种情况下，不会检查对源、webhook 或函数的任何权限。创建和管理操作的用户必须确保提交条件得到适当配置。

监控、故障排除和调试

使用以下平台工具可以更深入地了解函数发起的 webhook 执行情况：

  • Webhook 执行历史记录，可在 History 标签页（在 Data Connection中查看单个 webhook 时）中找到。
  • 函数使用历史可在 Ontology Manager中查看，其中记录了函数何时被执行，包括输入、输出以及触发该函数的用户。
  • 函数指标，可显示函数的近实时成功/失败次数和 P95 执行时长。
  • 函数的代码编写预览，提供性能分析、调试输出等功能。

最佳实践

在函数中调用外部源的 webhook 时，我们建议遵循以下最佳实践：

  • 请先使用 测试 webhook 侧面板 （在 Data Connection 中）对 webhook 进行彻底测试，然后再尝试在函数中使用这些 webhook。
  • 使用 webhook 输入和输出 record 类型参数（如有可能，请包含预期字段）。使用显式类型而非 JSON，意味着函数代码不太可能抛出意外的运行时错误。
  • 使用 isOk 和 isErr 内置函数（从 @foundry/functions-api 导出）来检查成功和错误状态，并通过 name 字段进一步确定错误类型。
  • 如果用户将通过单次函数调用同时写入外部系统和本体论，请记住，即使对外部系统的写入成功，对本体论的写入也可能失败。请确保已制定相应措施来处理此类不一致情况，并在必要时让用户能够查看其对这两个系统所做的修改状态。
