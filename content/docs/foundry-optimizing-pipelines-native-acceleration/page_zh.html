原生加速

您可以通过启用原生加速来提升 Spark 的性能，使用 Velox ↗.

原生加速是一种利用底层硬件优化来提升批处理作业性能的技术。这些性能提升是通过将计算从 Java 虚拟机（JVM）语言转移到原生语言（如 C++）来实现的，这些语言会被编译为机器代码并直接在机器的硬件上运行。通过使用特定于平台的功能，原生加速旨在显著缩短处理大规模数据工作负载所需的时间，从而加快作业执行速度并提高资源利用率。

原生加速适用于 Python 转换 和 如果希望用户在每次运行预览前手动确认，请开启.

构建分析

您可以在 Spark 详情 页面中对原生加速的构建进行基本分析。在 查询计划 标签页中，选择 物理计划下，您将看到类似以下内容：

== Physical Plan ==
AdaptiveSparkPlan
+- == Final Plan ==
   Execute InsertIntoHadoopFsRelationCommand
   +- WriteFiles
      +- CollectMetrics
         +- VeloxColumnarToRowExec
            +- ^ ProjectExecTransformer
               +- ^ InputIteratorTransformer
                  +- ^ InputAdapter
                     +- ^ RowToVeloxColumnar
                        +- ^ HashAggregate
                           +- ^ VeloxColumnarToRowExec
                              +- ^ AQEShuffleRead
                                 +- ^ ShuffleQueryStage
                                    +- ColumnarExchange
                                       +- ^ ProjectExecTransformer
                                          +- ^ RowToVeloxColumnar
                                             +- * ColumnarToRow
                                                +- BatchScan parquet

虽然与传统的 Spark 查询计划大体相似，但您会注意到一些关键差异。原本的 ProjectExec 节点被替换为 ProjectExecTransformer。这意味着该操作将在 Velox 查询引擎中以原生方式执行。查询计划中所有被卸载的节点都会在树中标记为 ^ 符号。原生执行的代码块由 RowToVeloxColumnar 和 VeloxColumnarToRowExec节点夹在中间。这些节点负责将 Spark 数据集转换为 Arrow DataFrame，反之亦然。这种序列化/反序列化操作具有显著的开销。

通常有两种模式表明原生加速性能不佳：

  • 以原生方式执行的节点比例很小，如 ^ symbol.
  • 所示。大量的 RowToVeloxColumnar and VeloxColumnarToRowExec 节点导致较高的序列化开销。

如果性能不如预期，这种分析会很有帮助。对管道的小改动可能会对卸载的计算量产生很大影响。诸如 检查点 之类的功能可用于手动将构建中可以全部以原生方式执行的代码块组合在一起。

原生加速的实现与架构

Foundry 的原生加速实现基于 Apache Gluten ↗ 项目。Foundry 原生加速利用 Velox ↗ 查询引擎在运行时加速 Spark 作业。Velox 使用 C++ 编写，并且 在设计时明确考虑了数据库加速 ↗，提供了开发人员 API 以便在 Arrow DataFrame ↗上运行算子级别的操作。Gluten 提供了必要的“粘合层”，将 Spark 运行时与 Velox 绑定在一起。

在此设置中，管道首先像普通构建（即不使用原生加速的构建）一样生成 Spark 查询计划。然后对计划应用额外的优化规则，以识别查询的哪些部分可以使用 Velox 运行。此决策基于 Velox 是否具有等效的实现，以及 Gluten 中是否存在该实现的映射。查询可以在算子级别进行卸载：这大致对应于类似 SELECT, FILTER，或 JOIN的 SQL 语句。查询计划中任何可以卸载的部分都会在此阶段被标记。

规划步骤完成后，查询将通过正常的 Spark 引擎执行。这意味着所有任务调度、执行器编排和生命周期管理都照常进行。区别在于当执行器到达查询计划中被标记为原生执行的部分时。如果发生这种情况，将调用 Velox 的实现，而不是 Spark 中的默认实现。

这种架构特别有利，因为它支持并非所有计算都可以使用 Velox 完成的查询。这是因为卸载决策是在算子级别而非整个计划级别做出的。支持的算子数量在不断增加，但用户编写的代码（如 UDF ）永远无法被卸载，因为不存在对应的原生实现。

为什么原生加速更快？

Spark 是用 Scala（一种 JVM 语言）编写的，并包含许多优化，例如 代码生成 ↗ 来提升其性能。此外，JVM 本身也包含诸如 C2 编译器 ↗ 等优化，旨在尽可能利用平台特定的特性。然而，C++ 等原生语言在性能上仍然更胜一筹，原因有三个基本方面：

  • 编译时优化： Java 和 Scala 会被编译为字节码，然后由 JVM 执行；而 C++ 等原生语言则直接编译为机器码。这使得 C++ 编译器能够在编译时执行大量优化，从而显著降低运行时开销。相比之下，JVM 语言依赖即时（JIT）编译，这种编译发生在执行期间，并且由于需要在编译耗时与快速启动运行之间取得平衡，可能无法达到同等程度的优化。
  • 无垃圾回收（GC）： 在 C++ 中，内存管理是手动处理的，这消除了与垃圾回收（GC）相关的开销。在 JVM 语言中，GC 过程可能引入不可预测的暂停和开销，从而影响性能，尤其是在内存密集型应用中。
  • 直接硬件访问以及向量化 API 的可用性： C++ 提供对硬件特性和底层系统资源的直接访问，使开发者能够利用平台特定的优化以及 SSE、AVX 和其他 SIMD（单指令多数据）指令等向量化 API。这种直接访问可以实现精细的性能优化，而在 JVM 语言中，抽象层可能会阻碍同等程度的硬件交互，因此这类优化不容易实现。

原生加速的内存配置注意事项

在 Foundry 中使用原生加速运行 Spark 需要与普通批处理管道稍有不同的配置。Spark 支持使用 堆外内存 ↗。堆外内存是不由 JVM 管理的内存，可消除 GC 开销，从而带来更好的性能。默认情况下，我们在 Foundry 中不启用堆外内存，因为这样做会为管道引入额外的维护成本。启用堆外内存是原生加速所必需的，因为被 Velox 修改的 DataFrame 必须位于堆外，才能被原生进程访问。对于除 Velox 数据转换之外的所有内容，Foundry 仍需要足够的堆内内存（例如，编排、调度和构建管理代码仍在 JVM 中运行），但理想情况下，大部分工作现在将在堆外执行。将管道配置为使用原生加速会在平衡堆内和堆外内存方面引入额外的维护成本。
