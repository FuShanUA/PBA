事务

Foundry 的 Iceberg 目录在标准 Iceberg 的基础上进行了扩展，增加了 全有或全无的事务语义。当作业通过 Foundry 的构建系统执行多次写入时，所有写入要么全部成功，要么全部被丢弃，这与 Foundry 目录数据集现有的保证相一致。本页面介绍了 Foundry 的 Iceberg 事务语义的工作原理、其与默认 Iceberg 行为的对比，以及对编写管道的意义。

本页面所述的事务保证仅在通过 Foundry 的构建系统运行作业时适用。从外部客户端向 Foundry 的 Iceberg 目录写入数据时，您将获得标准 Iceberg 事务行为。请参阅 PyIceberg API 文档 ↗ ，以了解事务在该上下文中的具体工作方式。

Foundry Iceberg 事务语义

在 Foundry 中运行 构建 时，Foundry 会提供 “全有或全无”的更新。Foundry 会自动将所有 Iceberg 表的读取和写入封装在单个事务中。用户无需采取任何操作来配置此行为；这是使用 Foundry 构建系统写入 Iceberg 表时的默认行为。

相比之下，标准 Iceberg 缺乏多更新事务保证。相反，它提供 原子更新：每个更新都是单独应用的。这是一个经过深思熟虑的设计选择，可实现乐观并发，即多个写入者可以同时操作同一张表。虽然这种模型对于单次写入事务而言效果良好，但对于在单个事务中执行多次写入的管道来说，无论这些更新是应用于一张表还是多张表，都可能出现正确性问题。Foundry 的“全有或全无”事务模型通过协调作业中所有写入的提交解决了这一问题，因此部分更新永远不会对外可见。

特别地,Foundry 的事务模型提供以下保证:

  • 全有或全无提交:作业中的所有表更新会一并提交。如果作业在任意时刻失败,任何部分写入都不会对下游消费者或其他作业可见。这与 目录数据集事务的行为一致。
  • 可重复读取: 如果在作业内多次读取同一个表,则每次都会返回相同的数据,即使两次读取之间该表被外部更新也是如此。在作业执行期间,您的管道将看到其输入的稳定、一致的视图。
  • 作业可以看到自己的写入: 作业内执行的写入操作对同一作业中的后续读取立即可见。在事务提交之前，这些写入对所有其他作业和外部读取者均保持不可见。
  • 多表快照隔离： Foundry 在事务开始时捕获所有输入表的一致快照。这确保了无法在作业中途部分读取对输入的部分外部更新，并确保数据溯源——即哪个版本的输入生成了哪个版本的输出——能够被正确记录。

示例：增量连接管道

下面通过一个示例来说明这种差异：

假设您有一个作业，该作业会增量读取名为 orders 和 customers的两个表中的新行，对它们进行连接，并将结果追加到两个表中： order_summary 和 customer_metrics。某天，该作业在运行中途失败，此时已完成对第一个表（order_summary）的写入，但尚未写入第二个表（customer_metrics）。

按照标准的 Iceberg 事务语义： 第一次写入仍然有效。该 order_summary 表此时将反映新的数据批次，而 customer_metrics 则没有。这两个输出处于不一致状态。当随后重试该作业时，它会重新读取相同的输入行，并将这些行写入 order_summary 再次，从而重复上一次部分运行的数据。

使用 Foundry Iceberg 事务语义： 第一次写入不会被提交。 order_summary 该表将 不会 反映新的数据批次。两张表均保持不变并处于一致状态。当作业随后重试时，它会正确地将新数据写入两张表，且不会产生重复。

作业排队与乐观并发

Foundry 的构建系统确保在任意时间点，针对给定输出最多只有一个作业在运行。写入同一输出的作业会进行排队并按顺序运行，而非并发运行。这意味着在实践中，常规管道作业不可能出现写入冲突，但管道作业与 Iceberg 维护作业之间可能会产生写入冲突。

相比之下，标准 Iceberg 采用乐观并发机制，允许多个写入者同时操作同一张表，冲突会在提交时被检测并解决。Foundry 的事务模型舍弃了乐观并发，转而采用更严格的更新与正确性处理方式。如果事务确实遇到了冲突的并发更新，提交将失败，构建系统会重试该作业。正确性始终能够得到保证，但代价是在出现冲突更新时需要重新计算该作业。

冲突的一个常见来源是 维护任务 ，例如压缩（compaction），这些任务目前与常规管道作业并发运行。如果在作业运行期间压缩任务更新了表，该作业的事务将无法提交，构建系统将重试该作业。对于频繁进行压缩的表，这可能会导致偶尔的重试。

Iceberg 快照类型与 Foundry 数据集事务

如果您熟悉 Foundry 数据集，那么您所了解的事务类型与 Iceberg 快照类型之间的对应关系如下：

Iceberg 快照类型Foundry 数据集事务描述
追加快照APPEND添加新数据文件；现有文件保持不变。
覆盖快照UPDATE, SNAPSHOT添加和删除数据文件，从而更改逻辑记录集（包括部分覆盖和完全覆盖）。
删除快照DELETE删除数据文件或添加删除文件，以在逻辑上删除行。
替换快照（无对应项）重写数据文件但不更改逻辑内容（例如压缩合并）。
为什么首次写入会显示为追加快照？

一个常见的混淆点： 对新 Iceberg 表的首次写入 会被记录为 追加快照，即使其意图是完全替换表内容。这是预期行为。当表为空时，追加数据和替换数据在逻辑上是等价的，因为没有可覆盖的内容。Iceberg 将该操作记录为“追加”，因为只添加了文件，而没有删除任何文件。实际影响是：如果您在表的历史记录中看到预期为全量加载的操作却显示为追加快照，请检查它是否为该表的首次写入。在对非空表进行后续全量重写时，该操作将正确显示为覆盖快照。
