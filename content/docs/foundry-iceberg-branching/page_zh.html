Foundry 的 Iceberg 目录中的分支隔离

Foundry 的 Iceberg 目录扩展了标准 Iceberg，使每个分支都能独立跟踪其自身的当前架构、默认分区规范和默认排序顺序。这些操作的隔离范围仅限于其运行的分支，不会影响表的 main （master）分支或任何其他分支。这意味着 Iceberg 表的行为与 Foundry 用户对目录数据集的既有预期相符，即在分支上进行的工作是完全隔离的，同时仍符合 Iceberg REST 目录规范 ↗。

本页面介绍分支隔离的工作原理、它如何扩展默认的 Iceberg 行为，以及在 Foundry 中使用 Iceberg 时该机制如何自动应用。此外，还介绍了在使用外部 Iceberg 客户端时如何选择启用此行为。

本页面所述的分支隔离适用于通过 Foundry 构建系统运行作业的情况。从外部客户端向 Foundry 的 Iceberg 目录写入时，默认情况下将采用标准 Iceberg 分支行为。或者，您也可以选择启用 Foundry 的分支隔离。请参阅 将分支与外部客户端结合使用 以了解详情。

Foundry 中的分支隔离

在 Foundry 中运行 构建 时，Foundry 会提供 分支隔离 对于 Iceberg 表。这意味着 Foundry 会自动将模式、分区规范和排序顺序的变更隔离到关联的分支，确保这些分支级变更不会无意间修改其他分支。用户无需进行任何配置操作；这是使用 Foundry 构建系统写入 Iceberg 表时的默认行为。

请注意，此处所述的针对模式的分支级行为同样适用于分区规范和排序顺序，它们（与模式一样）可以在 Foundry 中的分支上独立演进。分支级元数据会作为附加属性存储在表的 Iceberg 元数据文件中。例如： "foundry.branch.feature-branch.schema-id" : "3"。

标准 Iceberg 行为

在标准 Iceberg 中，模式是跨所有分支共享的表级概念，即表在所有分支之间仅跟踪一个当前模式。请参阅 Apache Iceberg 文档 ↗ 以了解详情。这意味着，在任何分支上对表模式的修改都会更改 main 以及所有其他分支的模式。

在所有分支上共用单一 schema，使得在合并到生产环境之前，很难在分支上独立开发或验证 schema 变更。要在分支上测试 schema 变更，就需要修改表的全局 schema。任何此类变更，无论源自哪个分支，都会立即影响该表在所有分支上的所有消费者 main。

Foundry 的行为

Foundry 的 Iceberg 目录通过自动跟踪特定于分支的 schema、分区规范和排序顺序解决了这一问题。在分支上运行的作业（例如， my-branch）看到的是该分支正在跟踪的 schema，而不是主分支上的 schema main。该作业在该分支上所做的 schema 变更 my-branch 会存储到关联的分支（在本例中为 my-branch）并且不会改变主分支上的当前 schema main 完全不变。

下表总结了哪些内容属于分支作用域、哪些属于表作用域，以及哪些内容在所有分支之间共享：

元数据Foundry 扩展分支默认 Iceberg 分支
架构历史表作用域表作用域
表属性表级表级
当前快照分支级分支级
当前架构分支级表级作用域
默认分区规范分支级作用域表级作用域
默认排序顺序分支级作用域表级作用域

请注意，在 Foundry 扩展分支中，虽然 当前 架构以分支为作用域，而 架构历史 以表为作用域。这意味着，当分支添加新列时，该架构会被添加到表的共享架构列表中，但不会被设置为当前架构 main。

如何建立分支上下文

当作业在 Foundry 构建系统中的分支上运行时，Foundry 会自动将分支上下文注入到该作业的所有目录操作中。作为用户，您无需进行任何配置。您的管道会针对该分支读取输入并写入输出，无需任何额外代码。

示例

以下示例说明了两种最常见的场景：在分支上创建新表，以及在分支上演进现有表的模式。

示例：在分支上创建新表

假设您正在开发分支上构建一个新表 feature/customer-scores。您的转换会创建一个输出 Iceberg 表，并向其写入初始数据。

Copied!
1import pyarrow as pa
2from transforms.api import transform
3from transforms.tables import IcebergOutput, TableOutput
4
5
6@transform.using(customer_scores=TableOutput("/<path>/customer_scores"))
7def compute(customer_scores: IcebergOutput):
8    data = pa.table(
9        {
10            "customer_id": pa.array([1, 2, 3], type=pa.int64()),
11            "score": pa.array([0.91, 0.74, 0.88], type=pa.float64()),
12        }
13    )
14    customer_scores.write_table(data)

以下是 customer_scores 表在特性分支上写入数据后的状态：

Foundry 扩展分支默认 Iceberg 分支
架构于 feature/customer-scores新建架构新建架构
架构于 main空新建架构
数据于 feature/customer-scores存在存在
数据位于 main无无

使用 Foundry 的分支隔离时： 该分支拥有初始架构和快照。该表存在于 main，但架构为空且没有数据。

使用默认 Iceberg 分支时： 该分支的架构显示在 main。

示例：在分支上演进现有表的架构

假设您现在有一个表 customer_scores 已投入生产。您正在测试对管道的一些潜在更改，并希望添加一个新列和修改现有列的类型，作为在分支上运行的作业的一部分，该分支为 feature/scoring-v2，而不影响生产环境中的下游消费者看到的内容，这些内容位于 main。

Copied!
1import pyarrow as pa
2from transforms.api import transform
3from transforms.tables import IcebergOutput, TableOutput
4
5
6@transform.using(
7    customer_scores=TableOutput("/<path>/customer_scores")
8)
9def compute(customer_scores: IcebergOutput):
10    data = pa.table(
11        {
12            "customer_id": pa.array(["c1", "c2", "c3"], type=pa.string()),
13            "score": pa.array([0.91, 0.74, 0.88], type=pa.float64()),
14            "score_v2": pa.array([0.95, 0.80, 0.92], type=pa.float64()),
15        }
16    )
17    customer_scores.write_table(data)

以下是该表在作业运行后的状态，作业运行于 feature/scoring-v2:

已启用架构 feature/scoring-v2新架构新架构
已启用架构 main旧架构新架构
数据位于 feature/scoring-v2存在存在

借助 Foundry 的分支隔离： 新列和类型变更仅限于该分支。 main 保留其原始 schema，因此下游消费者不受影响。

使用默认 Iceberg 分支时： 该分支和 main 共享同一个当前 schema，因此写入操作要么无法通过 schema 验证，要么会强制您更新 main的 schema，从而将变更暴露给下游消费者。

在外部客户端中使用分支

Foundry 的 Iceberg 目录完全符合 Iceberg REST 目录规范 ↗。

从外部工具访问 Foundry 的 Iceberg 目录时，该目录的行为取决于是否设置了 X-PLTR-Branch 标头。从外部客户端使用分支时，请设置 X-PLTR-Branch 标头，以确保 Foundry 分支行为的一致性。

当设置了 X-PLTR-Branch 标头时：

  • 所有读写操作都会自动限定在该分支范围内。
  • 在 X-PLTR-Branch 请求头中设置的分支将在未指定分支限定符（或引用了 main ）时作为默认值使用。如果请求中指定了具体的（非main）分支，则将使用该分支而非请求头中设置的分支。例如，如果请求头设置为 featurebranch1，那么 SELECT * FROM table 和 SELECT * FROM table.branch_main 将引用 featurebranch1，但 SELECT * FROM table.branch_featurebranch2 将引用 featurebranch2。

当 X-PLTR-Branch 标头未设置时，将应用 Iceberg 的默认行为：

  • 快照读取将使用与所引用快照关联的 schema。例如， SELECT * FROM table VERSION AS OF <snapshot_id>。
  • 分支读取将使用 main的 schema（表级作用域）。例如， SELECT * FROM table.branch_my_branch。
  • 写入操作将依据 main的架构（表级作用域）进行验证；不符合架构的写入操作将失败，而不会适应该分支。
  • 架构变更将应用于 main上的表级作用域架构，而不会隔离在该分支内。

在外部设置 X-PLTR-Branch 请求头

要为 PyIceberg 客户端设置分支，请将该请求头添加到您的目录属性中：

Copied!
1from pyiceberg.catalog import load_rest
2
3catalog = load_rest(
4    "foundry",
5    {
6        "uri": "https://your.foundry/iceberg",
7        "token": "eyJwb...",
8        "header.X-PLTR-Branch": "my-branch"
9    },
10)

对于 Spark，请将标头作为目录配置属性传递：

Copied!
1spark = (
2    SparkSession.builder
3        ...
4        .config("spark.sql.catalog.foundry.header.X-PLTR-Branch", "my-branch")
5        ...
6        .getOrCreate()
7)

有关将外部客户端连接到 Foundry 目录的更多信息，请参阅 对 Iceberg 客户端进行身份验证 和 示例：本地 Jupyter。

限制和注意事项

在使用分支隔离时，请注意以下事项。

单个分支适用于作业中的所有表

当作业在分支上运行时，该分支上下文会统一应用于该作业读取和写入的所有表。目前无法在同一作业中为不同的输入或输出表配置不同的分支。Foundry 会验证所有解析后的输入分支是否与作业的分支一致，如果不一致，则会引发错误。

分支引用的架构和分区规范会受到保护

如果某个分支正在跟踪特定的架构或分区规范，则该架构或规范无法从表中被删除，即使是运行在 main。这样可以防止并发运行的清理或维护操作在无提示的情况下破坏分支。删除分支后，该保护将自动解除。

Iceberg 分支合并过程不遵循分支隔离

Iceberg 的原生分支合并操作（例如 cherry-pick 和 fast-forward）仅作用于快照引用，无法识别 Foundry 的分支范围 schema 属性。如果您使用这些操作将分支合并到 main，则该分支的 schema 不会被沿用，且 main 将保留其现有 schema。为确保分支上的 schema 变更能够反映到 main，请合并您的代码并在 main 上通过 Foundry 的构建系统重新构建。

被排除的 REST 端点

某些特权 REST 端点无法从 Foundry 分支调用，特别是：

  • dropNamespace
  • updateNamespace
  • dropTable
  • renameTable
  • commitTransaction
  • createView
  • dropView
  • renameView

版本兼容性

分支隔离功能适用于 transforms-tables 库版本 0.1211.0 及更高版本。
