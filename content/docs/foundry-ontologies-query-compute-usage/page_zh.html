本体论查询的计算用量

Foundry 本体论是一个数据后端，它将基于文件的数据映射到以组织为中心的对象，并为数据探索、数据分析、运营数据编辑、情景分析等提供高速查询服务。本体论将数据存储在多模态存储后端中，每个后端都有各自的用途，并且可以在单个请求中被灵活查询。查询 Foundry 本体论需要了解下面讨论的一些基础概念。

如果您与 Palantir 签订了企业合同，请在进行算力使用量计算之前联系您的 Palantir 代表。

核心概念：对象类型和对象集

第一个重要概念是 对象类型 与其对应的 对象集的对象集合都应来自同一个周围生成器区域。 对象类型 是实体本身的语义表示（例如对象的名称和属性）。

对象类型具有对应的 对象集，其中包含对象本身。 对象集 的大小对应于传入数据集的行数以及本体论操作所创建和删除的对象数量。

核心概念：查询类型

第二个重要概念是 查询类型的概念，其中包括筛选、聚合、Search Around 和写回操作。每种查询类型都需要算力来执行。请参阅 Ontology Query Compute (2026) 以了解每种查询类型当前的算力秒开销。

调查来自本体论查询的 Foundry 算力使用量

在 Foundry 中，算力秒归属于平台中的资源，而不是归属于与这些资源交互的用户。

对于本体论查询，算力的归属方式有多种。一般规则是，算力会附加到查询发起的资源上。但是，当没有用于生成算力的已保存资源时（例如通过 API），算力将附加到被查询的对象类型上。如果在单个请求中查询多个对象，则算力将在这些对象之间平均分配。

以下资源类型的本体论查询算力归属于这些资源本身，而不是底层对象：

  • Workshop 应用程序
  • Carbon 页面
  • Quiver 分析和仪表板
  • Vertex 应用程序
  • Slate 应用程序
  • Foundry Machinery 应用程序
  • Foundry Rules 资源
  • Foundry Automate
  • AIP 逻辑
  • SQL Console 工作表
  • OSDK 应用程序

以下交互模式的本体论查询算力直接附加到它们所查询的对象类型上，因为没有可以附加算力的固定资源。

  • 对象浏览器
  • 对象 API（包括 OSDK）

Ontology Query Compute (2026)

自 2026 年 1 月 1 日起生效

以下算力模型将于 2026 年 1 月 1 日生效，并取代下文 遗留版 章节中找到每种模块类型如何处理导航操作的详细信息和示例。

Ontology Query Compute 由用户和代理对本体论的使用驱动。请考虑决定算力使用量的主要因素：

因素 1：用户和代理的数量

算力秒是累积计量的。针对本体论运行的查询和转换越多，总体算力使用量就越高。查询量随用户交互（例如应用程序刷新和交互式查询）以及代理式转换线性增长。

因素 2：查询类型

用户可以通过以下查询类型访问其本体论，每种查询类型都对应每次查询的最小算力秒开销。实际算力使用量可能更高，具体取决于查询的复杂程度、对象集的大小或被查询的对象数量。

  • 基础查询： 按原样返回对象集，或对某些属性进行基本筛选后返回。
  • Search Around 查询： 接收传入的对象集，并基于传入集的某个属性对另一个对象集执行二次筛选。
  • 聚合查询： 接受一个输入对象集，并对集合中所有对象的某个属性运行聚合函数（例如 sum or avg）。
  • 本体论 SQL 查询: 使用标准 Spark SQL 语法直接针对对象类型、关联和接口运行 SQL 查询，作用于对象存储。
  • 高级查询： 其他查询类型未涵盖的任何查询。例如，对整个对象集的嵌入向量应用语义搜索。
  • 派生属性查询： 派生属性 是在查询时根据对象的其他属性或关联的值计算得出的属性，包括对关联对象的属性进行聚合或选择。派生属性随后可用于同一请求中的进一步操作，例如过滤、排序或聚合。
  • 操作： 用于替换指定对象集中对象属性值的写回操作。操作具有最低开销为 18 计算秒，并随编辑对象的数量而扩展，除第一个对象外，每编辑一个对象会产生额外的 1 计算秒。
  • 本体论计算（Phonograph）[旧版]： 针对仍使用对象存储 v1（OSv1）后端的对象的查询。这些查询在资源管理应用程序中显示为“Ontology Compute (phonograph)”。 现有的 OSv1 计算模型 已为这些查询保留。

遗留版

以下部分描述了 2026 年 1 月 1 日之前生效的旧版计算模型。保留这些内容仅供参考。有关当前计算模型，请参阅 Ontology Query Compute (2026) 部分。

在旧版模型下，查询本体论使用计算秒的方式如下：

  • 用于查询开销的固定最低计算秒数。
  • 额外的按比例扩展的计算秒数，根据为查询提供服务的计算量来衡量。

使用对象存储 v1 衡量计算 [旧版]

对象存储 v1（Phonograph）将数据存储在持久、可水平扩展的集群中的一组分布式索引中。在这些索引中，数据位于由本体论查询引擎遍历的大型数据结构中。执行查询时，引擎可以通过遍历索引来避免在搜索过程中处理大量数据。此过程称为“剪枝”（pruning）。

使用此引擎，您可以通过最多评估少 1000 倍的记录来搜索数十亿条记录。对记录的每次物理评估称为一次“命中”（hit）。对象存储 v1 旨在最大限度地减少每次查询中的命中次数。

使用对象存储 v2 衡量计算 [旧版]

对象存储 v2（OSv2）以增强的索引格式存储对象，该格式由 Palantir 优化，可实现高速索引、Search Around 和写回，以及平滑交接给多个计算后端以完成复杂任务。这包括作为查询一部分的完全并行化的 Spark 计算组合。

鉴于对象存储 v2 也使用高效的索引结构， 命中 的原则同样适用于对象存储 v1 的基本查询。但是，计算秒也可能被作为查询一部分启动的按需 Spark 容器使用。

对对象存储 v2 后端中对象的查询按以下模式使用计算：

  • 最低计算秒开销为 16 计算秒每次查询，适用于对象存储 v1 后端中的对象。
  • 最低计算秒开销为 4 对象存储 v2 后端中每个查询的 compute-seconds。对象存储 v2 的优化结构比对象存储 v1 所需的开销更少，因此具有更低的最低 compute-second 开销。
  • 当进程在查询的剪枝过程中执行计算工作时，需要额外的 compute-seconds。额外的 compute-seconds 会随着索引中对象的数量以及查询类型而增加。
  • 在对象存储 v2 (OSv2) 中，索引剪枝同样需要额外的 compute seconds。但是，当对超过 100,000 个对象运行 search-around，或在单个请求中对超过 10,000 个对象执行写回操作时，OSv2 还支持按需 Spark 集群搜索。这些 Spark 集群的使用量计算方式与平台上所有其他基于 Spark 的应用程序相同。请参阅 并行计算文档 以了解相关说明。
  • 带有写回到本体论的操作具有最低开销。每个操作的 compute-second 开销为 18。操作的开销还会随写回请求中编辑的对象数量而增加，产生额外的 1 计算秒。
  • 通过 Functions on Objects 运行的函数具有最低开销。具体而言，每次函数执行都有固定的开销 4 compute-seconds.

了解 Foundry 计算使用量随本体论查询变化的驱动因素 [旧版]

  • 一个非常简单的规则是，每个查询的固定计算使用量随查询数量的增加而线性增长。执行的查询越少，总体使用的计算量就越少。
  • 对对象集服务的更复杂查询（例如通用多对象搜索）将针对每种对象类型启动多个子查询。将搜索限制为单个对象类型，以减少所使用的查询数量。
  • 对较小对象集的查询比对较大对象集的查询使用的计算量更少，因为 命中 在查询中的数量与所查询对象集的大小成正比。
  • 在执行其他操作之前进行预先过滤，将充分利用高度索引化的后端结构。这将减少 命中 在查询中的数量，从而降低总体计算使用量。这对于聚合和 Search Around 尤为重要，因为经过过滤的对象集比完整对象集所需的处理计算量更少。
