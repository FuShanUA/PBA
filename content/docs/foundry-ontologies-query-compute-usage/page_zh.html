使用本体论查询的计算用量

Foundry 本体论是一个数据后端，它将基于文件的数据映射到以组织为中心的对象，并为数据探索、数据分析、运营数据编辑、情景分析等提供高速查询。本体论将数据存储在多模态存储后端中，每个存储后端都有各自的用途，并且可以在单个请求中灵活查询。查询 Foundry 本体论需要了解下文讨论的一些基础概念。

如果您与 Palantir 签订了企业合同，请在开始计算用量之前联系您的 Palantir 代表。

核心概念：对象类型和对象集

第一个重要概念是 对象类型 与其对应的 对象集之间的区别。 对象类型 是实体本身（例如对象的名称和属性）的语义表示。

每个对象类型都有一个对应的 对象集，其中包含对象本身。 对象集 的大小对应于传入数据集的行数以及本体论操作创建和删除的对象数量。

核心概念：查询类型

第二个重要概念是 查询类型，其中包括筛选、聚合、Search Arounds 和回写操作。每种查询类型都需要计算资源才能执行。请参阅 本体论查询计算 (2026) 以了解每种查询类型当前的计算秒数开销。

使用 Foundry 本体论时， 查询类型 会针对 对象集 由以下 Foundry 应用来执行：

  • Object Explorer
  • Workshop
  • Quiver
  • Slate
  • Vertex
  • Foundry Rules
  • Foundry Machinery
  • Object APIs (OPIs)

从上述任一来源查询本体论，都会使用计算秒数来运行查询。

调查来自本体论查询的 Foundry 计算用量

在 Foundry 中，计算秒数会归属于平台中的资源，而不是与这些资源交互的用户。

对于本体论查询，计算资源的归属方式有多种。作为一般规则，计算资源会归属于发起查询的资源。但是，当没有可用于生成计算资源的已保存资源时（例如通过 API），计算资源将归属于被查询的对象类型。如果在单个请求中查询了多个对象，则计算资源将在这些对象之间平均分配。

对于以下资源类型，本体论查询计算将归属于资源本身，而非底层对象：

  • Workshop 应用
  • Carbon 页面
  • Quiver 分析和仪表板
  • Vertex 应用
  • Slate 应用
  • Foundry Machinery 应用
  • Foundry Rules 资源
  • Foundry Automate
  • AIP Logic
  • SQL Console 工作表
  • OSDK 应用

由于没有可附加计算的固定资源，以下交互模式的本体论查询计算将直接附加到其所查询的对象类型。

  • Object Explorer
  • 对象 API（包括 OSDK）

本体论查询计算（2026）

自 2026 年 1 月 1 日起生效

以下计算模型将于 2026 年 1 月 1 日生效，并取代下文 旧版 章节中描述的旧版模型。

本体论查询计算由用户和代理对本体论的使用所驱动。请考虑决定计算使用量的主要因素：

因素 1：用户和代理的数量

计算秒数按累计方式计量。针对本体论运行的查询和转换越多，总体计算使用量就越高。查询量随用户交互（例如应用刷新和交互式查询）以及代理式转换线性增长。

因素 2：查询类型

用户可以通过以下查询类型访问其本体论，每种查询类型均对应每次查询的最低计算秒开销。实际计算用量可能更高，具体取决于查询复杂度、对象集大小或查询的对象数量。

  • 基础查询： 按原样返回对象集，或基于某些属性进行基本筛选。
  • Search Around 查询： 接收传入的对象集，并基于传入对象集的某个属性对另一个对象集运行二级筛选。
  • 聚合查询： 接收输入对象集，并运行聚合函数（例如 sum 或 avg），作用于集合中所有对象的某个属性。
  • 本体论 SQL 查询： 使用标准 Spark SQL 语法，直接在对象存储上针对对象类型、关联和接口运行 SQL 查询。
  • 高级查询： 其他查询类型未涵盖的任何查询。例如，对整个对象集的嵌入向量应用语义搜索。
  • 派生属性查询： 派生属性是在运行时根据对象上其他属性或关联的值计算得出的属性，包括对关联对象的属性进行聚合或选择。派生属性随后可用于进一步操作，例如在同一请求中进行筛选、排序或聚合。
  • 操作: 用于替换指定对象集中对象属性值的写回操作。操作的最低开销为 18 计算秒,并随编辑对象的数量而增加,每编辑一个对象将产生额外的 1 计算秒(首个对象除外)。
  • 本体论计算 (Phonograph) [旧版]: 针对仍使用 Object Storage v1 (OSv1) 后端的对象执行的查询。这些查询在资源管理应用程序中显示为“本体论计算 (phonograph)”。 现有的 OSv1 计算模型 已为这些查询予以保留。

通过本体论对象查询衡量 Foundry 计算 [旧版]

旧版

以下各节介绍了 2026 年 1 月 1 日之前生效的旧版计算模型。此内容保留以供参考。有关当前计算模型,请参阅上文的 本体论查询计算 (2026) 部分。

在旧版模型下，查询本体论按以下方式使用计算秒数：

  • 用于查询开销的固定最低计算秒数。
  • 额外的按比例缩放的计算秒数，其数量根据为该查询提供服务所使用的计算量来衡量。

使用 Object Storage v1 [Legacy] 衡量计算量

Object Storage v1（Phonograph）将数据存储在一个持久且可水平扩展的集群中的一组分布式索引中。在这些索引中，数据存在于大型数据结构内，由本体论查询引擎进行遍历。执行查询时，引擎可以通过遍历索引，避免在搜索过程中处理大量数据。此过程称为“修剪”（pruning）。

使用此引擎，您可以搜索数十亿条记录，而所需评估的记录数量最多可减少 1000 倍。对一条记录的每次物理评估称为一次“命中”（hit）。Object Storage v1 旨在将每次查询中的命中次数降至最低。

使用 Object Storage v2 [Legacy] 衡量计算量

对象存储 v2 (OSv2) 以增强的索引格式存储对象，该格式由 Palantir 针对高速索引、Search Arounds 和回写进行了优化，并可平滑地交接给多个计算后端以完成复杂任务。这包括将完全并行化的 Spark 计算作为查询的一部分。

鉴于对象存储 v2 也使用高效的索引结构，对象存储 v1 中关于 命中数 的相同原则同样适用于基本查询。但是，作为查询一部分而启动的按需 Spark 容器也会使用计算秒。

对对象存储 v2 后端中的对象进行的查询按以下模式使用计算资源：

  • 每个查询的最低计算秒开销为 16 计算秒，适用于对象存储 v1 后端中的对象。
  • 每个查询的最低计算秒开销为 4 计算秒，适用于对象存储 v2 后端中的对象。对象存储 v2 的优化结构所需的开销低于对象存储 v1，因此其最低计算秒开销也更低。
  • 当进程通过查询的剪枝过程执行计算工作时，需要额外的计算秒数。额外的计算秒数会随索引中的对象数量以及查询类型而相应增加。
  • 在 Object Storage v2 (OSv2) 中，索引剪枝同样需要额外的计算秒数。但是，当在超过 100,000 个对象上运行 search-around，或在单个请求中对超过 10,000 个对象运行写回操作时，OSv2 还支持按需 Spark 集群搜索。这些 Spark 集群的使用量计入方式与平台上所有其他基于 Spark 的应用程序相同。请参阅 并行计算文档 以了解详细说明。
  • 向本体论执行写回的操作具有最低开销。每个操作的计算秒数开销为 18。此外，操作的开销还会随写回请求中编辑的对象数量而增加，对于超出第一个对象的每个被编辑对象，会产生额外的 1 计算秒数。
  • 通过对象上的函数运行的函数具有最低开销。具体而言，每次函数执行的固定开销为 4 计算秒数。

本体论 V2 查询4

通过本体论查询了解 Foundry 计算用量的驱动因素 [旧版]

  • 根据一个非常简单的规则，每个查询的固定计算用量会随查询数量的增加而线性增长。执行的查询越少，总体上使用的计算资源就越少。
  • 对对象集服务的更复杂查询（例如通用多对象搜索）会针对每个对象类型启动多个子查询。请将搜索限制为单个对象类型，以减少所使用的查询数量。
  • 对较小对象集的查询使用的计算资源少于对较大对象集的查询，因为查询中的 命中 数量与所查询对象集的大小成正比。
  • 在执行其他操作之前进行预先筛选，可以充分利用高度索引化的后端结构。这将减少查询中的 命中 数量，从而降低总体计算用量。这一点在聚合和 Search Around 操作中尤其重要，因为处理筛选后的对象集所需的计算资源少于完整对象集。
