将数据写回 Phonograph [Legacy]

遗留版

对象存储 v1（Phonograph）写回功能处于 遗留 开发阶段，预计不会再进行额外的开发。任何新的工作流都不支持 Phonograph 写回。

我们推荐 迁移到对象存储 v2 以利用本体论的改进和演进的架构。此外，我们建议使用操作（Actions）配合 操作小部件 来对本体论应用更新和更改。请参阅 操作类型文档 的文档以获取更多信息。

要从 Slate 中捕获用户输入/数据修改并将其保存到 Foundry，需要三个组件：

  1. 源数据集： 这是 Foundry 中已存在的、您希望使其可供编辑的数据集。该数据集必须具有主键。
  2. Phonograph 同步： Phonograph 是一个手动编辑缓存，允许 Slate 捕获用户对源数据集的输入更改。您将把数据集同步到 Phonograph（而不是 Postgres），这将使数据集在 Slate 中可用并允许用户编辑。
  3. 写回数据集： 这是您将在 Foundry 中创建的、用于存储源数据集的用户修改版本的数据集。源数据集将始终保持未修改状态，而存储在 Phonograph 缓存中的所有用户编辑都将保存到 Foundry 中的写回数据集。

添加源数据集

首先，在您的 Slate 应用程序中的 DataFrame 选项卡中添加源数据集。我们将添加一个名为 asteroid_notes 选项。 + 添加 按钮的简单派生数据集。此概念性数据集包含小行星名称和一个名为 research_notes 的空白列，用于保存用户输入的关于该小行星的信息。

添加数据集后，您将查看该数据集的同步设置。我们将配置一个到名为 Phonograph 的手动编辑缓存的同步。

写回索引不支持 struct 列类型，这意味着具有 DateTime 列类型的数据集将无法建立索引。您可以使用 Contour 或 SQL 或 Python 转换将 DateTime 列转换为 Timestamp 然后再建立索引。

选择属性： 主键。您选择的主键必须唯一标识单行数据。通常，您需要在转换中组合多个列，以在建立索引之前生成合适的主键。可以将一组列定义为联合主键；但这会增加编辑数据的复杂性。

配置主键后，我们将创建用于在 Foundry 中存储用户编辑的写回数据集。选择"浏览"以在 Foundry 中创建一个可保存您的编辑的数据集。在弹出窗口中，您将指定数据集的名称以及您希望在 Foundry 中创建该数据集的位置。

读取更新时使用 Search 服务还是 Storage 服务

Search 服务的端点使用关联 Phonograph 表的 搜索索引 。此搜索索引与 Storage 服务的 Post Event 端点不会同步更新，这意味着从更改被写入到更改出现在对 Search 端点的查询中之间存在少量延迟。一种简单的模式是使用 Toast 小部件创建一个计时器，如下所示：

  1. q_postEvent.success -> w_successToast.open
  2. w_successToast 超时配置为 5000 (5s)
  3. w_successToast.close -> q_getAllRows

您可能需要向上或向下调整 toast 的持续时间，以确保您正在检索已更改的行。同时请确保为您的 getAllRows 查询添加一个 sort 块，因为默认排序是按行文档的最后更新时间戳进行的，这意味着被编辑的行会"移动"到所有结果的末尾。

或者，为您的应用程序定义将数据展示与数据持久化到 Phonograph 分离的模式。这可以通过使用一个状态变量来跟踪当前视图，然后在用户触发时将该数据定期保存回 Phonograph 来实现，但 不会自动重新运行查询来获取所有行。这种模式提供了更好的用户体验（更新即时显示），但需要更复杂的设计。

对 Table Storage Service的任何请求（包括通过 primaryKey 值列表检索行）， is 保证包含所有编辑，因此可以安全地串联事件，例如： q_postEvent.success -> q_getRowByPrimaryKey.run

在这种情况下，通过主键查找检索到的特定行的任何更改都保证包含在结果中。

添加新行

添加新行的操作与编辑行完全相同；只需将上述示例中的 rowAdded 为 rowModified 替换即可。

需要注意的是，尝试添加一个与现有行具有相同主键的新行将会失败。一种简单的做法是触发一个 toast 组件 来简单地提醒用户该行已存在。

一种对用户更友好的做法是使用一个 q_validatePrimaryKey 对 Get Rows 端点进行查询，使用用户输入的主键来检查该行是否已存在。如果存在，则在 f_createTableEditEvent 中生成一个 rowModified 事件，否则使用 rowAdded.

管理延迟

由于手动编辑缓存的底层架构，在成功调用 Post Event后，编辑不保证立即出现在主索引中。目前正在努力使 Get All Rows 和 Get Rows 调用变为同步，这样如果您将 q_getAllRows 设置为在 q_postEditEvent 查询成功时触发，则任何编辑都保证会出现。但是，如果您依赖于 search 端点，则需要容忍几秒钟的延迟，直到搜索索引更新完成。

最简单的方法是在编辑查询和获取所有行查询之间插入一个 toast 。在 q_postEditEvent.success 事件上触发 toast，并设置 3-4 秒的持续时间（以毫秒为单位的值为 3000-4000）。然后您可以在 q_getAllRows 事件上触发 w_editSuccessToast.closed 查询，该延迟应该为索引更新提供足够的时间。

对于更复杂的工作流，您可以考虑进行额外的工作，将用于显示 Slate 应用的状态与编辑索引的状态分离。为此，在页面加载时，您可以使用 q_getAllRows 查询的结果填充一个 Slate 变量，该变量将成为您的“前端状态”。您的所有编辑/删除/更新事件都将对此前端状态变量进行更改，而不是直接触发对后端的查询。您可以定期将前端变量的状态与查询返回的数据进行对比，并创建批量查询的有效负载以应用所有更改。

您可能还希望以 toast 或“未保存的更改”计数器以及一个用于保存所有更改的手动按钮的形式提供一些用户反馈。除了复杂的长生命周期应用之外，这种设置对于其他情况来说过于繁重。在大多数情况下，toast 方法已经足够，而且对 Get Rows 和 Get All Rows 端点的改进应该很快就会使其在几乎所有情况下都过时，因此如果您正在考虑此选项，最好联系 Palantir 团队进行进一步讨论。

聚合

直方图 search 端点还支持聚合，用于在您的索引数据中生成统计数据和对值进行分桶。

支持一部分 ElasticSearch 2.0 Aggregation ↗ 语法： value_count, max, geohash_grid, terms, top_hits, sum, cardinality, avg, nested, filter, histogram, min.

由于 Elasticsearch 的限制，某些聚合的结果可能是近似的。在使用任何类型的聚合之前，请参阅 Elasticsearch 文档并了解它是精确的还是近似的。如果是近似的，您应在继续之前判断这是否适合您的用例。
