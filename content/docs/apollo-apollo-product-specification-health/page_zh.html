自定义健康检查的要求

expected-state-k8s 是一个 Spoke 服务，用于从您的集群收集状态和健康信息，并将其转发到您的 Apollo Hub。它会监视任何随 Apollo 安装的实体，如果在 Pod 上发现 health.probe 注解，则会收集健康信息。必须在您的集群中安装 expected-state-k8s，才能将自定义健康检查转发到您的 Apollo Hub。

为了让 expected-state-k8s 发现健康端点，您应该在希望启用健康报告的 Helm chart 中的 Deployment 或 StatefulSet 的 pod spec template 部分添加以下注解。

注解

health.probe 注解会告知 expected-state-k8s 在何处探测容器以获取健康状态。其格式如下：

Copied!
1
apollo.palantir.com/health.probe: '{"containerProbes":{"<CONTAINER_NAME>":{"path":"/<CONTEXT_PATH>","port":"<PORT>"}}}
  • CONTAINER_NAME 是提供健康端点的容器名称。
  • CONTEXT_PATH 是 /status/health 端点在您的容器上实现的路径。例如，如果您的端点在 /hello-world/status/health 处提供服务，则应为 CONTEXT_PATH 输入 /hello-world。如果您的端点直接在 /status/health 处提供服务，则可以将此值设置为 /。
  • PORT 是您的容器提供 <CONTEXT_PATH>/status/health 端点所使用的端口。

以下是一个 Helm chart 示例，其中为示例 Product 应用了这些标签和注解：

  • 在 test-deployment 部署中创建的容器名为 test-container。
  • test-container 在端口 8446 上的 /telemetry/status/health 处提供健康状态端点。

kind: Deployment
metadata:
  name: test-deployment
spec:
  template:
    metadata:
      annotations:
        apollo.palantir.com/health.probe: '{"containerProbes":{"test-container":{"path":"/telemetry","port":"8446"}}}'

一旦 expected-state-k8s 看到 Pod 上的注解，它将查询由 apollo.palantir.com/health.probe 注解配置的健康端点。所有查询都将通过 HTTPS 执行，因此您的端点必须接受 TLS 加密流量。

副本健康状况

健康状况是在服务副本级别上反映服务运行健康状况的指标。定义了以下状态：

  • HEALTHY:服务副本完全正常运行，没有任何问题。
  • REPAIRING:服务副本处于降级状态运行，但能够自动恢复。如果重启服务中的任何副本，可能会导致状态转换失败。例如，当 Cassandra 副本首次引导加入集群时，如果在此期间它或集群中的任何其他副本被重启，引导将会失败。
  • WARNING:服务副本处于趋向错误的状态。如果不采取纠正措施，健康状态预计将变为 ERROR。
  • ERROR:服务副本在运行方面处于不健康状态。

计算服务副本健康状态

副本的健康状态由其所有健康检查中最严重的健康状态决定，健康状态按严重程度从轻到重排序如下：

  1. HEALTHY
  2. REPAIRING
  3. WARNING
  4. ERROR

实现

服务应实现一个接受 GET 请求的 REST 端点。该端点应满足以下要求：

  • 可每 5 秒被调用一次，而不会对性能产生任何影响。对于调用频率应较低的资源密集型健康检查，服务应相应地缓存健康检查的结果。
  • 可通过相对于服务配置的 apollo-spec-status-endpoint 的 /status/health 路径访问（参见端点）；例如，https://<host>:<port>/<apollo-spec-status-endpoint>/status/health。为支持开源软件的 side-car，该端点可以位于与服务主端点不同的端口上；但对于 Palantir 开发的软件，应位于主端口上。

该端点应对所有健康状态返回 HTTP 200 OK 响应码。如果端点返回 5xx 错误码，则将被解释为执行健康检查时发生内部服务器错误，等同于服务返回 ERROR。

服务可以包含多个独立的健康检查，但应通过单个端点来表示整体健康状态。

状态元数据

服务应通过以有效的 JSON 正文响应 HTTP GET 请求，来提供描述其当前状态状况的元数据。

每个健康检查应表示为一个包含以下字段的 Check 对象：

  • type：字符串，表示健康检查类型的常量。值应为非空、大写、以下划线分隔且不含空格的 ASCII 字母，([A-Z_])
  • state：HealthState，上述健康状态之一。
  • message：字符串，描述检查状态的文本，应提供足够的信息，以便在包含于警报中时能够对该检查采取行动。消息中呈现的任何信息都应经过脱敏处理，并可安全地移出环境。
  • params：map<string, any>，有关健康检查性质的其他信息。这些信息也应经过脱敏处理，并可安全地移出环境。

JSON 正文应包含以下内容：

  • checks：map<string, Check>，一个从检查类型到 Check 对象的映射，这些对象描述了端点实现的每个健康检查的状态。键与 Check 中的 type 字段相对应。副本的整体状态应对应于其所有健康检查中最严重的状态。

完整的 JSON 响应必须小于最大长度 10 KB（10,000 字节）。如果响应超过此限制，报告基础设施可能会在存储有效负载之前移除检查消息和参数。如果响应因长度而被修改，报告器将以 WARNING 状态添加一个额外的 HEALTH_CHECK_MAX_LEN 检查。
