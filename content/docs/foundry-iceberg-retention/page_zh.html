Iceberg 表保留

Foundry Iceberg 表支持通过快照过期和移除孤立文件来实现保留和清理。这些操作会从 Iceberg 元数据中移除旧的表历史，并有助于在表随时间不断更新的过程中限制存储增长。本页面介绍如何在 Foundry 中针对单个表使用 Iceberg 维护过程来实现保留。

使快照过期

在 Iceberg 表上实现保留的主要机制是通过 expire snapshots 维护过程 ↗。对 Iceberg 表的每次数据写入都会创建一个 快照。快照过期会从表的元数据中移除较旧的快照。快照一旦过期，便不再出现在表的快照历史中，您也无法回滚到该快照或通过时间旅行访问该快照。

在配置 Expire snapshots 维护任务时，请根据表必须保留的历史记录量来选择保留设置。常见设置包括：

  • 要保留的最少快照数： 无论快照存在的时间长短，始终至少保留这个数量的最新快照。
  • 要保留的最短时间或时间窗口： 无论存在多少较新的快照，始终保留在配置时间窗口内的快照。

如果快照满足任一配置的阈值，则该快照将被保留。例如，假设某个表配置为至少保留 3 个快照和至少 30 天的历史记录。由于配置的历史记录，即使存在许多较新的快照，该表也会保留 10 天前的快照；同样，只要某个快照是最新的 3 个快照之一，即使该快照已超过 30 天，也会被保留。

在适用的情况下，快照过期会独立应用于每个 Iceberg 分支。例如，如果要保留的最小快照数为 3 ，而您的表有两个分支，则最小快照数设置意味着 每个 分支都有三个快照受到保护。因此，最小快照数设置可以保护 最多六个不同的快照 ，分布在两个互不重叠的分支中。当删除某个分支时，仅受该分支保护的快照将在未来的某次保留运行中符合过期条件。

您还可以使用 标签 ↗ 来保护特定的较旧快照，防止其过期。

使用 Expire snapshots时，请牢记以下注意事项：

  • 使快照过期时请务必谨慎。过期的快照会从表元数据中移除，且无法恢复用于回滚或时间旅行。如果下游增量消费者依赖较旧的快照来解析变更，也可能会受到影响。
  • 快照过期过程将遵循相关的 Iceberg 表属性 ，除非在过程中被显式覆盖。例如， history.expire.max-snapshot-age-ms 和 history.expire.min-snapshots-to-keep 表属性将在未指定 older_than 和 retain_last 过程参数时生效。

移除孤立文件

孤立文件是表存储位置中未被当前表元数据引用的文件，而当前表元数据包括所有未过期快照所引用的文件。写入失败、元数据清理或之前的快照过期操作都可能遗留孤立文件。

Foundry 会定期自动对所有 Iceberg 表执行孤立文件移除，以清理这些旧文件。此外，您也可以为您的表手动配置 Remove orphan files 任务，方法是前往 Maintenance 标签页。

移除孤立文件时的延迟文件删除

Foundry 与开源 Iceberg 的孤立文件清理不同，它只会物理移除位于所配置的灾难恢复回溯窗口之外的文件。该窗口内的文件即使不再被当前表元数据引用，也可能被保留。请参阅 延迟文件删除与灾难恢复 以了解更多详情。

延迟文件删除与灾难恢复

Foundry 的 Iceberg 实现将元数据清理与物理文件删除解耦。这确保了相关的孤儿文件在过期后会被保留一小段时间，以符合 Foundry 的 灾难恢复 流程。

这意味着 Foundry 的行为在以下方面与开源实现不同：

  • 在开源 Iceberg 中，快照过期通常还会删除不再被保留的快照所引用的物理文件。 Expire snapshots 在 Foundry 中会从表元数据中移除快照，这与开源 Iceberg 中的做法相同，但物理文件的删除会推迟到以后进行。
  • 在开源 Iceberg 中，孤儿文件移除操作将删除该流程中所提供的 older_than 时间戳之前的所有孤儿文件。 Remove orphan files 在 Foundry 中只会删除既早于用户提供的 older_than 时间戳、又早于您环境中配置的灾难恢复回溯窗口的孤儿文件。

为了防止灾难恢复备份意外失效，Foundry 管理的 Iceberg 表的行为就如同已设置了属性 gc.enabled=false。这可以防止用户意外运行可能在灾难恢复窗口内删除文件的原生 Iceberg 操作。

示例与指南

每次 Iceberg 提交都会生成一个快照，包括追加、覆盖、删除以及压缩（compaction）等替换操作。因此，保留固定数量快照的保留配置，其所保留的实际时间历史量可能相差很大，具体取决于表的提交频率以及所产生提交的类型。

请根据回滚需求、时间旅行（time-travel）预期、下游增量构建节奏以及存储管理目标来选择保留设置。如果下游消费者构建频率较低，应保留足够的快照历史，以便其解析上次处理的快照与当前表状态之间的变更。
