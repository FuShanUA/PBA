什么是公共应用程序？

一个 公共应用程序 是由 Foundry 托管的网站，与一个受限且仅限允许列表的未认证本体论 API 配套，两者均通过 Foundry 子域名提供服务。公共应用程序使开发者能够直接在 Foundry 上构建面向互联网的体验，而无需将数据导出到外部托管平台。公共应用程序的最终用户不登录 Foundry，因此任何能够访问该子域名的人都可以加载该网站，并调用其公开的少量未认证本体论操作。Foundry 通过由该应用程序管理的服务用户代为处理身份验证。

何时使用公共应用程序

公共应用程序支持以下工作流：其最终用户是公众成员，他们没有、也不应拥有 Foundry 账户。常见模式包括：

  • 单向数据收集表单： 向公众成员发送链接，让他们能够提交信息；每份提交内容都会通过非函数支撑操作存储在本体论中，且用户无需获得对其所提交数据的回访访问权限。
  • 公共数据分发仪表板： 展示本体论数据的预计算聚合视图，并允许有限的最终用户交互，例如按已知维度进行筛选。
  • 公共注册与报名流程： 从已知受众处收集意向、联系方式或注册信息，而无需这些用户加入 Foundry。
  • 静态网站着陆页： 部署完全无需与本体论交互的着陆页。

公共应用程序结构

Foundry 将公共应用程序组合为三个对客户可见的部分：

  1. 未经身份验证的网站： 您应用程序的静态资源（HTML、CSS 和 JavaScript）通过 Foundry 子域名提供服务，无需 Foundry 登录。这类似于一个 Foundry 托管的 OSDK 应用程序 但不包含 登录流程。
  2. 最终用户浏览器中的 OSDK： 您的应用程序使用 OSDK 在用户的浏览器中进行本体论调用，且仅使用您明确为未经身份验证的访问而启用的操作。
  3. 未经身份验证的 API 代理： 来自浏览器的每个本体论调用都会通过 Foundry 管理的代理进行路由，该代理会在请求到达本体论之前，以应用程序服务用户的身份对请求进行认证。最终用户永远不会持有、看到或传输 Foundry 令牌。

公共应用程序会以应用程序服务用户的身份执行每个请求，因此，公共应用程序的资源范围 （在 Developer Console 中配置） 以及该服务用户可见的资源，共同决定了其可暴露数据的最大范围。

公共应用程序可以由 仅 一个 无需身份验证的网站 或 以下组合组成： 一个 无需身份验证的网站 和一个 无需身份验证的 API 代理。

安全与保护模型

Foundry 会根据您所在 enrollment 的 入口策略来暴露公共应用程序，这些策略可能宽泛至无需身份验证的开放互联网，因此 Foundry 默认会应用多项保护措施。开发人员无法配置这些默认保护措施，因为它们的存在是为了确保 enrollment 的稳定性并限制潜在的滥用。

本体论操作的严格允许列表

在公共应用程序中，您只能调用一小部分本体论操作。无论调用用户拥有何种权限，Foundry 都会在代理层阻止任何会触发非常量计算的操作，包括函数、由函数支撑的操作、搜索、聚合以及 search-arounds。请参阅 当前支持的功能文档 以查看被阻止操作的完整列表。

按应用程序划分的速率限制

Foundry 会在执行任何身份验证交换之前，对未经身份验证的流量应用按应用程序划分的速率限制。这可以保护平台的其余部分免遭公共互联网上的滥用，并确保一个应用程序的流量不会耗尽另一个应用程序的容量。

继承的入口和 Web 应用防火墙（WAF）保护

Public Application 的子域会继承父级注册域的入口策略。如果您的注册被限制为特定的一组区域或网络（例如，仅限美国），则相同的限制也适用于该 Public Application。所有请求在到达 Foundry 之前都会经过注册的 WAF。Foundry 提供单个应用程序的入口策略配置，允许 Public Application 提供比注册更宽泛的入口策略。

仅限服务用户身份

该应用程序作为 服务用户 运行，该服务用户由 Foundry 管理。Public Application 中不存在针对每个最终用户的身份，因此，例如，Foundry 无法将回写归属于公众中的具体个人。对于需要每个最终用户身份的工作流，您不应使用 Public Application。有关服务用户和客户端凭据授予的背景信息，请查阅 OAuth2 客户端文档。

资源治理

只有当您有权移除该资源上的所有 标记 和 组织标记 时，才能将资源添加到公共应用程序。如果您无法做到，Foundry 会阻止您将资源添加到应用程序的范围。

此导出控制模型可确保资源只有通过明确且经过审计的决策流程才可从公共互联网访问，而该决策流程由已拥有解除数据各项限制权限的人员做出。

创建和公开公共应用程序时如何缓解风险

公共应用程序可以配置为无需身份验证即可供互联网上的任何人访问，因此作为应用程序开发者，您有责任实施以下各节中概述的风险缓解实践， 这些实践是对 上述 Foundry 管理的保护措施的补充。

确保 URL 标识符不可猜测

任何能够访问相应 URL 并满足该注册项入口策略的人，都可以访问公共应用程序提供的所有内容。您应确保 URL 中的标识符不可猜测（例如，随机生成的 UUID）。只有有意公开发布的数据才应纳入范围。

消除计算暴露风险

目前,函数驱动的工作流之所以被阻止,正是因为它们可能会使注册暴露于计算成本攻击。如果您的工作流需要更繁重的处理,请在 Foundry 中以异步方式执行。例如,配置一个 自动化任务 来处理应用程序已写入的数据,而不是尝试从公共应用程序按需运行它。

确保所有暴露的资源都可以设为公开

将资源添加到公共应用程序后,该资源便可以从公共互联网访问。您有责任确保所添加的资源确实需要公开,并将每次添加都视为一项导出决策。

审批要求

每个公共应用程序都需要由 信息安全官 在您的注册中进行用例审查,然后才能启用。 信息安全官 负责确认以下事项:

  • 预期的工作流适合在面向互联网且无需身份验证的界面上运行。
  • 添加到应用程序中的资源确实需要能够从公共互联网访问。
  • 您作为开发者,了解 相关风险 并已设计工作流来缓解这些风险。

此项审查 是在标准子域名审批之外额外进行的。该审批由 同一角色在 Control Panel 中执行,是 公共应用程序设置流程的一部分。。在请求子域名之前，请先记录已获批准的用例，以便审批人掌握做出决策所需的背景信息。
