审计日志类别

审计日志类别简化了安全监控，让您能够根据 发生了什么 来识别感兴趣的事件，而无需枚举所有 Foundry 服务中的每一个可能的事件名称。您无需跟踪数百个特定于服务的事件名称，类别让您可以专注于数据加载、数据导出或身份验证尝试等高级操作，而无需关心日志是由哪个产品或功能生成的。

类别为何重要

在传统的审计日志系统中，安全分析师必须了解每个服务的实现细节才能编写有效的查询。例如，在调查潜在的数据泄露时，您可能需要知道相关的事件名称是 EXPORT_DATASET、DOWNLOAD_FILE、CREATE_EXTERNAL_CONNECTION 以及其他数十个名称，同时还要随着新功能的添加不断维护此列表。

审计日志类别通过抽象解决了这个问题。在 audit.3 架构中，每个事件都必须记录在一个或多个标准化类别下，这些类别提供一致的请求和结果参数。这意味着：

  • 与服务无关的查询： 筛选 dataExport 即可查找所有数据导出事件，而无需关心是哪个 Foundry 产品执行的导出。
  • 面向未来的监控： 新的导出功能将使用 dataExport 类别记录日志；您无需更新查询。
  • 更快的调查： 减少理解系统内部机制的时间，将更多时间用于分析用户行为。
  • 可预测的结构： 每个类别都明确定义了将出现的请求和结果字段，使自动化分析更加可靠。

Audit.2 与 audit.3 架构

虽然 audit.2 日志可能包含类别信息，但其使用是可选的且不受强制约束。这意味着类别可能完全缺失，或者相关的请求和结果参数可能不遵循一致的结构。

相比之下， audit.3 架构强制使用类别，并提供以下保证：

  • 每条审计日志必须指定至少一个类别。
  • 每个类别都明确定义了将出现的请求和结果字段。
  • 标准参数使分析无需特定于服务的知识。

字段命名： audit.3 使用 requestFields 和 resultFields 来表示参数信息，而 audit.2 使用 request_params 和 result_params.

请参阅我们的 审计日志概述 文档，以获取有关架构差异和迁移指导的全面信息。

示例工作流

使用类别的典型安全监控工作流如下所示：

1. 确定感兴趣的类别

根据您的安全需求，确定哪些类别是相关的。例如：

  • 调查潜在的数据访问： dataLoad
  • 监控导出： dataExport
  • 审查登录： userLogin

2. 按类别查询日志

使用外部 SIEM 或包含 Pipeline Builder 的 Foundry 审计日志导出数据集来筛选日志。用伪代码表示如下：

allLogs.filter {log -> interestingCategories.any{log.categories.contains(it)}}

性能提示： 审计日志数据集可能包含非常大量的数据。在执行聚合或可视化之前，请务必先使用 time 列进行筛选，以确保查询性能。

3. 分析结构化参数

对于每条匹配的日志，检查 requestFields 和 resultFields。这些参数包含用户提交和系统返回的具体信息，二者分开存放以帮助您区分：

  • 请求字段 (requestFields）：用户提供了什么（例如，他们请求了哪些资源）。
  • 结果字段 (resultFields）：系统返回了什么（例如，实际加载了哪些资源）。

例如，带有 dataLoad 类别的日志将包含该交互期间加载的所有资源列表（以 requestFields or resultFields形式），让您无需知道是哪个具体的 Foundry 服务处理了该请求，就能立即了解数据访问模式。

4. 交叉引用类别

许多事件会生成包含多个类别的日志。在调查潜在事件时，您可以验证用户虽然加载了许多数据集（dataLoad），但通过确认其活动中不存在 dataExport 类别，可以确定没有发生实际导出。
