在 Pipeline Builder 中使用 LLM 节点

Pipeline Builder 中的 Use LLM 节点提供了一种便捷的方法，可大规模地对您的数据执行大语言模型（LLM）操作。在 Pipeline Builder 中集成此节点后，您可以在各种数据转换之间无缝地融入 LLM 处理逻辑，无需编写代码即可将 LLM 集成到您的管道中。

Use LLM 节点包含预先设计好的提示词模板。这些模板借助资深提示词工程师的专业经验，为初学者提供了使用 LLM 的友好入门方式。您还可以 运行试验 ，在输入数据集的几行数据上迭代优化您的提示词，然后再对整个数据集运行模型。此预览功能可在几秒钟内完成计算，加快反馈循环并改善整体开发流程。

要使用此功能，用户必须 获得平台管理员授予的自定义工作流的 AIP 功能权限 。

选择数据集

要将 LLM 应用于数据集，请在您的工作区中选择一个数据集节点，然后选择 使用 LLM.

选择模型

Use LLM 节点同时支持 Palantir 提供的模型和已注册的模型。Palantir 提供的模型默认可用，其中包括来自 支持的 LLM.

除 Palantir 提供的模型外，Use LLM 节点还支持 已注册的模型 ，这些模型由 Data Connection 中的 REST API 源 或 计算模块支撑。选择 注册 标签页，在模型选择器中选择您的已注册模型之一。

可选配置

输出类型

在提示页面上，您可以指定 LLM 输出需要符合的所需输出类型。选择 输出类型 选项（位于屏幕底部附近），然后从下拉菜单中选择首选类型。

Struct 输出解析行为

当您将 Use LLM 节点配置为输出 struct 类型时，该节点会使用严格解析将 LLM 的响应转换为指定的 schema。如果 LLM 输出不符合预期的 struct schema，该节点将失败并显示类似以下的错误 Cannot coerce to provided output type.

这种严格行为对于非交互式管道流程是有意为之的，可确保 schema 不匹配被清晰地呈现，而不是静默地产生错误数据。

如果遇到强制转换错误，一个实用的解决方法是将 Use LLM 节点配置为输出 JSON 字符串而不是 struct，然后使用后续转换将该字符串解析为您所需的 struct 类型。这种方法使您能够更好地控制管道中解析错误的处理方式。

包含错误

同样在提示页面上，您可以将输出配置为在输出值旁边显示 LLM 错误。此配置会将您的输出类型更改为一个 struct，其中包含您的原始输出类型和错误字符串。要包含 LLM 错误，请勾选 包含错误.

旁边的复选框。要将输出恢复为不含错误的原始输出，请取消勾选 包含错误 复选框，轻松开启或关闭此功能，从而灵活控制错误透明度。

跳过已处理的行

为了节省计算成本和时间，您可以通过切换以下选项来跳过已处理的行 跳过重新计算行.

当 跳过重新计算行 已启用时，将根据传递到输入提示中的列和参数，将行与先前处理过的行进行比较。具有相同列值和参数值的匹配行将获得缓存的输出值，而无需在未来的部署中重新处理。缓存键仅由提示中实际使用的那些列的值构成——如果某一行在不属于输入提示的列上存在差异，它仍会匹配缓存并复用之前计算的输出。缓存不适用于上一次部署中输出值为错误或 null的行；这些行将在下一次运行时重新计算。

输入行在多次构建之间必须是确定性的。 缓存机制使用基于所选输入列和具体行的哈希值来标识行。如果上游转换（例如去重）在多次构建之间产生了不同的物理行——即使逻辑值相同——缓存也不会被使用。为确保缓存正常工作，请确保 LLM 节点上游的任何去重或过滤步骤都是确定性的，例如使用窗口函数来一致地选择相同的代表性行。

Use LLM 节点的缓存存储在一个 Foundry 数据集中，实际上没有实际的行数限制，只要输入是确定性的且在多次构建之间看到相同的行，即可支持数千万行的大规模用例。

如果对提示进行了需要重新计算所有行的更改，则可以清除缓存。LLM 视图上方将显示一条警告横幅。

要清除缓存，请选择红色的垃圾桶图标。如果缓存被清除，将触发一个快照，并且所有行将在下一次部署中重新处理。

如果输出类型发生更改，缓存将自动清除。发生这种情况时，将显示一条警告横幅。如果这是一个错误操作，您可以选择 撤销更改 在横幅中。

对缓存状态的任何更改都将显示在 更改 页面中，在合并分支时。

如果一个具有多个下游输出的 Use LLM 节点启用了 跳过重新计算行 ，则必须将这些输出放在同一个作业组中。否则，在尝试部署时将出现以下错误：

创建新的作业组 在默认作业组之外，以修复此错误。

[高级] 显示模型配置

对于每个提示，您可以为该 Use LLM 节点配置所使用的模型：

  • 模型类型： GPT 实例的模型类型，例如 3.5 or 4。Use LLM 节点还支持开源模型，例如 Mistral AI 的 Mixtral 8x7b。
  • 温度： 较高的温度值会使输出更加随机，而较低的值会使其更加集中和确定。
  • 最大 Token 数： 这将限制输出中的 token 数量。您可以将 token 视为语言模型用来理解和处理书面语言的小文本片段。
  • 停止序列： 如果 LLM 生成命中任何停止序列值，将停止生成。您最多可以配置四个停止序列。

试运行

在每个 Use LLM 看板的底部，您可以使用示例测试您的特定 LLM。选择 试运行 选项卡，并在左侧输入您想要测试的值。然后选择 运行.

要测试更多示例，您可以选择 添加试运行.

要直接从您的输入数据中添加示例，请导航至 输入表 选项卡，并选择您要在试运行中使用的行。选择 使用这些行进行试运行，然后您将自动返回到 试运行选项卡 ，其中您选择的行将作为试运行填充。

运行试运行后，您可以查看发送给模型的原始提示词和原始输出。只需选择 </> 所选试运行右侧的图标。

这将打开一个包含以下详细信息的对话框：

  • 初始提示词：发送给模型的确切提示词，包括我们的后端所做的任何修改或添加。
  • 中间 LLM 输出：LLM 的所有输出，包括任何失败的输出。
  • 更正：针对任何失败所做更正的详细信息。
  • 最终输出：LLM 提供的最终结果。

选择左侧的相应标题，可在面板右侧查看原始文本。

评估套件

要对您的 Use LLM 节点进行更全面的测试，请使用 LLM 评估套件。虽然 试运行 让您可以在单个示例上快速测试提示词，但评估套件使您能够：

  • 在套件中配置多个评估
  • 在隔离的测试环境中运行评估
  • 使用评估器（例如 精确字符串匹配
  • 将评估结果存储在输出数据集中
  • 跟踪构建进度并查看详细结果

在部署之前使用评估套件验证您的 LLM 逻辑。

Spark 批处理管道中的计算资源使用情况

Spark 通常以 CPU 核心为粒度进行并行处理；一个有用（尽管略有简化）的心智模型是每个核心一次处理一行数据。对于大多数操作（例如算术运算），这种架构是高效的，因为所有计算都在本地进行。然而，当进程与外部 LLM 交互时，大部分计算在外部进行，进程将大部分时间花在等待响应上。在这种情况下，通过每个核心使用多个线程来实现并发要高效得多，从而有效利用等待时间来发送新请求。

如上所述，Use LLM 节点在每个核心上使用多个线程来发送大量并发请求。即使使用默认的 超小型计算配置文件（仅使用单个核心），并发程度也非常高。

您可以通过使用提供更多核心的计算配置文件（更多执行器或每个执行器更多核心）来进一步提高并发度，但随着核心数量的增加，您的作业可能会遇到 LLM 提供商或 AIP施加的速率限制。Use LLM 节点的实现包含重试逻辑，因此即使遇到这些速率限制，作业也能成功，但配置多个核心可能会低效或浪费，因为这些核心大部分时间都在重试失败的请求。

在调整并发度时，我们建议您使用默认的 Extra Small 计算配置文件作为基线。如果您想进一步提高并发度，请非常缓慢地扩展（每次增加不超过两个核心），并在作业的 Spark 详情页面中监控“所有任务的总运行时间”与“作业持续时间”之间的相关性趋势。理想情况下，随着核心的增加，作业持续时间应该减少，而所有任务的总运行时间应保持不变或仅略有增加。如果所有任务的总运行时间开始显著增加，尤其是作业持续时间没有相应减少，则说明核心过多，应该缩减规模。

函数执行器路由

通过 Use LLM 节点进行的 LLM 调用是通过函数执行器路由的，而不是直接发送到语言模型服务（LMS）。函数执行器负责在管道中编排 LLM 处理逻辑。由于这种架构，使用 LLM 模型的大型构建除了 LLM 计算成本外，还会产生函数执行器的使用量。

在规划容量和理解大量使用 LLM 处理的管道的资源消耗时，考虑这一行为非常重要。
