利用线上部署数据

模型推理历史数据集会跟踪线上部署的请求和响应。对于模型开发者希望了解真实客户和用户如何使用模型的生产用例，此功能可提供宝贵的反馈。

例如，设想使用实时部署在网站上提供推荐。模型推理历史会记录用户访问情况以及为每位用户提供的推荐。借助这些数据，开发者可以分析数据集，以确定推荐对特定用户的有效性。在这种情况下，数据集通过支持使用情况分析来创造价值，从而为优化和资源分配方面的决策提供参考。

虽然当前的 模型评估流程 支持持续再训练和性能评估，但这些现有功能并不提供有关模型使用情况的用户反馈。因此，与模型推理历史数据集不同，这些功能更适用于已有训练和测试数据（而非实时数据）的场景。

模型推理历史是从建模目标的“部署”页面创建的。

创建后，该数据集将记录关键信息，例如时间戳、用户 ID、请求 UUID 以及输入和输出的 JSON 表示形式。

from transforms.api import transform_pandas, Input, Output, lightweight

@lightweight
@transform_pandas(
    Output('/Project/folder/output'),
    df=Input('/Project/folder/input')
)
def compute(df):
    return df[df['Name'].str.startswith("A")].sort_values(by="Age")

转换基准测试研究

通过比较优化复杂转换与简单转换的基准测试,可以展示 Lightweight API 的优势。作为背景,下面展示的两个基准测试图演示了一项受控优化比较:五种计算引擎在 19 种不同数据集大小上执行相同的转换逻辑,对七次重复运行的端到端平均运行时间进行比较。条带表示标准误差。每个转换均分配了 8 个 vCPU 和 32 GB 内存。折线的提前终止表示达到了内存不足(OOM)状态。Polars 以流式模式使用,可通过 .polars(lazy=True) 访问。

下面的基准测试图展示了一条相当复杂的管道,包含一个 explode 操作,后接多个 join 和一个 group-by,并分别使用 Pandas、Polars 和 PySpark 的 API 进行了原生实现。

展示复杂转换优化的基准测试图

在这种情况下,使用无 Spark 的 Lightweight 后端时,启动开销几乎减半。此外,两个针对单节点优化的数据处理库 Pandas ↗ 和 Polars ↗ 在约 1000 万行以内的数据规模上仍然明显更快，因为它们不像 Spark 那样需要等待受网络限制的 shuffle 操作结果。然而，对于更大的数据集和更复杂的操作，Spark 的查询计划在规模化扩展时效率要高得多，因此在这些用例中推荐使用 Spark。

相比之下，将更简单的管道应用于更大的数据表明，即使在超大规模的数据集上，Spark 也并不总能超越 Polars。

展示对简单转换进行优化的基准测试图

上图突出显示了一个关键观察结果：所实现的转换逻辑非常简单，仅包含对某一列的单个过滤操作，而数据集并未按该列进行分区。在这种管道较为简单的场景中（例如算子较少、内存友好的连接），Lightweight Polars 的流式模式 ↗ 大幅超越 Spark，建议用于所有规模的数据集。提醒一下，当 @transform 被 @lightweight装饰时，将无法访问 Spark 方法。

  • 支持自定义 Docker 镜像
  • 支持增量转换

Foundry 中的语义搜索支持现已正式发布 [GA]

发布日期：2023-11-13

随着向量属性和函数的推出，Palantir Foundry 现已支持在本体论中进行语义搜索。用户现在可以为本体论中的对象创建向量属性类型，并对对象（FoO）使用 K 近邻（KNN）函数，以实现对对象的语义搜索。借助此功能，您可以使用基于本体论的模型输出，从而获得更准确的结果。

Foundry 中的语义搜索功能可支持多种用例，包括改善文档库用户搜索特定主题时的体验。借助语义搜索支持，可以将用户的查询与其语义含义进行匹配，并返回相关对象。此外，通过访问本体论，这些结果还可以回传到 LLM 中，以生成实用且用户友好的提示词，从而增强现有的 AIP 构建器功能。

什么是语义搜索？

语义搜索是一种搜索技术，它会考虑查询的上下文，以返回更准确、更相关的搜索结果。与不考虑上下文、仅简单匹配查询中完整短语的关键字搜索不同，语义搜索融入了用户搜索词背后的含义。

Foundry 对语义搜索的支持得益于针对本体论的多项增强功能，包括：

  • 在 Object Storage v2 (OSv2) 中引入向量属性类型
  • 通过对象上的函数执行 K 近邻 (KNN) 搜索

根据从 Foundry 建模目标获取的浮点数组生成向量属性，随后即可在 FoO 函数中使用 KNN 搜索相似向量。有关详细的端到端语义搜索工作流示例，请参阅 语义搜索工作流教程。

配置向量属性类型

新的向量类型可用于将模型生成的嵌入捕获到本体论中。它们可以在任何具有固定维度的浮点数组数据集字段上创建。有多种用于比较向量的相似度函数，可根据用例和模型输出进行选择。

在 Ontology Manager 中，您可以配置向量属性：首先选择类型，然后选择维度（即该属性所基于的模型的输出长度），最后选择相似度函数，该函数决定了您希望如何将此向量属性类型与其他具有相同向量属性类型的对象进行比较。

对象上的 K 近邻函数

新增了对象上的 K 近邻（KNN）函数支持，简化了创建函数以对对象类型进行语义查询的过程。可以使用模型实时生成的向量或对象中已有的向量对该对象类型执行 KNN 搜索。有关更多信息，请查阅 文档中关于对象上的 KNN 函数的内容。

有关此公告相关主题的更多信息，请参阅以下文档：

  • API 中的 K 近邻：对象集

组织权限将分两个阶段从 Platform Settings 迁移到 Control Panel 组织权限将分两个阶段从 Platform Settings 迁移到 Control Panel，旨在提高清晰度、减少混淆，并为平台管理员提供更灵活的权限设置。目前，控制用户 Foundry 使用体验的各项设置（包括权限管理、成员资格、标记类别和组成员资格）均在 Platform Settings 界面中管理，但将通过此次迁移整合到 Control Panel 中。

  • 第一阶段 （从 11 月 20 日当周开始）：Platform Settings 工作流/权限已添加到 Control Panel 角色中。

  • 第二阶段 （预计 2024 年第一季度）：平台设置权限的其余成员将迁移至包含相应工作流/权限的控制面板角色中。用户完成迁移后，旧版组织平台设置将仅在控制面板中提供。第二阶段变更的详细信息将在未来的公告中说明。

请仔细阅读以下通知，了解权限更新将如何影响您和您的组织。

我们为什么要这样做？

我们发现有些用户对于哪些权限在控制面板中授予、哪些在平台设置中授予感到困惑。整合到单一界面可以提高清晰度并降低管理工作流的复杂性。

当前的权限系统不够灵活，且由于某些任务仅限最高级管理员访问，给他们带来了过重的工作负担。控制面板中的角色支持开箱即用的自定义，并且可以通过自定义角色以细粒度的方式授予这些工作流的权限。

这些变更将如何影响用户和现有权限？

到第二阶段结束时，所有现有权限将被自动迁移，不会造成任何访问权限或特权的损失。但是，有几点重要变更需要注意：

第一阶段变更（于 11 月 20 日当周生效）

为了摆脱对 Platform Settings 权限的使用，我们首先必须在 Control Panel 中将这些权限/工作流授予相应的角色。系统将创建一个新角色，并为部分现有角色添加新的工作流，从而使现有角色成员获得与角色描述相符的额外权限。

我们建议您出于安全方面的考虑，提前将以下变更与贵组织的角色成员资格进行对照审查，并在必要时在 Control Panel 中更新角色。

以图形方式展示第一阶段变更中角色到 Control Panel 角色映射关系的图表

组织管理员获得 Manage 权限以及在 Platform Settings 中授予的其他权限

组织管理员获得用于管理权限、成员资格、标记类别以及控制 Expand Access/Apply Organization 的工作流。

拥有组织管理员默认角色的用户将能够执行先前通过 Platform Settings 授予的工作流（管理权限、管理成员资格、管理标记类别和查看组成员资格）。此项变更秉承了我们的理念，即组织管理员是一个具有高度特权的角色，应当能够管理组织的所有方面。

Expand access 将保持独立，并且不会自动授予组织管理员。但是，组织管理员将能够管理具备此能力的用户和组，方法是导航至 Control Panel > 组织权限 选项卡。

组织设置查看者新增权限 View group membership

拥有“组织设置查看者”默认角色的用户将获得查看组织群组成员资格的能力。目前，该 Control Panel 角色授予对 Control Panel 中组织权限的只读访问权限，但未来几个月内将增加更多只读工作流。

数据治理官新增权限 Manage marking categories

拥有“数据治理官”默认角色的用户将获得管理组织标记类别的能力。

[新增] Users and groups administrator 默认角色

Control Panel 将新增一个名为“用户和群组管理员”的默认角色。被添加到该角色的用户将获得管理组织成员资格的能力。

[新增] 组织 Marking permissions 选项卡

Control Panel 中的“组织权限”部分将新增“标记权限”选项卡。该选项卡将一对一替换平台设置中的“Apply Organization”和“Expand access”板块。

Control Panel 上新增“标记权限”选项卡，供组织管理员查看组织权限和现有权限

第二阶段变更(计划于 2024 年第一季度)

在第二阶段中，现有的权限授予将自动迁移至控制面板角色，平台设置中的界面将被完全弃用并移除。第一阶段启动后，我们将提供有关第二阶段详情的补充说明。在第一阶段开始时，我们鼓励管理员：

  • 不再依靠平台设置来管理这些权限，而是通过相应的控制面板角色来授予这些权限；以及
  • 手动审核平台设置中现有的权限授予，并将其迁移至目标控制面板角色。

如需详细了解权限及其基元在 Foundry 中的运作方式，请查阅关于 注册与组织 的 Foundry 文档。

Objects Monitoring 更名为 Automate [GA]

发布日期：2023-11-02

Automate，将于 11 月 20 日当周正式发布，是一款全新的、完全向后兼容的产品，将取代对象监控，成为 Foundry 中所有业务自动化的统一入口。所有现有的对象监控器都将自动迁移到新应用程序，并继续正常运行，无需任何更改。

Automate 摘要页面一览

除了对象条件之外，Automate 还允许用户设置时间条件，并将这些条件关联到在满足条件时自动执行的操作或通知。Automate 在对象监控的基础上进行了众多改进和扩展，提供全新设计的自动化创建用户界面、更多用于配置条件和效果的选项，以及与平台中其他应用程序的原生集成。

用于稳健配置的新条件和效果

除了 Automate 能够创建永不过期的自动化之外，您现在还可以配置各种新的条件、效果和原生集成，从而为您提供更大的自动化灵活性。

条件

  • 时间条件：配置计划，并在预先设定的时间执行效果（例如，“每周一上午 9 点”）。
  • 对象集条件
    • 对象修改条件：当对象的任意属性或特定属性发生更改时触发效果
    • 允许内联指定受监控的对象集（不再需要已保存的 Hubble 探索）
    • 新增执行模式（除现有的批量模式外）
      • 按对象执行：允许为每个触发自动化的对象单独触发效果
      • 按组执行：允许为预定义的组触发效果
    • Live Patch 支持：可实时监控的对象集现在能够立即获取来自操作的变更
  • 时间与对象集组合条件：在预定义时间检查对象集条件（例如，"每周一上午 9 点且针对任何新的警报对象"。）

效果

  • 通知
    • 基于属性的收件人：使用对象属性为通知效果动态设置收件人
    • 附件：选择 Notepad 或 Notepad 模板，自动以 PDF 形式附加到电子邮件通知中
      • Notepad
      • Notepad 模板
        • 支持从对象条件传递受影响的对象
    • 基于函数的通知
      • 支持传递单个受影响对象、对象引用、对象列表和对象集参数
  • 操作
    • 支持以对象集参数的形式提供动态对象集定义

原生集成

  • 原生 Notepad 集成
    • 直接在 Notepad 中设置自动化，无需切换到 Automate
  • 原生 Ontology Management Application (OMA) 集成
    • 从 OMA 设置自动化，并查看与特定对象类型或操作类型关联的所有自动化

开发路线图上有哪些内容？

我们计划扩展 Automate 的功能，并将其进一步嵌入其他 Foundry 应用程序，重点改进以下方面：

  • 对流式对象类型的支持
  • 基础设施改进，以提升执行上限
  • 与 Machinery 的原生集成
  • 与 Foundry Logic 的原生集成

有关更多信息，请查阅 Automate 文档，或了解如何 开始使用 Automate。
