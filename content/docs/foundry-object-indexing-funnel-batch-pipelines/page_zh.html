Funnel 批处理管道

Funnel 批处理管道是内部作业管道，负责以批处理方式将数据（包括来自 Foundry 数据源的数据和用户编辑）高效地编排索引到 OSv2 中，确保本体论中的数据和元数据保持最新。

Funnel 批处理管道的组件

一个 Funnel 批处理管道由一系列 Foundry 构建作业:

  • 以及
  • 合并变更
  • 索引
  • 水合

下面的屏幕截图展示了一个 Funnel 批处理管道示例。

以及

在变更日志作业中，当数据源接收到新数据或事务时，Funnel 会自动计算所有数据源的数据差异，然后在 Funnel 管道中创建中间变更日志数据集。变更日志数据集会接收 APPEND 事务 ，其中包含每个事务中的数据差异，以提供 增量计算语义. 这些变更日志数据集由 Funnel 拥有和控制，因此用户无法访问。

合并变更

在合并更改作业中，变更日志步骤中的所有变更日志数据集以及来自 Actions 的任何近期用户编辑，都会按对象类型的主键进行联接，以合并所有更改并将其存储在单独的数据集中。这些合并后的数据集由 Funnel 拥有和控制，因此用户无法访问。

索引

变更合并后，Funnel 会为每个对象数据库启动一个索引作业，将包含所有已合并变更的最终数据集中的所有行转换为与为该对象类型配置的对象数据库兼容的格式。例如，对于标准的 OSv2 数据库，上一步中的合并变更数据集内的所有行都会被转换为索引文件；这些文件存储在一个单独的索引数据集中。这些索引数据集由 Funnel 拥有和控制，因此用户无法访问。

水合

索引作业完成后，各对象数据库必须为查询准备好已索引的数据。以 OSv2 为例，此准备步骤涉及将索引文件从数据集下载到 OSv2 数据库搜索节点的磁盘中。该过程称为 水合，是我们用于更新对象类型数据的 Funnel 批处理管道示例的最后一步。

数据填充（hydration）作业的进度会在 Ontology Manager 应用程序中报告，如下面的屏幕截图所示。

完成这些步骤后，对象类型即可投入使用，并可由其他服务在外部或 Foundry 中进行查询。

实时与替换 Funnel 管道

当对象类型发生数据更新或 schema 更新时，会涉及两条独立的 Funnel 管道。下面的屏幕截图展示了这两条 Funnel 管道：

实时管道

Funnel 实时管道 使用来自 Foundry 数据源的新数据更新生产环境中的对象类型。每当相应的数据源更新时，实时管道便会运行。此外，如果检测到用户对对象的编辑，则无论支撑数据集是否有任何显式更新，实时管道都会每六小时运行一次；这可确保在索引到 Funnel 拥有的数据集的过程中，用户编辑会在合并变更步骤中得到持久化。

用户编辑将应用于以下位置的索引： 对象数据库 中的索引;常规的六小时作业间隔使内置控制机制能够将此数据持久地存储在 Foundry 中。

替换管道

如果对象类型的架构发生变化且先前管道的架构不再是最新的,就必须预配一个新的 替换管道 来编排对象类型的更新。架构变更可能包括向对象类型添加新的属性类型、更改现有属性类型,或将对象类型的输入数据源替换为另一个数据源。

在线上管道继续按其惯常节奏运行的同时,Funnel 会在后台编排替换管道,而不会影响向用户提供的线上数据。在替换管道首次成功运行后,线上管道将被弃用并由替换管道取代;对象类型的架构和数据也将相应更新。

尽管 schema 变更是 Funnel 预配替换管道的最常见原因，但 Funnel 有时也会出于性能原因，基于各种启发式方法自动预配替换管道。

增量重建索引与完全重建索引

以下文档特定于规范的 Object Storage v2 数据存储。有关 Object Storage v1 (Phonograph) 索引行为的信息，请参阅 OSv1 文档.

增量索引（默认）

规范的 Object Storage v2 数据存储会自动计算数据源中每个新事务的数据差异，并仅对新数据更新进行增量索引。Funnel 管道默认对所有对象类型使用增量索引。增量索引使 Funnel 管道的运行速度比重新索引所有数据更快。

例如，假设您有一个包含 100 个对象的对象类型，由一个包含 100 行的数据源支撑。如果在新数据更新中有 10 行发生了变更，则无需重新索引全部 100 个对象，而无论 事务类型 在输入数据源中， Funnel 批处理管道 将创建一个新的 APPEND 事务，该事务将写入变更日志数据集，且仅包含这 10 行修改过的数据。

增量数据集的增量索引

对象存储 v2 在同步由增量数据集支撑的对象类型时，使用“最新事务优先”策略。如果数据集针对同一主键包含多行，则最新事务中行的数据将存在于本体论中。在单个事务中不能有重复的主键。此行为与以下内容无关： 用户编辑与数据源更新冲突 的处理方式。

考虑一个增量数据集，它通过 APPEND 事务接收行更新，这种数据集通常称为变更日志数据集。同一数据的新版本由一个新行表示，该行包含更新后的值但主键相同，并在单个事务中被追加到数据集。名为 is_deleted 的列默认不会被视为删除列。要使用删除列，数据源架构必须包含可标识该列的旧版 Object Storage v1 变更日志元数据。

Object Storage v2 按如下方式同步变更日志数据集：

  • 如果某个主键出现在多个事务中，将保留最新事务中的行。
  • 每个事务中，每个主键最多只能包含一行。
  • 删除列只有在旧版 Object Storage v1 变更日志元数据中声明时才会生效。

您可能需要对变更日志数据集执行增量窗口转换，以确保每个事务中每个主键最多只包含一行。

Iceberg 表数据源

An Iceberg 表 用作 OSv2 对象类型数据源时，其当前内容中每个对象主键最多只能包含一行。追加行时，Iceberg 不会强制执行此要求。

追加行会保留数据集和 Iceberg 表中的先前行。对于 增量数据集，OSv2 会使用每个主键最近一次事务中的行来填充索引对象。不支持通过追加重复主键来更新对象（针对 Iceberg 表数据源）。

由 Iceberg 表支撑的对象类型不支持重复主键。存在重复主键时，增量索引可能看似成功，但只要仍存在任何重复主键，完整重新索引就会失败。此外，如果您删除其中一行重复数据，即使表中仍存在另一行具有相同主键的数据，该对象也可能从索引中被移除。

为保持主键唯一，请仅为新主键追加行，并使用 UPDATE or MERGE INTO 来更改现有行。

在将数据集数据源迁移到 Iceberg 表之前，请确保您的管道在整个表的当前内容中保持主键唯一。如果您的管道通过追加具有现有主键的行来更新对象，请继续使用数据集数据源，直到您的管道在整个表的当前内容中保持主键唯一。

视图增量索引

数据集视图 在增量索引方面存在限制。由于视图抽象了底层数据结构，Funnel 会尝试使用增量构建来节省成本。但是，存在以下限制：

  • 带删除列的视图 始终会被完全重新索引，因为 Funnel 无法确定哪些行已被删除。
  • 增量构建可能会产生不一致的结果 当去重列值与事务顺序冲突时。Funnel 采用“最后编辑优先”策略:如果具有较大去重列值的行落在增量窗口之外,这些行将被忽略。为避免这种情况,可以添加删除列来触发全量重建索引,或者确保去重列值始终随每个事务递增。
  • 从最新视图中删除数据的保留策略 在底层数据集上,如果旧数据被删除,则可能会导致意外结果。在这种情况下,全量重建索引将产生正确的结果。

全量重建索引(特殊情况)

Funnel 管道将在以下情况下使用批量索引(即重新索引所有对象):

  • 当输入数据源中超过一定百分比的行在同一事务中被修改时,与计算变更日志并进行增量索引相比,重建索引在计算上的开销可能更低,速度也更快。默认阈值设定为同一事务中 80% 的行发生变更。
  • 当对象类型架构中的某些更改需要 Funnel 替换管道时,该管道将在后台创建一个全新的 Funnel 管道(包括 OSv2 索引)。
  • 当用户通过 Ontology Manager 触发完全重新索引时。

监控 Funnel 管道

Funnel 管道由多个构建作业组成; 监控视图 使用户能够跟踪 Funnel 管道中特定作业的运行状况,方法是创建一组 （过去 30 天内），以及任何.

用户可以在本体论管理器中选择 监控此对象类型的健康状况 来创建监控视图。这会将用户带到 监控视图 标签页（位于数据健康应用程序中），如下方截图所示。

在监控视图标签页中，用户可以为实时管道和替换管道中的监控作业创建规则。用户还可以添加 同步传播延迟 规则，以便在对象数据库中已索引数据的新鲜度超过规则中定义的阈值时收到通知。

相比之下，Object Storage v1 (Phonograph) 使用 健康检查 来监控本体论实体的同步；在 OSv1 中，针对对象类型只有一个同步作业，用户可以直接在同步作业上定义这些健康检查。

调试管道

Foundry 构建作业可能会因多种原因而失败。具有 View 对象类型的支撑数据源权限的用户可以通过以下方式查看管道错误 实时管道 仪表板位于对象类型的 数据源 标签页中。在管道图中选择失败的作业，然后选择 失败的作业 如下方屏幕截图所示。

或者，若要列出特定对象类型的所有构建作业，用户可以导航到 构建应用程序 以及通过左侧面板的搜索筛选器按对象类型进行筛选。
