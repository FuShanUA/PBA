聚合注意事项

在 Foundry 中，根据您所处理数据的复杂程度和数据量，应用程序可能无法以完全准确的方式显示结果（也称为“非精确聚合”），这是由高基数聚合的性质所致。

直方图 object-set-service API 提供以下与聚合准确性相关的字段，您可以在可用的情况下使用这些字段来优化准确性：

  • API 调用方可以在请求中添加 AggregationExecutionMode 并将其设置为 PREFER_ACCURACY。设置后，API 响应会变慢，但会提供更准确的结果，但不保证完全准确。
  • 聚合响应包含一个 AggregateResultAccuracy 字段，用于指示结果是否准确。

Foundry 中的每个产品在指示聚合可能不精确方面略有不同的行为。请查看以下部分，了解非精确聚合在 Foundry 中可能如何呈现的示例，以及用户在达到准确性时应考虑的事项。

如需更多指导，请联系 Palantir Support。

Object Explorer 和 Workshop

请考虑以下两个直方图截图，显示来自包含 2000 万个对象的数据集的数据。第一张截图是在 Object Explorer 中打开的数据集，第二张是 Workshop 中的 Workshop Filter List 部件。

这些直方图是使用两个聚合请求构建的。第一个请求尝试获取按计数排名的前 100 个桶，收到的是近似响应。第二个请求再次获取这 100 个桶的计数，但额外地，仅筛选出这 100 个桶以确保计数的准确性。

虽然显示的计数是准确的，但第二个直方图仍然不准确，因为所显示的桶并不是按计数排列的实际前 100 个桶，这是由于第一个聚合响应并不准确。

Object Explorer 和 Workshop 向 OSS 发送的请求未指定 AggregationExecutionMode，而 OSS 默认为 PREFER_SPEED.

Quiver 透视表和 Workshop 透视表

在 Quiver 和 Workshop 透视表中按计数对列进行降序排序时，排名靠前的桶不会按正确顺序显示。在这种情况下，非精确聚合可能表现为以下错误消息之一：

  • "Too many values for column, not all are displayed"
  • "Showing approximate results due to computational limitations"
  • "Only loading first 1,000 values per property. Filter your data for more accurate results."

时间序列转换 Example Bucket 列未按预期进行降序排列。

这些并不是按计数排列的真正排名靠前的桶，因为 Quiver 和 Workshop 未在支撑透视表的聚合请求中指定排序。排序是在前端使用返回的桶完成的。

本体论 SDK (OSDK)

OSDK 被设置为 PREFER_ACCURACY ，其有限的聚合复杂性意味着每个查询响应都将是 ACCURATE.

函数

函数始终使用 PREFER_ACCURACY，因此给定桶的值将是正确的。目前无法在函数调用期间同时 groupBy 和 orderBy 。以下代码片段演示了当前的一个示例：在后端进行 groupBy 并在内存中排序。

    @Function()
    public async aggregateOnMoreBucketsThanAuthorized(): Promise<TwoDimensionalAggregation<string, Double>> {
        // Aggregate and sum
        const aggregation = await Objects.search()._af20mInstancesObv2()
                 .groupBy(o => o.exampleBucket.topValues())
                 .count()

        aggregation.buckets.sort((b1, b2) => b2.value - b1.value);
        return aggregation;
    }
