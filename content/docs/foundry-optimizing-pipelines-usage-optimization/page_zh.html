Foundry 使用优化

Foundry 使用优化最佳实践

本指南旨在提供优化 Foundry 使用的方法和最佳实践。本文档首先介绍 Foundry 中的使用量是如何确定的，其次介绍如何识别使用浪费和管道优化。这些建议对项目经理或平台管理员也可能有所帮助，因为它们侧重于监控和优化组织的使用消耗。

除了此处列出的最佳实践之外， Linter 还会检查 Foundry 中是否存在反模式，并提供有针对性的改进建议，以改善资源状态。您可以评估并采纳这些建议，以降低成本、优化本体论，并提高管道的稳定性和弹性。

何时进行优化

在考虑如何为您的工作流实施这些最佳实践时，重要的是不要陷入过早优化管道或工作流这一众所周知的陷阱。用户应避免过早优化管道，并且不应期望有一种放之四海而皆准的优化策略。

我们建议按照以下思维步骤来验证您的方法是否合理：

  • 工作流是否已完成并正常运行？如果没有，请注意过早优化可能会影响工作流的功能。
  • 此次优化是否有明确的目标，例如可视化时间或成本，并将其作为推动后续决策的成功指标？
  • 针对上述目标，是否已经确定了明确的瓶颈？

如果其中一些问题尚未得到解答，则可能表明还需要更多的前期工作才能成功完成优化。

考虑到这一点，以下是一些优化工作的正面和反面示例：

  • [正面示例] 一个正常运行的管道成本为 X 美元，一位工程师被问及是否可以降低该成本。 资源管理 应用显示大部分成本与计算资源相关。工程师查看构建频率后发现，尽管没有人每天使用该计划任务，但它每天都运行。将计划任务设置为较低频率运行可将消耗降低约 28%。此后，该管道将不再是平台上成本最高的管道，工程师可以专注于改进下一个瓶颈。
  • [反面示例] 一位工程师被要求设计一种高级策略来优化管道的存储成本，这需要投入大量工程时间。该策略实施后，存储成本有所下降，但整体基础设施账单保持不变。为什么？因为基于节省成本的目标，瓶颈（存储）被错误地识别了。尽管数据集的存储规模确实过高，但相对于计算而言存储成本较低，这意味着该变更对工作流的总使用成本影响甚微。

通用最佳实践

优化 Foundry 使用的一些通用实践包括：

  • 设置项目以便能够在资源管理应用中跟踪使用情况
  • 利用资源队列
  • 尽可能使用增量管道
  • 管理计划任务，确保其运行满足而不超出组织的需求
  • 优化 Spark 使用（取决于您对实施的熟悉程度）

步骤 1：了解 Foundry 使用的组成部分

Foundry 使用由三个部分组成：Foundry 计算、本体论容量和 Foundry 存储。

大多数账户都采用这种三维模型；但是，某些账户的使用标准可能有所不同。请与您的 Palantir 代表确认相关条款。

1. Foundry 计算

Foundry 计算 由数据集成和分析工具驱动。Foundry 计算主要有三种类型：批处理、交互式和流式。

批量计算表示以“批量”方式运行的查询或作业，即它们按一定的计划周期或在临时需要时被触发在后台运行。批量计算作业在不运行时不消耗任何计算资源。批量计算的一些示例包括所有转换作业、从 Contour、代码工作簿构建数据集、数据健康检查以及同步到本体论/索引存储。

交互式计算表示实时评估的查询，通常作为交互式用户会话的一部分。为了向用户提供快速响应，交互式计算系统会保持常开的空闲计算资源，这意味着交互式查询往往比批量评估占用更多计算资源。交互式计算的主要形式是 Contour - Contour 仪表板、分析以及嵌入的 Contour 图表都是交互式计算的示例。

流式计算表示持续接收消息并使用任意逻辑处理这些消息的常开处理作业。流式计算按流准备好接收消息的时间长度计量；与批量计算和交互式计算相比，流式计算的成本最高。流式计算的示例包括流式转换和 管道构建器 流。

批量、交互式和流式的计算用量由以下因素驱动：

  • 数据逻辑： 应用于数据的逻辑是影响 Foundry 用量的最大因素之一，也是用户最能施加影响的因素。
  • 转换速度： 转换速度通过并行化作业来实现。Foundry 可以扩展到数千台同时运行的机器，以快速处理大型数据集上的海量计算。然而，更快的结果和作业并行化可能会引入开销和低效，从而可能导致更多用量。
  • 计算类型： 不同类型的计算在相同数据上执行所需的计算量不同。例如，批处理往往比流式数据处理占用更少的计算资源，因为批处理仅在运行期间使用计算资源，而流式处理是常开的。
  • 数据规模和类型： 数据越多，处理数据所需的计算资源就越多。
  • 数据新鲜度： 计算新结果的频率越高、计划转换越多，执行所需的计算资源就越多。

2. 本体论容量

Foundry 用量的第二个组成部分是 本体论容量。Foundry 的独特能力之一是本体论层。本体论是企业数据与您的组织所关注的对象之间的转换层。本体论是对您的数据世界的分类，使组织能够以更具体的概念（例如“飞机”或“汽车”）来思考他们的数据，而不是描述这些数据的众多行和列的聚合。如果您不熟悉本体论，可以 从文档中了解更多信息.

本体论容量由以下因素驱动：

  • 对象数量： Foundry 的本体论层可以扩展到每种对象类型数十亿个对象。某种对象类型的总本体论容量与对象总数直接相关。
  • 对象大小： 本体论对象各自可以拥有数百个任意类型的属性。具有更多或更大属性（例如长文本或图像）的对象会使用更多的本体论容量。
  • 对象间关联数量： 与其他对象有大量关联的对象可能会因其关联元数据的大小而使用更多的本体论容量。

3. Foundry 存储

Foundry 存储 计量 Foundry 中存储在非本体论转换层中的通用数据，有时称为“冷存储”。

数据集分支和先前的事务（以及视图）会影响单个数据集占用的磁盘空间大小。Foundry 提供了多种保留规则，帮助您保持 Foundry 实例的精简。当文件从带有某个 DELETE 事务的视图中移除时，这些文件并不会从底层存储中删除，因此会继续产生存储成本。减小大小的唯一方法是使用保留（Retention）功能清理不必要的事务。提交一个 DELETE 事务或更新分支并不会减少已使用的存储。

步骤 2：了解如何跟踪 Foundry 使用量

直方图 资源管理应用程序 为组织提供了可见性和透明度，帮助其了解自身的 Foundry 使用量消耗情况。该应用程序使用户能够查看按每种 Foundry 使用量类型（Foundry 计算、本体论容量和 Foundry 存储）细分的 Foundry 使用量消耗情况。用户可以按资源（项目）、来源（应用程序）和用户查看使用量。

在尝试确定可以在哪里优化 Foundry 使用量时， 首先应查看的是资源管理应用程序。它可以让您查看哪些资源占用了最多的计算资源，并识别瓶颈所在。从这里，您可以利用 Foundry 使用优化最佳实践 来识别可能减少使用量的方法，但请始终记住—— 专注于瓶颈.

步骤 3：设置项目以便能够跟踪 Foundry 使用量

项目与资源管理应用程序

如上所述，计算资源默认在资源管理（RMA）中按项目级别进行管理；在 RMA 中，我们可以看到按项目度量的 Foundry 计算、本体论容量和 Foundry 存储指标。因此，正确的项目设置对于有效跟踪整个数据管道的使用量指标至关重要。正确的设置将使数据工程师或平台管理员能够在管道的关键阶段监控这些使用量指标，以识别可优化的区域。不正确的设置将导致无法识别数据管道中资源密集且计算成本高昂的部分。

用于跟踪 Foundry 使用量的推荐项目结构

应使用 Foundry 项目来实现结构合理的数据管道。项目设置与管道阶段的最佳实践在 推荐的项目和团队结构文档中有深入介绍。确保项目遵循推荐的结构（从数据源导入原始数据到实际工作流），将使用户能够分析管道关键阶段的计算和存储指标。

权限

在寻找使用量缩减策略时，管理员应考虑团队中哪些人应该有权创建项目和资源。将此权限限制在少数熟悉设置最佳实践的人员，可以减少项目和资源的扩散，从而减少不必要的存储和计算。允许任何用户在平台上创建项目，很可能导致项目偏离跟踪使用量的推荐结构，从而产生不必要且成本高昂的管道，最终推高使用量。组织可以根据平台上的用户数量和数据访问限制，以不同方式管理其项目创建权限；建议制定确定此权限的流程，并对拥有权限的人员进行正确项目结构的教育，以便对这些资源进行适当的使用量监控。

步骤 4：资源队列

Resource Management 应用程序中一项使您能够控制 Foundry 中支出的关键功能是 选项卡允许您查看分配给该项目的。为了限制与特定项目或多个项目相关联的计算资源量，您可以将项目捆绑到队列中。每个队列将被分配一个特定的资源限制，用于定义同时使用的最大 vCPU 数量。例如，您可以为某个队列分配 XXX 个 vCPU，这将是所分配项目在任何给定时间运行的最大 vCPU 数量。这将确保您能够了解并掌握每个项目将消耗的使用量。

第 5 步：增量管道

增量管道 通常用于处理随时间发生显著变化的输入数据集。通过避免对未发生变化的行或数据文件进行不必要的计算，增量管道能够降低端到端延迟，同时最大限度地减少计算成本。实现这一目标的方法是理解 SNAPSHOT 和 APPEND 事务之间的区别。

快照事务

默认事务类型为 SNAPSHOT。快照事务被视为对数据集中所有数据的替换。这意味着当您打开一个最新事务类型为 SNAPSHOT的数据集时，预览将仅包含该最新快照事务中接收到的数据。当您尝试在数据转换或 Contour 分析中读取该数据集时，情况也是如此——您将只能看到该最新事务中的数据。

快照是默认的事务类型，因为它是最易于使用的一种——每次同步运行时，它都会下载数据库查询返回的所有数据，并创建一个快照事务，有效地替换数据集中之前的所有数据。当然，先前事务中的文件在数据集的历史版本中仍然可用，但预览和使用该数据的下游转换现在将默认访问新事务。

当然，快照事务使用起来简单且不易出错，但每次都复制所有数据可能非常低效。一种可能的效率改进方法是改用 APPEND 事务类型。

追加事务

当数据集由追加事务组成时，其默认视图是所有事务的总和。这意味着当您使用 APPEND 事务类型时，您无需重新同步已上传的文件——只有新数据会被同步到 Foundry 中。这减少了 Foundry 的存储使用量，因为每个事务仅包含新增的文件，而不是源系统中所有可用数据的快照。

第 6 步：管理计划任务

优化 Foundry 使用量的另一种方法是通过计划任务。 计划在 Scheduler 工具中配置的 构建 用于定期运行，以保持数据在 Foundry 中持续流动。

计划任务应根据您组织的需求进行设置，但为了优化 Foundry 的使用，务必高效地设置计划任务，避免不必要的运行。例如，如果您将某个数据集的计划任务设置为每天早上 8 点刷新，但实际上并不需要每天早上 8 点获取更新的数据——您的组织就在浪费 Foundry 的使用量。相反，您应该根据实际需要更新数据的频率来设置计划任务，例如每隔一天早上 8 点。进行这样的调整可以将 Foundry 的使用量减少一半。

在思考优化计划任务的 最佳实践 时，需要牢记的两大主题是：1) 消除重复的计划任务，以及 2) 消除不必要的计划任务。

消除重复的计划任务

要识别冗余的调度，首先进入 调度指标 应用程序，并将节点颜色更改为 Schedule Count。如果所选节点关联了多个调度，请选择该节点并查看 管理调度 工具。在那里，您可以查看关联的调度，确定其所有者，以及它们是否可以合并。

最佳实践是确保管道中的每个数据集只关联一个计划构建。 让一个数据集由两个不同的调度构建，可能会导致排队、两个调度都变慢，以及浪费批量计算资源。

另一个减少冗余调度的最佳实践是避免全量构建，改用连接构建。举个例子：一个本体论管道包含原始数据集、清洗后的数据集、数据转换，最终生成本体论。与其设置三个调度——一个运行原始数据集，第二个运行清洗后的数据集，第三个运行转换后的数据集——您只需要一个调度，以原始数据集为触发器，以本体论数据集为目标。

消除不必要的调度

要识别不必要的调度，请进入 Data Lineage 应用程序，并按以下方式为节点着色： Time since last built。这使您可以查看哪些数据更新最频繁，并判断这对您的组织来说是否是最优的频率。

直方图 调度的频率和时间安排 是优化使用量的关键因素。您的组织需要多久更新一次数据？

  • 如果您的调度设置为每天运行，请考虑周末是否需要更新数据。如果不需要，将调度改为仅在周一至周五更新，可以为该管道或数据集节省近 30% 的 Foundry 批量计算使用量。
  • 如果您的调度设置为每天运行三次，您的组织是否每天使用三次刷新后的数据，还是每天夜间刷新一次就足够了？
  • 需要基于时间的触发器，还是基于条件的触发器即可？您是需要将管道安排为每天凌晨 2 点刷新，还是可以只在某个输入数据集刷新时才刷新？基于事件的触发器通常比基于时间的触发器更高效，能节省更多使用量。

此外，最好不要尝试将所有构建安排在同一时间，以确保调试更高效并使用更少的计算资源。在考虑频率和时间安排时，重要的是回归您组织的需求，确保您设置的刷新速率符合组织需要，但不要超出实际需求。

最后，重要的是查看 高级选项 在设置调度时。考虑启用 失败时中止构建 以减少浪费的批量计算。您还可以 将失败作业的允许尝试次数更新 为三次或更少（相比最多 5 次尝试）。还建议将重新构建之间的间隔设置为至少一到三分钟，以便让导致失败的任何小故障有时间自行解决。

第 7 步：优化 Spark

Spark 是一个开源的分布式集群计算框架，用于快速的大规模数据处理和分析。Spark 通过将工作拆分到不同系统并并行处理，而不是等待所有任务线性完成，使计算机能够更轻松、更快速地处理大量数据或分析任务。

首先需要说明的是，作为优化方面的一般最佳实践，我们建议仅在识别到特定瓶颈时才手动调整 Spark 配置，而不要将其作为整个平台上的常规做法。这是因为 Foundry 会逐步为没有手动覆盖设置的转换添加并启用新的优化功能。一个简单的例子是 Spark 3 中引入的动态资源分配。以前手动设置转换的执行器数量非常重要，而如今该数量会在执行时自动调整，以避免浪费。

优化 Spark 应仅由熟悉 Spark 概念并对其在管道中的使用方式有深入理解的用户来进行。

优化 Spark 的第一步是查看并理解 Spark 配置文件。 “Spark 配置文件” 是 Foundry 用来配置分布式计算资源（如驱动程序和执行器）的配置，为其分配适当数量的 CPU 核心和内存。大多数情况下，我们建议使用自动配置文件，而不是尝试手动调整；不过，有时您可能会发现使用了不必要的大型驱动程序。

您可以使用数据血缘上的 Spark 使用情况着色来识别可能正在使用较高级别配置文件的数据集。

以下是一些核心 Spark 概念 和术语，在开始优化之前需要先了解。

  • Driver 核数： 控制分配给 Spark 驱动程序的 CPU 核心数量。
  • 驱动程序内存（JVM，非堆外内存）： 控制分配给 Spark 驱动程序的内存量。
  • 执行器核心： 控制分配给每个 Spark 执行器的 CPU 核心数量，进而控制每个执行器中并发运行的任务数量。
  • 执行器内存： 控制分配给每个 Spark 执行器的内存量，由其运行的所有任务共享。
  • 执行器数量： 控制为运行作业而请求的执行器数量。

除了 Spark 配置文件之外，以下最佳实践可作为在为减少 Foundry 使用量而优化 Spark 时的起点。

  • 通过在代码中尽早减少数据量来帮助 Spark 的查询优化器。
    • 顺序很重要——重新排列操作顺序，使任何数据过滤都在较早的阶段完成。
    • 丢弃不需要的内容——如果您等到最后才丢弃不需要的数据，这将消耗 Spark 的处理能力和时间。
  • 注意并尽量减少执行器之间的数据交换，也称为“混洗（shuffling）”。
  • 注意并尽量减少 Spark 操作（如 count, collect, take）的使用。与惰性执行的转换（如 filter, select）不同，操作会对计算图施加约束，并阻碍潜在的优化。
  • 注意 repartition（混洗并重新组织所有数据）与 coalesce（合并现有分区）之间的区别。
  • 注意并警惕数据倾斜。有许多解决数据倾斜的技术，其中包括使用广播连接（如果左侧数据集足够小）或“连接加盐（join salting）”技术。
  • 注意并最大化作业的并行度。 Spark详细信息 接口提供了每个步骤执行并行度的视图。如果您使用的是 Spark 动态执行器分配（默认启用），不必要的执行器会在可能时自动缩减，从而避免任何浪费。
  • 注意启动 Spark 任务的开销（可在 Foundry 中的 Spark 详情 接口中查看）。大量微小任务会导致开销和不必要的数据交换。根据经验法则，30 秒到 60 秒是一个合理的数值（需要结合该阶段的总时间来衡量）。

如果您在工作流中尝试在多个单输出转换与多输出转换之间做出选择，请查阅我们的指南： 优化多输出转换。
