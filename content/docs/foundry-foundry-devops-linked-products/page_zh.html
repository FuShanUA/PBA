关联产品

您可以将完整的工作流模块化为 Marketplace 商店中的一组关联产品。这样，较小的产品就可以被独立迭代和升级。

使用关联产品可以让您确保：

  • 一个产品的内容与另一个产品的输入之间的自动映射
  • 产品之间语义化版本的依赖关系
  • 安装时减少重复内容，因为多个产品中重叠的内容可以分离到一个上游产品中，供下游使用

例如，如果您的工作流包含数据清洗管道以及由清洗后的数据支撑的对象类型，那么管道和对象类型可以打包为单独的产品。管道产品与本体论产品之间的关联支持同时安装二者，并自动将管道产品中的清洗数据集内容映射到本体论产品所需的输入。

有关安装指南，请参阅 Install a product > Linked products.

关联产品来源

DevOps 从多个不同的来源生成关联产品：

  • 同商店关联产品： DevOps 会基于共享的源实体自动检测并关联同一商店内的产品。参见 打包关联产品.
  • 跨商店关联产品： DevOps 使用配置的商店链接来关联多个商店中的产品，这对于被其他 Marketplace 商店使用的共享上游产品非常有用。参见 跨商店关联产品.
  • 基于安装的关联产品： DevOps 会根据注册上共享相同源实体的现有安装，自动检测并关联产品。参见 基于安装的关联产品.
  • 手动关联的产品： 在打包过程中，用户可以手动在待发布产品与上游产品之间创建关联。请参阅 定义手动关联的产品.

打包关联产品

DevOps 会检查已打包的源实体，以确定产品之间的关联。默认情况下，DevOps 会在同一商店内查找关联产品，但您也可以配置 跨存储链接产品 来关联多个商店中的产品。在以下概念性示例中，有一个输出数据集的数据管道，以及一个由该数据集支撑的对象类型。

管道和对象类型可以打包为单独的产品，DevOps 将确保管道产品的输出数据集满足本体论产品的数据集输入要求。此关联是从源实体派生出来的。

例如，假设您的产品包含一个 Workshop 应用程序，该应用程序依赖于 Airplane 对象类型。DevOps 只会自动关联包含完全相同的 Airplane 对象类型作为内容的产品。

DevOps 会在下游产品打包时创建产品关联。上图中的本体论产品演示了这一点。换言之，DevOps 会查找其内容能够满足正在发布的草稿产品输入需求的产品。默认情况下，只会考虑同一商店中的产品，但 跨存储链接产品 可以扩展此范围以包含来自关联商店的产品。如果上游产品被重新打包以产生新的输出，而这些输出可以被下游产品使用，那么下游产品也必须重新打包以重新生成关联，从而确保工作流保持最新。

在打包产品时，您可以查看哪些其他产品可以为正在打包的草稿提供输入。您可以打开每个关联产品，查看两个产品之间的映射关系。

还可以使用 按关联产品分组 中的 输入 面板，以预览每个上游关联产品提供的输入。

定义手动关联的产品

当上游产品的输出恰好是待发布产品所需的输入资源时，DevOps 会自动创建指向上游产品的关联。如果另一个产品提供的兼容输出引用了不同的资源，您可以手动将这些输出映射到您产品的输入。这可提供相同的 安装体验 与自动关联的产品相同。

覆盖自动生成的关联

为已存在自动生成关联的上游定义手动关联的产品，将覆盖该自动生成的关联。请注意，与自动生成的关联不同，手动关联的产品 不 不会随着产品定义在不同版本间的演变而动态更新其映射。这意味着 DevOps 用户需要负责在产品演变时添加或移除映射中的输出。

要定义手动关联，请导航至 关联产品 您想要满足其输入的草稿的页面。然后选择 添加手动关联.

在对话框中，首先选择您想要满足草稿输入的上游产品。然后将每个草稿输入映射到该产品的上游输出。在下面的示例中，我们的 Supply Chain Resilience 产品是使用一个概念性数据集开发的。当我们部署该用例时，我们希望使用来自 Restock Ingest Pipeline.

破坏性变更

产品的破坏性变更是指会导致依赖该产品内容的工作流无法再正常运行的变更。例如，破坏性变更可能是删除内容或更改数据集列的类型。这意味着任何依赖的工作流都需要进行调整以适应这些新变更。

当存在破坏性变更时， 建议递增主版本号 （例如 2.0.0 to 3.0.0）以告知安装者产品内容中存在向后不兼容的变更。为确保下游产品能够继续将已发布的产品用作关联产品，打包者可能需要通过更新下游产品来处理这些破坏性变更。例如，可能需要进行更新以确保修改后的数据集列类型被正确使用，或者移除不再提供的输入。

递增主版本号会使产品的已发布版本与任何现有的下游关联产品不兼容。要恢复关联产品兼容性， 所有下游关联产品 都必须重新打包。

如果存在破坏性变更时选择了递增次版本号，安装者将能够选择该关联产品，但在安装时很可能会遇到错误。

最安全的做法是重新打包最近发布产品的所有下游产品，以便重新生成所有关联产品的映射。

拆分产品

通常，大型产品包含工作流的不同阶段（例如，数据清洗和应用程序）。这样的产品可以拆分为较小的产品，以便对每个部分进行更快速的迭代和发布。

通过将大型产品的部分内容分离到另一个产品中，您可以使用两者之间的自动映射将这两个产品一起安装。但是，这可能会导致现有安装中出现重复资源。

安装新创建的产品将创建新资源，而不是重用原始较大产品的已安装资源。

产品关联的最佳实践

以下是关联产品时需要考虑的一些技巧，以确保您的产品保持可维护性：

  • 从上游到下游依次打包产品。这可确保生成的产品关联是最新的。
  • 使用主版本号递增来指示产品的破坏性变更。
    • 重新打包下游产品使用者以重新生成产品关联。

跨商店关联产品

默认情况下，关联产品仅在同一个 store 内的产品之间生成。但是，您可以配置 store 关联，以支持跨多个 store 的关联产品。当您有共享的上游产品（例如通用数据管道或本体论定义）被其他 store 中的产品使用时，这将非常有用。

store 关联的工作原理

store 关联是 单向的 连接，允许您 store 中的下游产品关联到另一个 store 中的上游产品。当您关联到另一个 store 时，DevOps 在打包您 store 中的产品时，会将该 store 中的产品视为潜在的上游依赖项。

配置 store 关联

要配置 store 关联，请导航到应从另一个 store 接收关联产品的 store 的 Store 设置 。这需要对目标 store 执行 marketplace:link-to-local-marketplace 操作，该操作默认授予 store 查看者。

基于安装的关联产品

默认情况下，当一个产品的输出源实体直接引用与另一个产品的输入相同的资源时，会生成关联产品。基于安装的关联产品扩展了此行为，它会检测 enrollment 上已存在的上游安装的输出资源引用了下游产品的相同输入资源的情况。

当构建者基于从上游产品安装的资源（而非直接基于原始源实体）创建产品时，这非常有用。在这些情况下，下游产品的输入引用的是已安装的资源，而不是上游产品的打包内容。DevOps 会检测到已安装的资源源自上游产品，并自动生成关联的产品关系。
