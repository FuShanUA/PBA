检查点捆绑包

在向导出管道添加新的传输目标时，您可能希望新的传输目标能够快速追上导出管道的最新捆绑包。当导出管道拥有很长的捆绑包历史记录，逐一传输到新传输目标会耗费过长时间时，这一点尤其重要。

检查点捆绑包允许新的传输目标与导出管道的最新状态保持同步，而无需从导出管道历史记录的开头开始传输所有捆绑包。

术语

  • 快照捆绑包：没有依赖项的捆绑包。导入时，它可以将目标 Hub 更新为创建捆绑包时导出管道数据选择规则的最新状态。每个导出管道的第一个捆绑包始终是快照捆绑包。
  • 增量软件包：依赖于先前构建的软件包的软件包。它包含自其所依赖的上一个软件包以来的变更。
  • 检查点软件包：用于快速接入新传输目标的快照软件包。

下面是一个更详细地说明这些概念的示例。假设有一个导出管道，其数据选择规则选择 RELEASE 发布渠道上 example-product 的产品发布版本。example-product 有四个产品发布版本 1.0.0、1.1.0 和 1.2.0、1.3.0，分别在第 1、2、3 和 5 天发布。

如果导出管道使用增量策略：

  1. 在第 1 天，创建软件包 1。第一个软件包始终是快照软件包，因此会导出满足数据选择规则的最新资源。在本例中，RELEASE 发布渠道上 example-product 的最新发布版本是 1.0.0，该版本包含在此软件包中。
  2. 第 3 天，创建了捆绑包 2。管道使用增量策略，并创建一个增量捆绑包。增量捆绑包依赖于上一个导出捆绑包。它将仅包含自捆绑包 1 创建以来的变更。example-product 的 RELEASE 发布通道上有两个新的发布版本，即 1.1.0 和 1.2.0，因此这些发布版本被包含在该捆绑包中。请注意，1.0.0 已包含在捆绑包 1 中，因此不会包含在增量捆绑包中。
  3. 第 4 天，创建了捆绑包 3，即另一个增量捆绑包。由于 example-product 在 RELEASE 发布通道上没有新的发布版本，因此该增量捆绑包不包含任何产品发布版本。
  4. 假设导出管道配置为在成功创建 2 个增量捆绑包后创建检查点捆绑包。捆绑包 3 的成功构建将触发捆绑包 4（一个检查点捆绑包）的创建。检查点捆绑包是一种快照捆绑包，会导出满足数据选择规则的最新资源。在本例中，1.2.0 是 example-product 在 RELEASE 上的最新发布版本，因此被包含在该捆绑包中。
  5. 在第 5 天，创建了 Bundle 5。它是一个增量 Bundle，依赖于上一个增量 Bundle 3。自 Bundle 3 以来，RELEASE 发布渠道上出现了 example-product 的新发布版本 1.3.0，因此该发布版本包含在 Bundle 中。请注意，检查点 Bundle 不会影响未来增量 Bundle 的内容。

如果导出管道使用快照策略：

  1. 在第 1 天，创建了 Bundle 1。它是一个包含满足数据选择规则的最新资源的快照 Bundle。Bundle 中包含了 example-product:1.0.0。
  2. 在第 3 天，创建了 Bundle 2。由于导出管道使用快照策略，新 Bundle 将是一个快照 Bundle。鉴于 1.2.0 是 example-product 在 RELEASE 发布渠道上的最新发布版本，新的快照 Bundle 将包含 example-product:1.2.0。

配置检查点 Bundle

您可以在管道设置的构建设置部分配置检查点 Bundle。检查点 Bundle设置允许您指定创建检查点 Bundle 的频率。

默认情况下，每成功创建 10 个增量 Bundle 后，就会创建一个检查点 Bundle。当向导出管道添加新传输目标时，新传输目标将从最近的快照 Bundle（可以是检查点 Bundle）开始。

您可以为检查点 Bundle 的创建频率指定自定义值。该值表示在创建检查点 Bundle 之前应创建的增量 Bundle 的数量。值越大，检查点 Bundle 的创建频率就越低，新传输目标可能需要更长时间才能完成追赶。对于用于单个传输目标的导出管道（例如，仅将环境设置导出到单个目标 Hub 的管道），可以将该值设置为较高的值（例如 100），以降低检查点 Bundle 的创建频率。当源 Hub 的存储空间有限时，也建议采用此设置，因为检查点 Bundle 体积较大。

导出与导入

您可以在导出管道的导出捆绑包收件箱中查看检查点捆绑包。这些捆绑包将带有 CHECKPOINT 标记。

检查点捆绑包在捆绑包收件箱中的条目将显示为灰色，因为它们不会被传输到导出管道的任何现有传输目标，也绝不会在任何时候影响导出管道的状态。
