技术入门：Python 转换中的 Iceberg 变更日志

本指南介绍如何在 Python 转换 中配合 Iceberg 表使用变更日志。本指南涵盖了两种主要的变更日志模式、其运作机制，以及避免常见陷阱的最佳实践。

什么是变更日志？

变更日志是表中在两个时间点之间发生的变更（插入、更新和删除）的视图（由 Iceberg 快照 ↗表示）。变更日志可实现高效的增量处理，让您只需处理自上次运行以来发生变化的数据。

在 Foundry 中生成变更日志主要有两种方式：

  • 标识符变更日志 （推荐）：提供一个或多个标识符列；建议用于大多数用例。
  • 净变更日志：不提供标识符列；适用于输入数据没有一组可靠主键的情况。

标识符变更日志（具有标识符列）

当输入数据中有一个或多个能够唯一标识每一行并共同构成主键的列时，请使用“标识符变更日志”模式。该模式比“净变更日志”模式性能更高，并提供更丰富的语义，包括更新前（update-before）和更新后（update-after）记录。

标识符变更日志语法

要生成标识符变更日志，请运行 source.changelog 并提供一个主键数组：

Copied!
1
changelog_df = source.changelog(["id"])

标识符变更日志实现细节

Foundry 的“标识符变更日志”模式是使用 compute_updates 选项实现的，该选项位于 Iceberg 的 create_changelog_view ↗ 过程中。

使用 compute_updates：

  • 行的插入和删除分别表示为 INSERT 和 DELETE 变更。
  • 行更新基于标识符列，并表示为一对 UPDATE_BEFORE 和 UPDATE_AFTER 行，也称为 “更新前/后映像” ↗。

Foundry 的 API 在 Iceberg 的 create_changelog_view 之上实现了一个额外步骤，以获取事务范围内的最新更新。例如，如果某一行的值在某个快照中从 1 更新为 2 ，然后在后续快照中又从 2 更新为 3 ，那么生成的标识符变更日志将只显示一条 UPDATE_BEFORE ，其值为 2 ，以及一条 UPDATE_AFTER ，其值为 3。

Iceberg 表规范在元数据中支持 标识符字段 ↗ ，但并不强制唯一性。因此，转换的变更日志目前不依赖元数据中的标识符字段。

标识符变更日志架构

标识符变更日志的架构：

列名类型描述
所有数据列多种源表中的所有列
_change_typestring以下值之一： INSERT、 DELETE、 UPDATE_BEFORE、 UPDATE_AFTER
_change_ordinalint用于对变更进行排序的单调递增数字

标识符变更日志的变更类型

标识符变更日志的变更类型：

变更类型描述
UPDATE_BEFORE该标识符对应行的旧版本。
UPDATE_AFTER该标识符对应行的新版本。
INSERT此标识符的新行。
DELETE此标识符的行已被移除。

以下是一个标识符变更日志示例：

净变更日志（无标识符列）

当输入数据中没有一组能够唯一标识条目的标识符列时，请使用“净变更日志”模式。这种方法比“标识符变更日志”模式提供了更大的灵活性，但以牺牲性能为代价。

净变更日志语法

要生成净变更日志：

Copied!
1
changelog_df = source.changelog()

当无法信任主键或源数据中存在重复行时，请使用“净变更日志”模式。

净变更日志实现细节

Foundry 的“净变更日志”模式是使用 net_changes 选项实现的，该选项位于 Iceberg 的 create_changelog_view ↗ 过程中。

在 Iceberg 中，更新一行是通过删除一行和插入一行来实现的。行更新并没有固有的概念，因为删除与插入之间没有任何关联表明二者在语义上指向的是同一行。

“净变更变更日志”是最简单的一种变更日志，它将行更新表示为一对行，其中一行具有 _change_type 值 DELETE ，而另一行具有 _change_type 值 INSERT。（删除和插入分别由带有 DELETE 和 INSERT 的单行表示。）

“净变更”中的“净”指的是在一系列快照中合并行更新（插入、删除和更新）。例如，如果某一行的值从 1 更新为 2 （在一个快照中），然后从 2 更新为 3 （在后续快照中），那么“净变更变更日志”将显示一个 DELETE ，值为 1 和一个 INSERT ，值为 3。该 2 更新将被跳过。

净变更变更日志架构

净变更变更日志的架构：

列名类型描述
所有数据列多种源表中的所有列
_change_typestringINSERT 或 DELETE
_change_ordinalint用于对变更进行排序的单调递增数字

净变更变更日志的变更类型

净变更变更日志的变更类型：

变更类型描述
INSERT行插入
DELETE行删除

唯一性要求与常见陷阱

在处理变更日志时，您必须确保标识符列在两个阶段具有唯一性：源表和目标表。

源表中的唯一性（source.changelog([identifier_cols])）

当您调用以下内容时：

Copied!
1
changelog_df = source.changelog(["id"])

该 API 要求标识符列（此处为 id）能够唯一地标识您的 源表中的每一行。

如果源表中存在同一标识符的重复行，则创建变更日志将失败：

ValueError: Duplicate rows found for identifier columns ['id'] in changelog view.

如果您无法保证源数据中的唯一性，请改用净变更变更日志：

Copied!
1
changelog_df = source.changelog()  # No identifier columns

目标表中的唯一性（output.apply_changelog(changelog_df, keys)）

当您调用：

Copied!
1
output.apply_changelog(changelog_df, ["id"])

时， keys 参数会指定 目标表的标识符列。这些列必须与变更日志数据帧中的标识符列相匹配。目标表也必须以这些列为唯一键。

如果目标表中有多行与同一个键匹配，或者变更日志数据帧中存在该键的重复项， apply_changelog 将失败：

Exception: apply_changelog failed: duplicate keys detected in changelog dataframe for identifier columns ['id']

或

Exception: apply_changelog failed: multiple rows in destination table match key ['id']

请务必确保变更日志数据帧和目标表均已按标识符列完成去重，然后再调用 apply_changelog。

from pyspark.sql import functions as F
from pyspark.sql.window import Window

# Group rows by identifiers and order by change ordinal such that the latest
# row comes first (`_row_number == 1`). This allows us to filter a net changes
# changelog to only keep the latest row per identifier.
window = Window.partitionBy("id").orderBy(F.col("_change_ordinal").desc())
deduped_df = (
        changelog_df
        .withColumn("_row_number", F.row_number().over(window))
        .filter("_row_number = 1")
        .drop("_row_number")
)

output.apply_changelog(deduped_df, ["id"])

如果您跳过此步骤且存在重复数据， apply_changelog 将失败，如上所示。

总结与最佳实践

  • 优先使用 标识符变更日志 （如果您的标识符列在源中是唯一的）。
  • 使用 净变更变更日志 （如果您的数据中存在重复项，或者您无法信任源中的主键）。
  • 请务必先对变更日志数据帧进行去重，并确保目标表具有唯一键，然后再调用 apply_changelog ，以避免错误。
  • 请保持源表使用 copy-on-write 模式。变更日志扫描不支持 merge-on-read产生的删除文件。
  • 了解每种变更日志模式的语义和性能权衡。
