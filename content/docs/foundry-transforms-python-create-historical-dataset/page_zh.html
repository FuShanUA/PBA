从快照创建历史数据集

如果可能，历史数据集的最佳实践是在摄取时 以以下方式摄取 APPEND 事务。请参阅 警告 以了解其他详细信息。

工作流概览

有时，您可能会遇到这样的原始数据集：每次新的 SNAPSHOT 导入都会在每天、每周或每小时用数据集的当前数据替换先前的视图。然而，保留先前的数据以确定与先前视图相比发生了哪些变化通常很有用。如上所述，最佳实践是在摄取过程中通过使用 APPEND 事务并添加一个包含导入日期的列来处理此问题。但是，如果无法做到这一点，您可以使用 incremental 装饰器在 Python 转换中将这些定期快照追加到该数据集的 历史 版本中。请参阅下面的警告，了解此方法的注意事项和潜在的脆弱性。

@incremental(snapshot_inputs=['input_data'])
@transform.using(

    # Import and use datetime.now() instead if the input can change more than once per day.
    input_df = input_df.with_columns(pl.lit(date.today()).alias('date'))

    history.write_table(input_df)

from transforms.api import transform, incremental, Input, Output
from pyspark.sql.functions import current_date

@incremental(snapshot_inputs=['input_data'])
@transform.spark.using(
    input_data=Input("/path/to/snapshot/input"),
    history=Output("/path/to/historical/dataset"),
)
def my_compute_function(input_data, history):
    input_df = input_data.dataframe()

    # Import and use current_timestamp() instead if the input can change more than once per day.
    input_df = input_df.withColumn('date', current_date())

    history.write_dataframe(input_df)

为什么这样做有效

incremental 装饰器会对输入和输出的读/写模式应用额外的逻辑。在上面的示例中，我们使用 默认 作为输入和输出的读/写模式。

读取模式

当使用 SNAPSHOT 输入时，默认的读取模式是 current，这意味着它会读取整个输入 DataFrame，而不仅仅是自上次事务以来新增的行。如果输入数据集是通过 APPEND 事务创建的，我们可以使用 incremental 装饰器来使用 added 读取模式，从而只访问自上次构建以来新增的行。转换会从 current 输出获取 schema 信息，因此无需像读取 previous 版本的 DataFrame 那样传递 schema 信息，例如， dataframe('previous', schema=input.schema).

写入模式

当我们说转换以增量方式运行时，意味着输出的默认写入模式被设置为 modify。此模式会使用构建期间写入的数据修改现有输出。例如，调用 write_dataframe() 模式时调用 modify 模式时，会将写入的 DataFrame 追加到现有输出中。这正是本例中发生的情况。

验证数据集是否累积

累积发生在连续的构建之间，而不是在单个构建内部。第一次构建使用当前输入快照建立历史。当新的 SNAPSHOT 事务到达输入后，下一次构建会将该当前快照追加到现有历史中。

要观察历史的累积过程，请按照以下步骤操作：

  1. 运行一次转换。从未构建过的输出会以非增量方式运行，并使用 replace 写入模式，因此在第一次构建后看到一个快照是正常的。
  2. 在输入数据集上落一个新的 SNAPSHOT 事务，例如通过重新导入或重新同步源数据，然后再次运行转换。没有新输入事务的构建不会添加新的历史状态。
  3. 检查输出并确认它包含来自两个快照的行，这些行可通过示例中添加的日期或时间戳列来识别。如果快照每天可能落地多次，请使用时间戳而不是日期。
  4. 要确认构建是否以增量方式运行，请检查其作业的 增量报告 ：
    • 从以下位置查看构建报告 数据集预览, 调度指标，或 构建应用程序.
    • 在甘特图下方的列表中选择该作业，选择 Spark详细信息，然后打开 快照/增量 标签页。报告会显示作业为每个输入读取的事务范围。
预览以非增量方式运行

Code Repositories 预览功能始终以非增量方式运行转换，即使设置了 require_incremental=True 也是如此。因此，您无法在 Code Repositories 预览中观察累积，因为每次运行都会用当前快照替换输出。请使用 VS Code 预览（它会以增量方式运行转换），或者改为检查计划构建或手动构建的输出。

如果在使用不同的输入事务进行两次构建后，输出仍然只包含最新的快照，则第二次构建很可能以非增量方式运行并替换了输出。常见原因包括以下几种：

  • 已更改的 semantic_version
  • 被完全重写但未声明为 快照输入
  • 上一次事务由不同的转换生成的输出

要确认原因，请查看 增量计算的要求 并按上文所述检查构建作业的增量报告。该作业的 驱动程序日志 也会记录警告 transforms.api._incremental: Not running incrementally.

警告

由于此转换使用 SNAPSHOT 数据集作为输入，因此无法恢复构建可能因构建失败或其他原因而遗漏的快照。如果这是一个问题，请不要使用此方法。相反，请联系输入数据集的所有者，看看是否可以将其转换为 APPEND 数据集，以便您可以访问该数据集的上一个事务。这正是增量计算的设计工作方式。

此方法在以下情况下会失败：

  • 向输入数据集添加了列
  • 现有表的列数与输入数据架构不匹配
  • 输入数据集上的列更改了数据类型，例如从 integer to decimal
  • 您更改了输入数据集，即使该数据集具有相同的架构。在这种情况下，它将使用输入完全替换输出，而不是追加。

资源消耗增加

使用此模式可能会导致历史数据集中小文件的累积。 文件累积 并不是理想的结果，并且会导致构建时间增加以及 使用此历史数据集的下游转换或分析中的资源消耗增加 。批处理和交互式计算时间可能会增加，因为读取每个文件都有相关的开销。磁盘使用量可能会增加，因为压缩是按文件进行的，而不是跨数据集内的多个文件进行的。可以构建逻辑来定期对数据进行重新快照，从而防止发生此行为。

通过检查输出文件的数量，我们可以确定最佳的 增量写入模式。此模式允许我们将上一个事务的输出作为 DataFrame 读入，将其与传入的数据合并（union），并将数据文件合并（coalesce）在一起。这会将许多小文件变成一个较大的文件。

检查输出数据集文件系统中的文件数量，并使用 if 语句来设置 write_mode，如下例所示：

from transforms.api import transform, Input, Output, incremental

FILE_COUNT_LIMIT = 100

# Be sure to insert your desired output schema here
schema = {
    'Value': pl.Float64,
    'Time': pl.Datetime,
    'DataGroup': pl.Utf8
}

def compute_logic(df):
    """
    This is your transforms logic
    """
    return df.filter(pl.lit(True))

@incremental(semantic_version=1)
@transform.using(
    output=Output("/Org/Project/Folder1/Output_dataset_incremental"),
    input_df=Input("/Org/Project/Folder1/Input_dataset_incremental"),
)
def compute(input_df, output):
    df = input_df.polars('added')
    df = compute_logic(df)

    # Fetches a list of the files that are in the dataset
    files = list(output.filesystem(mode='previous').ls())

    if (len(files) > FILE_COUNT_LIMIT):
        # Incremental merge and replace
        previous_df = output.polars('previous', schema)
        df = pl.concat([df, previous_df])
        mode = 'replace'
    else:
        # Standard incremental mode
        mode = 'modify'

    output.set_mode(mode)
    output.write_table(df)

schema = {
    'Value': 'float64',
    'Time': 'datetime64[ns]',
    'DataGroup': 'object'

def compute_logic(df):
    """
    This is your transforms logic
    """
    return df[df.index >= 0]  # Equivalent to filter(True)

@incremental()

    else:
        # Standard incremental mode
        mode = 'modify'

    output.set_mode(mode)
    output.write_table(df)

from pyspark.sql import types as T
from transforms.api import transform, Input, Output, incremental

FILE_COUNT_LIMIT = 100

# Be sure to insert your desired output schema here
schema = T.StructType([
    T.StructField('Value', T.DoubleType()),
    T.StructField('Time', T.TimestampType()),
    T.StructField('DataGroup', T.StringType())
])


def compute_logic(df):
    """
    This is your transforms logic
    """
    return df.filter(True)

@incremental()
@transform.spark.using(
    output=Output("/Org/Project/Folder1/Output_dataset_incremental"),
    input_df=Input("/Org/Project/Folder1/Input_dataset_incremental"),
)
def compute(input_df, output):
    df = input_df.dataframe('added')
    df = compute_logic(df)

    # Fetches a list of the files that are in the dataset
    files = list(output.filesystem(mode='previous').ls())

    if (len(files) > FILE_COUNT_LIMIT):
        # Incremental merge and replace
        previous_df = output.dataframe('previous', schema)
        df = df.unionByName(previous_df)
        mode = 'replace'
    else:
        # Standard incremental mode
        mode = 'modify'

    output.set_mode(mode)
    output.write_dataframe(df.coalesce(1))
