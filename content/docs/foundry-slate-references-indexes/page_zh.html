优化索引和模式设计

本页文档重点介绍如何针对 Postgres 和 ElasticSearch 调优索引以获得最佳性能。我们通常建议在 Ontology 功能之上构建 Slate 应用，使用诸如 对象集 和 操作 等功能来读取和写入数据。

高性能且易于维护的应用依赖于合理拆分的数据集和适当的索引。

Postgres 模式设计的大多数方面与 Slate 完全无关。这些概念在其他地方已有详细记录，通用的数据库设计最佳实践不在本文讨论范围之内。如果你还不熟悉各种模式模式或关于选择哪些列建立索引的指导，通过 Google 搜索可以很快带你深入这个话题。

相反，本节重点介绍与 Slate 和 Foundry 特别相关的最佳实践。

尽可能将工作向上游推进

在应用开发过程的每个阶段，都要问一个问题：“在哪里做这项工作最合适？”并且始终倾向于将工作尽可能向上游推进。例如，如果你发现自己在编写复杂的 JavaScript 函数来聚合数据或提取指标，请问：“我能否改为在查询中完成这项工作？”

如果你在每次页面加载时都在查询中执行相同的工作，例如使用 SUM() 派生年度总计，或使用 DISTINCT()创建列表，请问问自己：“我能否在派生数据集中完成这项工作？”

在 Foundry 中，分布式存储和计算相比于在查询中或用户浏览器中完成的工作更“便宜”，因此应尽可能多地进行预计算。

Postgate (Postgres)

Postgate 封装了 Postgres 或 RDS，以便通过 PostgreSQL 查询对 Foundry 数据集进行简单的只读访问。请记住，应用查询的局限性通常由关系型数据库（而非平台其余部分的 Spark/HDFS）的特性决定，尤其是 Postgres 的特性。

在开发检索数据的查询时，使用 EXPLAIN ANALYZE 对查询进行性能分析并找出瓶颈。你可以在这篇 Thoughtbot 博客文章 ↗中了解更多关于 Postgres 如何解析你的查询以及如何解读 EXPLAIN ANALYZE 请求结果的信息。你还可以阅读我们更详细的说明： 为 Slate 优化 Postgres 查询.

你可以构建模块化查询以避免代码重复，并使用 Partials更好地封装共享逻辑。我们建议使用 partials 和函数，在保持查询简洁与足够详细易读之间进行权衡。

Phonograph (ElasticSearch)

Phonograph 提供一个读写数据存储，使用 ElasticSearch 风格的语法进行查询和聚合，同时支持在 Foundry 数据集之上进行 CRUD 操作。有关 Phonograph 实践的更多信息，请参阅 从 Slate 向 Foundry 回写数据.
