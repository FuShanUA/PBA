数据保护与治理

Foundry 使用户能够在企业范围内集成、转换、分析和运营数据，同时安全地协作和共享数据产品。每项数据战略和计划的重要组成部分是确保对数据的使用合法、正当、合规且恰当。数据保护和数据治理是使用 Foundry 的核心概念。

  • 数据保护 是指一系列技术和组织手段，用于确保个人数据的处理在任何时候都仅限于为实现正当处理结果所必需且相称的范围。
  • 数据治理 是指对整个处理生命周期（从摄取到访问再到删除）中的企业数据进行管理。

虽然世界各地的隐私法规各不相同，但大多数法规都要求采用系统化、程序化的手段来了解组织拥有哪些数据，以便恰当地使用和处理这些数据。在 Foundry 中，数据保护和数据治理相辅相成。本文档概述了可供客户使用的最佳实践和工具，以帮助在 Palantir Foundry 中处理数据（包括敏感数据或个人数据）时，促进充分且恰当的数据保护和数据治理。

本文档面向数据管理员、数据治理负责人、数据所有者以及在平台上处理敏感数据并希望了解 Foundry 保护这些数据的能力的用户。

Palantir 认为隐私和公民自由方面的考量应贯穿数据和 AI 工作流的整个生命周期。查看 实践中的隐私与公民自由 ，了解本指南背后的原则以及相关平台功能的概览。

数据保护原则

平台管理员和用户应始终负责任地处理企业数据，尤其是个人数据或敏感数据。公平信息实践原则（FIPPs）提供了一套实用的指导方针，作为处理个人数据的基础原则，以落实隐私保护。

公平信息实践原则（FIPPs）

下面，我们基于 经济合作与发展组织（OECD）关于隐私保护和个人数据跨境流动的指导方针 ↗:

  • 收集限制原则。 个人数据的收集应当受到限制，任何此类数据应通过合法且公平的方式获取，并在适当情况下征得数据主体的知情或同意。
  • 数据质量原则。 个人数据应与其使用目的相关，并在实现这些目的所必需的范围内保持准确、完整和最新。
  • 目的明确原则。 收集个人数据的目的最迟应在数据收集时予以明确，其后续使用应限于实现这些目的，或限于与这些目的不相抵触的其他目的，且在每次目的变更时均应予以明确。
  • 使用限制原则。个人数据不得为特定目的之外的目的被披露、提供或使用，除非 a) 经数据主体同意，或 b) 依据法律授权。
  • 安全保障原则。 个人数据应受到合理的安全保障措施的保护，以防范诸如数据丢失或未经授权的访问、破坏、使用、修改或披露等风险。
  • 公开性原则。 对于有关个人数据的发展、实践和政策，应实行公开的总体政策。应提供便捷的方式来确认个人数据的存在和性质及其使用的主要目的，以及数据控制者的身份和通常居住地。
  • 个人参与原则。 个人应享有以下权利：
    • 向数据控制者或以其他方式确认数据控制者是否持有与其相关的数据；
    • 在合理的时间内、以合理的方式、以易于理解的形式，以不超过合理标准的费用（如有）获取与其相关的数据；
    • 如果根据 (a) 和 (b) 项提出的请求被拒绝，有权获知理由并能够对该拒绝提出质疑；以及
    • 对其相关数据提出质疑，如果质疑成功，则将该数据删除、更正、补全或修改；
  • 问责原则。 数据控制者应对落实上述原则的措施的遵守情况负责。

这些 FIPPs 的共同主题之一是需要 数据最小化，即数据只能为明确且经授权的目的进行收集（“收集限制原则”）和使用（“使用限制原则”）（“目的明确原则”）。此外，在处理数据时必须始终考虑安全保障（“安全保障原则”）。

FIPPs 示例

例如，考虑以下场景。

一家金融机构（FI）在考虑如何处理提供银行服务所需的新客户计划时，可以应用 FIPPs。

在设立该计划时，该金融机构只会向注册该计划的客户收集运行该计划所必需的个人信息（“收集限制原则”），并预先提供所有目的（“目的明确原则”），同时公开披露数据处理的细节和方法（“公开原则”）。

在为用户准备数据时，数据所有者和准备者确保数据得到定期维护和审查，以便任何与数据相关的决策都使用准确的最新信息（“数据质量原则”），并确保所有数据都得到安全存储（“安全保障原则”）。定期审计审查等系统级流程确保数据仅用于预先指定的目的（“问责原则”）。数据准备就绪后，只有为经批准的目的处理数据的授权用户才能访问该数据（“使用限制”）。

同时，在消费者方面，该金融机构允许消费者定期请求访问、删除或更正信息（“个人参与原则”）。此外，除 FIPPs 之外，出于合规原因，可能还需要遵守金融行业关于数据保留时长的其他要求。

仅在这个示例中，就涉及处理数据的许多复杂性和考量因素。本文档中概述的最佳实践将概述 Palantir Foundry 中一系列广泛的技术工具，这些工具有助于在处理敏感数据（包括个人数据）时将这些基础原则付诸实践。

超越 FIPPs

FIPPs 只是评估个人或敏感信息隐私的起点。公平、非歧视和伦理原则也可能与个人数据处理相关。不同的法律、监管和行政要求可能因司法管辖区、行业和一般规范而异。请咨询法律顾问或隐私专家以获取相关要求的建议。

敏感数据分类

识别敏感数据是关键的第一步。背景很重要，因为某些数据是否被视为敏感取决于相关的隐私法规和规范。

敏感数据 在此被定义为任何被广泛分类的数据和/或需要额外安全保护的数据。一些法律正式将特定数据元素指定为敏感数据（例如欧盟的《通用数据保护条例》），而另一些则由数据所有者确定，或不论法律地位如何均被普遍认可（例如社会安全号码）。数据是否被归类为敏感数据通常在很大程度上取决于数据的类型或分类（例如个人身份信息）、工作流的类型（例如仅限于特定用途），或任何可能触发受限访问控制的内容（例如敏感的企业信息）。

敏感数据的一个常见例子是 个人身份信息（PII），其中包括直接标识符以及可用于重新识别或单独识别个人的其他相关信息。

敏感信息的示例包括：

  • 联系信息： 姓名、电子邮件、电话号码
  • 证件号码： 社会安全号码（SSN）、执照号码、病历号、税号（TIN）
  • 生物特征信息： 面部特征、指纹、个人图像、DNA
  • 日期： 出生日期、入院或出院日期
  • 位置信息： 家庭住址、办公地址、可穿戴设备位置数据、手机位置
  • 健康信息： 过去、现在或未来的身体或心理健康或状况、药物、治疗和诊断
  • 财务信息： 收入或资产、医疗账单或付款、账号
  • 其他敏感信息： 通话记录、IP 地址

根据司法管辖区或领域的不同，敏感数据的分类方式可能有所不同。以下是一些相关数据保护和隐私法规定义的示例：

欧盟《通用数据保护条例》（GDPR）

欧盟《通用数据保护条例》（GDPR）是一项明确界定个人数据的法规。概括而言，GDPR 将个人数据定义为任何可以识别个人身份的数据，并将种族和政治观点等特征归类为敏感信息。正式定义如下：

Article 4(1) ↗ GDPR 将个人数据归类为：

与已识别或可识别的自然人（“数据主体”）相关的任何信息；可识别的自然人是指可以直接或间接识别的人，特别是通过姓名、身份证号码、位置数据、在线标识符等标识符，或通过该自然人的身体、生理、遗传、心理、经济、文化或社会身份所特有的一个或多个因素来识别的人。

此外， Art. 9(1) ↗ GDPR 强调以下类型的个人数据属于需要额外层级保护和照料的特殊类别个人数据：

揭示种族或民族出身、政治观点、宗教或哲学信仰或工会成员身份的个人数据，以及基因数据的处理、用于唯一识别自然人的生物特征数据、与健康相关的数据或与自然人性生活相关的数据。

美国《健康保险流通与责任法案》（HIPAA）

美国《健康保险流通与责任法案》（HIPAA）在 HHS 的 详细指南 ↗ 中有所阐述，是美国处理医疗保健数据的常用框架。HIPAA 适用于医疗保健提供者和保险公司持有的数据，但不一定适用于同一数据的其他处理者。如需确认，请咨询法律顾问或隐私专家以获取相关要求的建议。

根据 HIPAA，

受保护的健康信息是指与以下内容相关的信息，包括人口统计信息：

  • 个人过去、现在或未来的身体或心理健康或状况，
  • 向个人提供的医疗保健服务，或
  • 过去、现在或未来为个人提供医疗保健服务的付款，且该信息可识别个人身份，或有合理依据相信可用于识别个人身份。受保护健康信息包括许多常见标识符（例如姓名、地址、出生日期、社会安全号码），当这些标识符可与上述健康信息相关联时即构成受保护健康信息。

例如，由 HIPAA 所涵盖实体处理的医疗记录、实验室报告或医院账单属于 PHI，因为每份文件都包含患者姓名和/或与健康数据内容相关联的其他身份识别信息。

其他

其他可能适用于您的组织或项目的相关国际数据保护框架包括：

  • 巴西 - 《通用数据保护法》(LGPD)
  • 日本 - 《个人信息保护法》(AAPI)
  • 加拿大 - 《个人信息保护和电子文档法》(PIPEDA)
  • 美国加利福尼亚州 - 《加州消费者隐私法》(CCPA) / 《加州隐私权法》(CPRA)
  • 美国弗吉尼亚州 - 《弗吉尼亚州消费者数据保护法》(CDPA)
  • 美国科罗拉多州 - 《科罗拉多州隐私法》(CPA)

上述列表并不全面，明确定义会因当地司法管辖区、地区或行业而异。请咨询您的法律、合规和/或数据保护团队，以了解相关的数据分类以及基于适用规则和法规的具体处理指南。

数据治理监督

在开始使用 Palantir Foundry 中的数据之前，请确保您已确定组织内数据保护和数据治理相关的主题专家 (SME) 和责任机构。处理企业数据（包括个人数据和其他敏感数据）涉及一系列考量因素：从法律和监管要求，到落实平台/数据所有者制定的组织规则。

在开始在 Palantir Foundry 中处理数据之前，以下是一系列需要遵循或与您的组织核实的常见流程：

确定治理委员会/主题专家 (SME)，或指定数据治理负责人

  • 治理委员会不一定是正式的组织，在不同组织中可能采取不同的形式。重要的是了解组织中的哪一方或哪些方是负责思考、裁决和协助解决数据治理和数据保护问题的责任方，以应对平台使用的发展、用例的扩展等情况。
  • 确保数据得到妥善处理的责任通常由相应的数据所有者承担。这包括确定如何将下文概述的数据处理基本原则应用于具体工作流程，还包括确保满足全系统的数据治理要求，例如确保通过以下方式对平台进行可问责的使用： 审计日志 以及配置相关的 保留策略.
  • 这些数据治理要求通常由组织的数据保护办公室 (DPO)、信息安全、合规或法务部门定义。
最佳实践

请与相应的数据所有者或数据控制者协商，以确定了解并能批准如何根据适用法规、使用协议和其他要求处理数据的相关方。

完成所需的隐私审查或隐私影响评估

  • 根据行业、地区/司法管辖区、应用或组织特定要求，在开始处理之前可能需要额外的文档。这可能以组织特定或监管要求的形式出现，需要准备诸如隐私阈值评估、隐私/数据保护影响评估、合规性评估、隐私声明、处理活动记录、系统记录通知 (SORN) 等文档。
  • 请与内部相关团队核实启动新项目的标准操作流程，尤其是当这些项目涉及处理敏感数据时。

与您的法律和合规团队合作

最佳实践和提示

确保数据最小化

在敏感数据对某些用户组或项目并非必需的情况下，删除包含该数据的列或行，以限制对下游敏感数据的访问。请确保对敏感数据的任何访问都仅限于数据所有者和/或相关数据保护和数据治理团队明确批准的用途。

为了提供额外的安全保障，我们建议使用 密码 服务通过加密操作（加密、解密或哈希）对数据进行混淆。Cipher 为用户提供了在 Foundry 存储和网络层面的先进加密基础上，在运营工作流中配置隐私和治理保护的工具。

确保数据使用的可问责性

Checkpoints 是一款 Foundry 应用程序，通过在执行某些敏感数据操作之前要求数据治理团队获取理由说明，来促进可问责性和用途限制。更多详情，请参阅 检查点 文档和工作流程，了解如何 为敏感操作请求理由说明.

最佳实践

如果在您的特定处理环境中，用户在执行被视为敏感的操作之前应提供理由说明和/或确认，请部署 Checkpoints。

查看审计日志

审计日志 记录用户在 Foundry 中执行的操作。Audit Explorer 是一款用于搜索和查看的 Foundry 应用程序 audit.3 审计日志。数据治理团队可以使用它来调查活动，并确认数据仅用于经批准的用途。Audit Explorer 还会将每次搜索记录为审计日志，因此审查者自身对审计数据的使用也是可审计的。更多详情，请参阅 Audit Explorer 文档.

扫描敏感数据集

Sensitive Data Scanner 是一款 Foundry 应用程序，使管理员能够创建针对特定组织的敏感数据定义（如 PII），以及制定在识别到符合该定义的数据时应采取的策略。Sensitive Data Scanner 可以手动触发，也可以配置为在后台运行并监视进入数据集、项目或平台的新数据。当 Sensitive Data Scanner 检测到某个数据集包含符合预先指定的敏感数据定义的信息时，该应用程序将触发配置的响应，例如通过创建 Foundry 生成的 Issue 来提醒管理员，或通过应用 安全标记主动锁定该数据集。更多详情，请参阅 Sensitive Data Scanner 文档.

配置数据保留和删除

数据保留 描述了管理数据在 Foundry 中存储时长以及数据如何从 Foundry 中移除的流程。根据 FIPPs 原则，一旦处理目的已实现，PII 等敏感数据通常需要尽快删除，以遵守适用的数据保护法规。

根据您的合同协议或合规需求，某些数据可能还需要保留。因此，您应注意，数据从 Foundry 中删除到某个时间点后将变得不可逆转，并应在整个保留过程中主动实施相关控制措施，例如资格审查。

我们强烈建议您尽早确定保留要求，最好在任何数据被摄取之前完成。

有关更多信息，请查看 Foundry 中的保留机制如何运作 以及 数据生命周期 如何应用感知血缘关系的保留策略。
