通过操作编辑对象

本节介绍本体论如何通过操作来管理对象编辑。

当操作应用于对象、关联或对象集时，数据修改逻辑会立即应用到对象数据库中的索引，并定期以由 Funnel 拥有和管理的 Foundry 数据集的形式刷入持久存储。更多信息请参阅以下文档： 用户编辑的持久存储.

实时数据上的用户编辑

当操作被触发时，操作服务会向 Funnel 服务发送一条修改指令。该指令存储在一个由 Funnel 管理的队列中，该队列具有偏移量跟踪功能，以支持多个用户同时编辑。对象存储 v2 会针对任何对象类型以及任何带连接表的多对多关联类型跟踪这些偏移量。偏移量会被应用到对象数据库中的实时索引数据上；如果作为本体论查询一部分发生的对象读取发生在用户修改发送之后，则该对象读取保证包含用户的编辑。

如何丢弃/清除/删除现有用户编辑

已包含用户编辑的数据只能通过额外的用户编辑来更新。除了进行额外的用户编辑（例如对象操作）来更新对象或重新创建对象之外，没有可以直接撤销单个用户编辑或删除操作的机制。

在某些情况下，可能需要丢弃所有现有用户编辑，以便将所有对象的状态重置为与输入数据源中的状态一致。例如，在生产环境中发布对象类型之前，您可能希望删除在测试对象类型期间应用的所有用户编辑。

对象存储 v2 提供了一种 模式迁移框架 用于迁移用户编辑。该 "放弃所有编辑" 指令可用于丢弃对象类型上的所有现有用户编辑。此迁移指令可通过点击 删除编辑 按钮，位于 编辑 已应用标签 数据源 选项卡中，位于本体论管理器）。

对象存储 v1（Phonograph）不支持模式迁移，但从对象类型中移除回写数据集配置将删除所有现有的用户编辑，可以作为一种变通方法。

本体论实体版本控制

在应用操作的过程中，会出于各种目的加载对象类型定义和对象实例，例如操作验证、 函数，以及操作 副作用。在应用操作的过程中，对象实例可能会发生变化，因此必须保证事务性，以避免潜在的数据正确性问题（例如将操作应用于错误的对象版本）。

本体论包含用于检查对象类型和对象实例版本一致性的机制，但对象存储 v1（Phonograph）和对象存储 v2 的行为有所不同。

前端消费者与操作服务器之间的实体版本控制

考虑以下场景：用户加载对象属性值时的版本为 {V1, V2, V3, ...} 在 操作表单中。前端消费者应用程序会调用 Actions 服务器的 /apply 端点并传入这些对象属性值，但该请求不包含版本信息。收到该请求后，Actions 服务器会加载 /apply 端点中的对象，版本为 {V1', V2', V3', ...}。无法保证这些版本 {V1, V2, V3, ...} 与 Actions 服务器加载的版本 {V1', V2', V3', ...} 始终一致。

Actions 服务器中的实体版本控制

对象存储 v1 (Phonograph) [计划弃用]

计划弃用

对象存储 v1 (Phonograph) 目前处于 计划弃用 阶段，并将于 2026 年 6 月 30 日之后不可用。 将您的对象类型和关联类型迁移 到对象存储 v2。请参阅 Migrate object types and many-to-many link types from Object Storage v1 to v2 干预 升级助手 以了解更多信息。 如果您对工作流中从 OSv1 到 OSv2 的迁移有任何疑问，请联系 Palantir 支持。

在对象存储 v1（Phonograph）中，操作服务器会跟踪已加载对象的版本，并在整个操作执行过程中从缓存加载相同的版本。当用户编辑在对象存储 v1（Phonograph）中被应用时，请求中会包含对象版本。对象存储 v1（Phonograph）随后会检查是否有任何对象版本发生了变化，并会抛出一个 StaleObject 错误。

这些检查确保了操作服务器内部的整体一致性。例如，对象存储 v1 保证一个操作将生成一个同步的 TypeScript v1 函数无法直接从源获取 OAuth 令牌。要在 TypeScript v1 函数中通过 OAuth 2.0 API 进行身份验证，请将调用封装在，在同一版本的对象上执行、验证并应用编辑。但是，不会检查属性级别的对象变更，因此对对象无关属性的用户编辑也可能触发 StaleObject 冲突。

对象存储 v2

在对象存储 v2 中，操作服务器在将用户编辑发布到 Funnel 服务之前会自行执行对象版本检查，但与对象存储 v1（Phonograph）相比，所检查的版本集合是服务器收集的版本的一个有限子集。

操作服务器仅检查直接用于生成编辑的对象的版本，例如某个对象的版本 A ，该对象的某个属性曾被复制到对象上 B，并且这些版本仅会与被编辑对象的版本进行比对。

此行为降低了 StaleObject 冲突，其后果是 OSv2 提供的保证较弱。在对象存储 v2 中，操作服务在整个操作过程中始终以相同的版本加载对象 /apply，但不保证在编辑生成范围之外读取的对象在操作执行期间未发生更改。

跨后端操作

如果某操作类型同时修改 OSv1 和 OSv2 中的对象，则该操作类型被视为“跨后端”。在这种情况下，Actions 服务会对以下内容执行检查：

  • OSv1 中所有被读取和/或编辑的对象，以及
  • OSv2 中所有被编辑的对象。

用户编辑的持久化存储

对象数据库中的所有索引数据均被视为临时数据，因此需要通过其他方式对所有本体论数据进行持久化存储。同样，通过操作应用的用户编辑也必须进行持久化存储。支撑对象类型的 Foundry 数据源已经以 Foundry 数据集、受限视图等形式进行了持久化存储。

正如在 Funnel 管道文档，Funnel 服务拥有并管理多个 Foundry 数据集，其中包括一个合并数据集，该数据集整合了来自数据源和用户编辑的数据。该合并数据集会自动构建；这样可以确保存储在队列中的用户编辑被持久地存储在 Foundry 中，并确保清空队列，以防止队列变得过大。默认情况下，此构建作业会在以下情况下触发：

  • 每当对象类型数据源中出现新的数据事务时，或
  • 在数据源中没有新数据的情况下，如果检测到任何对象上存在编辑，则每 6 小时触发一次。

解决用户编辑与数据源更新之间的冲突

Foundry 本体论中的对象既可以由输入数据源创建和修改，也可以由用户编辑创建和修改。当单个对象（即具有特定主键值的某一行或某个对象）同时从输入数据源和用户编辑接收数据时，这些接收到的值必须透明地加以解决，具体需通过一种 冲突解决策略.

删除不被视为编辑。一旦应用删除操作，无论数据源状态如何，该对象都将不再可见。如果该对象之后被重新创建，它将不会继承之前的编辑。

有两种解决冲突的策略：

  • 策略 1：应用用户编辑（默认）
  • 策略 2：应用最新值

策略 1：应用用户编辑（默认）

采用此策略时，对象的最终状态始终由应用于该对象的用户编辑决定，无论数据源将来对同一对象中已编辑的属性进行何种更新。

策略 2：应用最新值

使用此策略时，用户编辑会被有条件地应用；也就是说，只有当用户编辑的时间戳比来自数据源的给定对象的时间戳值更新时，用户编辑才会被应用。由于每次编辑的时间戳都是与来自数据源的未编辑时间戳值进行比较，因此可能出现某些较新的用户编辑被应用，而较旧的用户编辑在同一对象上未被应用的情况。

配置

冲突解决策略在对象类型级别进行配置，且仅支持 OSv2 对象类型。

用户可以在本体论管理器中的 数据源 部分。对象类型的每个数据源可以有不同的解决策略。例如，对于由两个数据源支撑的对象类型，一个数据源可以使用 Apply user edits (default) ，而另一个数据源可以使用 Apply most recent value。该 Apply most recent value 选项要求数据源包含时间戳类型的属性；日期属性类型不适用于此选项。时间戳属性用于比较并决定是否应用用户编辑。时间戳属性必须采用协调世界时 (UTC)。

行为

一旦为数据源保存了 Apply most recent value 冲突解决策略，对该数据源支撑的属性的所有用户编辑都将被有条件地应用。

对于每个有条件的编辑，解决过程会将支撑数据源中的时间戳值与该编辑关联的时间戳进行比较。对于应用于这些属性的用户编辑 在 冲突解决策略更改之后，它们将根据导致该编辑的操作提交的时间戳有条件地应用，而任何 现有的 对这些属性的编辑将根据冲突解决策略更改的时间戳有条件地应用。

如果支撑数据源中时间戳属性的值早于与用户编辑相关联的时间戳，则会应用该用户编辑，否则将忽略该编辑。

如果一次编辑更新了跨多个数据源的属性，那么这些编辑是有条件地应用还是始终应用，将由支撑该属性的数据源的解决策略决定。

请参阅下方更新后的流程图，以根据用户编辑和数据源更新来确定您对象的最新状态。

仅编辑属性

对于 仅编辑属性，无论输入数据源上的时间戳如何，用户编辑都将始终生效。

102工单二2050年1月1日 上午 9:00 UTCP2销售

假设某个操作类型， Change team 被用于修改 Team 属性设置为 Recruiting。如果将 Change team 操作应用于 Ticket Two，团队将被设置为 Recruiting。无论使用哪种策略来解决冲突，由于 Team 是仅编辑属性，因此编辑将生效。

当操作同时修改仅编辑属性和普通属性时，行为保持不变。普通属性的编辑会根据条件应用，而仅编辑属性的编辑则始终生效。

仅考虑输入数据源的值

本体论仅将编辑时间戳与来自输入数据源的时间戳值进行比较。即使用户通过用户编辑更改了时间戳属性，条件比较也只会发生在来自输入数据源的时间戳与用户编辑应用时间之间。

由于这一行为，时间戳属性必须由来自输入数据源的时间戳列支撑。如果源系统未提供用于指示数据馈送更新时间的时间戳值，则可以在数据管道中修改输入数据源的时间戳列。
