风格指南

PySpark 是一种封装语言，允许您与 Apache Spark 后端进行交互，从而快速处理数据。Spark 可以在跨服务器的分布式网络中对超大数据集进行操作，正确使用时能够带来显著的性能和可靠性优势。即使对于经验丰富的 Python 开发者而言，PySpark 也颇具挑战，因为其语法沿袭了 Spark 的 JVM 传统，因此所实现的代码模式可能并不为人熟知。

这份观点鲜明的 PySpark 代码风格指南基于我们在各类 PySpark 仓库中遇到的高频重复主题，介绍了常见场景及相关最佳实践。

为了强制执行一致的代码风格，每个主仓库都应启用 Pylint ↗ ，并使用相同的配置。我们还提供了一些 PySpark 专用检查器 ↗ ，您可以将它们额外纳入您的 Pylint 中，以匹配本文档中列出的规则。请参阅 有关启用风格检查的文档 ，了解我们为 Python 仓库内置的 Pylint 插件的详细信息。

除了 PySpark 的具体细节之外，整洁代码的通用实践在 PySpark 仓库中也很重要——Google 的 PyGuide ↗ 是一个不错的起点。

优先使用隐式列选择而非直接访问，除非用于消除歧义

Copied!
1
2
3
4
5
# bad
df = df.select(F.lower(df1.colA), F.upper(df2.colB))

# good
df = df.select(F.lower(F.col("colA")), F.upper(F.col("colB")))

首选方案可能看起来更复杂、更长且更杂乱——而这正是正确的；事实上，最好完全避免使用 F.col()。但在某些情况下，使用它或 替代性的显式选择是不可避免的。不过，有一个非常充分的理由 让我们更倾向于选择第二个示例而非第一个。

当像第一种情况那样使用显式列时，dataframe 的名称和 schema 都会被显式绑定到该 dataframe 变量上。这意味着，如果 df1 被删除或重命名，那么引用 df1.colA 就会失效。

相比之下， F.col("colA") 将始终引用名为 “colA” 的列，该列位于当前操作的 dataframe 中，而在这个例子中，该 dataframe 恰好名为 df。它完全不需要跟踪其他 dataframe 的状态，因此代码更具局部性，也更不容易出现“鬼魅般的超距交互”，而这类问题往往难以调试。

避免第一种情况的其他充分理由：

  • 如果 dataframe 变量名很长，那么涉及它的表达式很快就会变得难以驾驭；
  • 如果列名包含空格或其他不受支持的字符，导致必须通过方括号 运算符进行访问，那么 df1["colA"] 写起来的难度丝毫不亚于 F.col(“colA”)；
  • 赋值一个抽象表达式，例如 F.col("prod_status") == 'Delivered' 赋值给变量后，便可在多个 dataframe 中复用， 而 df.prod_status == 'Delivered' 始终绑定到 df

幸运的是，通常并不需要使用包含 F.col() 的复杂表达式。唯一的例外 是 F.lower、 F.upper、…… 以及这些 ↗。

注意事项

在某些情况下，可以访问来自多个 dataframe 的列， 而这些列的名称可能存在重叠。一个常见的例子是匹配表达式，例如 df.join(df2, on=(df.key == df2.key), how='left')。 在这种情况下，直接通过其所属的 dataframe 来引用列是没有问题的。你还可以使用 dataframe 别名来消除连接的歧义 （详见本指南中的 连接 部分）。

操作 Column 对象，而不是 DataFrame 对象

在编写转换逻辑时，应使用 Column 对象，而不是反复操作 DataFrame 对象。这种方法可以减少错误，并使代码可复用。

先定义 Column 对象

在转换开始时，定义所需的 Column 对象，这些对象来自输入 DataFrame。将你的逻辑应用于这些对象，而不是反复调用 DataFrame 方法：

df = df.withColumn('category', F.when(df.is_active, 'A').otherwise('B'))

# good - extract columns, operate on them, attach at the end
status_col = F.col('status')
status_lower = F.lower(status_col)
is_active = status_lower == 'active'
category = F.when(is_active, F.lit('A')).otherwise(F.lit('B'))

df = df.select(
    '*',
    status_lower.alias('status_lower'),
    is_active.alias('is_active'),
    category.alias('category')
)

    return F.length(name_col)

df = df.select('*', full_name.alias('full_name'), name_length(full_name).alias('name_length'))

延迟将列附加到 DataFrame

避免在整个转换过程中向 DataFrame 添加中间列。应仅在最后可能的时刻——最好是在写入输出数据集时——才将计算好的 Column 对象附加到 DataFrame 并为其赋予最终名称。

切勿覆盖 DataFrame 上的列

不要覆盖 DataFrame 上已有的同名列。这样可以减少因意外重用或遮蔽列而引起的混淆和细微错误。

# good - use distinct names or work with Column objects

amount_rounded = F.round(amount_cents, 2)
df = df.select('*', amount_rounded.alias('amount_cents'))

遵循这些规则有助于养成这样一种编码风格：将 DataFrame 级别的操作保留在顶层，而将可复用、可组合的逻辑实现为 Column 级别的函数。

避免迭代遍历列，应优先使用列表推导式

总体而言，for 循环在 Spark 中的效率较低。从较高层面来看，这是因为 Spark 采用惰性求值，一次只会处理一个 for 循环。如果循环的所有部分本可以一次性处理，这种方式可能会导致运行时间变长，还可能导致 Driver 内存溢出错误（OOM）。要将数据集中的所有列名从大写改为小写，我们建议不要使用下面第一个示例（标记为 # bad），而是改用列表推导式（如第二个示例，标记为 # good）：

Copied!
1
2
3
# bad
for colm in df.columns:
    df = df.withColumnRenamed(colm, colm.lower())
Copied!
1
2
3
4
# good
df = df.select(
    *[F.col(colm).alias(colm.lower()) for colm in df.columns]
)

使用 # good 示例中的列表推导式可以避免上文讨论的运行缓慢和查询计划问题，同时仍能获得相同的预期结果。

重构复杂的逻辑运算

逻辑运算通常位于 .filter() 或 F.when()内部，需要保持可读性。我们采用与链式函数相同的规则，即将逻辑表达式 保留在同一个代码块中，最多 3 个表达式。如果表达式变长，通常意味着代码可以简化或提取出来。将复杂的逻辑运算提取到变量或函数中，可使代码更易于阅读和推理，从而减少 bug。

F.when( (df.prod_status == 'Delivered') | (((F.datediff(df.deliveryDate_actual, df.current_date) < 0) & 
((df.currentRegistration.rlike('.+')) | ((F.datediff(df.deliveryDate_actual, df.current_date) < 0) & 
(df.originalOperator.rlike('.+') | df.currentOperator.rlike('.+')))))), 'In Service')

我们可以通过多种方式来简化上述代码。首先,专注于将逻辑步骤分组到几个命名变量中。PySpark 要求表达式用括号包裹。这一点与用于对逻辑运算进行分组的实际括号混合在一起,会损害可读性。例如,上述代码 中有一个冗余的 (F.datediff(df.deliveryDate_actual, df.current_date) < 0) 原作者并没有注意到它,因为它非常难以被发现。

使用 select 语句来指定架构契约

在 PySpark 转换的开头或返回之前执行 select 操作被认为是良好的 实践。这 select 语句指定了与读者和代码双方之间关于输入和输出预期数据框模式的契约。

任何 select 都应被视为一种清理操作，为转换中的下一步准备好可供使用的数据框。

始终力求让 select 语句尽可能 简单。考虑到常见的 SQL 惯用法，最多允许 一个 来自 spark.sql.function 的函数用于每个选定的列，外加一个可选的 .alias() 来为其指定一个有意义的名称。请记住 应尽量少用这种写法，并且如果超过 三 处此类用法出现在同一个 select 中，请将其重构为一个单独的函数，例如 clean_<dataframe name>() ，以封装该操作。

切勿 允许在 select 中使用涉及多个数据框的表达式，或诸如 .when() 之类的条件操作。

空列

如果需要添加空列来满足 schema 的要求，请始终使用 F.lit(None) 来填充该列。切勿使用空字符串或其他表示空值的字符串（例如 NA）。

除了在语义上正确之外，这样做的一个实际原因是保留使用诸如 isNull等实用工具的能力，而无需验证空字符串、null 值以及 'NA'等。

UDF(用户自定义函数)

当原生 PySpark 函数能够表达相同逻辑时，应避免使用 UDF,因为 UDF 的速度明显更慢。如果必须使用，请参阅 用户自定义函数 以获取实现指南和示例。

Collect(及相关函数)

始终避免使用会将数据收集到 Spark 驱动程序的函数，例如：

  • DataFrame.collect()
  • DataFrame.first()
  • DataFrame.head(...)
  • DataFrame.take(...)
  • DataFrame.show(...)

使用这些函数会失去 Spark 等分布式框架所带来的优势，导致性能下降或出现内存不足错误。我们强烈建议不要使用这些函数，而是使用：

  • 该 预览与调试 功能位于代码仓库中，可在开发转换时检查变量(包括 Spark DataFrame)的状态。
  • 使用原生 PySpark 函数（如果可能）或 UDF（仅在极少数无法使用原生函数编码逻辑的情况下）来处理 DataFrame 中的 map/aggregate 值。

连接

使用连接时要小心。如果你执行左连接，而右侧针对某个键存在多个匹配项，那么该行将被复制的次数与匹配项的数量相同。这被称为“连接爆炸”，可能会使数据集的大小急剧膨胀。除非你预期到这种成倍增加，否则请务必仔细检查你的假设，确保用于连接的键是唯一的。

糟糕的连接是许多难以调试的问题的根源。有一些方法可以帮助调试，例如显式指定 how ，即使你使用的是默认值（inner）：

flights = flights.join(aircraft, 'aircraft_id', how='inner')

另外，请避免 right 连接。如果你准备使用 right 连接，请调换 DataFrame 的顺序并改用 left 连接。这样更直观，因为 你执行操作所在的 DataFrame 正是连接所围绕的中心。

    F.col("flights.end_time").alias("flight_end_time"),
    F.col("parking.total_time").alias("client_parking_total_time")
)

但是，在这种情况下，请记住：

  • 如果不需要同时保留两列，可能最好在连接 之前 删除重叠的列；
  • 如果您确实需要同时保留两列，则可能最好在连接之前重命名其中一列；
  • 在输出数据集之前，您应始终先解决列的歧义，因为在转换运行结束后，您将无法再区分它们。

关于连接，最后提醒一句：请不要使用 .dropDuplicates() 或 .distinct() 作为权宜之计。如果观察到意外的重复行，这些重复行的出现几乎总是有其根本原因。添加 .dropDuplicates() 只会掩盖此问题，并增加 运行时开销。

事实上，超过三条语句的链式表达式非常适合拆分为单独的、命名良好的函数，因为它们本身已经是封装的、独立的逻辑块。

理由

对链式表达式设置这些限制有以下几个原因：

  • 区分 PySpark 代码与 SQL 代码。链式调用有悖于大多数(即使不是全部)其他 Python 风格规范。在 Python 中,你不进行链式调用,而是进行赋值。
  • 不建议创建大型单一代码块。这类代码块通常提取为具名函数会更有意义。
  • 这不必非此即彼;将链式调用限制在三到五行以内,便可在实用性与可读性之间取得平衡。
  • 如果你使用 IDE,这样做可以更轻松地使用自动提取功能或进行代码移动(例如,在 PyCharm 中使用 Ctrl/Cmd+Shift+Up)。
  • 大型链式调用难以阅读和维护,尤其是在链式调用嵌套的情况下。

多行表达式

之所以能够对表达式进行链式调用,是因为 PySpark 由 Spark 发展而来,而 Spark 源自 JVM 语言。这意味着一些设计模式被移植了过来,即链式调用能力。

然而,Python 无法优雅地支持多行表达式,唯一的替代方案是提供显式换行,或将表达式用括号包裹。只有当链式调用发生在根节点时,才需要提供显式换行。例如:

其他注意事项与建议

  • 要警惕过大的函数。一般而言，文件不应超过 250 行，函数不应超过 70 行。
  • 尽量将代码保持在逻辑块中。例如，如果多行代码引用了相同的内容，请尽量将它们放在一起。将它们分开会使读者更难理解上下文。
  • 测试你的代码。如果可以运行本地测试，请运行测试并确保新代码被测试覆盖。如果无法运行本地测试，请在你的分支上构建数据集，并手动验证数据是否符合预期。
  • 避免 .otherwise(value) 作为通用回退。如果你在将键列表映射到值列表时出现了多个未知键，使用 otherwise 会将所有这些掩盖为一个值。
  • 不要在仓库中保留被注释掉的代码。这适用于单行代码、函数、类或模块。请改用 git 及其分支或查看历史记录的功能。
  • 当遇到由整合多个不同源表组成的大型单一转换时，应将其拆分为自然的子步骤，并将逻辑提取到函数中。这样不仅便于在更高层级上阅读代码，还能实现代码的可重用性以及各转换之间的一致性。
  • 在命名函数或变量时，应尽量做到明确且具有描述性。除了包装对象转换的顶层转换之外，应力求体现函数实际执行的操作，而不是仅根据函数内部使用的对象来命名。
  • 除非有充分的理由，否则在引入新的导入别名时应慎重考虑。例如，如果导入的模块在多个不同文件中被大量调用，且该模块为几乎所有开发人员所常见和熟悉，那么这样做可能是合理的。一些已确立的别名包括 types 和 functions from pySpark from pyspark.sql import types as T, functions as F。
  • 避免在筛选条件、新列值和类似上下文中使用字面字符串或整数。而应将它们赋值给能够体现其含义的变量、常量、字典或类。这种方法可使代码更具可读性，并在整个仓库中保持一致。
