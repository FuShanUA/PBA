在 Postgres 中优化查询

本页面重点介绍如何在 Postgres 中对查询进行调优以获得最佳性能。我们通常建议在 Ontology 功能之上构建 Slate 应用，使用诸如以下功能 对象集 和 操作 来读取和写入数据。

设计响应式应用需要仔细的规划和考量。数据模型、查询结构和依赖关系图都在应用性能和可用性中扮演重要角色。本指南专注于可在 Slate 中编写的 PostgreSQL 查询的性能调优，包括性能启发式方法、识别调优机会的方法以及改进性能的建议。

查询性能调优是一个 迭代式 过程。为了产生“正确”的答案，有许多不同的方式可以编写同一个请求。

性能启发式方法

PostgreSQL 查询的目标执行时间为 <= 500ms。对于所涉及数据集少于 1000 万条记录的大多数用例来说，这应该是可以实现的，但在设计数据模型时需要仔细的规划和考量。

在评估查询性能时，尤其是对于新数据集，请确保在收集和分析统计信息之前多次运行查询。这有助于确保数据集已被正确缓存，并且性能更符合预期的使用情况。如果您想进一步了解 PostgreSQL 缓存，请参阅以下链接：

EXPLAIN...详解

EXPLAIN 是 Postgres 提供的一个特别有用的命令，用于返回查询执行计划。Postgres 收到的每个请求都会创建一个查询计划，该计划利用查询结构和数据属性来确定服务该请求的最快方式。本节首先回顾 EXPLAIN 命令，该命令在整个指南中都会被引用。

EXPLAIN

NODES

您可以将节点视为一个逻辑工作单元，或查询求值中的一个步骤。节点以倒置图的形式返回，这意味着响应的第一行是最后执行的工作单元。每个节点前面都有 ->.

-> Index Scan using event_type_idx on event (...)

为什么这很重要：这些节点将用于识别查询执行计划中的低效操作，并帮助确定性能调优工作的优先级。

COST

第一个数字是启动成本（检索第一条记录的时间）。第二个数字是从启动到完成处理整个节点的成本。

(**cost=86.83..4577.07** rows=2368 width=10)

成本是一个 估计值 由 Postgres 查询规划器基于对象（通常是表）的 统计信息生成。虽然这个数字并不代表实际运行时间，但它应与实际执行情况直接相关。

成本是多个工作组成部分的组合：顺序获取、非顺序（随机）获取、行处理、运算符（函数）处理以及索引条目处理。成本代表 I/O 和 CPU 活动；数字越大，Postgres 认为完成任务所需的工作就越多。Postgres 查询优化器根据成本来确定使用哪个执行计划。

ROWS

此计划节点将输出的估计行数。

(cost=86.83..4577.07 **rows=2368** width=10)

为什么这很重要：ROWS 可用于识别返回大量数据和/或行为不符合预期的节点。

WIDTH

该节点输出行的估计平均大小（以字节为单位）。

(cost=86.83..4577.07 rows=2368 **width=10**)

为什么这很重要：WIDTH 可用于识别输出具有超大属性或大量列的行的节点。

EXPLAIN ANALYZE

NODES

见上文。

实际时间

与 成本类似，第一个数字是启动所需的实际时间（以毫秒为单位）。第二个数字是从启动到完成处理整个节点的实际时间。

(**actual time=10.313..12.530** rows=4857 loops=1)

顾名思义，实际时间是通过执行语句来捕获的。关键字 ANALYZE 告诉 Postgres 在显示执行计划的同时执行查询。如果查询超时导致问题，移除 ANALYZE 将只返回查询计划，这应该比执行查询快得多。

为什么这很重要：这是最清晰的指标，用于指示哪些节点或操作导致了性能问题。

ROWS

该节点输出的估算行数。

(actual time=10.313..12.530 **rows=4857** loops=1)

为什么这很重要：ROWS 可以帮助提供上下文，说明 为什么 某个特定操作为何可能比预期花费更长时间。

LOOPS

报告该节点的总执行次数。所显示的实际时间和行数值是每次执行的平均值。将 LOOPS 值乘以实际时间即可得到在该节点中花费的总时间。

(actual time=10.313..12.530 rows=150 **loops=10**)

理解操作（计划节点）

扫描

  • sequential scans （顺序扫描）：Seq Scan 操作会扫描存储在磁盘上的整个关系（表）（类似于 TABLE ACCESS FULL）。对关系执行顺序扫描总是可行的；无论关系的模式、大小、约束以及是否存在索引。
    • 以下是顺序扫描的特征：
      • 启动速度快（顺序 I/O 比随机访问快得多）。
      • 每个数据块只读取一次。
      • 产生无序的输出。
  • index scans：Index Scan 执行 B 树遍历，遍历叶子节点以找到所有匹配的条目，并获取相应的表数据。它类似于 INDEX RANGE SCAN 后跟 TABLE ACCESS BY INDEX ROWID 操作
    • 以下是 Index Scan 的特征：
      • 随机访问比顺序 I/O 慢得多。
      • 需要额外的 I/O 来访问索引。
      • 可能会多次读取同一个数据块。
      • 产生有序的输出。
  • bitmap index/heap scans：普通 Index Scan 每次从索引中获取一个元组指针，并立即访问表中的该元组。位图扫描则一次性从索引中获取所有元组指针，使用内存中的“位图”数据结构对其进行排序，然后按照元组物理位置的顺序访问表元组。
    • 以下是位图索引/堆扫描的特征：
      • 具有索引选择性的顺序 I/O。
      • 启动速度慢，因为需要读取并排序所有索引元组。
      • 通常被选用于 IN 和 =ANY(array) 运算符，以及低选择性的索引扫描。
      • 可以组合多个索引。
      • 产生无序的输出。
  • index only：Index Only Scan 执行 B 树遍历并遍历叶子节点以找到所有匹配的条目。不需要访问表，因为索引包含满足查询所需的所有列（MVCC 可见性信息除外）。

连接

连接操作通常一次只处理两个表。当查询涉及连接两个以上的表时，连接会按顺序执行：先连接两个表，然后将中间结果与下一个表连接，依此类推。在连接的语境中，“表”一词因此也可以指“中间结果”。

  • nested loop：通过从一个表获取结果，并针对第一表的每一行查询另一个表，来连接两个表。
    • 通常是性能最差的连接形式。
    • 快速产生第一条记录。
    • 如果第二个子节点较慢，可能出现负面性能影响。
    • 唯一能够执行 CROSS JOIN 的连接方式。
    • 唯一能够处理不等连接条件的连接方式。
  • merge join：（排序）合并连接像拉链一样合并两个已排序的列表。连接的两侧都必须预先排序。
    • 只能用于等值连接条件。
    • 通常对大型数据集性能最佳。
    • 需要有序的输入——这可能需要缓慢的排序或索引扫描。
    • 启动速度慢，因为需要读取并排序所有索引元组。
  • hash joins：哈希连接（Hash Join）会将连接一侧的候选记录加载到哈希表中（在计划中标记为 Hash），然后针对连接另一侧的每条记录对该哈希表进行探测。
    • 只能用于等值连接条件。
    • 通常在大表与小表连接时性能最佳。
    • 仅适用于可哈希的数据类型。
    • 由于需要对较小的表进行哈希处理，启动速度较慢。
    • 如果表统计信息过期或不正确，性能会受到负面影响。

聚合

  • GroupAggregate：根据 GROUP BY 子句对已预排序的数据集进行聚合。此操作不会缓冲大量数据。
  • HashAggregate：使用临时哈希表对记录进行分组。HashAggregate 操作不需要预排序的数据集；相反，它会使用大量内存来物化中间结果（非流水线式）。其输出没有任何有意义的排序。
  • Unique
  • WindowAgg：表示使用了窗口函数。

其他

  • Sort
    • 出现在 ORDER BY、DISTINCT、GROUP BY、UNION 和合并连接中。
    • 启动时间较长。
    • 如果排序可以容纳在 work_mem中，则可以使用快速排序。
    • 如果排序无法容纳在内存中，将会溢出到磁盘并使用临时文件，这可能非常昂贵。
  • Limit
    • 同时处理 LIMIT 和 OFFSET。
    • 如果没有 WHERE 子句，可用于 min() 和 max()。
    • 为 OFFSET 跳过的记录仍会被生成/物化，但在返回结果之前会被丢弃。
    • 子扫描的成本仍然是全部成本。
    • 排序结合 limit 可以使用优化形式的排序。

查询调优最佳实践

SELECT

  • 仅包含显示所需的属性，这将有助于限制为支持请求而获取的页面数量。

DISTINCT

  • DISTINCT 来自 PostgreSQL 代码库中较旧的部分，使用效率较低的方法来识别不同记录。
  • 如果可能，请避免使用 DISTINCT ，可改用 GROUP BY 或子查询。

JOIN

  • 连接表时，请尝试在 ON 子句中使用简单的等值条件（例如 a.id = b.person_id）。这样做可以使用更高效的连接技术（例如使用哈希连接而非嵌套循环连接）。
  • 在可能的情况下将子查询转换为 JOIN 语句，因为这通常能让优化器理解意图，从而可能选择更好的计划。
  • 正确使用 JOIN：您是否仅仅因为得到重复结果而使用 GROUP BY 或 DISTINCT？这通常表明 JOIN 使用不当，可能导致更高的成本。
  • 如果执行计划使用哈希连接，而表大小估算错误，则可能非常慢。因此，请通过审查您的 vacuum 策略来确保表统计信息准确。
  • 尽可能避免相关子查询；它们会显著增加查询成本。
  • 在根据条件检查行是否存在时使用 EXISTS，因为它会“短路”（找到至少一个匹配项时即停止处理）。

WHERE 子句

  • 尽可能避免使用 LIKE。
  • 避免向 IN() 语句中传入大型列表——可以考虑改用 JOIN 条件，或将逻辑调整为基于排除的方式。
  • 避免在 WHERE 子句中使用函数调用。

GROUP BY 与 GROUPING SET

请参阅 PostgreSQL GROUPING SETS 文档 ↗.

UNION 与 UNION ALL

UNION 会消除重复记录；这需要对相关表进行排序。

鉴于与该请求相关的成本，我们强烈建议避免使用 UNION。需要使用它的情况应该很少；如果确实需要，应在从 Slate 查询之前在 Transforms 层中完成。

UNION ALL 不会消除重复记录，而是会高效地将一个表的行追加到另一个表。

请参阅 常见错误：UNION 与 UNION ALL ↗.

索引

在以下条件下考虑添加索引：

  • 避免顺序扫描（seq scan），除非是小表和/或查询要获取超过 5% 的行。
  • 如果使用多列索引，请注意定义所包含列时的顺序。
  • 在常用列上使用选择性高的索引。
