保持高性能

增量转换可以确保管道更新时仅处理新行，从而帮助最大限度地减少资源使用。在 Foundry 中，增量转换只能向数据集添加新行，而不能替换或删除行。数据摄取也可能属于这种情况。由于每次运行通常只处理少量数据，因此每次添加的数据量都很小，但在渲染活动视图时，必须将所有这些添加内容一并考虑在内。

通常情况下这没有问题，但当累积了数万甚至数十万次小更新时（在连续构建数周或数月后可能会发生这种情况，具体取决于频率），读取和写入性能可能会开始下降。这可能由多个相关因素引起，具体讨论如下。

可能的原因

文件数量过多

数据集中文件过多会导致访问当前视图数据的后端请求变慢。这可能导致预览不可用、Contour 中出现故障，以及转换（尤其是 Python 转换）严重变慢，这是由于在该语言环境中加载文件存在特殊的开销。

随着时间的推移，任何涉及活动数据集视图的操作都将被低效的数据读取所主导，以至于最初以分钟为单位运行的转换最终可能需要数小时甚至数天。在极端情况下，后端请求甚至可能超时，导致构建失败。

此外，作为在 APPEND 或 UPDATE 事务中将 Spark DataFrame 写入输出的一部分，增量转换需要构建一个内存列表，其中包含输出当前视图中的所有现有文件。对于包含大量文件的输出，此操作可能耗时很长，并且可能需要使用较高的驱动程序内存 Spark 配置文件 以避免内存不足错误。

事务数量过多

与文件过多类似，视图中过多的 事务 也会导致变慢。然而，这种变慢不仅发生在请求文件时，还发生在解析视图范围时，这会影响数据集功能，例如计算统计信息、加载历史记录等。在转换中，这种变慢会体现在预计算阶段，即环境正在设置且尚无任何 Spark 详细信息时，这使得该问题难以调试。

通常，事务与文件会同步累积，但在某些情况下，即使文件数量相对较少，空事务也可能导致问题。相反，如果每个事务包含大量文件，即使事务数量相对较少，也可能产生大量文件。

可能的解决方案

定期快照

保持增量管道高性能的最简单且在某些情况下最有效的解决方案是运行定期快照。快照将重新处理全部数据，并用可以高效分区的新视图替换输出。快照是一种计算密集型操作，这也是通常选择增量处理而非常规处理的原因，但偶尔进行快照有助于防止同一视图中文件或事务过度累积。为了确定快照频率，管理员应在读取和写入数据的性能之间进行权衡。

快照事务具有级联效应，即每个使用已被快照的输入的增量转换都会对自身进行快照。我们无需直接强制增量转换运行快照，只需对转换的某个输入进行快照，然后让 Transforms 应用程序确定该增量转换也需要进行快照。因此，设置增量管道定期快照的一种有效方法是设置一个将按预期快照计划构建的虚拟输入，并使该虚拟输入始终以快照模式运行。

定期快照存在以下几个缺点，如下所述：

  • 快照可能会使血缘关系变得复杂，因为虚拟输入会出现在搜索结果和文件夹结构中，这可能会造成混淆。
  • 快照操作可能非常昂贵，即使执行频率不高。
  • 在快照运行期间，任何更新都无法在管道中传播，这可能会影响 SLA（服务级别协议）。
  • 快照不适用于原始数据集，例如由 Data Connection 同步支撑的数据集。
  • 并非每个转换的编写方式都支持快照（尽管我们建议它们始终应该支持）。

数据集投影

处理增量构建最推荐的方法是添加一个 数据集投影 到相关的数据集上。数据集投影提供了一种查询数据集中数据的替代机制，其存储和更新独立于规范数据集。由于这些特性，数据集投影可以摆脱增量计算的仅追加模型，并在数据量增长时自动重组其内部数据表示。这称为压实（compaction）——压实确保从投影读取数据时始终保持高性能，无论规范数据集中有多少文件或事务。

这对于增量管道尤其有用，因为数据集投影无需与规范数据集完全同步，读取者就能受益于性能提升。所有 Foundry 产品都知道如何将来自投影和规范数据集的数据组合起来，重建出与没有投影时相同的视图。例如，如果某个数据集有 100 个增量事务，并且有一个基于前 99 个事务构建的投影，那么将从投影中读取 99 个事务，而只从数据集中读取 1 个。因此，通常每天或每周更新一次数据集投影就足够了，这使得维护成本在计算上非常低廉。

由于数据集投影是与规范数据集分离的资源，因此可以在任何时候构建，即使规范数据集本身正在构建中（反之亦然）。读取者只会使用根据有效事务确定的当前状态。例如，如果某个数据集正在构建事务 10，而投影同时开始构建，它将从事务 9 读取。在这种场景下查询数据的读取者将从投影中读取事务 1-8，从数据集中读取事务 9，实际上看到的数据与直接从数据集读取时相同。

数据集投影的缺点包括：

  • 数据集投影比仅使用数据集本身占用更多存储空间。
  • 数据集投影无法开箱即用地与 Foundry Retention 配合使用。
  • 数据集投影不会以任何方式修改规范数据集（因此如果移除投影，读取将再次变得低效）。

保留策略

有时，管道的用例并不要求在平台内永久保留历史数据，只保留最近的事务即可，这可以通过 Foundry Retention 自动完成。在这种情况下，只要转换逻辑不包含任何跨事务的依赖关系（例如聚合或差分计算），增量管道的构建无需特殊考虑。需要在 Python Transforms 中为增量装饰器设置一个特殊的 allow_retention 标志（否则 DELETE 事务将触发快照运行）。

保留策略变更的缺点包括：

  • 丢失历史数据。
  • 如果事务从数据角度来看不是自包含的单元，保留策略可能导致状态不一致（例如，有结束事件但没有匹配的开始事件）。

其他可考虑的选项

中止事务

在某些情况下，事务提交时可能包含零个文件，或仅包含空文件。这些事务对视图没有影响，但它们被视为有效更新，会触发调度以及所有相关的副作用，从而可能导致计算浪费。空事务还可能大幅增加文件数和事务数。

最好在源头（通常是 Data Connection）避免空事务 同步。Data Connection 始终会中止不含任何文件的事务，但仍可能生成空文件。空事务在使用自定义插件时可能是一个特别的问题；有时可能无法修改插件来避免空事务（例如，如果需要非空事务来更新 Data Connection 的增量元数据）。在其他情况下，无文件事务可能由转换或其他方式提交。

为了最大限度地减少这些空事务或无文件事务的影响，我们可以在管道中最上游的转换处显式中止事务。当我们检测到收到空输入，或最终得到空输出时，可以调用 .abort() 作用于输出对象；这将导致作业及其事务被中止。被中止的事务实际上已被取消，不会触发调度或引起任何副作用。中止事务将打破链条，阻止空事务在管道中向下传播。中止事务也不会计入失败统计（而故意使构建失败则会计入失败统计）。

被中止的构建被视为成功，并且会推进输入事务指针。因此，在输入非空时中止会丢弃数据，如果您因其他原因（例如前置条件失败）想要停止构建，这可能并不符合预期。

变更日志数据集

变更日志逻辑使您能够在仅追加事务上实现编辑语义，从而在增量管道中可靠地执行连接和聚合。然而，除了前面提到的文件数和事务数问题之外，在仅追加事务上实现编辑语义可能导致行数无限增长，使得在到达状态解析阶段（或需要独立快照）时，转换性能越来越差。

控制此类管道的行数稍微有些棘手。快照是可行的，并且在存在部分状态的中间转换中可能大有帮助（因为这些状态在完全重建时大多会消失）。但要充分利用快照的优势，逻辑必须将行折叠到其最新状态，而这并不总是可取的（在某些情况下，我们可能想知道行在任意时间点的状态，而不仅仅是最新状态）。数据集投影的作用有限。而且，如果行不是原子单元，保留策略可能无法达到预期效果（例如，我们最终可能得到一个没有匹配开始事件的结束事件）。因此，在设计此类管道时必须格外小心。
