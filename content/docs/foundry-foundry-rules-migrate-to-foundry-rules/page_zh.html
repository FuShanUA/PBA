迁移到 Foundry Rules

虽然对 Taurus 的长期支持仍在继续，但一些组织可能希望将其现有的 Taurus 工作流迁移到 Foundry Rules，以受益于更多功能，例如更轻松地进行更改和执行管道维护，以及进一步的开发更新。请注意，Taurus 将继续获得长期支持。

通过将 Taurus 用例迁移到 Foundry Rules，您可以获得以下优势：

  • 简化的部署，可在几分钟内通过单个 Foundry Rules 配置页面完成。
  • 通过对 Foundry Rules 配置进行单步更改即可完成修改和维护。
  • 开箱即用的执行，无需与管道代码交互，包括流式工作流。
  • 内置代码生成器，可支持需要自定义管道代码的高级 Foundry Rules 用例。

最优的 Foundry Rules 工作流应针对一个特定用例，其中包含您希望用户编写的一种类型的规则。如果您有多个用户组和多个规则编写应用程序，可以考虑多次使用迁移向导来创建多个规则工作流。

迁移注意事项

在迁移到 Foundry Rules 之前，请考虑以下事项：

  • 如果您将 Taurus 用作更大型产品方案（例如供应链优化、反洗钱或面向汽车行业的 QMOS），则目前无需执行任何迁移。

  • 如果您的 Taurus 用例较为复杂，包含以下任意组合，则迁移将需要一些重构工作，您应权衡前文所述的优势与所需变更程度之间的利弊：

    • 您的 Taurus Workshop 模块包含多个规则编辑器小部件，它们针对不同的用户组具有不同的配置。
    • 您的 Taurus 代码仓库使用了 Taurus 软件包的高级功能，或者以特定方式应用规则逻辑。使用高级功能的一个示例可能是：代码仓库运行提案来创建潜在影响分析。
    • 您的 规则操作 实现可选可见性，使用对象定位器、对象集或附件字段类型。

  • 如果您正在积极地向 Taurus 用例中添加更多输入数据集、对象类型或规则输出，则 Foundry Rules 提供的新配置界面可以提高可维护性。即使您选择将 Java 代码仓库与 Foundry Rules 工作流结合使用，您仍将受益于部分代码生成。

将 Taurus 工作流迁移到 Foundry Rules 工作流

以下过程将使用您现有的对象类型和 Workshop 模块，但会创建并行管道和新的输出数据集，以防止干扰运行中的管道。

升级到 V2 时，将执行以下过程：

  • 检查您工作流中的时间序列
  • 升级现有应用程序
  • 如有必要，解除旧应用程序的关联
  • 完成迁移所需的手动操作

首先，请按照以下说明操作：

  1. 导航至 Foundry Rules （位于 Foundry 工作区导航侧边栏），然后前往 旧工作流 选项卡。

  2. 选择本体论，然后从列表中找到 V1 原型，或使用搜索字段进行查找。

  3. 选择 从旧版本迁移。

  4. 选择主规则编辑器 Workshop 资源，并查看用于保存新 Foundry Rules 工作流的目标文件夹。如有必要，请重命名工作流。然后，选择 开始

  5. Foundry Rules 迁移向导将检查您的现有设置是否包含 时间序列。如果是，您将需要配置关联类型和时间序列同步。完成额外配置后，请选择 保存规则工作流 。

  6. 某些资源可能需要导入到项目中。请查看并展开以核实资源列表，然后完成屏幕上显示的所需操作，再选择 保存。

  7. 选择 升级规则应用程序。

  8. 如果出现提示，请选择 取消关联旧应用程序。

  9. 最后，请留意屏幕上的指引，并针对新升级的管道，根据您的使用场景遵循相应的说明：

    • 我的 Foundry Rules 输出直接馈送到本体论对象类型。
      • 如果您的输出馈送到本体论对象类型（例如，未经过任何额外转换），那么您需要替换该对象类型中 对象的支撑数据集 ，以便警报来自新版本的 Foundry Rules。

此选项将导致 在对象类型为 V1 时丢失对象编辑。否则，如果您必须保留编辑内容，则可以 保留支撑数据集 ↗ ，并确保其内容是新规则输出的直接副本。

  • 我对 Foundry Rules 输出应用了额外转换。
    • 您应该使用新的输出数据集来替换转换中原有的规则输出。对于高级使用场景，您可以注册一个 自定义仓库来计算规则输出。
  • 我还有其他规则编辑器 Workshop 应用程序。
    • 如果您的所有规则编辑器都具有相同的输入和输出，您可以让它们全部引用此 Rules 工作流。您可以使用 Archetype 的部署菜单部署更多规则编辑器 Workshop 应用程序，该菜单位于左侧的 “应用程序” 选项卡中。如果您的规则编辑器服务于不同的用例且具有不同的配置，您应该通过部署新的 Rules Archetype，在专用工作流中迁移每一个规则编辑器。
  1. 完成上述步骤后，选择 “标记迁移已完成”。您的用例现已在新的 Foundry Rules 设置中正常运行。

验证迁移

要检查到 Foundry Rules 的迁移是否成功，请访问规则输出数据集所在项目的链接。

打开规则输出数据集并选择 “构建” 或转到“计划任务”选项卡并 “添加构建计划”。

构建成功即表示到 Foundry Rules 的升级过程已成功完成。

  • 为什么我的数据集构建成功，但其中却没有数据？

    构建作业包含另一个名为“规则状态数据集”的数据集，其中包含每条规则的信息以及该规则未能正常运行的原因。此外，您可能尚未重新运行写回数据集；请参见 《编写并运行规则指南》中的第四步。该数据集也可以在 Build 页面的 转换配置 部分中找到：

  • 如果其他人同时对 Rules 应用程序进行更改，为什么我无法取消迁移？

如果您已完成 Rules 应用程序的升级阶段，而另一名用户在您随后尝试 取消 迁移时对 Rules 应用程序进行了更改，就会发生此错误。

要解决此问题，请打开 Rules Workshop 应用程序并发布较早的迁移版本，以撤销所做的手动更改。之后，您便可以成功取消升级过程。

  • 为什么当规则编辑器小组件和提案审核小组件不各恰好有一个时，迁移就无法继续进行？
    • Rules 应用程序在设计时可以包含任意数量的规则编辑器小组件和任意数量的提案小组件，但 Taurus 和 Foundry Rules 中的配置方式有所不同。在 Taurus 中，可以为小组件配置独特的属性，例如让每个小组件拥有不同的可用输入。迁移不会合并多个小组件的配置，而是将一个规则编辑器小组件转换为一个 Rules 工作流。然而，在新的 Foundry Rules 设置中，不同的配置应各自成为独立的 Rules 工作流。
    • 要解决迁移中的此问题，您应考虑以下场景及相应的解决方案。之后，请再次完成迁移向导。请注意，Workshop 更改已建立版本控制，以支持在必要时还原更改：
      • 您意外创建了多个规则编辑器小部件，而其中只有一个是相关的。您应从 Workshop 模块中移除不相关的小部件，然后重新尝试迁移。
      • 您有多个配置相同的小部件。您应只保留其中一个，移除其余小部件。迁移完成后，您可以复制并粘贴更新后的小部件，以重新创建应用程序的设计。
      • 您有多个配置不同的小部件。在这种情况下，您应将 Workshop 模块拆分为多个模块，每个模块包含一个规则编辑器小部件，并为每个模块创建一个 Rules 原型。请选择向导上的 从旧版本迁移 选项，以便从每个 Workshop 模块创建配置，从而节省时间。
