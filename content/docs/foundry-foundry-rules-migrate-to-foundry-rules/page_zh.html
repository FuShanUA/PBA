迁移到 Foundry Rules

虽然 Taurus 会继续获得长期支持，但一些组织可能希望将其现有的 Taurus 工作流迁移到 Foundry Rules，以受益于更多功能，例如更轻松地进行更改和执行管道维护，以及进一步的开发更新。

通过将 Taurus 用例迁移到 Foundry Rules，您可以受益于：

  • 简化的部署，可在单个 Foundry Rules 配置页面上在几分钟内完成。
  • 通过对 Foundry Rules 配置进行单步更改来进行修改和维护。
  • 开箱即用的执行，无需与管道代码交互，包括流式工作流。
  • 内置代码生成器，支持需要自定义管道代码的高级 Foundry Rules 用例。

最佳的 Foundry Rules 工作流针对一个特定用例，包含您希望用户编写的一种类型的规则。如果您有多个用户组和多个规则编写应用程序，可以考虑多次使用迁移向导来创建多个规则工作流。

迁移注意事项

在迁移到 Foundry Rules 之前，请考虑以下事项：

  • 如果您将 Taurus 用作更大的产品方案，例如供应链优化、反洗钱或汽车行业的 QMOS，此时无需执行迁移。

  • 如果您的 Taurus 用例较为复杂，包含以下任意组合，则迁移将需要一些重构工作，您应权衡前文所述的收益与所需更改的范围：

    • 您的 Taurus Workshop 模块有多个规则编辑器小部件，为不同用户组提供不同的配置。
    • 您的 Taurus 仓库使用了 Taurus 软件包的高级功能，或以特定方式应用规则逻辑。使用中的高级功能示例可能是仓库运行提案以创建潜在影响分析。
    • 您的 规则操作 实现可选可见性，使用对象定位器、对象集或附件字段类型。

  • 如果您正在积极向 Taurus 用例中添加更多输入数据集、对象类型或规则输出，Foundry Rules 提供的新配置界面可以提升可维护性。即使您选择将 Java 仓库与 Foundry Rules 工作流结合使用，您也将受益于部分代码生成。

将 Taurus 工作流迁移到 Foundry Rules 工作流

以下过程使用您现有的对象类型和 Workshop 模块，但会创建一个并行管道和新的输出数据集，以防止对运行中的管道造成干扰。

升级到 V2 时，将执行以下过程：

  • 检查工作流中的时间序列
  • 升级现有应用程序
  • 如有必要，取消关联旧应用程序
  • 完成迁移所需的手动操作

首先，请按照以下说明操作：

  1. 导航至 中使用，以对实时运营数据和 IoT 数据进行实时分析。 从 Foundry 工作区导航侧边栏中，然后前往 旧工作流 标签页。

  2. 选择本体论，并从列表中找到 V1 原型，或使用搜索字段。

  3. 选择 从旧版本迁移.

  4. 选择主规则编辑器 Workshop 资源，并查看用于保存新 Foundry Rules 工作流的目标文件夹。如有必要，请重命名工作流。然后，选择 开始时间

  5. Foundry Rules 迁移向导将检查您现有的设置是否包含 时间序列。如果是，您将需要配置关联类型和时间序列同步。选择 保存 Rules 工作流 在您完成其他配置后。

  6. 某些资源可能需要导入到项目中。查看并展开以验证资源列表，然后完成所需的屏幕操作，然后选择 保存.

  7. 选择 升级规则应用程序.

  8. 如果被请求，请选择 取消关联旧应用程序.

  9. 最后，请注意屏幕上的指导，并根据您对新升级管道的用例遵循相应的说明：

    • 我的 Foundry Rules 输出直接馈送到本体论对象类型中。
      • 如果您的输出直接输入到本体论对象类型（例如，没有任何额外的转换），那么您需要替换 对象类型的支撑数据集 ，以便警报来自新版本的 Foundry Rules。

此选项将导致 如果对象类型为 V1，则丢失对象编辑。否则，如果您必须保留编辑，您可以 保留支撑数据集 ↗ ，并确保其内容是新规则输出的直接副本。

  • 我在我的 Foundry Rules 输出上应用了额外的转换。
    • 您应该使用新的输出数据集来替换转换中以前的规则输出。对于高级用例，您可以注册一个 自定义仓库来计算规则输出.
  • 我有其他规则编辑器 Workshop 应用程序。
    • 如果您的规则编辑器都具有相同的输入和输出，您可以让它们全部引用此 Rules 工作流。您可以使用 Archetype 的部署菜单部署更多规则编辑器 Workshop 应用程序，位置在 应用程序 左侧的选项卡。如果您的规则编辑器服务于不同的用例并具有不同的配置，您应该通过部署新的 Rules Archetype 在专用工作流中迁移每一个规则编辑器。
  1. 完成这些步骤后，选择 标记迁移已完成。您的用例现在已在新 Foundry Rules 设置上运行。

验证迁移

要检查到 Foundry Rules 的迁移是否成功，请访问保存规则输出数据集的项目的链接。

打开规则输出数据集并选择 构建 或转到 Schedules 选项卡并 添加构建计划.

成功的构建表明到 Foundry Rules 的升级过程已成功完成。

  • 如果其他人同时对 Rules 应用程序进行更改，为什么我无法取消迁移？

如果您已完成升级 Rules 应用程序的阶段，而当您随后尝试 取消 迁移时，另一个用户对 Rules 应用程序进行了更改，则会发生此错误。

要解决此问题，请打开 Rules Workshop 应用程序并发布较早的迁移版本，以撤销手动所做的更改。然后您将能够成功取消升级过程。

  • 为什么迁移在没有恰好一个规则编辑器和一个提案审查器小部件的情况下无法继续？
    • Rules 应用程序可以设计为包含任意数量的规则编辑器小部件和任意数量的提案小部件，但在 Taurus 和 Foundry Rules 之间的配置方式不同。在 Taurus 中，可以为小部件配置独特的属性，例如在每个小部件中提供不同的输入。迁移不会合并多个小部件的配置，而是将一个规则编辑器小部件转换为一个 Rules 工作流。然而，在新的 Foundry Rules 设置中，不同的配置应各自成为独立的 Rules 工作流。
    • 要在迁移中解决此问题，您应考虑以下场景及相应的解决方案。之后，再次完成迁移向导。Workshop 的更改已版本化，以支持在必要时还原更改：
      • 您意外拥有多个规则编辑器小部件，但只有一个相关。您应从 Workshop 模块中删除不相关的小部件，然后再次尝试迁移。
      • 您有多个配置相同的小部件。您应只保留一个小部件，删除其余所有小部件。迁移完成后，您可以复制并粘贴更新后的小部件，以重新创建应用程序的设计。
      • 您有多个配置不同的小部件。在这种情况下，您应将 Workshop 模块拆分为多个模块，每个模块包含一个规则编辑器小部件，并为每个模块创建一个 Rules 原型。选择 从旧版本迁移 在向导上，从每个 Workshop 模块创建配置以节省时间。
