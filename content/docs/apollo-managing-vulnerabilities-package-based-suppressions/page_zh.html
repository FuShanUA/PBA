基于软件包的抑制

Apollo 会检测您产品中的漏洞，并召回包含这些漏洞的发布版本。抑制项会告知 Apollo，对于您已经审查并接受的发现项，停止召回相应的发布版本。这样，您的团队就不会因当前无法处理的漏洞而受到干扰。

一种 基于软件包的抑制，或称“软件包漏洞抑制”，是一种抑制类型，其针对的是由 Package URL (PURL) 标识的软件包，而非单个漏洞。您无需一次只抑制一个 CVE，而是定义一条规则，来描述该抑制适用于哪些漏洞、哪些软件包以及哪个范围。只要该软件包出现在该范围内，此规则就会屏蔽所有匹配的发现项，包括未来扫描中出现的发现项。

概述

Apollo 中有两类抑制：

  • 人工请求的抑制： 您在 Risk Management 应用中创建的抑制，包括基于软件包的抑制。
  • 宽限期抑制： 一个固定的时间窗口，用于在受影响的发布版本被召回之前处理某个 CVE。宽限期从漏洞首次被发现时开始，而非从扫描运行时开始。

基于软件包的抑制之所以存在，是因为产品中的某些漏洞并非来自产品团队编写的代码。这些漏洞来自产品所依赖但既无法控制也无法修补的软件包。逐个 CVE 地处理这些发现并不具备可扩展性。单个软件包可能会随着时间的推移持续产生一系列 CVE，而相同的软件包在每一个使用它们的产品中都会被一次又一次地重新分类处理。通过 PURL 定位软件包，可以让您在一个地方接受某个软件包的风险，而无需在每个新 CVE 出现时都提交单独的请求。

定义宽泛的规则并不等于获得了抑制软件包的全面许可。请选择既符合您的产品又符合其理由的最窄定义。每项抑制都会开启一个 变更请求 ，该请求必须先获得批准才能生效，并且每项抑制都必须附带必需的理由和必需的到期日期。任何抑制都不会被静默执行，每次变更都会保留完整的审计跟踪记录。

核心概念

术语含义
软件包漏洞抑制一种抑制类型,通过 PURL 针对整个软件包而非单个漏洞。在规则范围内,无论软件包位于哪一层,它都会静默该软件包中所有与规则的漏洞匹配器相匹配的当前和未来发现。使您能够逐个软件包地接受风险。
软件包由 PURL 标识的软件组件(pkg:type/namespace/name)。生态系统是标识的一部分,因此 pkg:rpm/redhat/coreutils 和 pkg:deb/ubuntu/coreutils 是不同的软件包。软件包可以来自操作系统层,也可以来自操作系统层之外。
发现在一个或多个已扫描镜像中发现的(软件包,CVE)对。这就是您执行抑制操作所针对的单元。
范围抑制的适用范围:特定镜像仓库、镜像前缀、SLS 发行版、产品或全局。
类别抑制某项发现的原因。它驱动下游的审查和自动化流程。
状态发现相对于其 SLA 的状态:处于宽限期内、已逾期或已被抑制。当变更请求尚在处理中时,会显示待处理抑制的指示器。

常见模式

基于软件包的抑制支持多种工作流。以下是一些常见模式:

  • 针对来自单个软件包的所有漏洞。 通过 PURL 匹配该软件包，并使用涵盖所有严重性等级的漏洞匹配器，从而在您的范围内抑制该软件包中当前和未来的 CVE。
  • 仅针对来自特定操作系统供应商的漏洞。 使用 软件包命名空间 URL 匹配器来匹配在该供应商的命名空间下发布的所有软件包，从而使该规则仅适用于该供应商的软件包。
  • 自动抑制没有可用修复的漏洞。 使用 按属性匹配 并选择 Not fixed 和 Won't fix 修复状态，这样没有可用修复的发现项就不会导致您的 Release 被召回。
  • 自动抑制低于特定严重性等级的漏洞。 使用 按属性匹配 并仅选择较低的严重性等级，从而在您的范围内抑制低风险的发现项。

PURL 软件包

软件包是由 软件包 URL标识的软件组件，通常缩写为 PURL。PURL 的格式为 pkg:type/namespace/name，例如 pkg:rpm/redhat/perl-overload 或 pkg:golang/golang.org/x/sys。

其中的 type 表示打包生态系统，例如 rpm、 deb、 golang、 npm或 maven。生态系统是软件包标识的一部分，因此 pkg:rpm/redhat/coreutils 和 pkg:deb/ubuntu/coreutils 会被视为不同的软件包，即使它们同名。软件包可以来自镜像的操作系统层，也可以来自该层之外。

其中的 namespace 是在其生态系统中对软件包进行分组的前缀，例如 OS 软件包的操作系统供应商，或语言软件包的模块路径。在 pkg:rpm/redhat/perl-overload中，命名空间为 redhat；而在 pkg:golang/golang.org/x/sys中，命名空间为 golang.org/x。命名空间是软件包标识的一部分，因此 pkg:rpm/redhat/coreutils 和 pkg:rpm/suse/coreutils 被视为不同的软件包，即使它们的类型和名称相同。有些软件包没有命名空间，在这种情况下该部分为空，例如 pkg:npm/lodash。

name 是软件包在其类型和命名空间内的自身标识符，例如 perl-overload 在 pkg:rpm/redhat/perl-overload 中，或 sys 在 pkg:golang/golang.org/x/sys中。仅凭名称本身无法标识软件包；同一名称可能出现在不同的类型和命名空间下，并指代不相关的软件。

当您通过 PURL 匹配软件包时，仅需提供 type、 namespace以及 name。请省略以下内容：

  • 版本，跟在 @ 之后（例如 @1.2.3）。
  • 限定符，跟在 ? 之后（例如 ?arch=x86_64）。
  • 子路径，跟在 #之后。

您可以通过 软件包版本匹配器 （如下所述）来单独控制版本。通过针对 type、 namespace以及 name，一条规则即可覆盖某个软件包在所有镜像和发布版本中出现的所有位置。每当该软件包中出现相关的 CVE 时，您都无需创建新的抑制。

开始之前

您需要拥有风险管理应用程序的访问权限，以及创建漏洞抑制的权限。权限在 权限 选项卡中设置，该选项卡位于 设置与配置 页面中，该页面位于 Apollo 侧边栏。请授予 审批者 角色（位于 漏洞抑制 下），以配置可审批抑制变更请求的人员。

每个抑制都会创建一个变更请求。对于每个变更请求，您都必须提供明确的理由和必填的到期日期。

创建基于软件包的抑制

规则仅在其抑制范围、软件包匹配器和漏洞匹配器全部匹配时才适用。以下步骤将逐一介绍创建表单的各个部分。

打开风险管理应用程序

选择 风险管理 ，可在 应用程序 菜单（位于左侧边栏）中找到。

打开抑制表单

导航到 漏洞 选项卡，找到您想要抑制的发现结果。或者，使用 操作 菜单（位于右上角）直接打开抑制表单。该表单也可以通过 产品发布安全 页面和 Bundle 安全 页面访问。

该 操作 菜单提供 创建漏洞抑制 和 以 CSV 格式下载所有抑制项。

选择抑制范围

在 “规则” 步骤中，选择 “范围” ，即抑制生效的范围。范围控制规则涵盖哪些 Apollo 资源。请选择能覆盖您场景的最细粒度选项。

  • 镜像仓库： 精确匹配指定的镜像仓库名称。这是默认选项，也是范围最窄的选项。
  • 产品： 匹配一个或多个产品的所选 SLS 版本。
  • SLS 发行版： 匹配一个或多个产品 ID 的 SLS 发行版。
  • 高级选项： 使用较少见的抑制范围来抑制发现结果。选择 “高级选项” 后会显示以下内容：
    • 镜像前缀： 匹配以任一指定前缀开头的镜像仓库名称。
    • 全局： 匹配组织中的所有制品。

当您选择 “镜像仓库”时，请使用 “镜像仓库” 字段来添加一个或多个仓库。移除 registry 和 tag 或 digest 后，会对仓库名称进行精确匹配。例如，输入 team/service。

选择要抑制的漏洞

在 “漏洞”下，选择 “漏洞匹配器”。您可以直接声明漏洞，也可以定义一组自动匹配漏洞的规则。漏洞必须与每个属性组都匹配；组内的值互为替代项。

显式漏洞 ID 仅匹配您指定的漏洞 ID。

使用 漏洞 ID 字段添加每个 ID。漏洞 ID 必须与扫描器报告的完全一致，例如 CVE-2024-0056。

按属性匹配 会匹配满足每个属性组的所有漏洞，让您能够覆盖具有相同特征的当前和未来 CVE。

  • 严重性： 漏洞的严重性必须为所选值之一： Critical， High， Medium， Low，或 Unspecified。
  • 来源： 漏洞的来源必须为所选软件包源类型之一： Library package 或 OS package。
  • 修复状态： 漏洞的修复可用性状态必须为所选值之一： Not fixed， Fixed，或 Won't fix。
  • 已知利用情况： 漏洞是否已知遭到积极利用，必须匹配所选值之一： Known to be actively exploited 或 Not known to be actively exploited。
  • 已排除的漏洞 ID： 您在此处添加的漏洞 ID 永远不会匹配，即使它们满足每个所选属性组也是如此。使用此选项可在原本范围较广的属性匹配中排除特定 CVE。

选择要针对的软件包

在 软件包下，定义规则针对哪个软件包。软件包必须匹配所选的名称规则、版本规则以及每个已配置的限定符。

选择 软件包名称匹配器 来控制规则识别软件包的方式：

  • 所有软件包： 匹配所有软件包。仅当漏洞和范围规则已确保抑制操作安全时，才使用此选项。
  • 软件包 URL： 通过 PURL 匹配一个或多个软件包。
  • 软件包命名空间 URL： 匹配在某个命名空间下发布的所有软件包。
  • 上游软件包名称： 通过上游软件包名称进行匹配。

选择一个 软件包版本匹配器 来控制哪些版本在范围内：

  • 所有版本： 匹配该软件包的所有版本。
  • 精确版本： 仅匹配您指定的版本。
  • SLS 版本范围： 匹配处于 SLS 版本范围内的版本。

使用 软件包限定符 通过限定符值（例如架构）进一步缩小匹配范围。

当您选择 软件包 URL时，请使用 软件包 URL 字段来添加每个 PURL。您可以匹配 PURL 软件包 ，依据 type、 namespace以及 name，并省略版本、限定符和子路径。

选择抑制类别

虽然您正在抑制发现结果，但未来的扫描仍会继续检测到它们。 抑制类别 记录了未来扫描产生相同发现结果为何是可以接受的。请选择最能说明这些发现结果应被抑制的原因。

  • 误报： 当扫描器错误地标记了您的产品中实际并不存在的漏洞时，请使用此类别。如果扫描器正确地分类了软件内容，但产品并未受到该漏洞的影响，请勿使用此类别。要将其作为误报进行抑制，请提供文档和证据，证明该漏洞是扫描器错误发现的。
  • 不予修复： 当发现结果因属于您产品的运营需求而无法或不予修复时，请使用此类别。要在此类别下进行抑制，请提供可防范该漏洞的缓解控制措施的证据。
  • 供应商依赖： 当发现结果来自某个依赖项，但上游供应商没有可用的补丁时，请使用此类别。要将其作为供应商依赖项进行抑制，请提供经研究确认不存在修复方案的证据。
  • 计划修复： 当该漏洞的修复已由供应商计划并安排发布时，请使用此类别。要将其作为计划修复进行抑制，请提供计划修复的证据，例如供应商公告的链接，或跟踪该修复问题的链接。

请参阅 抑制类别 以了解每个类别的摘要。

回答理由问卷

请回答您所选择类别对应的问卷。这些字段为必填项。撰写每个答案时，请确保安全审核人员无需再向您询问更多背景信息即可做出决定。

具体问题取决于您所选择的类别。您需要提供以下信息：

  • 无法立即进行修复的具体原因。
  • 将采取的修复措施。
  • 您的目标修复日期以及完成修复所需的步骤。抑制的过期日期应与此日期保持一致。
  • 产品架构或安全模型中存在哪些可在此期间降低被利用风险的安全缓解措施，例如网络限制、监控、防火墙、使用限制、代码库中未使用的部分，或位于身份验证保护之后。

为抑制设置 过期时间 。请从预设选项中进行选择，例如 1 周、 3 个月或 1 年，或选择 自定义日期 以自行设置。必须设置过期时间，因此不存在无限期的抑制。

验证预测的影响

在 验证 步骤中，请在提交前查看该规则将针对的发现项。这就是您正在创建的抑制的预测影响。

该表格列出了每个匹配的发现项及其 CVE、该发现项所在的 版本 ，以及 包 由其 PURL 标识。在提交变更请求之前，请使用此视图确认规则符合您的预期。

审查抑制放置位置

在 “放置” 步骤中，Apollo 会建议每条新规则的添加位置。根据您指定的规则，Apollo 会建议将规则添加到现有抑制中，或创建新的抑制。在提交变更请求之前，请审查每条规则的放置位置。

  • 抑制 ID： 系统根据所选规则为该抑制建议的标识符。您可以对其进行修改。
  • 描述： 关于该抑制所涵盖内容的建议描述。您可以对其进行修改。
  • 为所有“创建新抑制”的规则使用同一个抑制 ID 和描述： 为每条创建新抑制的规则统一应用同一个 ID 和描述。

每个抑制都在各自的变更请求中进行修改，因此将规则合并到更少的抑制中意味着需要审批的请求更少。

提交变更请求

提交变更请求时，Apollo 会为每个抑制创建一个请求。每个请求都必须单独进行审查和批准。

每个变更请求都需经过安全审核人员的审核。请求一经批准，相应发现项将在下次扫描时转为“已抑制”状态。如果请求被拒绝，该发现项将保留在您的列表中，以便重新浮现，供您处理。

抑制范围

范围控制抑制适用于哪些 Apollo 资源。请选择能够覆盖您情况的最细粒度选项。

范围覆盖内容
镜像仓库精确匹配指定的镜像仓库名称。这是默认选项，也是范围最窄的选项。
产品匹配一个或多个产品的所选 SLS 版本。
SLS 发行版匹配一个或多个产品 ID 的 SLS 发行版。
镜像前缀匹配以任一指定前缀开头的镜像仓库名称。可在 高级选项中使用。
全局匹配组织中的所有制品。仅当软件包范围本身已足以确保抑制安全时才使用此选项，并预期会受到更严格的审查。可在 高级选项中使用。

范围不会改变由谁审批请求或请求的路由方式，但会改变审核人员所权衡的风险大小。

抑制类别

类别记录了抑制发现项的原因，并会驱动下游的审查和自动化。请选择与您情况相符的类别。

类别适用场景
误报扫描器错误地标记了您的产品中实际并不存在的漏洞。需要提供文档和证据，证明该漏洞属于误报。
不予修复由于某项发现是您产品运营所必需的，因此无法或不会对其进行修复。需要提供能够防范该漏洞的缓解控制措施的证据。
供应商依赖某项发现源自某个依赖项，但上游供应商没有可用补丁。需要提供研究证据，证明没有修复方案。
已计划修复该漏洞的修复方案已由供应商列入计划并安排发布。需要提供已计划修复的证据，例如供应商公告的链接或跟踪该修复的问题单。

治理与审查

每项抑制都必须通过安全变更请求进行处理。要让审查顺利进行，以下两点最为重要：

  • 每个请求都必须附有清晰的理由说明。理由含糊的请求将被退回修改。
  • 每项抑制都必须设置过期时间。 过期 日期为必填项，因此任何抑制都不会无限期有效。
