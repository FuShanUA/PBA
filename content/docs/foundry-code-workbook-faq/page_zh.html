我可以轻松地将我的所有工作从一个工作簿移动到另一个工作簿吗？

可以。您可以在工作簿之间复制粘贴节点（工作簿图中的元素）。

  1. 按住 Ctrl 的同时选择您想从一个工作簿中复制的节点。不支持复制粘贴 Contour 看板节点。
  2. 使用右键上下文菜单复制所选节点。
  3. 选择目标工作簿的图，然后使用组合键粘贴节点 Cmd+V （macOS）或 Ctrl+V （Windows）。新节点将被导入到您的新工作簿中。

我可以将转换节点设置为变量吗？

不可以。代码工作簿图上的每个转换节点都必须返回一个表或数据框（例如带有列的二维数据结构）。

返回顶部

为什么每个转换节点都需要返回一个表或数据框？

Foundry 中产物的原子单位是数据集。每个转换节点都需要返回一个表或数据框（例如带有列的二维数据结构），以便每个节点都可以注册为 Foundry 数据集，从而在整个 Foundry 的其余部分中使用。此外，Code Workbook 中的表或数据框必须以有效的 schema 返回，这样才能生成数据集（例如，至少存在一列、列名不重复、列名不包含无效字符等）。

初始化我的环境需要多长时间？

Code Workbook 的默认配置平均初始化时间为 3-5 分钟。但是，如果您在 Code Workbook 配置文件中添加了额外的软件包，初始化时间可能需要 20-30 分钟，具体取决于这些软件包的复杂性和相互依赖关系。随着环境中软件包数量的增加，初始化时间往往会显著增加。

初始化缓慢通常表明环境定义过大或过于复杂。初始化时间往往会随环境中软件包数量的增加而呈超线性增长，因此您可能需要简化任何自定义环境。在某些情况下，Code Workbook 可能会预初始化常用环境以加快初始化速度。如果您基于默认配置文件创建了自定义环境，初始化时间较慢可能是由于缺少预初始化。了解更多关于 优化自定义环境初始化时间

如果浏览器标签页超过 30 分钟不活动，环境可能会因不活动而丢失。

如何恢复我之前从 Code Workbook 中删除的代码？

如果这些转换已构建到数据集中，您可以使用 比较 生成的数据集预览的功能来查看当时的代码。然后您可以从那里复制粘贴相关的转换。遗憾的是，如果该代码位于中间转换中，则无法恢复。

Code Workbook 是一个比 Code Repositories 更具迭代性的平台，后者具有完整的 git 提交和发布功能。如果您有其他可用的分支，我们建议您检查这些分支中是否有被删除的转换。

Spark 环境和自定义库

找不到所需的 Python 库

默认情况下，任何可用的 Python 包 Conda Forge ↗ 都可以添加到您工作簿的自定义环境中。如果该 Python 库包含在 Conda Forge 中，那么您可以直接自定义环境以将其包含在内。

要进行故障排除，请执行以下步骤：

  1. 选择 Environment > Customize Environment 在右上角。
  2. 搜索所需的库并添加 自动 （这将采用升级版本，但如果模块升级，可能会使您容易受到意外中断的影响）或该库的特定版本。
  3. 选择 更新 Spark 环境.

环境重新加载可能需要一段时间，而且使用自定义环境通常会比使用默认环境慢，因为默认环境会保持“预热”状态，而每个自定义环境都需要从头开始启动。

返回顶部

导入 Python 库时遇到问题

有时可能需要使用 Code Workbook 中尚未提供的库。可以将这些库添加到您的可用列表中，但这需要一些手动操作。

要进行故障排除，请执行以下步骤：

  1. 确认该 Python 库不在工作簿自定义 Spark 环境列表中。
  2. 如果不存在，请评估是否有其他可用的库可以提供相同的功能。
  3. 如有必要包含此库，请联系 Palantir Support。
  4. 该库可用后，您可以参考之前的故障排除步骤来添加库。

创建环境失败

我正在尝试更新我的工作簿环境，它显示“Waiting for Spark / Initializing environment”一段时间，然后报错并显示“Failed to create environment”消息。

要进行故障排除，请执行以下步骤：

  1. 确认是否对工作簿的 Spark 环境进行了任何自定义更新。如果有，那么您的调查应集中在添加的任何自定义库上。
  2. 确保没有将任何模块固定到特定版本。通常，使用模块的最新版本是良好的做法。
  3. 移除所有自定义库，查看 Spark 环境是否能加载。
  4. 如果某个特定库导致您的 Spark 环境无法加载，请上报给 Palantir Support。

重试器错误

运行导入包或任何基本命令时返回以下错误：“com.github.rholder.retry.RetryException: Retrying failed to complete successfully after 3 attempts. at com.github.rholder.retry.Retryer.call(Retryer.java:174)”。在工作簿中使用 Pandas 时，Code Workbook 应用程序仍会在转换之前将 Spark 数据框转换为 Pandas 数据框，这会在驱动程序上消耗大量内存，很可能导致 OOM。

要进行故障排除，请执行以下步骤：

  1. 验证您的转换单元格是否正在使用 Pandas，以及此问题是否出现在专门运行 Pandas 的代码中。
  2. 如果此计算可以在 Spark 中完成，我们强烈建议重新配置您的代码以使用 Spark，因为它具有并行性且可扩展性更强。
  3. 当此计算必须在驱动程序上执行时，作为最后的手段，我们建议使用增加驱动程序内存的配置文件。

保存为数据集失败

此问题可能由多种原因引起，但最常见的情况是返回包含有效 schema 的表或数据框。如果以下步骤均无法帮助您识别所遇到的特定错误，请参考我们关于 构建和检查错误的指南.

要进行故障排除，请执行以下步骤：

  1. 确保转换节点返回的是表或数据框。
  2. 确认表或数据框符合作为数据集写入 Foundry 的基本要求，例如：
    1. 至少有一列。
    2. 所有列名均有效（例如不包含空格或无效字符）。
    3. 没有重复的列名。
  3. 如果您确信此转换节点应该能够写出到数据集，请尝试运行另一个转换节点或构建一个新的、非常简单的转换节点。
    1. 这可以帮助确定问题是本地问题（例如该特定转换节点发生了意外情况）还是更系统性的问题（例如转换节点总体上无法保存到 Foundry）。
    2. 如果是本地问题，请继续调试用于创建此表 / dataframe 的代码。
    3. 如果是系统性问题，请将该问题上报给 Palantir Support，并提供您调查中的所有相关信息。

更新输入数据集预览后，工作簿未自动重新计算

当选择 更新表预览 （用于输入表）时，仅会更新输入数据集的视图，Foundry 中的底层数据集不会自动刷新。

要进行故障排除，请执行以下步骤：

  1. 如果在选择 更新表预览 （用于输入表）后输入数据集仍未刷新，则：
    • 打开这些数据集，查看它们是否一直构建失败。
    • 如果输入数据集一直构建失败，那么这就可以解释为什么您在 workbook 中看不到任何更新的信息。请从这里继续调试。
    • 如果输入数据集按预期构建，但与您在 code workbook 中看到的预览不匹配，则：
      • 尝试从 code workbook 中删除该输入表，然后重新添加。
      • 如果此方法无效，且预览与实际表之间仍存在差异，请联系 Palantir Support。
  2. 如果选择 更新表预览后转换节点未更新，这是预期行为，因为它们不受此操作的影响。要更新 code workbook 中的所有转换节点，请选择 run -> run all。这将在遵守构建依赖关系的前提下运行您 code workbook 中的所有转换节点。

无法将我的分支合并到 master

当您发现无法将分支合并回 main 时，最常见的问题是 master 分支受保护。可能存在合并冲突相关的问题，但这将在另一章节中介绍。

要进行故障排除，请执行以下步骤：

  1. 确定该分支是否受保护。
  2. 如果该分支受保护，请找到其所有者并请求他们合并您的分支。
    • 对于给定的 workbook，在 master上开启分支保护，并确保您想要限制其合并分支的用户仅拥有该 Workbook 的 compass:edit 权限。
    • 在内部，Code Workbook 有四个与分支相关的权限级别： view, edit, maintain日 manage。默认情况下， compass:read 会展开为 view, compass:edit 会展开为 edit日 compass:manage 会展开为 maintain and manage.
    • 创建分支并准备合并到父分支始终只需要 edit 权限。合并到受保护的分支需要 maintain 权限。更改分支保护设置需要 manage permissions.
    • 更多信息请参阅我们的 分支概览.
  3. 如果该分支未受保护，那么您会遇到合并冲突，即存在与 master branch.
    • 中的代码冲突的非增量代码。在这些情况下，请在将您的分支合并回 master.
    • 更多信息请参阅我们的 合并分支 documentation.
  4. 如果 master 分支未受保护，也没有合并冲突，但您仍然无法将您的分支合并到 master，请联系 Palantir Support。

让单元格计算更快

假设我的数据集输入为（1000 行 * 30 列）+（100 万行 * 30 列），并且转换中包含大量窗口 / 列派生步骤，我该如何让计算运行得更快？

要进行故障排除，请执行以下步骤：

1. 重构

对于实验或快速迭代，将代码重构为多个较小的步骤而不是单个大步骤通常是一个好主意。

这样，您可以先计算上游单元格，将数据写回 Foundry，并在后续步骤中使用这些预先计算好的数据。如果您在不更改这些早期步骤逻辑的情况下反复重新计算，就会产生过多的工作量。

具体来说：

workbook_1:
  cell_A:
    work_1 : input -> df_1
      (takes 4 iterations to get right): 4 * df_1
    work_2: df_1 -> df_2
      (takes 4 iterations to get right): 4 * df_2 + 4 * df_1
        = 4 df_2 + 4 df_1
    work_3: df_2 -> df_3
      (takes 4 iterations to get right): 4 * df_3 + 4 * df_2 + 4 * df_1
  total work:
    cell_A
     = work_1 + work_2 + work_3
     = 4 * df_1 + (4 * df_2 + 4 * df_1) + (4 * df_3 + 4 * df_2 + 4 * df_1)
     = 12 * df_1 + 8 * df_2 + 4 * df_3

相反，如果您将 work_1 和 work_2 写入各自的单元格中，您执行的工作将如下所示：

workbook_2:
  cell_A:
    work_1: input -> df_1
      (takes 4 iterations to get right): 4 * df_1
  cell_B:
    work_2: df_1 -> df_2
      (takes 4 iterations to get right): 4 * df_2
  cell_C:
    work:3: df_2 -> df_3
      (takes 4 iterations to get right): 4 * df_3
  total_work:
    cell_A + cell_B + cell_C
       = work_1 + work_2 + work_3
       = 4 * df_1 + 4 * df_2 + 4 * df_3

如果您假设 df_1、df_2 和 df_3 的计算成本相同， workbook_1.total_work = 24 * df_1，而 workbook_2.total_work = 12 * df_1，因此您可以预期在迭代时获得接近 2 倍的速度提升。

2. 缓存

对于任何“小”数据集，您应该通过选择工作簿，然后选择来对其进行缓存 Actions > Cache.

这会将行保留在工作簿的内存中，而无需从写回的数据集中获取。“小”是一个基于多个必须考虑因素的任意判断，但 Code Workbook 会尽力进行缓存，并在数据集过大时向您发出警告。

3. 函数调用

您应该尽可能坚持使用原生 PySpark 方法，切勿直接在数据上使用 Python 方法（例如循环遍历单个行、执行 UDF）。PySpark 方法调用以 Scala 编写的底层 Spark 方法，并直接针对数据运行，而不是在 Python 运行时中运行；如果您仅将 Python 用作与此系统交互的层，而不是作为与数据交互的系统，您将获得 Spark 本身的所有性能优势。

4. 降采样

如果您能够从大型输入数据集中派生出自己的准确样本，则可以将其用作转换的模拟输入，直到您完善了逻辑并希望针对完整数据集进行测试为止。

在编写任何一行 PySpark 代码之前，请考虑对超过一百万行的数据集进行降采样和缓存；这样您可能会获得更快的周转时间，而不会因数据集过大而缓慢地发现语法错误。

5. 总结

一个良好的 Code Workbook 如下所示：

  • 离散的代码块，用于执行您期望稍后重用但不需要反复重新计算的特定物化操作。
  • 降采样至“小”尺寸。
  • 缓存的“小”数据集，可实现非常快速的获取。
  • 仅使用利用快速底层 Spark 库的原生 PySpark 代码。
