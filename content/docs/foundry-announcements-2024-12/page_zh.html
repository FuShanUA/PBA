语义搜索 KNN 联接现已在管道构建器中推出

发布日期：2024-12-19

KNN 联接 现已在管道构建器中面向所有租户推出。这一强大功能使您能够为左侧数据集中的每一行从右侧数据集中找出最邻近的 K 行，让您的数据合并任务更加高效、准确。

什么是 KNN 联接？

KNN（K 最近邻） 是一种根据相似度来匹配和合并两个数据集中各行的方法。设想您有两个条目列表，并且想要找出其中一个列表中与另一个列表中的条目最相似的条目。KNN 联接的做法是将一个列表中的每个条目与另一个列表中的所有条目进行比较，并找出最接近的匹配项。

要使用该功能，请选择 联接 面板，然后选择 KNN 联接 作为 联接类型。以下屏幕截图展示了选择 KNN 联接类型的示例：

配置为基于每部电影关键词的相似度获取最接近的三部电影的 KNN 面板。

时间序列警报自动化功能介绍 [GA]

发布日期：2024-12-10

我们很高兴与大家分享：您现在可以配置自动化，在时间序列数据满足特定条件时发送警报（即“事件”）。借助时间序列警报功能，您可以随时掌握组织内关键工作流的动态，例如了解机器压力何时超过设定限值，或产量何时低于预期结果。

要开始使用时间序列警报，您首先需要使用 Quiver 中的 时间序列搜索 卡片在时间序列数据中识别感兴趣的时段。然后，时间序列搜索背后的逻辑将被保存，并在同类型的对象之间复制，此操作使用 Automate。当您配置的告警自动化运行时，任何新识别出的时间间隔都将作为对象输出到预配置的警报对象类型中。

时间序列告警功能将于 2024 年 12 月 16 日当周正式发布。

时间序列条件逻辑位于 Automate 应用中。

为什么我应该使用 Quiver 和 Automate 进行时间序列告警？

您的自动化首次运行时，将检查整个时间序列是否存在警报。此后，它将仅检查新数据。换言之，此产品默认以增量方式运行。这与 Foundry Rules 和 FoundryTS 都不同，后两者每次运行时都会检查整个时间序列是否存在警报。因此，将 Quiver 与 Automate 结合用于时间序列告警，将比之前的那些解决方案性能更高、成本更低。

时间序列告警的下一步是什么？

时间序列告警自动化并非实时解决方案。尽管可以对由流支撑的时间序列上的搜索逻辑进行自动化，但这些自动化并不会直接在流式数据之上运行，而是在 归档数据集。这会产生至少 10 分钟的额外延迟，因为归档作业每 10 分钟运行一次。我们的团队将在未来几个月专注于构建实时告警解决方案。

在我们的文档中详细了解时间序列告警自动化。

发起访问请求比以往更加便捷，组属性和描述现在可在请求工作流中查看。

请求工作流的关键改进

当平台中的项目包含许多组时，在请求访问权限时可能难以确定应选择哪个组。以下一些新功能可帮助您配置更好的请求体验，并更透明地了解组的详细信息：

  • 组描述（如果已设置）现在会显示在请求流程中组名称的下方。
  • 现在可以为组配置属性，以便筛选可供选择的组。例如，您可以添加 Role 属性添加到组中，以便您可以筛选出具有特定权限的组。如需详细了解如何设置组属性，请参阅我们的 文档。
  • 现在会自动向请求创建者发送电子邮件通知。这些通知是可选的，您可以选择 在需要时退出接收。

改进后的 请求访问权限 对话框，新增了组描述和筛选支持功能。

审核工作流的关键改进

访问请求审核者现在可以从以下可读性和易用性改进中受益，这些改进有助于高效处理请求：

  • 现在，撤销误批准的访问请求变得容易得多。如果您是请求审批者，现在可以使用新的 还原 选项（在每个子任务上可用）。



    该 还原 选项在已批准的标记访问请求上可用。

  • 请求审核者不再需要导航至 平台设置 来查看用户所属的组。现在,审阅者可以直接查看请求中引用的组,以及发起请求的用户所属的组。



    打开的访问请求,弹出窗口显示该用户当前所属的组。

Pipeline Builder 现已支持伪代码渲染

发布日期：2024-12-10

从今天开始，您可以使用伪代码转换渲染来提升管道的可读性体验。

什么是伪代码？

伪代码是一种以通俗语言记录算法或流程步骤的简化方式。它看起来有点像代码，但不遵循特定编程语言的语法，因此更易于阅读和理解。

伪代码具有以下优势：

  • 提升可读性： 您现在可以选择以更简洁的伪代码格式显示您的转换，对于熟悉或偏好这种逻辑表示方式的用户而言，这样更容易理解其中的逻辑。
  • 自动适应屏幕： 伪代码会自动调整以适应您的屏幕，因此您无需担心无休止的滚动。

管道构建器图中新增的伪代码视图选项，展示了在调整屏幕宽度时自动进行的布局调整。

您可以在 设置 下的 用户偏好 中开启此偏好，也可以在任意转换路径中使用 </> 图标来开启。

请注意,启用伪代码并不会提供向管道构建器中编写代码的方法,也不会影响 diff 视图、连接、联合或 LLM 节点。该功能旨在提供有关每个转换所执行操作的更完整摘要,以便于快速浏览和理解。

Workshop 中对双向 iframe 小组件的支持 （通过 iframe 嵌入基于 OSDK 构建的应用程序或外部 Web 应用程序来实现）现已可在 Workshop 中使用，方法是使用一个 插件 ↗ 该插件便于与 Workshop 进行双向通信。双向通信的功能包括：

推出无服务器 Python 函数支持 [Beta]

发布日期:2024-12-03

Foundry 中对 Python 函数的无服务器支持现已进入 Beta 阶段。与 TypeScript 一样，只要您标记并发布了函数仓库，即可运行 Python 函数，无需任何额外设置。使用无服务器后端的 Python 函数将可在 Workshop、Actions 以及当前可以使用 TypeScript 函数的任何其他位置中使用。这一全新的高性能后端无需任何设置或用户管理的资源即可运行函数。

无服务器 Python 目前以 Beta 版本提供，并正在陆续启用。您可以按照下方截图所示，在 Ontology Manager 中导航至您的函数，以验证是否已启用无服务器选项。

在无服务器 和已部署函数支持之间进行选择，适用于您现有的 函数（在 Ontology Manager 中）。

如果您的注册环境中尚未提供无服务器选项，请联系 Palantir 支持团队以启用该功能。

启用后，在您完成打标签和发布操作后，所有新的函数仓库将默认使用无服务器后端。无需进行其他任何配置或设置。您可以在 Palantir 的 Python 文档中详细了解 Python 函数。 您还可以在 Ontology Manager 中，将使用 "deployed" 后端的现有 Python 函数切换为无服务器模式。

我们通常推荐使用无服务器模式，并且在已启用该功能的环境中，它是默认选择。为帮助您考虑选用哪种模式，请查看以下指南。

已部署函数具有以下无服务器函数所不具备的功能：

  • 支持 外部数据源。
  • 鉴于已部署函数具有长期运行的特点，如果函数能够容忍重启，则可能实现本地缓存。

已部署函数存在一些不适用于无服务器执行的限制：

  • 可以按需执行单个函数的不同版本，从而使升级更加安全。而部署函数一次只能运行一个函数版本。
  • 只要部署处于运行状态，部署函数就会持续产生成本，而无服务器函数仅在执行时才会产生成本。
  • 与基础设施由系统自动管理的无服务器函数相比，部署函数需要更多的前期设置和长期管理。
  • 函数的执行环境是为每次新执行而创建的，因此执行之间不会意外共享任何状态。

要详细了解功能上的差异，请查看以下相关文档页面：

  • 无服务器函数
  • 部署函数
