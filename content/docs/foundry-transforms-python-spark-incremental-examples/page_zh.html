追加

仅追加型增量计算是指这样一类计算：其中新增的输出行仅是新增的输入行的函数。这意味着，为了计算其输出，转换会执行以下操作：

  • 查看任何新增的输入数据，
  • 计算任何新的输出行——这些行仅是这些新增输入行的函数，以及
  • 将新的输出追加到现有输出中。

更改列类型、将日期格式化为字符串以及筛选都是仅追加型计算的示例。在这些示例中，每个新增的输入行都会被转换或删除，以生成输出行。

请注意，使仅追加转换成为增量转换的唯一区别是 incremental() 装饰器。

以增量方式运行时，默认读取模式为 added ，表示转换仅读取新的学生数据，而默认写入模式为 modify ，表示转换仅将筛选后的新学生数据追加到输出中。

以非增量方式运行时，默认读取模式为 added ，表示转换读取完整输入，而默认写入模式为 replace ，表示转换将输出替换为筛选后的全部学生数据。

合并与追加

有时，转换需要引用其先前的输出，以便以增量方式计算更新。这方面的一个示例是 distinct() ↗ 方法。 要在转换中删除重复行（假设当前输出正确），转换必须对输入中的任何新行进行去重，然后检查这些行是否已存在于输出中。

@incremental()
@transform(
    students=Input('/examples/students_hair_eye_color'),
    processed=Output('/examples/hair_eye_color_processed')
)
def incremental_distinct(students, processed):
    new_students_df = students.dataframe()
    processed.write_dataframe(
        new_students_df.distinct().subtract(
            processed.dataframe('previous', schema=new_students_df.schema)
        )
    )

这里，我们使用了 previous 读取模式来读取输出数据集。这将返回 DataFrame ↗ ，即上一次构建期间输出的数据。由于可能不存在 previous 输出，我们必须向 dataframe('previous') 调用提供 schema，以便能够正确构造空的 DataFrame。

from pyspark.sql import functions as F

@incremental()
@transform(
    students=Input('/examples/students_hair_eye_color'),
    processed=Output('/examples/hair_eye_color_processed')
)
def incremental_group_by(students, processed):
    # Compute the hair color counts for only the new students.
    new_hair_counts_df = students.dataframe().groupBy('hair').count()

    # Union with the old counts
    out_schema = new_hair_counts_df.schema
    all_counts_df = new_hair_counts_df.union(
        processed.dataframe('previous', schema=out_schema)
    )

    # Group by hair color, summing the two sets of counts.
    totals_df = all_counts_df.groupBy('hair').agg(F.sum('count').alias('count'))

    # To fully replace the output, we always set the output mode to 'replace'.
    processed.set_mode('replace')
    processed.write_dataframe(totals_df.select(out_schema.fieldNames()))

同样,由于有可能没有 previous 输出,我们必须为该 dataframe('previous') 调用提供模式,以便能够正确构建空的 DataFrame。

模式不同时的合并与追加

有时,增量转换需要根据添加到无模式输入数据集中的文件创建一个 Spark DataFrame,然后将该 DataFrame 的内容追加到输出中。对于此类转换,有两种实现模式。

  • 静态指定预期模式,并强制要求生成的 DataFrame 具有该模式(通过忽略输入数据中的额外字段、为输入数据中缺失的字段填充空值等方式)。

  • 动态捕获输入数据中存在的任何字段。

对于动态捕获这种实现模式,必须确保追加到输出的 DataFrame 的模式是 兼容的 与现有输出兼容。若要使模式与现有输出兼容，必须满足以下条件：

  • 新数据中与现有输出中的列同名的列，其类型也必须相同。

  • 现有输出中的所有列都必须存在于新数据中。

  • 新数据中不存在名称与现有数据中的列仅大小写不同的列；例如，新数据中不能存在列 Value ，前提是现有数据中已经存在列 value 。

为了确保满足这些条件，需要动态检查现有数据的模式，这意味着调用 dataframe('previous') 时不指定模式。只要转换以增量方式运行，就支持此做法。

from functools import reduce

from pyspark.sql import functions as F
from transforms.api import transform, incremental, Input, Output
from transforms.verbs.dataframes import sanitize_schema_for_parquet


@incremental()
@transform(
    csvs=Input('/examples/dataset_of_csvs'),
    parsed=Output('/examples/parsed_csvs')
)
def incremental_read_csv(ctx, csvs, parsed):
    input_fs = csvs.filesystem()

    def process_file(f):
        df = (
            ctx.spark_session.read
            # Set inferSchema to False so that every column is a string
            # This prevents issues due to inconsistent inference results between files,
            # both within and across incremental builds.
            .option("inferSchema", False)
            .option("header", True)
            .csv(input_fs.hadoop_path + "/" + f)
        )
        sanitized = sanitize_schema_for_parquet(df)

        # Make all columns lowercase to prevent issues due to inconsistent casing
        # between files, both within and across incremental builds.
        # Note that this logic does not handle the situation
        # where a single file contains columns differing only in case.
        return sanitized.select(*(F.col(a).alias(a.lower()) for a in sanitized.columns))

    dfs = [process_file(f.path) for f in input_fs.ls()]

    if len(dfs) == 0:
        parsed.abort()
        return

    df = reduce(
        lambda a, b: a.unionByName(b, allowMissingColumns=True),
        dfs[1:],
        dfs[0],
    )

    if not ctx.is_incremental:
        parsed.write_dataframe(df)
    else:
        existing_columns = parsed.dataframe("previous").columns
        columns_in_new_data = set(df.columns)
        resolved_schema_df = df.select(
            *df.columns,
            *(
                F.lit(None).cast("string").alias(col)
                for col in existing_columns
                if col not in columns_in_new_data
            )
        )
        parsed.write_dataframe(resolved_schema_df)

利用增量转换连接大型数据集

假设您有两个表—— Orders （由客户提交）和 Deliveries （已完成）——而您想要计算一个表 DeliveryDuration ，其中包含物品送达所需的时间。尽管 Orders 和 Deliveries 表只会追加新行，且绝不会有任何行被修改，则对这两个增量数据集进行简单连接是行不通的。例如， Orders 表可能包含 orderIds ，它们尚未出现在 Deliveries 表中。

Orders:                               Deliveries:
+---------+---------------+           +---------+--------------+           +---------+------------------+
| orderId | submittedDate |           | orderId | deliveryDate |           | orderId | deliveryDuration |
+---------+---------------+           +---------+--------------+   ---->   +---------+------------------+
| 1001    | 2019-08-21    |  join on  | 1001    | 2019-08-23   |           | 1001    | 2                |
+---------+---------------+  orderId  +---------+--------------+           +---------+------------------+
| 1002    | 2019-08-22    |
+---------+---------------+
| 1003    | 2019-08-23    |
+---------+---------------+

假设 orderId 在 Orders 和 Deliveries 两张表中均严格递增，我们可以检查最后一个 orderId ，即我们为其计算 deliveryDuration （maxComputedOrderId），并仅获取 Orders 和 Deliveries 表中 orderId 大于 maxComputedOrderId的行：

from transforms.api import transform, Input, Output, incremental
from pyspark.sql import types as T
from pyspark.sql import functions as F

@incremental(snapshot_inputs=['orders', 'deliveries'])
@transform(
    orders=Input('/example/Orders'),
    deliveries=Input('/example/Deliveries'),
    delivery_duration=Output('/example/New_Delivery_Date')
)
def compute_delivery_duration(orders, deliveries, delivery_duration):
    def to_fields(datatype, names, nullable=True):
        return [T.StructField(n, datatype, nullable) for n in names]

    # Generate a schema to pass for deliveryDuration
    fields = to_fields(T.IntegerType(), ['orderId', 'deliveryDuration'])

    # Explicitly define the schema as you can't refer to the previous version schema
    maxComputedOrderId = (
        delivery_duration
        .dataframe('previous', schema=T.StructType(fields))
        .groupby()
        .max('orderId')
        .collect()[0][0]
    )

    # At first iteration, maxComputedOrderId is empty because delivery_duration dataset doesn't exist yet
    if maxComputedOrderId == None:
        maxComputedOrderId = 0

    ordersNotProcessed = orders.dataframe().filter(F.col('orderId') > maxComputedOrderId)
    deliveriesNotProcessed = deliveries.dataframe().filter(F.col('orderId') > maxComputedOrderId)

    newDurations = (
        ordersNotProcessed
        .join(deliveriesNotProcessed, 'orderId', how='left')
        .withColumn('deliveryDuration', F.datediff(F.col('deliveryDate'), F.col('submittedDate')))
        .drop(*['submittedDate', 'deliveryDate'])
    )

    delivery_duration.write_dataframe(newDurations)

处理 schema 或逻辑变更

假设我们希望从现在开始向增量数据集添加另一列。向输出添加另一列不会使 is_incremental 标志失效，因此下一次运行将计算新行并写入包含新列的数据，而该列在之前写入的所有行中都将为 null。

然而，我们可能也希望为之前的行填充该列。提高转换的 semantic_version 将使其以非增量方式运行一次，而如果您使用的是 “added” 读取模式，输入将包含所有数据，使您能够对其进行重新计算并添加新列。

如果您的转换一直在基于快照输入创建 历史数据集，那么情况就会变得稍微复杂一些，因为之前的数据位于输入上的一堆快照事务中。在这种情况下，请联系您的 Palantir 代表。

在本示例中，我们讨论了添加新列，但上述推理适用于各种逻辑变更。

在分支上开发增量代码

创建一个新分支并在其上运行构建时，将以增量方式运行构建。简而言之，您创建分支时所基于的原始分支上最后提交的事务，将被视为新分支上首次构建的上一个事务。

示例总结

我们了解了如何通过以下方式增量处理数据：

  • 获取新增的行，对其进行处理并将其追加到输出中，
  • 获取新增的行，根据输出中已有的行对其进行过滤，然后将其追加到输出中
  • 获取新增的行，基于新行和输出中已有的行计算聚合，并用新的聚合统计数据替换输出
  • 利用增量转换连接大型数据集

我们还探讨了如何：

  • 处理增量转换的架构或逻辑变更
  • 在分支上开发增量代码，而无需基于输入的完整内容重新构建

如果输入数据集已积累了大量事务，或者以 SNAPSHOT 模式运行，请设置 事务限制 来约束每个作业读取的数据量。详情请参阅 限制增量输入的批量大小。

增量 Python 错误

要理解增量错误，先了解以下概念会更容易，有时甚至是必要的： 事务 和 数据集视图。

Catalog 事务错误

有用的背景信息

当作业以增量方式运行时，其增量输入数据集仅由未处理的事务范围组成，而非完整的数据集视图。

假设某个数据集的事务历史如下：

SNAPSHOT (1) --> UPDATE (2) --> UPDATE (3) --> UPDATE (4) --> UPDATE (5)
                                   |
                       Last processed transaction

上次构建该数据集时，最新的事务是 (3)。此后，事务 (4) 和 (5) 已提交，因此未处理的事务范围是 (4) — (5)。

该数据集 视图 是事务范围 (1) — (5)。位于视图“顶部”（即最新）的事务有时被称为分支的 HEAD （同样是与 git 类比）。就像在 git 中一样，分支是指向事务的指针，因此我们说该分支 指向 于事务 (5)。多个分支可以指向多个事务，且分支之间可能共享事务历史：

SNAPSHOT (1) ─> UPDATE (2) ─> UPDATE (3) ─> UPDATE (4) ─> UPDATE (5)     [develop]
                                 |
                                 └─> UPDATE                              [feature-branch]

错误： Catalog:TransactionsNotInView

为了使作业能够增量运行，会在作业开始时执行一系列检查。 其中一项检查会验证未处理事务范围是否为严格增量（即仅追加的文件更改，参见 增量计算的要求）。它通过比较未处理事务范围和已处理事务范围中的文件来实现这一点。

但是，如果分支的 HEAD 已被移动，增量作业现在处于不一致状态：比较这两个范围已不再有意义，因此，一个错误 Catalog:TransactionNotInView 会被抛出。

请参见下图，了解此错误可能如何发生：

SNAPSHOT (1) ─> UPDATE (2) ─> UPDATE (3)      ─> UPDATE (4) ─> UPDATE (5)
                   |          (last processed                  (branch's previous
                   |            transaction)                     HEAD, now orphan)
                   |
                   └─> UPDATE (6) --> UPDATE (7, branch's current HEAD)

这里，已处理事务范围为 (1) — (5)，当前分支的 HEAD 指向 (7)，当前视图由事务 (1)、(2)、(6) 和 (7) 组成。

这是一种不一致的状态，因为并非所有已处理的事务都位于分支 HEAD 的上游：事实上 (3) 并不在其中。换句话说，之前的 HEAD (3) 已不再是当前视图的一部分，这就是为什么 Catalog:TransactionNotInView 会被抛出。

错误： Catalog:InconsistentBranchesOrder

另一个可能被抛出的 Catalog 错误是 Catalog:InconsistentBranchesOrder，当最后处理的事务（prevTransaction）大于分支的 HEAD（endTransaction）时。如果数据集的 HEAD 被移动到早于上一个事务的某个事务，则可能会发生这种情况。

请参阅下方图示，了解此错误是如何发生的：

SNAPSHOT (1) --> UPDATE (2) --> UPDATE (3) --> UPDATE (4) --> UPDATE (5)
                                   |                             |
                               Current HEAD            Last processed transaction

错误修复

分支的 HEAD 可能因以下两个原因而发生变化：

  • 用户有意使用 Catalog 端点更新了分支的 HEAD。
  • 某些事务不是通过转换作业提交的。例如，在 Code Workbook 中合并分支时，数据集也会被“合并”。
  • 但是， Code Workbook 数据集上的事务始终 SNAPSHOT，因此不会导致不一致的状态。

要修复此问题，您需要执行以下任一操作：

  • 以快照方式运行转换；例如，通过提升语义版本号。这将开启新的数据集视图，从而重置上述增量检查。
  • 手动更新分支的 HEAD，使其指向已处理范围之后的事务。使用 updateBranch2 端点，并将最后处理的事务作为 parentRef。只有经验丰富的用户才应使用此端点。
