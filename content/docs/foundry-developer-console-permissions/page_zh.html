权限

本节介绍了使用 Developer Console 和 OSDK 所需的各种权限。这些角色和权限可以在 角色 部分中进行管理，该部分位于 Foundry Settings中。

用户权限

Beta

Compass 管理的用户权限正处于 beta 开发阶段。此功能适用于启用了 基于分类的访问控制 (CBAC) 的注册环境，也可能适用于其他注册环境。

请参阅 用户权限 [旧版] （如果你的注册环境不支持 Compass 管理的用户权限）。

你在 Developer Console 中创建的应用程序会自动继承权限，例如由 角色、 标记或 组织强制实施的权限，这些权限来自其父级 项目或文件夹。

如果你的项目使用默认角色集，那么 Developer Console 应用程序用户可能具有以下角色之一，这些角色完全可配置：

  • Viewer： 可以查看应用程序详细信息；如果应用程序 托管在 Foundry 上，还可以查看其托管的网站，并使用生成的 OSDK 开发应用程序。 Viewer 无法编辑应用程序信息、添加或修改实体，也无法生成新版本的 OSDK。
  • Editor： 可以编辑应用程序信息和 OAuth 参数、添加或修改实体，并生成新版本的 OSDK。
  • Owner： 权限等同于 Editor，并且可以与其他开发者共享该应用程序。

只有当您至少拥有对应用程序执行 查看应用程序配置 (third-party-application:view-application-config) 操作的权限时，该应用程序才会显示在 Developer Console 主页列表中，该权限默认通过 Viewer 角色授予。

OSDK 应用程序中由 LMS 支撑的函数

对于通过操作调用由 Language Model Service (LMS) 支撑的逻辑函数的 OSDK 前端应用程序，已登录用户必须至少拥有对 Developer Console 应用程序的 Viewer 权限。如果没有此权限，LanguageModelService 将返回 PERMISSION_DENIED 或 missing can:attribute 错误。此要求仅适用于 OSDK 前端应用程序——在 Object Explorer 或 Workshop 中执行时，相同的操作可能可以正常运行，因为这些环境中适用不同的权限流程。

关联的 OAuth 客户端

Developer Console 始终会将自定义应用程序关联到 OAuth 客户端，您可以在组织级别通过 Control Panel对其进行管理。要更改 OAuth 客户端的身份验证设置，您必须有权访问 启用第三方应用程序 和 管理第三方应用程序密钥等工作流，这些权限通常通过 Third-party application administrator 角色授予，该角色位于 Control Panel 的 组织权限 扩展中。此角色还授予您创建关联的 OAuth 客户端的能力，而这是 在 Developer Console 中创建自定义应用程序所必需的。

您还可以按客户端逐个管理 OAuth 客户端，具体可在 共享与令牌 部分（位于您的 Developer Console 应用程序中）进行，并使用 OAuth2 client 角色上下文。例如，您可以配置一个自定义角色，使其仅包含 轮换第三方应用程序客户端密钥 (multipass:rotate-client-secret) 操作，并将该角色授予仅需为特定应用程序轮换客户端密钥的用户。

请使用 管理 OAuth 客户端 选项卡（位于 共享与令牌 部分），在编辑您的应用程序时与组织、用户和组共享该客户端。

关联的 OAuth 客户端权限未来可能会与应用程序权限合并。

委派应用程序管理

您可能希望允许用户创建和管理自己的 Developer Console 应用程序，而不授予他们对组织中所有 OAuth 客户端的广泛第三方应用程序管理员权限。为此：

  1. 创建自定义角色集 此类角色集仅授予与 Developer Console 相关的权限（例如 third-party-application:create-application 和 third-party-application:view-application-config），同时不授予更广泛的 OAuth 客户端管理权限，例如 Manage OAuth 2.0 clients。
  2. 代表用户创建应用程序 并通过 共享与令牌 部分将这些应用程序共享给他们。这样，用户便只能管理其被授予访问权限的特定应用程序。

创建应用程序

要创建新应用，您需要：

  • 创建应用 (third-party-application:create-application)操作权限（针对所选文件夹），默认通过 Owner 或 Editor 角色授予。
  • 创建第三方应用 工作流（针对所选组织），通常通过 Third-party application administrator 角色（在 Control Panel 中）授予 ，如上文所述。

网站托管

  • 要查看托管在 Foundry 上的网站，您必须具备 查看应用网站 (third-party-application:view-application-website)操作权限（针对 Developer Console 应用），默认通过 Viewer 角色授予。如果您希望用户能够查看网站，但无法访问 Developer Console 中的应用配置，则可以创建仅授予此操作的自定义项目角色。

  • 要在 Foundry 上部署网站，您必须具备 部署应用网站 (third-party-application:deploy-application-website)操作权限（针对 Developer Console 应用），默认通过 Editor 角色授予。

  • 具有 Information Security Officer 角色的 Foundry 用户可以批准或拒绝创建域名的请求。

详细了解如何在 Foundry 上托管 OSDK 应用。

应用权限

Developer Console 支持两种类型的应用：

  • 面向客户端： 前端服务，包括 Web、桌面或移动应用。这些应用不得用于存储客户端凭据。
  • 后端服务： 一种用于支持后端工作流的应用程序，例如应用程序服务或守护进程。此类应用程序可用于安全地存储客户端凭据。

同一个应用程序可以同时包含面向客户端和后端两种类型。您创建的应用程序类型将决定可以使用哪种权限类型和 OAuth 工作流，如下文所述。

权限类型

创建应用程序时，您必须选择用于访问应用程序数据的权限类型。共有两种权限类型可用：

  • 用户权限： 用户的权限将决定其可以在 Foundry 本体论中读取和写入哪些内容。此权限类型将使用 Authorization code grant OAuth 工作流。
  • 应用程序权限： 您的应用程序将使用生成的服务用户来获得权限，而不是应用用户权限。此权限类型将使用 Client credentials grant OAuth 工作流。

面向客户端的应用程序必须使用用户权限选项以及 Authorization code grant OAuth 工作流。

示例

假设您正在构建一个显示车辆数据的应用程序。

如果您希望用户仅查看 Cars 其有权访问的内容，请选择应用 用户权限。如果您希望用户能够查看所有 Bikes，而不受用户权限的限制，请选择应用 应用程序权限 以使用生成的服务用户为应用程序授予单独的权限。

如果您希望用户查看所有 Cars 他们有权查看的 以及 所有 Bikes，请选择同时使用两种权限选项。

资源访问限制

当您向应用程序的 SDK 添加资源时，这些资源及其依赖项将被自动添加到应用程序的资源访问限制中。虽然用户必须拥有这些资源的相关权限，但资源访问限制可确保用户仅能通过给定的 OAuth 令牌访问为此应用程序批准的资源。

例如，在向 SDK 配置添加新的对象类型、关联类型、操作类型或函数时，任何所需的底层数据集或相关资源都将被添加到资源访问限制中。

为使应用程序正常运行，您可能需要手动管理这些限制 当依赖项发生变化时 或 当移除资源时。

当依赖项发生变化时

如果在添加之后，应用程序 SDK 中资源所需的依赖项发生了更改，您应更新应用程序的资源访问限制，以包含已更改的依赖项。您可以通过开发者控制台完成此操作，当应用程序的限制已过时，您可以在其中查看警告以及用于修正限制的引导式工作流。例如，如果为已包含在应用程序 SDK 中的对象类型配置了新的支撑数据集，则可能需要执行此操作。

在应用程序 SDK 页面上检测到过时依赖项时显示的示例警告。

针对过时依赖项的示例修正工作流，此处显示的是对象类型缺少数据集的情况。

移除资源时

如果您创建的应用程序 SDK 新版本移除了先前包含的资源，而这些资源又被立即从资源访问限制中移除，则当前版本应用程序的使用将会中断。为防止这种情况发生，您必须从 SDK 中移除先前包含的资源，但将这些资源继续保留在资源访问限制中，直到您将所有客户端升级到新版本应用程序为止；此后，从限制中移除先前包含的资源也是安全的。

当您从 SDK 中移除资源时，Developer Console 应用程序将显示一个警告，确认您是否也要将它们从限制中移除，还是将其保留。您可以稍后在 OAuth 与限制 页面中清理旧资源。

迁移到 Compass 管理的用户权限

截至 2026 年 2 月，Compass 管理的用户权限正处于 beta 开发阶段。如果您的租户未启用此功能，则可以参考旧版 下方用户权限部分。随着 Compass 管理的用户权限逐步走向正式发布，您应参考 下方迁移步骤 以迁移至 Compass 管理的用户权限。

用户权限 [旧版]

应用程序不再继承项目权限，而是将 Developer Console 用户自动设置为其所创建应用程序的 Owner 。随后，应用程序所有者必须与其他开发者共享该应用程序，并在其应用程序的 共享与令牌 部分中向特定用户授予权限。

您可以在 危险区域 面板中删除 Developer Console 应用程序，该面板位于特定应用程序的 概览 部分。与 Compass 资源移入回收站的工作流不同，已删除的应用程序无法恢复。

请按照以下迁移步骤操作，以确保您的 Developer Console 应用程序由 Compass 管理。

迁移步骤

迁移期间权限会被替换

将 Developer Console 应用迁移为项目范围应用时，应用的现有权限结构不会被保留。迁移后，应用将像任何其他项目资源一样，从目标项目继承资源权限。您可以在迁移对话框中预览最终生成的权限，然后再进行确认。网站查看者将由项目的权限决定，而不是由之前存在于独立应用上的任何自定义角色决定。根据项目的权限配置，这可能会导致能够查看网站的人数增多或减少。

迁移应用需要 “将旧版应用迁移到 Compass” （third-party-application:migrate-application-to-compass）操作，该权限默认通过 Owner 角色授予。

  1. 打开您的应用并选择 “将应用迁移到项目”。

  1. 请按照 “迁移到 Compass 资源” 弹窗中的说明来选择位置。

  1. 查看权限变更并选择 “提交” 以确认。

迁移后，您的应用将出现在所选位置。现在，您可以像对任何其他 Compass 资源一样对该应用执行操作，例如 移动、共享和移至回收站。

网站查看者权限

以前，您可以使用 “共享与令牌” 部分来授予用户查看托管网站的权限，但不能查看应用程序的配置。

虽然对于 Compass 管理的应用程序，此功能默认不再可用，但您可以 创建自定义项目角色 以保持单独的查看权限。为防止现有工作流中断，请在迁移之前先在项目或文件夹上分配此角色。这样可以确保目标用户组能够访问网站，但无法在 Developer Console 中查看应用程序的配置。

Marketplace 应用程序

通过 Marketplace 部署的 Developer Console 应用程序之前并未与其他安装资源创建在同一位置。随着迁移到 Compass 管理的用户权限，通过 Marketplace 安装的新应用程序也将在 您提供的位置中创建。

迁移来自 Marketplace 产品的打包应用程序并不会自动迁移其之前部署的安装。每个安装还必须按照 迁移步骤独立完成迁移。如果安装处于锁定状态，系统可能会提示您先将其解锁，以便您将应用程序移动到该位置。

现有的迁移前安装即使其状态与迁移后的源应用程序不匹配，也不会被阻止，而是会显示一条警告。您可以按照上述迁移步骤手动迁移这些安装。
