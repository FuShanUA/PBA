本体论设计：最佳实践

设计良好的本体论可为您的组织创建统一且直观的表示形式，从而实现无缝的数据集成、跨职能协作以及强大的分析能力。本节既提供了一套便于快速参考的设计指南，也对支撑这些指南的核心设计原则进行了深入探讨。

设计指南

以下指南是本体论设计的实用检查清单。在适用的情况下，每条指南都基于一个 核心设计原则、 反模式或 结构性建议.

  1. 对现实建模，而非系统： 对象类型应表示现实世界中的实体，而非单个源系统或部门的表示形式。
    • 设计原则： 领域驱动设计
  2. 有意识地策划： 每个属性都应具有明确的业务或技术价值。
    • 结构性建议： 规范化和派生属性
  3. 跨团队协作： 本体论设计应让来自多个部门或团队的干系人参与。团队各自为政是造成重复问题的主要原因。
    • 设计原则： 不要重复自己
  4. 保持对象类型聚焦： 每个对象类型应代表一个独立的实体。
    • 设计原则： 领域驱动设计
  5. 选择合适的工具： 使用操作类型处理人工或智能体决策，使用管道处理自动化转换。
    • 反模式： 金锤子
  6. 使用接口进行抽象： 当实体具有共同特征时，应使用接口对抽象进行建模，而不是创建宽泛、稀疏的对象类型。
    • 设计原则： 组合优于深层层级结构
  7. 记录您的决策： 在 Ontology Manager 中记录对象类型、属性和关联。

核心设计原则

这四项原则源自政府与商业实施项目中积累的丰富实践经验，并按优先级顺序呈现。在发生冲突时，优先级较高的原则优先。

优先级原则核心思想
1领域驱动设计对现实世界进行建模，而不是对源数据建模。
2不要重复自己如果你已经三次构建了同样的东西，就该重构了。
3对扩展开放，对修改关闭保护核心模型。使构建者能够对其进行扩展。
4组合优于深层层次结构优先采用通过接口实现的多重继承。保持各部分可插拔。

实际考量应始终纳入任何决策之中。请参阅关于 实用主义与权衡 的章节，以了解更多信息。

1. 领域驱动设计

本体论建模的是现实世界，而非源数据。

对象应表示在语义上有意义的现实世界概念（例如 Patient、 WorkOrder或 Vessel），而不是数据库表、API 响应或电子表格工作表。关联应表示真实的关系（“该患者曾到访该设施”），而不是连接键或外键产物。

当被要求“将数据集本体化”时，请克制将列 1:1 映射到属性后就认为工作已完成的冲动。 大杂烩 反模式会产生一个照搬源系统模式怪癖而非有用语义的 Ontology。设计良好的 Ontology 应当使用起来直观自然；用户或 AI 智能体应当能够毫无阻碍地浏览它，因为其结构与他们已有的领域思维方式相契合。

反模式

  • 对象类型照搬源系统数据表，而非领域实体
  • 属性从源数据列 1:1 映射而来，未经整理筛选
  • 名称来自源系统的命名惯例（dtLastInspMod），而非业务语言（lastInspectionDate）
  • 对象模型是通过查看数据而非理解领域来设计的
  • 包含多个实体的单个源数据行被建模为单个对象类型

示例

一个包含列 order_id、 customer_name、 customer_email、 product_sku和 quantity 的 CSV 描述了至少三个现实世界实体，而不是一个：

反模式的影响

问题影响
不直观的模型用户和 AI 智能体无法自然地导航本体论，因为其结构与他们对该领域的思考方式不匹配。
与源的脆弱耦合源系统中的架构变更会破坏本体论的使用方，因为本体论镜像了源结构，而不是对其进行抽象。
遗漏的关系以列形式嵌入的实体（例如 customer_name 订单上）无法被独立地链接、搜索或进行推理。
复用性差由单一系统的模式所塑造的对象类型，很难被其他团队或用例采用。

最佳实践

  1. 在查看源模式之前，先识别现实世界中的实体： 与领域利益相关者合作，定义哪些概念重要。单个数据集通常描述多个实体。
  2. 将身份与观测分离： 如果一行表示关于某个实体的测量或事件，则该实体和该观测很可能是不同的对象类型。
  3. 命名应便于人类理解： API 名称应直观且具有自文档性。优先选择 person.children 而非 person.linkedChildPersonObjects。优先选择 equipment.lastInspectionDate 而非 equipment.dtLastInspMod。
  4. 先对领域建模，再映射数据： 先理解领域，再设计对象模型，然后将源数据映射到该模型中。不要试图查看数据并照搬其结构。
  5. 将非语义类型标记为隐藏： 当特定工作流需要使用非语义类型（即服务于技术目的、而非用于建模现实世界领域实体的类型）时，应将其标记为隐藏，以保持本体论默认视图的整洁。这些类型仍可供构建者在构建应用程序时使用。

2. 不要重复自己（三次原则）

如果你已经三次构建相同的东西，就应该进行重构。

重复的对象类型、冗余的属性以及复制粘贴的工作流，对于人类和需要对本体论进行推理的 AI 智能体来说，都是一种维护负担和上下文管理问题。目标是让每个概念都拥有单一的标准表示，并且对该概念的每个操作都拥有单一的标准工作流。三次法则是应用这一原则的实用触发条件：出现一次是巧合，出现两次是模式，出现三次就意味着该重构了。

反模式

  • 多个对象类型共享同一组属性和相似的关联
  • 相同的派生属性逻辑或操作逻辑出现在多个类型中
  • 不同团队为略有不同的目的创建了几乎完全相同的对象类型
  • 存在复制粘贴的工作流，在不同类型之间仅有细微差异

反模式的影响

问题影响
维护负担必须在每个副本中复制变更。遗漏的更新会导致副本之间产生漂移。
上下文不明确用户和 AI 智能体无法确定多个几乎相同的类型中哪一个是规范类型。
行为不一致重复的操作或派生属性逻辑会随着时间推移逐渐产生分歧，导致相互冲突的结果。
浪费开发精力各个团队以略有不同的形式重复构建相同的内容，而不是协作构建一个共享模型。

最佳实践

  1. 审查重复项： 如果多个对象类型具有共同的结构（相同的属性、相似的关联、相似的操作），请评估它们是否应改为带有区分属性的单一类型，还是应实现共享接口。
  2. 整合共享逻辑： 如果相同的派生属性或操作逻辑出现在多个类型中，请将其提取到接口或共享函数中。
  3. 统一团队特定的副本： 当不同团队创建了几乎相同的对象类型时，应将其统一为单一的规范表示形式，并配置适当的安全性或筛选机制。
  4. 应用“三次法则”： 一处重复尚可接受。两处是警示信号。三处则意味着是时候重构了。

3. 对扩展开放，对修改关闭

保护核心模型。让构建者能够对其进行扩展。

一旦对象类型、接口或工作流经过实战检验并投入生产，其核心结构就应保持稳定。组织中的其他开发者和团队应能够在它之上进行构建，添加实现某个接口的新对象类型，或添加使用现有对象的新工作流，而无需修改核心模型。

反模式

  • 对既定对象类型频繁进行破坏性更改，并级联影响到依赖的应用程序
  • 新用例需要修改现有核心类型，而不是对其进行扩展
  • 团队需要编辑共享接口或操作来满足特定团队的需求
  • 为某个团队的扩展所做的安全更改会无意中影响其他使用者

反模式的影响

问题影响
破坏性变更对核心类型的修改可能会破坏整个组织中依赖这些类型的应用程序、操作和工作流。
范围蔓延核心类型会为每个新用例不断累积属性和逻辑，逐渐演变为一个 上帝对象.
所有权纠缠多个团队修改同一个核心类型，导致合并冲突和职责归属不明。
安全泄露在没有清晰边界的情况下扩展核心类型，可能会无意中扩大数据访问范围。

最佳实践

  1. 识别关键要素： 确定哪些属性和关联是实体真正不可或缺的基础。将这些内容锁定。
  2. 为扩展而设计： 在创建核心类型和接口时，请预料到其他人会在其基础上进行构建。为关联扩展类型和新的接口实现留出空间。
  3. 扩展而非修改： 在向现有模型添加内容时，请考虑新增内容应归属到核心类型还是扩展（新的关联对象类型、新的接口实现或新的属性命名空间）。
  4. 强制执行安全边界： 核心数据模型应具有明确定义的安全边界，以确保扩展本体论时不会无意中扩大访问权限。

4. 组合优于深层层次结构

优先通过接口实现多重继承。保持各部分可插拔。

Foundry 的本体论支持通过接口实现多重继承，因此实体可以从多个聚焦的抽象中组合行为，而不是依赖单一继承链。

反模式

  • 深层单一继承链，子类型的存在仅仅是为了组合父类型的能力
  • "组合"类型，例如 SchedulableBuilding 或 InspectableVehicle 将两个不相关的概念合并为一个类型
  • 工作流与特定对象类型紧密耦合，而实际上它们本可以在共享接口上运行
  • 向实体添加新能力需要重构继承链

反模式的影响

问题影响
组合爆炸每种新的能力组合都需要在层次结构中新增一个中间类型。
脆弱的层级结构对父类型的更改会不可预测地级联影响到所有后代类型。
有限的复用性基于链中深层的特定类型构建的工作流，无法复用于共享相同能力的其他类型。
语义失真人为设计的父类型（如 SchedulableBuilding）并不代表真实世界中的概念，违反了 领域驱动设计原则。

最佳实践

  1. 围绕能力或角色设计接口： 使用专注的接口，例如 Inspectable、 Schedulable、 Billable或 Depreciable ，以捕获特定的行为或属性集。
  2. 使用分类接口进行聚合： 分类标识接口（例如， MilitaryAsset 实现者为 Aircraft, Vessel, GroundVehicle）特别适用于下钻调查或类似的聚合工作流。
  3. 在工作流中以接口为目标： 在构建操作、函数和应用程序时，请尽可能以接口为目标。基于 SchedulableResource 接口无需修改即可适用于竞技场、会议室和车辆。
  4. 组合而非继承： 当实体需要多种能力时，应实现多个接口，而不是将其插入深层的单继承链中。

实用主义与权衡

这些原则是指导方针，而非定律。

现实中的约束条件（包括截止日期、遗留系统、部分平台支持以及用户技能水平）意味着理想的本体论设计并非总能立即实现。请使用以下指导方针来权衡取舍：

指导方针详细说明
引导走向良好的设计，而不是成为阻碍如果某项工作需要在紧迫的期限内可用，就先构建一个合理的方案，并留出明确的改进路径。
明确指出权衡取舍在推荐捷径时，请说明为此牺牲了什么，以及何时可能会产生影响。例如，反规范化在你当前的规模下可能运行良好，但如果对象数量超过 1 万个，你可能需要重新审视。
优先选择渐进式改进，而非推倒重来式的大规模重构一个虽有瑕疵但已投入使用并产生价值的本体论，胜过一个仍在设计中的理论上完美的本体论。
捍卫关键不变量命名质量、语义清晰度和安全设计在后期很难修复。在实现细节上可以走捷径，但不要在这些方面妥协。

本体论是为您的组织提供动力的软件。请像对待生产代码库一样精心对待它，但应优先考虑业务价值，而非追求完美。
