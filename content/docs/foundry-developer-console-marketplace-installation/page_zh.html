使用 Marketplace 安装 Developer Console 应用程序

使用 Marketplace 来打包并安装 Developer Console 应用程序 到各个 Foundry 环境中。您可以对应用程序或其代码仓库进行打包：

  1. 应用程序打包： 将 Developer Console 应用程序与其元数据和 OAuth 客户端一起打包。这是使用 Production 和 Singleton 产品交付已部署网站的推荐方法。请注意，如果不存在网站资产，您仍可以使用此方法交付 OAuth 客户端。请参阅 打包并安装 Developer Console 应用程序 了解详情。
  2. 源代码打包： 打包网站代码仓库（不包含 Developer Console 应用程序）。对于模板化应用程序以及在目标环境中创建不同 Developer Console 应用程序的情况，这是推荐的方法。请参阅 对 Developer Console 关联源代码进行打包和模板化 了解详情。

同时打包应用程序及其源代码在 引导 尚无现有网站的 OAuth 客户端时可能很有用。在这种情况下，您可能需要在安装后修改应用程序代码，并发布使用已安装 OAuth 客户端的网站。此工作流对于 生产 应用程序而言并不常见，因为已安装的应用程序始终与最新的网站资产（如果存在）相匹配，因此源代码实际上会被忽略。

本体论实体 API 名称在安装过程中不会自动重新映射。这适用于应用程序安装和源代码安装。这意味着，如果已安装的应用程序使用了目标本体论中不存在的 API 名称，则该应用程序可能无法正常运行。请参阅 处理 API 名称变更 以了解跨环境管理 API 名称一致性的策略。

打包和安装 Developer Console 应用程序

打包的应用程序包括：

  • 网站资源： 具有生成的网站资源的应用程序的静态文件和内容安全策略（请参阅 网站托管）。默认情况下，DevOps 会打包网站资源的最新已部署版本；如果源环境中不存在已部署的资源，则会回退到最新的未部署资源版本。
  • 应用程序元数据： 名称、描述和配置。
  • OAuth 客户端： 客户端类型、授权类型、重定向 URL。
  • 资源限制： 本体论 SDK 和 Platform SDK 资源。

在 DevOps 中打包应用程序

在 Foundry DevOps中，将 Developer Console 应用程序添加为产品的输出。Developer Console 应用程序具有两种类型的依赖项：

  1. 应用程序限制中的本体论实体（及其依赖项）和 Compass 项目。
  2. 需要在安装过程中定义的参数输入。其中包括用于网站托管的子域名和安全标记。

安装应用程序

从 Marketplace 安装应用程序时会自动创建 Developer Console 资源并配置 OAuth。了解有关 安装产品的更多信息。在某些情况下，您需要在安装过程中执行手动步骤：

  • 在 Bootstrap 模式下，Marketplace 可能会自动重写本体论 API 名称，以避免同一本体论内的名称冲突。例如，如果安装对象类型 API_NAME=Truck ，而目标本体论中已存在对象类型 API_NAME=Truck ，则 Marketplace 可能会将所安装的对象类型重命名为 Truck_1。这可能会破坏通过 API 名称引用对象的已安装应用程序。在随应用程序一同安装本体论实体时，请在安装过程中选择 始终安装源本体论 API 名称 。这将保留原始 API 名称，而不是为其添加前缀或进行修改，从而确保应用程序代码继续正常工作。
  • 当打包的应用程序使用子域名托管时，会在 Marketplace 安装过程中定义一个新的子域名。这通常需要额外的审批，且往往来自信息安全官。安装完成后，若要批准该子域名，请导航至 网站托管 页面（位于 Developer Console 中）。在获得此批准之前，该网站将无法访问。

Compass 管理的权限

Compass 管理的用户权限目前处于 beta 开发阶段，可能不适用于您的注册。

使用 Compass 管理的用户权限时，Marketplace 会在您提供的位置中创建 Developer Console 应用程序以及其他安装资源。

如果您正在将先前部署的应用程序迁移到 Compass 管理的权限：

  • 从 Marketplace 产品迁移打包的应用程序并不会自动迁移其先前部署的安装。
  • 每个安装都必须按照权限文档中的迁移步骤单独进行迁移。
  • 如果安装处于锁定状态，系统可能会提示您先将其解锁，然后再将应用程序移动到目标位置。

升级应用程序

要更新作为 Marketplace 产品一部分的已安装应用程序：

  1. 在源环境中更新应用程序。
  2. 如果要更新网站资产，请先 在 Developer Console 中部署 。DevOps 将打包最新部署的网站资产。
  3. 请在 Foundry DevOps中创建新的产品版本。

应用程序参数重新映射

对于包含已构建网站资产的应用程序，Marketplace 会在安装过程中自动映射应用程序参数。以下值将被替换为目标环境的对应值：

  • Foundry URL
  • OAuth 客户端 ID
  • OAuth 重定向 URL
  • 本体论 RID
  • 本体论 API 名称

要使自动映射正常工作，应用程序必须从 index.html 中的 meta 标签读取这些值，而不是从应用程序自身打包的代码中读取。使用 @osdk/create-app ↗ v2.1.3+ 或 Foundry 中的 VS Code 工作区创建的应用程序 默认情况下按此方式配置。

与网站参数不同，本体论 API 名称在安装过程中不会自动重新映射。请参阅 处理 API 名称变更 ，了解跨环境管理 API 名称一致性的策略。

import { createClient, type Client } from "@osdk/client";
import { createPublicOauthClient, type PublicOauthClient } from "@osdk/oauth";

function getMetaTagContent(tagName: string): string {
    const elements = document.querySelectorAll(`meta[name="${tagName}"]`);
    const element = elements.item(elements.length - 1);
    const value = element ? element.getAttribute("content") : null;
    if (value == null || value === "") {
        throw new Error(`Meta tag ${tagName} not found or empty`);
    }
    if (value.match(/%.+%/)) {
        throw new Error(
            `Meta tag ${tagName} contains placeholder value. Add ${value.replace(/%/g, "")} to your .env files`,
        );
    }
    return value;
}

const foundryUrl = getMetaTagContent("osdk-foundryUrl");
const clientId = getMetaTagContent("osdk-clientId");
const redirectUrl = getMetaTagContent("osdk-redirectUrl");
const ontologyRid = getMetaTagContent("osdk-ontologyRid");

export const auth: PublicOauthClient = createPublicOauthClient(
    clientId,
    foundryUrl,
    redirectUrl,
);

export const client: Client = createClient(foundryUrl, ontologyRid, auth);

将本体论 RID 添加到 .env 文件中：

VITE_FOUNDRY_ONTOLOGY_RID=<ri.ontology.main.ontology.your-ontology-rid>

这些代码更改仅适用于 TypeScript OSDK 2.0。如果您使用的是 OSDK 1.x，请先 迁移到 OSDK 2.0。

自定义 Workshop 小组件集成

自定义 Workshop 小组件 的部署方式与 Developer Console 应用程序类似。请参阅 将小组件集添加到 Marketplace 产品。

限制

  • 机密客户端密钥： 机密客户端 可以打包，但需要在目标环境中进行人工干预才能生成新密钥。您可以在 Developer Console 中生成新密钥，方法是导航到 OAuth 和限制 并选择 轮换密钥。
  • 不支持独立 OAuth 客户端： 独立 OAuth 客户端无法通过 Marketplace 进行打包和部署。请使用 不受限制的应用程序 作为替代。
  • 不支持固定版本的函数： 所有 函数 在应用程序的 OSDK 中，必须使用最新版本才能被打包。固定了函数版本的应用目前与 Marketplace 不兼容。此限制可能会在未来的版本中发生变化。

打包和模板化与 Developer Console 关联的源代码

您可以像打包任何其他代码仓库一样打包应用程序源代码。与 应用程序打包不同，诸如本体论 RID 和重定向 URL 等配置参数不会在源代码中重新映射。这意味着当源代码随应用程序一起交付时，应用程序网站将在目标环境中正常运行，但源代码文件仍包含原始环境的参数。

模板化（Beta）

模板化是一项实验性功能，它将任何 {{}} 语法视为模板变量，包括代码中已存在的模式。例如，如下形式的 JSX 内联样式 style={{color: 'red'}} 将被错误地解释为模板输入。在启用模板化之前，请检查代码库中是否存在现有的双花括号模式。

对于仅源代码的安装，您可以对应用程序进行模板化，以便在安装时自动重写参数。模板化通常适用于 Bootstrap 模式 下的以下情况：

  • 举办训练营或 Workshop，让所有开发者使用预配置的 OSDK 应用程序引导其代码。
  • 为用户提供示例，帮助他们快速开始工作。
  • 为所有 React 项目强制实施一套 UI 标准。
  • 提供一个使用一组共享本体论资源的 React 模板。

要将应用程序模板化：

  1. 在代码中的变量上添加 handlebars（例如， {{my_variable}}），这些变量需要在安装期间重写。
  2. 在 DevOps 中，添加相关的代码仓库并启用 源代码模板化 （在代码仓库配置菜单中）。
  1. 对于自定义参数，Marketplace 会提示用户提供这些参数的值，并在安装期间对其进行解析。 保留参数 将在安装时自动替换。
  2. 从 Marketplace 安装模板时，系统将自动为用户创建一个新的代码仓库和一个关联的 Developer Console 应用程序。当使用此软件包进行引导时， Bootstrap 选项必须在安装过程中选中。

使用 handlebar 参数时，应用程序将因类型检查而无法通过 CI 检查。这意味着您无法将网站资产（在 CI 检查通过后才会部署）与模板化代码打包在一起。

我们建议不要对本体论 API 名称映射使用参数。包含大量模板化 API 名称的应用程序会变得难以维护和调试。对于复杂的部署，请将本体论资源定义为 输入项 因此安装者会提供匹配的资源。模板最适合较简单的变量替换。参见 处理 API 名称变更 以了解推荐的策略。

处理 API 名称变更

OSDK 通过 API 名称引用本体论实体。这意味着，已安装的 Developer Console 应用（或应用代码）所使用的实体在源本体论和目标本体论中必须具有相同的 API 名称，应用才能正常运行。

此行为与大多数 Foundry 应用不同，后者使用非人类可读的 RID 来引用资源，这些 RID 会在不同 enrollment 之间进行映射。例如，一个 Workshop 应用若引用了对象类型 rid=X 则在部署时可能会被重写，以引用对象类型 rid=y。相比之下，已编译的 OSDK 应用程序资产和原始 OSDK 代码旨在保持人类可读，并在源仓库和目标仓库之间保持一致。

为确保实体 API 名称的一致性，应尽可能将本体论资源和应用程序一同打包和安装。本体论资源应与 Developer Console 应用程序一起作为产品输出（或作为与第一个产品一同部署的第二个产品的输出）。这样一来，Marketplace 在目标本体论中创建的资源将具有与源资源相同的 API 名称，从而防止中断。安装本体论实体时，请选择 始终安装源本体论 API 名称 以保留原始名称。

有四种处理 API 名称冲突的策略，分为两类：

将本体论与应用程序一同打包时： 如果目标本体论中已存在具有相同 API 名称的对象类型，Marketplace 将应用一个 安装前缀，这可能会破坏 OSDK 代码。为避免此问题，请使用 完全限定名称 或 单独的空间。

不将本体论与应用程序一同打包时： 如果目标环境已具有所需的本体论资源，请直接引用它们。请使用 接口 当源对象类型和目标对象类型有意设计为不同但共享相同结构时。如果对象完全相同但名称不同， 请手动修改 API 名称 以在不同环境之间保持一致。

完全限定名称

为防止打包本体论时发生冲突，在源环境中定义本体论实体时应使用完全限定的 API 名称。完全限定的 API 名称包含命名空间前缀，使其在所有本体论中全局唯一。只要应用程序在每个本体论中仅部署一次，即作为 Singleton 产品，完全限定名称即可保证不会出现 API 名称冲突。

可以在 Ontology Manager中配置完全限定名称。

使用独立的空间

对于多组织或开发生命周期工作流，使用不同的 空间 是消除 API 名称冲突的另一种方法。API 名称唯一性仅在空间级别强制执行。每个空间与一个本体论一一对应，因此用户可以将其视为本体论级别的唯一性。

接口

有时，冲突的 API 名称实际上代表同一 接口的两种实现。在这些情况下，请考虑重写应用程序代码以使用接口而非具体对象类型。

例如，考虑一个应用程序使用了 medicine 源本体论中的对象类型，而目标环境中存在 vaccine 对象类型来代替。这可以通过将 medicine 表示为接口而非对象类型来简化。该 medicine 接口随后将作为 Marketplace 产品的一部分进行部署，并且，在目标本体论中， vaccine 将实现 medicine。这种方法的优势包括：代码人类可读、构建时抽象清晰，以及在目标环境中进行合理的本体分类。

换言之，基于接口而非对象类型构建应用程序可以保证应用程序代码清晰易读，并且通常能完全免除对象映射的需要。

手动修改 API 名称

当源环境和目标环境中存在相同但 API 名称不同的对象时，您需要手动编辑 API 名称，使其在各环境之间保持一致。更改 API 名称可能会破坏引用这些实体的其他应用程序或函数，因此请谨慎操作。
