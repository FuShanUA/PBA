本体论设计：结构指导

以下章节提供了关于如何在本体论中构建属性、关系和访问控制的指导。

规范化和派生属性

每个事实只存储一次。请使用派生属性以获得便利。

反规范化数据（将值从关联对象复制到父对象）可能存在风险。当数据源发生变化时，必须更新每一个副本。规范化可以保持数据的一致性，而派生属性则能为您提供反规范化访问的便利，且无需维护成本。

并非所有计算值都相同。正确的方法取决于某个值能否从稳定的输入中安全地预先计算，还是需要与动态的本体论变更保持同步。

预计算值与动态派生值

类型特性推荐工具示例
预计算基于同一对象上的属性计算得出；输入很少发生变化，或仅因管道数据摄取而发生变化。管道转换fullName = firstName + " " + lastName

输入稳定且在同一管道中更新，因此预计算是安全的，且不会增加任何运行时开销。
动态派生取决于通过操作、自动化或其他本体论级操作而发生变化的关联对象或值。派生属性directReportCount

员工通过操作进行调动、入职和离职。统计关联对象数量的派生属性 Employee 会自动保持正确。

当某个值依赖于通过操作所做的变更时，每个可能影响该值的操作也必须更新该值。如果有任何操作未能做到这一点，该值将一直保持错误，直到发现该差异为止。

反模式

  • 相同的值作为属性存储在多个对象类型上
  • 属性会过时，因为它们是在其他地方维护的值的副本
  • 更新单个现实世界的事实需要向多个对象写入
  • 整数或计数属性是手动维护的，而不是根据关联计算得出的

性能注意事项

派生属性在运行时求值。其性能特征因规模而异：

规模建议
低至中等（每个查询少于约 1 万个对象）可以放心使用派生属性。对于大多数工作流，运行时求值的性能足以满足需求。
高（每个查询超过约 1 万个对象）由于查询路径开销较高，派生属性可能引入延迟。采用反规范化可能是合理的权衡，但这应当是一个经过深思熟虑并有文档记录的决策，而非默认选择。

最佳实践

  1. 将每个事实存储在一处，即存储在其语义所属的对象上。
  2. 使用派生属性 在查询时计算或聚合来自关联对象的值。
  3. 监控性能 ，并随规模增长持续关注。如果派生属性在大规模场景下带来不可接受的延迟，请考虑采用选择性反规范化。
  4. 记录所有反规范化 ，注明其理由、事实来源以及用于保持副本同步的更新策略。

结构体

将语义相关的字段组合到结构体中。

当某个属性天然包含多个字段(例如,包含街道、城市、州和邮政编码的地址)时,请使用结构体,而不要将其扁平化为多个单独的属性。结构体可保留语义分组,并支持捕获更丰富的元数据。

何时使用结构体

场景示例
多字段值地址(街道、城市、州、邮政编码)、坐标(地理坐标点、海拔)
带有元数据的值带有置信度分数、来源引用和推理过程的 AI 生成输出
具有选择逻辑的多值属性多个电话号码，reducer 会呈现其中的主要号码

主要优势

优势详细信息
语义分组地址是一个概念，而不是十个互不相关的属性。本体论反映了这一点。
元数据捕获结构体可以随主值一起携带来源、置信度和时间戳信息。
Reducer 支持在多值场景中，reducer 可以呈现最相关的值（例如，时间戳最新的 lastOccupied 字段）。
主字段行为结构体可以指定一个或多个主字段，使其在接口和查询中表现得像一个简单属性，或作为一个仅包含部分字段的结构体。

在 AI 优先的工作流中，结构体尤其有价值，因为大语言模型（LLM）的输出既包含主要结果，也包含相关的元数据（推理、来源引用、置信度分数）。应将这些内容一起捕获，而不是分散在不相关的属性中。

最佳实践

  1. 识别多字段属性 其中字段在语义上相关且总是同时使用。
  2. 定义结构体 并使用清晰的字段名称和类型。
  3. 指定主字段 使结构体在大多数情况下表现得像简单属性。
  4. 使用归约函数 为多值结构体属性呈现最相关的值。
  5. 捕获元数据 （来源、置信度、时间戳）与主值一同存储在结构体中，尤其适用于 AI 生成的输出。

接口

使用接口来构建可复用、面向未来的抽象。

接口是实现 “不要重复自己”设计原则 以及 开放/封闭扩展性的主要工具。它们定义了一种共享形态（属性、关联、操作），可由多种对象类型实现，从而使工作流能够面向接口而非单个类型。

何时使用接口

场景示例
跨类型的通用属性Inspectable 与...对接 lastInspectionDate 和 inspectionStatus，由...实现 Vehicle， Equipment， Facility
共享工作流一个针对 SchedulableResource 的调度工作流无需修改即可适用于竞技场、会议室和车辆
分类分组一个 MilitaryAsset 接口，由 Aircraft、 Vessel、 GroundVehicle 实现，用于下钻聚合工作流
多级抽象SchedulableResource extends Trackable，为更广泛的追踪抽象添加特定于调度的属性

平台注意事项

即使当前平台工具尚未完全支持基于接口的工作流，使用接口进行设计也能奠定基础，并随着支持的扩展而带来回报。

情境指导
接口在您的工作流中得到完全支持直接以接口为目标。单个工作流即可涵盖所有实现类型。
在特定上下文中接口尚未受支持现在定义接口，并作为临时措施，为每种类型复制一份工作流。这种做法的效率并不低于不使用接口的方式，而且一旦支持可用，便确立了清晰的整合路径。

请查看我们的 接口文档 以了解当前的支持详情。

最佳实践

  1. 识别共同形态： 如果多个对象类型共享属性、关联或操作，请定义一个捕获共享形态的接口。
  2. 围绕能力或分类法设计接口： 能力接口可能包括 Inspectable、 Schedulable或 Billable。分类接口可能包括 MilitaryAsset 或 MedicalDevice.
  3. 在工作流中以接口为目标： 尽可能针对接口构建操作、函数和应用程序。
  4. 扩展接口以实现多级抽象： 接口可以扩展其他接口，从而构建分层抽象。
  5. 先搭建脚手架，日后再整合： 即使由于当前平台支持存在缺口，某些工作流必须暂时按类型重复，也要定义接口。

关联与对象支撑的关联类型

关联应表示具有语义意义的关系。

每种关联类型都应回答一个明确的领域问题，例如：

  • 该患者到访了哪个设施？
  • 该员工属于哪个团队？
  • 该工单中使用了哪台设备？

何时使用关联类型

关联类型适用场景示例
直接关联该关系是有意义的，但其本身不携带任何元数据。Employee → Department
由对象支撑的关联该关系携带自身的元数据（日期、角色、状态、分配）。Employee → VentureStaffing → Venture （带有 role， startDate， allocation）

并非每个关联对象都需要在每个上下文中可见。有些工作流关注联接元数据，而另一些则只需要直接连接。由对象支撑的关联使您能够根据工作流公开其中任一视图。

关联设计不当的影响

问题影响
元数据丢失直接关联无法捕捉关系在何时、为何以及以何种身份存在。
歧义的多重关联诸如 ventureRole 之类的源对象属性在实体参与多重关系时会产生歧义。
无意义的关联仅因两个数据集共享外键而存在的关联会为本体论增添噪声，并干扰导航。

最佳实践

  1. 验证语义： 避免创建仅因两个数据集共享外键而存在的关联。请思考该关系在领域中是否具有实际意义。
  2. 评估该关系是否包含元数据： 如果包含（如日期、角色、状态），请使用对象支撑的关联类型来捕获这些元数据。
  3. 呈现恰当的详细程度： 根据具体情境,设计工作流时既可使用直接关系,也可使用通过关联对象建立的详细关系。
  4. 为清晰起见,请为关联命名: 关联名称应从各个方向描述关系。请参阅 命名规范 以了解更多信息。

命名规范

优化以提高人类的可读性和智能体的可导航性。

一致且具有描述性的命名是提升本体论质量最具影响力的投资之一。清晰的名称使本体论对人类和 AI 智能体都更易于导航,而一旦本体论投入使用,名称将更难以修正。

命名规则

元素约定良好示例不良示例
对象类型领域专家能够识别的单数具体名词Patient, WorkOrder, FlightSegmentData, Item, Record
属性简洁、不言自明；不包含编码的类型信息或实现细节age, status, lastInspectionDatedtLastInspMod, nVAL01, fieldX
关联在每个方向上都能自然阅读department (员工 → 部门), employees (部门 → 员工)relatedItems, link1
日期在整个本体论中始终遵循单一约定createdDate, updatedDate, effectiveDate混用 createdDate 和 dateOfCreation
歧义术语用具体含义加以限定monetaryValue, quantityOnHand, riskScorevalue, quantity, score

示例

✗ Avoid                                    ✓ Prefer
────────────────────────────────────────   ────────────────────────────────────────

Property: dtLastInspMod              →     Property: lastInspectionDate

Property: value                      →     Property: monetaryValue
                                           Property: quantityOnHand

Link: Item → Related Item            →     Link: Product → Supplier
                                           Link: Employee → Supervisor

最佳实践

  1. 在构建之前建立命名规范： 预先就日期、状态、标识符和关联的模式达成一致。
  2. 遵循本体论的既定规范： 如果本体论已经使用 createdDate，请勿引入 dateOfCreation。
  3. 限定有歧义的属性： 使用 monetaryValue， quantityOnHand，以及 riskScore。请勿使用 value， quantity，且 score。
  4. 根据关系命名关联： 从 Employee 到 Department 的关联应为 department （从员工的角度）以及 employees （从部门的角度）。
  5. 与最终用户一起审查命名： 对构建者来说似乎清晰的名称，对使用者来说可能含义模糊。请与每天使用本体论的人员一起验证。

安全设计

以语义化方式设计安全，遵循最小权限原则。

本体论中的安全应使用在领域内有意义的术语来表达，而不是使用数据基础设施的术语。用户应当能够查看安全配置，并理解哪些内容受到保护以及为何受到保护。

安全模型

结合行级和列级安全，实现细粒度的单元格级访问控制：

安全层控制示例
行级用户可以查看的对象VIP 患者仅限资深医务人员查看
列级用户在可见对象上可以查看的属性临床记录仅限医护团队查看
单元格级别（组合）行限制与列限制的交集VIP 患者的临床记录仅对高级护理团队可见

安全设计不当的影响

问题影响
出于安全目的而重复定义的类型模式会逐渐失去同步；为某一类型添加的属性很容易在另一个类型上被遗漏。违反了 "不要重复自己"设计原则。
默认权限过于宽松以宽泛访问权限起步、之后再收紧的做法，可能在锁定完成之前就暴露敏感数据。
以临时过滤代替策略分散在应用程序代码中而非在本体论层强制执行的安全逻辑十分脆弱，且难以审计。
边界不一致不遵循域边界的安全边界更难以推理分析，也更容易存在漏洞。

最佳实践

  1. 从严格限制开始，再有意识地逐步开放： 默认采用最小访问权限，并按需逐步放宽，而不是先开放再限制。
  2. 将行级安全与列级安全结合使用 以实现细粒度的单元格级访问控制。
  3. 使安全与域边界保持一致： 如果您的领域具有天然的访问边界（区域经理查看其区域的数据；护理团队查看其患者的数据），请使用本体论关系和安全策略（而非临时性的数据过滤）对这些边界进行建模。
  4. 避免为了安全而重复创建对象类型： 一个具有精心设计的安全策略的类型，优于多个架构重复的类型。
  5. 审查新的本体论路径以确保访问控制的一致性： 确保新增的关联、类型或属性能够保持对受限数据的预期保护。

请使用本页面的指导，确保安全边界与领域边界保持一致，然后参阅我们的 安全与治理文档 以了解配置详细信息。
