中止事务

Python 转换提供了中止 事务 的支持，允许在输出数据集未发生变化（没有新数据写入数据集）时使作业成功完成。这是通过使用 transform （如果 并调用 .abort_job() ，该选项位于 ctx 对象在转换中可用。

在某些条件下，如果您需要防止输出数据集和下游数据集更新，可以使用中止事务。一旦您的输出数据集更新，下游数据集将被视为过期（stale），并且它们将在下次构建时更新（手动或通过计划构建）。它提供了一种替代构建失败的方案，使您更容易识别真正的失败。

中止的事务将在您的数据集 事务历史中显示为灰色的成功作业。这使您能够一眼区分成功的构建是否产生了已提交的事务。

以下是您可能希望中止事务的一些示例场景：

  • 您有一个基于输入数据集内容来更新数据集的自定义条件。
  • 您的数据集需要强制构建，因为它不会过期。例如，通过调用 API 获取数据而不是使用输入数据集的数据集。
  • 您有一个回写数据集，它在计划执行时总是更新（详细示例见下文）。

添加验证，使用 abort_job() 对于总是更新但并不总是产生更改输出的数据集，可以通过避免不必要的下游更新来节省计算资源。

from transforms.api import transform, Input, Output
from datetime import date
import polars as pl

@transform.using(
    holiday_trips=Input('/examples/trips'),
    processed=Output('/examples/trips_processed')
)
def update_daily_trips(ctx, holiday_trips, processed):
    holiday_trips_df = holiday_trips.polars()
    todays_trips_df = holiday_trips_df.filter(
        pl.col("trip_date") == date.today()
    )
    if (todays_trips_df.height == 0):
      ctx.abort_job()
    else:
      processed.write_table(todays_trips_df)

from transforms.api import transform, Input, Output
from datetime import date

@transform.spark.using(
    holiday_trips=Input('/examples/trips'),
    processed=Output('/examples/trips_processed')
)
def update_daily_trips(ctx, holiday_trips, processed):
    holiday_trips_df = holiday_trips.dataframe()
    todays_trips_df = holiday_trips_df.filter(holiday_trips_df.trip_date == date.today())
    if (todays_trips_df.count() == 0):
      ctx.abort_job()
    else:
      processed.write_dataframe(todays_trips_df)

使用 if (len(todays_trips_df.head(1)) == 0) 通常会返回比 if (todays_trips_df.count() == 0) 更快的结果，因为它只检查是否至少存在一行，而不是不必要地统计所有行。

中止的事务与被忽略的作业有何区别？

当作业被标记为“ignored”（忽略）时，计算不会运行，因为 Foundry 判定输出数据集并未过期。当事务被中止时，作业会运行并成功完成，但输出数据集保持不变，且不会提交任何事务。

中止的事务与增量事务有什么关系？

增量转换仅使用已提交的事务读取输入和输出的数据集视图。这意味着它们在执行增量计算时会忽略中止的事务。

当在增量转换的整个作业上显式中止事务时，下次构建将读取（并因此重新处理）输入，就像中止的事务从未发生过一样，从而能够增量运行。

中止单个输出会破坏增量构建

使用 PySpark 时，可以对 abort() 单个数据集调用，而不是对整个作业调用。但是，不建议采用这种方法，因为它可能导致增量计算出现问题。

特别是，如果仅在部分输出上中止事务，构建将无法增量运行。对于事务已中止的输出，输出作业规范将使用先前的输入事务范围，因为已中止的事务会被忽略。对于事务已提交的输出，输出作业规范将使用当前的输入事务范围。输入事务范围的这种不匹配意味着转换无法再增量运行。

在多输出增量转换中，如果仅在部分输出上显式中止事务，则下一次构建将作为快照运行，并伴随失败的增量计算检查 Provenance records for the previous build are inconsistent。如果 require_incremental=True 已设置，构建将失败并报错 InconsistentProvenanceRecords。这是因为输出的当前视图现在将由不同的输入事务生成。

您应该使用 .abort_job() 类上的 TransformContext 来中止整个作业，而不是在运行增量构建时中止单个输出。这将中止 所有 构建中的输出。如果使用 v2_semantics，那么这是在允许后续构建增量运行的同时中止输出的唯一方法。
