使用 Linter 生成可操作的建议，即将正式推出 [GA]

发布日期：2024-09-24

我们很高兴地宣布，Linter 将于 10 月 7 日当周面向所有部署正式推出。此次变更包括 UI 更新、可扩展性改进、建议的可见性功能，以及帮助用户针对建议采取行动的修复助手。当工作流设计产生不必要的成本、未使用最新的 Palantir 平台功能或未遵循最佳实践时，Linter 会生成主张明确、可操作的建议。您可以使用这些建议来降低成本、优化您的本体论，并提高整个部署中管道的稳定性和韧性。

借助 Linter，您可以更好地了解 Palantir 平台提供的各种功能，同时监控可能有助于实现您用例目标的平台更新。Linter 默认处于启用状态；如果您是平台管理员，您可以 配置用户组对 Linter 的访问权限 ，方法是导航至 Control Panel > Application access （针对正确的 Organization），并选择 Manage 选项（位于 Linter 旁边）。

为什么要创建 Linter？

Palantir 平台是托管工作流的最佳场所。虽然应用程序构建者力求设计出优化的工作流，但实际情况是，设计决策在实践中可能被证明是次优的。为了解决这一问题，我们创建了 Linter，以确保工作流使用可用的技术，并通过更高效地利用资源和功能来实现相同的结果。

何时应该使用 Linter？

Linter 可随时使用，无论您是刚刚开始使用 Palantir 平台，还是已经拥有复杂而庞大的工作流。Linter 会监控新的和现有的工作流，并持续提供建议，同时定期执行扫描，以收集并分析您 enrollment 的状态。这些扫描会识别出符合预定义 规则 的资源列表，并生成一份 建议 列表（基于扫描结果）。

Linter 的 Impact Tracking UI，显示已执行建议的数量

由于 Palantir 平台功能经常更新，Linter 扫描的结果是动态的，可能每天都在变化。为了跟上这些变化，您可以设置一个 扫描计划 ，以定期扫描项目中的 Foundry 资源，而这些项目属于某个 空间。

示例扫描计划、生成新计划的选项、 操作 下拉菜单以及最近的扫描状态

降低成本并优化工作流

在 beta 阶段使用 Linter 的用户调查并消除了大量以计算小时计的云成本浪费，带来了可量化的改进。客户获得的成效与其平台使用情况相关，但即便是开发者基数相对较小的客户，也从 Linter 中受益，实现了其云成本目标。

Linter 的影响跟踪 UI，显示已落实建议的数量

一些客户组织了冲刺来调查并处理 Linter 建议，而另一些客户则将 Linter 定位为资源使用方面的辅助工具，在较长的时间段内分散投入精力。如今，许多客户专门投入时间处理 Linter 建议，将其作为 Palantir 平台合作的核心部分。

除了降低成本之外，Linter 还被用于推荐工作流更新，以使用 Palantir 平台中新推出的功能。其中包括使用 轻量级转换 和 原生 Spark 加速的机会，而这两项功能在今年年初时尚未推出。

自 Linter beta 版发布以来，除了可扩展性改进之外，还新增了以下功能：

  • 对 Linter 规则的扩展，例如新增了“数据集可使用轻量级构建”规则。
  • 引入了修复助手，用于简化修复的生成，并为建议实施相应操作。
  • 用于 影响跟踪 和编辑 清理计划的用户界面。

推出简化且更稳定、更快速的模型部署工作流

发布日期：2024-09-12

以往，部署用于实时推理的机器学习模型需要投入时间和精力，通过 Modeling Objectives设置实时部署，这是我们用于管理生产级建模工作流的工具。现在，您可以在模型概览页面上一键点击 Start deployment 或 Start & run 选项来部署模型，无需经过 Modeling Objectives 应用流程。此外，我们还推出了多项基础设施改进，可实现更快的启动速度、更简洁的函数集成、通过 Compute Modules实现的自动扩缩容、自动升级、推理类型安全等。

用户现在可以直接从模型概览页面部署模型。

简化自动升级并自动缩容至零，以节省成本

现在，模型部署可以在模型概览页面中进行全面管理。您可以在同一界面中启动、停止部署，更新模型扩缩容配置，并测试推理。由于部署现在由 Compute Modules 支撑，您可以受益于其自动扩缩容能力，根据模型的推理流量和使用情况动态启动或缩减副本。

例如，如果您的请求负载仅在特定时间出现，您现在可以设置可供使用的副本数量范围，使其能够根据实际请求量进行伸缩。如果您的模型部署会定期处于未被查询的状态，您甚至可以将副本数量缩减至最低为零，从而获得潜在的成本节省。

根据模型部署需求配置运行时伸缩和资源可用性。

模型部署会跟随用户的模型分支，从而实现无缝更新。只需从代码仓库或代码工作区发布新的模型版本，现有的模型部署将随之升级，确保所有下游工作流始终指向最新的模型。

无需 TypeScript 仓库即可实现函数集成

现在，模型部署可以轻松注册为函数，并可直接用于 Workshop，从而为您节省构建和使用 TypeScript 代码仓库所需的时间和精力。此外，您还可以受益于对表格输入和输出的支持，Modeling Objectives 应用中现已支持将更多类型的模型作为函数。具体而言，使用 pandas API 的模型（表格输入/输出）现在可以直接集成到 Workshop 应用中，这意味着您不再需要设置从 pandas 数据帧到 TypeScript 参数的转换层。另外，具有参数输入和输出的模型将继续受到支持。

对于其他 API 形式，模型可以使用一个 API 名称进行发布，以便在需要时仍可在 TypeScript 代码仓库中使用，例如在启用 Workshop 无法直接调用的函数时。

从模型部署中发布函数。

显著提升了稳定性并缩短了启动时间

我们还采用了完全容器化的模型，这是建模基础设施的一项重大变革，意味着模型现在是一个 Docker 镜像，将完整的模型环境、适配器实例和模型权重全部打包在一起，从而确保更快的启动速度。此外，容器化镜像无需连接 Palantir 平台即可启动。在内部测试中，模型部署仅需一分钟即完全就绪，而实际部署则需要三分钟；在大型、复杂的环境中，启动时间的缩短所带来的影响日益显著。

有保障的推理类型安全

现在，我们可以通过使用 Apache Arrow 与模型的容器进行通信，从而保证推理类型安全。这确保了用户的推理输入完全按照模型适配器 API 中指定的方式传递给模型适配器逻辑。例如，如果模型的 API 声明需要提供一个整数参数，则输入值将被转换为整数；如果无法成功转换，则会抛出错误。此外，日期时间和时间戳值现在也能安全、准确地传递。

Python 3.8 将于 2025 年 1 月 31 日弃用

发布日期：2024-09-12

Palantir 平台正在根据开源 Python 的生命周期结束 (EOL) 时间表弃用 Python 3.8。因此，系统将尝试在代码仓库中进行自动升级；而需要手动操作的是 Code Workbook 以及较旧的 foundry_ml 模型。从 Python 3.9 开始，我们将紧密遵循 Python 的 EOL 弃用时间线。请查看文档中的 Python 版本部分 ，以了解支持的版本及各自的弃用时间线。我们建议始终将资源保持在最新受支持的 Python 版本上。

为什么要弃用 Python 3.8？

开源 Python 每年都会将旧版 Python 标记为 生命周期结束（EOL）↗ 并停止官方支持。Python 3.8 即将进入 EOL，继续使用 EOL 的 Python 版本会带来安全风险。此外，开源库会不断发布新版本，而这些新版本不再兼容已弃用的 Python 版本，可能会导致未迁移的工作流出现检查和作业失败。

作为用户，弃用对我意味着什么？

如果您拥有使用已弃用 Python 版本的资源，请注意以下重要日期：

  • 2025 年 1 月 31 日： 依赖于已弃用 Python 版本的工作流将不再受支持，出现故障时您将无法获得任何支持。如果事先与 Palantir 达成一致，少量资源可加入白名单以获得延长支持。
  • 2025 年 4 月 30 日： 所有依赖 Python 3.8 或更早版本的工作流将不再受支持，并且可能会出现故障。

将 Foundry 资源迁移至受支持的 Python 版本

Foundry 资源迁移将遵循以下模式：

  • 代码仓库：将以自动补丁拉取请求的形式尝试自动升级。无论优先级如何，将对所有使用 Python 3.8 的资源尝试此操作。
  • 其他资源：将显示包含从已弃用 Python 版本迁移说明的信息横幅。请查看 故障排除指南 以了解更多信息。

目前，平台支持的最新 Python 版本为 Python 3.11。

未来 Python 版本弃用

从 Python 3.9 开始，Palantir 平台将紧密跟随上游生命周期结束时间表，并在 Python 版本达到上游生命周期结束后立即在平台内弃用。欲了解更多信息，请参阅文档中的 Python 版本 相关内容。

通过跳过已处理的行来优化 Pipeline Builder LLM 构建

发布日期：2024-09-10

我们很高兴地宣布，Pipeline Builder 现在可以在 Use LLM 节点和 Text to Embeddings 转换中跳过之前已处理的行，从而节省成本并提升性能。此前，在管道构建过程中，每一行都会被重新处理。而现在，行结果可以被缓存，也就是说，这些结果会被存储起来，并在后续构建中重复使用。通过跳过已处理的行，您可以同时节省时间和成本；经测试的使用案例显示，构建时间从 3 小时缩短至仅 20 分钟。

要开始使用，请在配置 Use LLM 或 Text to Embeddings 时启用 “跳过重新计算行” 选项。启用后，系统会根据传递到输入提示词中的列和参数，将各行与之前已处理的行进行比较。列值和参数值均相同的匹配行将在后续部署中直接获取缓存的输出值，无需重新处理。

该 “跳过重新计算行” 选项。

如果对提示词的更改需要重新计算所有行，用户可以手动清除缓存。在这种情况下，LLM 视图上方会出现一条警告横幅，只要输出类型保持不变，用户就可以选择保留之前缓存的所有值。

带有警告横幅的 LLM 视图,告知用户提示词或模型配置已更改。

在管道中的 Use LLM 节点和 Text to Embeddings 转换上启用此功能,可以提高工作流效率并降低计算成本。

在 Pipeline Builder 中使用多个受保护分支

发布日期：2024-09-03

现在，您可以在 Pipeline Builder 中保护多个分支，以实现更高水平的治理，并防范意外更改。受保护分支只能通过拉取请求进行修改，且更改必须经过指定的审批流程才能合并。通过实施受保护分支，您可以确保仅进行经授权的修改，并提高数据工作流的安全性和完整性。

要开始使用，请在 Pipeline Builder 中的 设置 > 管理分支 下配置受保护分支：

该 管理分支 选项（位于设置下拉菜单中）。

选择 分支保护 选项卡，然后选择要保护的分支以及所需的审批策略。所有受保护的分支都将遵循相同的审批策略。

该 分支保护 选项卡，其中显示了两个额外的受保护分支和审批策略选项。

使用多个受保护的分支可最大限度地降低意外更改的风险，并打造更加可控的开发环境，让您更加安心。
