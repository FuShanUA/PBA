理解依赖关系

在 Slate 中理解“事情为何发生”

在 Slate 中，所有小部件、函数、变量和查询都被建模为 节点 图中的节点。每个节点 求值 得到一个 JSON 输出，而其他节点 被模板化 to 参考 该输出。这些引用定义了 依赖关系 节点之间的依赖关系，Slate 利用它来理解何时 重新求值 节点（即：新的用户输入；查询执行；变量值更新）。

“开发” Slate 应用程序的一个主要过程就是通过添加以下内容来定义这些节点： 小部件 - 用于显示输出和捕获输入； 函数 - 用于对数据进行轻量处理以供显示以及处理应用程序登录；以及 查询 - 用于查询数据或连接其他 Foundry 服务 API，然后通过 Handlebar 语法配置它们的依赖关系。

依赖关系图

你随时可以在 依赖关系图 选项。 依赖项 标签页中查看该依赖关系图的表示形式，以了解 Slate 如何解释你通过 Handlebar 引用配置的关系。这种图表示形式 is 你的应用程序 - 如果它表示的内容看起来“不对”，那么你的出发点应该是去理解 为什么 而不是假设该图错误地表示了你的应用程序。

每当应用程序中发生意外情况时，首先查看“依赖关系”标签页，以了解出现异常的小部件的上游节点。寻找可能导致节点基于无关的查询或用户输入而重新求值的意外关系。

有时将依赖关系图视为“惰性”的会很有帮助 - 它只在上游引用发生变化时才重新求值节点，从而避免不必要的工作 的行，其状态是独立计算的。键值为。当上游节点更新为 相同的值 时，这可能会导致令人困惑的行为 - 下游查询不会执行，下游小部件也不会重新渲染。这种情况常见于涉及重置用户输入的模式中 - 在你的 Foundry 中搜索 依赖关系图与事件框架入门 教程以及 重置小部件选择 示例，以了解其实际效果以及如何使用 Math.random() 向依赖关系图求值中注入熵并确保节点重新求值。

事件

借助依赖关系图，Slate 会根据上游依赖关系的状态处理确定何时应重新计算函数或何时应重新运行查询的复杂性。大多数工作流都可以使用此功能进行配置，作为 Slate 开发者， 始终 应该首先考虑尽可能依赖依赖关系图。

然而，在某些情况下，使用显式的触发器/操作对来补充依赖关系图是有意义的，Slate 将其称为“事件”。一些简单的场景包括：在查询完成时触发显示横幅或提示框、在用户点击某项内容以查看更多详情时打开对话框，或在配置若干输入后通过按钮点击运行查询。

一旦你意识到事件框架的强大功能，可能会倾向于通过基于事件的解决方案来看待 Slate 中的每个开发任务。这可能导致一种常见的失败模式：单个应用包含数百个事件/操作对。虽然从技术上讲这是可行的，但这种复杂性使得难以逐步梳理应用程序的预期行为，甚至可能阻碍简单的调试。

根据经验法则，请尽量保持事件“链”简短，并倾向于依赖依赖图（Dependency Graph）而非事件的解决方案。如果您发现应用增长到超过 50 个事件，尤其是当这些事件不仅仅是触发提示（toast）或启动查询时，这是一个停下来仔细思考应用架构的好时机，寻找重构和简化开发的机会，或将应用进一步分解为子应用。

事件与循环依赖

Slate 依赖图在技术上是一个“有向无环图”（DAG），这意味着节点关系是有向的（即从根节点到叶节点存在层级结构，节点解析沿该方向进行），并且整个图必须是无环的，这意味着 Slate 会尝试阻止您在依赖图中配置任何“循环”——无论多长。

然而，通过使用 事件 并设置变量值或触发查询，确实可能为您的应用程序添加循环，这将导致非确定性行为。如果您的工作流似乎必须使用循环依赖，请退一步考虑其他模式——几乎总有办法实现所需的工作流功能。

管理查询执行

依赖图框架的一个含义是，默认情况下整个依赖图会在页面加载时解析。这意味着每个查询和函数都会按照图中每个节点解析所需的顺序运行。在实践中，这通常意味着，如果您在开发过程中没有多加注意，您会慢慢发现页面加载性能下降，直到开始出现间歇性超时。根本原因几乎总是许多作为“根”节点的查询，即它们没有上游查询依赖——这意味着 所有 这些查询将尝试同时运行。这可能导致排队和负载削减，因为同时存在的浏览器连接过多、对同一张（或多张）表的并发查询过多，以及返回到应用程序的网络流量过大。最终结果是查询非确定性失败，以及应用程序在页面加载时感觉迟缓，甚至完全无法使用。

Postgate 的连接池与排队

在 Postgate 中，您的应用程序的每个用户都有一个 专门为其创建的连接池（如果他们最近已经使用过该应用程序，则会从缓存中恢复）。每个连接池一次最多限制为 10 个连接，这可以防止任何单个应用程序实例过载 Postgate，因为 Postgate 由您应用程序的所有用户以及使用已同步数据的其他应用程序共享。在性能方面，这一限制实际上会带来 更好的 性能，而不是让所有查询一次性通过（如果超过 10 个），因为 Postgres 响应的并发查询越少，全局速度就越快。 性能优于一次性放行所有查询（如果超过 10 个），因为 Postgres 同时响应的查询越少，整体速度越快。

一旦 10 个连接全部用完，其余的查询请求就会排队，每个请求在连接可用时获取一个连接。但是，连接池不会让连接无限等待，而是会对等待连接超过五秒的查询超时。这意味着，如果您有多个耗时数秒的查询使连接池饱和，那么原本可能很快的查询——例如，当您使用 测试 按钮单独运行它时——可能需要很长时间，甚至超时。

此问题的解决方案包含几个部分：

  1. 设计您的应用程序工作流，使查询分散开并依赖于用户输入。一种常见的模式是对预先聚合的表或 DISTINCT 表运行一些小查询来填充一组筛选器，但“强制”用户进行一些选择并点击 提交 按钮来运行实际获取数据的查询。
  2. 在开发查询时应谨慎行事，注意平衡查询总数——尤其是在页面加载时运行的“重型”（平均返回时间超过5秒）查询的总数，与每个查询返回的数据量。确保您的查询没有做不必要的工作——请参阅以下相关章节： 索引和模式 and Postgres 调优 above.
  3. 通过指定查询执行前必须满足的附加条件，或将查询设置为 manual 来控制查询的执行时机，然后通过事件（通常是按钮点击）触发查询。

进一步展开第二点，在所有开发工作中，您都应力求代码简洁——您的代码应以最高效的方式完成必要的工作。这通常是 Slate 查询的一个败笔，它们会花费大量时间反复执行相同的工作。考虑这个简单的查询，用于填充一个供用户选择类别的下拉列表：

对于应由用户操作触发的查询，这是正确的模式。但是，将过多的查询链接在一起可能会导致不必要的复杂性；请参阅 事件 部分中的指导。手动查询从其触发器运行后，依赖关系图会自动更新所有下游依赖项。您无需基于 q_queryName.success.

JavaScript 函数的最佳实践和常见模式

函数提供了根据用户选择和应用程序状态对数据进行轻量操作或执行逻辑的能力。一些经常被忽视的模式和功能可以让您使用函数的工作更简洁、更简单。

通过返回复杂对象来避免重复工作

如果你查看 验证用户输入的示例，你会注意到验证函数返回的不是单个值，而是一个 JavaScript 对象。Slate 可以解析这些对象，并通过 Handlebars 使它们在应用程序的其他任何地方可用。

这意味着，例如，如果你需要派生几个新的显示列以在不同的 widget 中使用，与其为每个列创建一个函数，不如构建一个函数来创建所需的所有不同格式的显示值，并将它们全部在一个对象中返回。下一节将更详细地探讨这个示例。

在将逻辑合并到更少的函数中（这有助于减少重复工作并保持相似工作的整合）与将逻辑拆分开（这有助于封装离散操作并更容易找到所需的代码）之间，始终存在一种平衡。请牢记这种权衡，并在完善应用程序的过程中定期重构你的函数。
