获取大小

输出的获取大小是每次数据库往返查询中获取的行数。通过调整获取大小，您可以更改每次同步的网络调用总数。但是，获取大小会影响内存使用；增加获取大小会加快同步速度，但代价是增加内存使用。我们建议从获取大小：500 开始，并据此进行调整。

获取大小配置是否可用取决于您的 JDBC 驱动程序。如果您需要在输出配置中使用该参数，请确保您的驱动程序与获取大小参数兼容。

最大文件大小

您还可以调整输出文件的最大文件大小（以字节或行数为单位）。这样做可以提高数据上传到 Foundry 的性能和可靠性。

当以 Bytes为单位指定文件大小时，字节数必须至少是 Parquet（128MB）或 Avro（64KB）写入器内存缓冲区大小的两倍。

以字节为单位指定的最大文件大小是近似值；输出文件的实际大小可能略小或略大。

优化 JDBC 同步

如果您正在设置新的同步或遇到性能问题，请考虑切换到增量同步或并行化 SQL 查询，以提高同步速度和可靠性。

我们建议首先尝试增量同步方法。如果问题仍然存在，再继续并行化 SQL 查询。

JDBC 增量同步

通常，同步会导入目标表中所有匹配的行，无论数据在同步之间是否发生了变化。相比之下，增量同步是有状态的同步，使您能够对同一个表执行 APPEND 样式的事务，而不会重复数据。

从 JDBC 数据源摄取大型表时，可以使用增量同步。要使用增量同步，表必须包含一个严格单调递增的列。

请按照以下步骤配置增量 JDBC 同步：

  1. 将事务类型设置为 APPEND ，该选项位于 编辑同步 page.
  2. 然后，选择 启用 菜单中选择 增量 section.
  3. 接下来，提供一个单调递增的列以及该列的初始值。请选择一个小于您打算导入的任何值的值；增量同步将导入值大于已导入最大值的行。

示例： 一个 5 TB 的表包含数十亿行数据，您希望将其同步到 JDBC 源。该表有一个名为 id的单调递增列。可以将同步配置为每次摄取 5000 万行，使用 id 列作为增量列，初始值为 -1，配置的限制为 5000 万行。

首次运行同步时，前 5000 万行（基于 id升序排列）中包含 id 值大于 -1 的行将被摄取到 Foundry 中。例如，如果该同步运行了多次，且上次运行期间摄取的最大 id 值为 19384004822，则下一次同步将摄取接下来的 5000 万行，从第一个 id 值大于 19384004822 的行开始，依此类推。

请记住还要在 SQL 查询中添加限制。例如，如果您的查询是 SELECT * FROM "sales"."region"，它可以变为 SELECT * FROM "sales"."region" WHERE sale_id > ? limit 100000；每次构建运行时，将向 Foundry 导入 100000 行。查询中的 ? 值将自动更新为上次运行的值。

对于处理无时区定义的时间戳列的 JDBC 系统，时间戳将被假定为以 UTC 表示，增量查询将据此运行。

并行化 SQL 查询

并行功能会针对目标数据库运行多个独立的查询。在并行化 SQL 查询之前，请考虑它可能如何影响实时更新的表，因为在略微不同的时间执行的查询对这些表的处理方式可能不同。

如果切换到增量同步后性能没有改善，您可以将 SQL 查询并行化，将其拆分为多个较小的查询，由代理并行执行。

为此，您必须将 SQL 查询更改为新的结构。例如：

SELECT
/* FORCED_PARALLELISM_COLUMN(<column>), FORCED_PARALLELISM_SIZE(<size>) */
*
FROM <table_name>

查询所需的并行化详细信息说明如下。

FORCED_PARALLELISM_COLUMN(<column>)：指定用于划分表的列。它应该是一个数值列（或产生数值列的列表达式），且其分布应尽可能均匀。

FORCED_PARALLELISM_SIZE(<size>)：指定并行度。例如， 4 将产生五个同时运行的查询：四个查询拆分指定并行化列的值，另一个查询查询并行化列中的 NULL 值。

例如，使用上面的 SQL 查询 SELECT * FROM sales_data，我们可以通过添加额外的详细信息来将其并行化：

SELECT
/* FORCED_PARALLELISM_COLUMN(sales_id), FORCED_PARALLELISM_SIZE(4) */
*
FROM "sales"."region"

当在并行化中使用包含 WHERE 条件的 OR 子句时，请将条件用括号括起来，以指示条件的求值方式。例如： SELECT /* FORCED_PARALLELISM_COLUMN(sales_id), FORCED_PARALLELISM_SIZE(4) */ * FROM "sales"."region" WHERE (condition1 = TRUE OR condition2 = TRUE)

将数据导出到 JDBC 源

Data Connection 支持将带有 schema 的数据集表导出到 JDBC 源。

请查阅我们的文档，了解如何 启用、配置和调度 JDBC 导出.

JDBC 源的导出配置选项

使用 JDBC 源进行表导出需要指定目标数据库、schema 和表。这些输入决定了 Foundry 导出的目标位置，并且必须与目标数据库中已存在的值相匹配。

您可以手动输入目标数据库、架构和表的值，也可以使用 Explore & autofill 按钮查看源预览，以浏览目标数据库中存在的表，并根据您的选择自动填充输入内容。

导出模式

您必须选择一个 导出模式.

批处理大小

批处理大小是指在 Foundry 与您的源之间传输数据时，单个批次中处理的记录数量。调整批处理大小会影响数据导出操作的性能和效率，从而实现资源使用的优化并缩短执行时间。

默认情况下，导出批处理处于禁用状态。启用导出批处理后，您可以选择介于以下范围之间的批处理大小： 2 和 5000。如果您的源所依赖的驱动程序支持导出批处理，则此配置将在下次执行导出时生效。

运行状况检查

健康检查会在源上运行，以验证底层源的活跃状态和可用性。默认情况下，这些检查每 60 分钟运行一次，并由分配给该源的每个代理执行。对于 JDBC 源，健康检查以如下方式实现： SELECT 1 查询。

导出任务（旧版）

导出任务 是一项旧版功能， 不 建议在新实现中使用。所有新的导出都应使用当前的 推荐的导出工作流。本文档面向仍在使用旧版导出任务的用户提供。

写入模式

  • ErrorIfExists: 如果表已存在则失败（默认）
  • Append: 追加到现有表
  • Overwrite: 替换现有表数据
  • AppendIfPossible: 首次导出时覆盖，后续导出时追加。在执行增量导出时可能需要此选项。

直接写入与暂存写入

当 writeDirectly: false （默认），写入流程如下：

  1. 数据导出到 {tableName}_staged_
  2. 暂存表被重命名为最终表
  3. 原始表被删除

当 writeDirectly: true，数据将直接写入最终表，这在执行增量导出时可能是理想的选择。

复制模式

copyMode 控制数据如何复制到数据库。

  • insert 使用连续的 INSERT 语句（每行一条），批处理大小可配置（默认）
  • directCopy: 对每个文件使用一条 COPY 语句以获得更好的性能。仅在导出到 PostgreSQL 数据库时可用。

标识符加引号

quoteIdentifiers 控制是否应为标识符加引号。

默认值为 true ，因为在许多情况下，有效的 Foundry 列名可能不是有效的数据库列名，例如由于特殊字符（1_column, my column, my-column）或保留字（level, values).

您可能希望将其设置为 false （如果您导出到 Oracle DB 或 IBM DB2，因为在这类数据库中，每当引用列时都需要为其加引号。

增量导出

增量导出允许您仅导出自上次导出以来已更改的数据。当 incrementalType 设置为 incremental时，首次导出的行为类似于快照，导出所有数据并记住上次导出的事务。后续导出仅在上一个事务仍存在于数据集中时才包含新事务；否则，将回退到完整快照。

对于 JDBC 导出，此选项是按数据集指定的，而不是全局指定的。

推荐的方法使用暂存表模式：增量数据先写入临时表，然后使用 preSql 和 afterSql 语句将其合并到最终目标。设置 writeDirectly: true 以避免创建额外的临时表，并使用 writeMode: AppendIfPossible 以在首次运行时覆盖、在后续运行时追加。

特定数据库的注意事项

Teradata

导出将创建一个 MULTISET 表，并将数据集中的第一列视为分区键。请重新排列您的列，使第一列具有较多的值，以避免所有行都被索引到同一个分区下。

Teradata 不支持在一个事务中执行多个数据定义语言（DDL）语句。在每次执行 DROP、CREATE、RENAME 之后，导出器都会进行一次提交。

性能优化

导出大量数据时，您可能需要使用以下选项：

  • 在您的终端会话中将 parallelize: true 以并行方式导出每个输入数据集，并使用以下配置定义线程数 datasets.[].exporterThreads。该数据集中每个文件的导出将以指定的线程数并行执行。一个较好的初始值是代理上可用的核心数。

  • 调整 batchSize 根据数据库和内存限制进行调整

故障排除

如果遇到批量插入错误（例如 PreparedStatement batch request 失败），请考虑以下解决方案：

列排序： 将高基数列放在数据集的前面。像 Teradata 这样的数据库会将第一列用作分区键，如果第一列基数较低，可能导致所有行都被索引到单个分区下，从而引发失败。

字符串编码： 确保您的字符串数据使用与目标数据库兼容的字符编码。Teradata 要求使用 ASCII 或 Latin-1 编码，而不是 UTF-8。您可能需要在导出前对数据进行清理或转换。

通过批量大小进行调试： 将其减少 batchSize 到 1 以隔离有问题的行。这会减慢导出速度，但有助于准确识别由于数据质量问题或约束冲突而导致失败的行。
