API：查询模型或建模目标的实时部署

在直接模型部署和建模目标中，您都可以创建实时部署，并通过 HTTP 端点托管您的模型。您可以在实时部署的 查询 标签页中，通过以下方式在生产环境中使用该模型： 模型上的函数，或直接使用实时部署 API。

要直接查询托管的模型，请从以下端点选项中进行选择：

  • 多输入/输出（I/O）端点： 一种灵活的端点，既可以处理复杂的托管模型和输入类型，也可以处理只有单一输入和输出的简单模型。多 I/O 端点的 URL 以 /v2 为后缀，也称为“v2 端点”。
  • 单一 I/O 端点 [已弃用]： 一种旧版端点，只能处理 API 由单一输入和输出组成的简单托管模型。单一 I/O 端点也称为“v1 端点”，未来将被弃用。

单一 I/O 端点已弃用，仅在建模目标部署中受支持。

多 I/O 端点

多 I/O 端点（有时称为“v2 端点”）是一种灵活的端点，支持一个或多个输入以及一个或多个输出。

  • URL： <ENVIRONMENT_URL>/foundry-ml-live/api/inference/transform/ri.foundry-ml-live.<LIVE_DEPLOYMENT_RID>/v2
    • <ENVIRONMENT_URL>: See section 有关如何思考问题类别并识别它们的更多细节 的文档以获取更多信息。
  • HTTP 方法： POST
  • 身份验证类型： Bearer 令牌
  • 必需的 HTTP 标头：
    • Content-Type: Must be "application/json".
    • Authorization: Must be "Bearer <BEARER_TOKEN>"，其中 <BEARER_TOKEN> 是您的身份验证令牌。
  • 请求正文： 一个 JSON 对象，包含要发送给模型的信息。其预期结构取决于所部署模型的 API。
  • 响应： 成功的响应将返回状态码 200 以及一个表示模型返回的推理响应的 JSON 对象。该对象的结构将反映当前部署模型的 API。

import requests

url = '<ENVIRONMENT_URL>/foundry-ml-live/api/inference/transform/ri.foundry-ml-live.<LIVE_DEPLOYMENT_RID>/v2'

inference_request = { 'inference_data': [ { 'text': 'Hello, how are you?' } ] }

response = requests.post(
    url,
    json=inference_request,
    headers={ 'Content-Type': 'application/json', 'Authorization': 'Bearer <BEARER_TOKEN>' })

if response.ok:
    modelResult = response.json()
    print(modelResult)
else:
    print("An error occurred")

单一 I/O 端点

不再建议在新的实现中使用单一 I/O 端点。请优先使用上文所述更灵活的多 I/O 端点。

  • URL： <ENVIRONMENT_URL>/foundry-ml-live/api/inference/transform/ri.foundry-ml-live.<LIVE_DEPLOYMENT_RID>
  • <ENVIRONMENT_URL>: See section 有关如何思考问题类别并识别它们的更多细节 的文档以获取更多信息。
  • HTTP 方法： POST
  • 身份验证类型： Bearer 令牌
  • 必需的 HTTP 标头：
    • Content-Type: Must be "application/json".
    • Authorization: Must be "Bearer <BEARER_TOKEN>"，其中 <BEARER_TOKEN> 是您的身份验证令牌。
  • 请求正文： 一个包含以下字段的 JSON 对象：
    • requestData：一个数组，包含要发送给模型的信息。其预期结构取决于所部署模型的 API。
  • 响应： 成功的响应将返回状态码 200 以及一个包含以下字段的 JSON 对象：
    • modelUuid：一个标识模型的字符串。
    • responseData：一个对象数组，其中每个对象表示模型的推理响应。这些对象的结构取决于所部署模型的 API。

环境 URL

在上面的示例中， <ENVIRONMENT_URL> 占位符代表您环境的 URL。要获取您的环境 URL，请从部署的 查询 标签页中复制 curl 请求并提取该 URL。

错误处理

最常见的 HTTP 错误代码详述如下：

  • 400： 由无效请求或模型失败引起。
    • 通常由模型推理期间发生的异常引起。堆栈跟踪通常会在响应体中提供，以帮助调试。
    • 如果请求不符合模型 API，也会返回此错误代码。
  • 422: 由格式不正确的请求引起。请确认请求中的 JSON 有效且符合预期格式。
  • 429: 由请求过多引起。请使用退避策略重试或降低并发数。速率限制取决于您的环境。
  • 500: 由内部服务器或部署错误引起。可能需要人工干预。
  • 503: 服务或部署不可用。这可能发生在部署资源不足、内存耗尽、无法并发处理更多请求，或正在自动尝试重启时。请使用退避策略重试。可能需要人工干预。
